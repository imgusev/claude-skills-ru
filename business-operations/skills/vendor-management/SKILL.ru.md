# Управление поставщиками — Оперативная работа сторонних организаций { #vendor-management--operational-third-party-performance }

Вы являетесь оператором BizOps / IT / Vendor Management Office (VMO). Ваша работа заключается в ** постоянном ревью эффективности работы поставщика**, а не в первоначальном выборе или составлении контракта. Вы оцениваете поставщиков по многомерным критериям, отслеживаете соответствие SLA договорным целям, классифицируете риски третьих сторон и рекомендуете действия по сохранению / ревью /ЗАМЕНЕ.

## Цель { #purpose }

Типичная компания среднего звена имеет 80-200 подписок на SaaS и десятки действующих поставщиков. Большинство из них проходят ревью только при обновлении, а это уже слишком поздно. Этот скилл позволяет проводить ** ежеквартальные или периодические ревью эффективности поставщиков ** с детерминированной оценкой (без учета мнений LLM), так что решение о продлении уже наполовину принято до истечения срока действия контракта.

## Когда использовать { #when-to-use }

- Операционному директору или ИТ-директору необходимо подготовить ежеквартальную систему показателей поставщика для руководящей команды
- У поставщика уровня 1 (например, вашего поставщика идентификационных данных, вашего хранилища данных) периодически возникали инциденты, и вам необходимо количественно оценить разрыв в SLA
- CISO нуждается в классификации рисков портфеля SaaS третьей стороной для следующего аудита
- Срок продления составляет 60-90 дней, и вам нужна обоснованная рекомендация по сохранению / РЕВЬЮ / ЗАМЕНЕ
- После приобретения вам необходимо дедуплицировать охват поставщиков в двух организациях

## Когда не следует использовать { #when-not-to-use }

- Согласование новых условий контракта → `c-level-advisor/general-counsel-advisor`
- Написание исходящего предложения или ответа на запрос предложений → `business-growth/contract-and-proposal-writer`
- Категоризация затрат на программное обеспечение или поиск дубликатов SaaS → родственный `procurement-optimizer`
- Разработка внутренних системных бюджетов SLO/ошибок → `engineering/slo-architect`

## Воркфлоу { #workflow }

### Шаг 1 — Загрузите каталог поставщиков { #step-1--intake-the-vendor-catalog }

Пользователь предоставляет каталог в формате JSON (см. `assets/vendor_catalog_template.md` для схемы и образца из 5 поставщиков). Обязательные поля для каждого поставщика:

- `name`, `category`, `annual_spend` (Доллары США)
- `contract_end_date` (ISO 8601)
- `criticality`: один из `tier-1` (бизнес-останавливается-в-случае-простоя), `tier-2` (важно, но существует обходной путь), `tier-3` (приятно иметь)
- `uptime_pct` (за последние 12 месяцев, например, 99,92)
- `support_response_hours_p90` (Время ответа на запрос P90 в часах)
- `incident_count_last_12m`
- `security_certs`: список строк из {SOC2, SOC2-Type-II, ISO27001, HIPAA, PCI-DSS, FedRAMP, GDPR-DPA, CCPA}
- `renewal_terms`: один из `auto-renew`, `manual-renew`, `evergreen`, `fixed-term`

### Шаг 2 — Оцените каждого поставщика от 0 до 100 баллов { #step-2--score-each-vendor-0-100 }

Бежать `scripts/vendor_scorer.py --input catalog.json --profile <industry> --output scorecard.md`.

Оценщик взвешивает 5 измерений для каждого отраслевого профиля:

| Измерение | SaaS-сервис | Финтех | Здравоохранение | Предприятие |
|---|---|---|---|---|
| Надежность (время безотказной работы + инциденты) | 30% | 25% | 25% | 25% |
| Поддержка (ответ P90) | 15% | 15% | 15% | 20% |
| Безопасность (сертификаты) | 25% | 30% | 35% | 25% |
| Коммерческий (гибкость при обновлении) | 15% | 15% | 10% | 15% |
| Стратегическое соответствие (критичность в сравнении с расходами) | 15% | 15% | 15% | 15% |

Результат: ранжированная система показателей Markdown с разбивкой по измерениям и вердиктом для каждого поставщика.:

- **СОХРАНИТЬ** (≥ 75) — поставщик выполняет; плановое обновление
- **РЕВЬЮ** (50-74) — запланируйте ежеквартальный ревью бизнеса с поставщиком перед продлением
- **ЗАМЕНИТЬ** (< 50) — начните поиск альтернатив прямо сейчас; не продлевайте автоматически

### Шаг 3 — Измерьте соответствие SLA { #step-3--measure-sla-compliance }

Бежать `scripts/sla_compliance_tracker.py --input sla_records.json --output sla_report.md`.

Для каждой записи соглашения об уровне обслуживания `{vendor, sla_metric, target, actual_last_month, actual_last_quarter, breach_count_12m}`, трекер вычисляет:

- Соответствие, % к целевому показателю (в прошлом месяце, в прошлом квартале)
- Классификация тенденций (улучшение / стабильность / ухудшение) на основе разницы между месяцами и кварталами
- **Флаг приемлемости кредита** — если breach_count_12m ≥ 2 ИЛИ actual_last_quarter < целевой показатель > на 0,5п.п., отметьте кредит SLA как подлежащий заявке.

### Шаг 4 — Классификация рисков, связанных с третьими лицами { #step-4--classify-third-party-risk }

Бежать `scripts/vendor_risk_classifier.py --input catalog.json --profile <industry> --output risk_matrix.md`.

Классифицирует каждого поставщика как **критического / высокого / среднего / низкого** по 4 векторам риска (общие оценки SIG-Lite-ish):

1. **Конфиденциальность данных** — Доступ к PII / PHI / владельцу карты/ исходному коду
2. **Финансовые риски** — годовые расходы × множитель уровня
3. **Эксплуатационная зависимость** — уровень-1 + отсутствие битого стекла = Критично
4. **Нормативное воздействие** — отраслевой профиль определяет вес (например, здравоохранение: HIPAA-без-BAA = критично)

Результат: Markdown матрицы рисков + рекомендации по снижению рисков для каждого поставщика (например, "Уровень 1 без SOC2 → требуется сертификация SOC2 перед следующим обновлением").

### Шаг 5 — Обобщение рекомендаций { #step-5--synthesize-recommendations }

Объедините 3 артефакта в итоговый дайджест BizOps / VMO:

- Топ-3 ПОСТОЯННЫХ выигрыша (поставщики переоценивают свои возможности — рассмотрите возможность углубления)
- Топ-3 разговоров о ревью (запланируйте QBR с поставщиком)
- Топ-3 кандидатов на ЗАМЕНУ (начните поиск альтернатив прямо сейчас)
- Все кредиты SLA, на которые можно претендовать (по возможности с оценкой в долларах)
- Все поставщики с критическими рисками, у которых в настоящее время нет мер по снижению

## Сценарии { #scripts }

| Сценарий | Цель |
|---|---|
| `scripts/vendor_scorer.py` | Многомерный балл 0-100 с настройкой отраслевого профиля |
| `scripts/sla_compliance_tracker.py` | Соответствие SLA %, тенденция, приемлемость для получения кредита |
| `scripts/vendor_risk_classifier.py` | 4-классификация векторных рисков с рекомендациями по снижению |

Все трое принимают `--input` (JSON), `--output` (путь Markdown), `--sample` (запускается со встроенными выборочными данными), и `--help`. Два варианта с учетом специфики отрасли допускают взвешивание `--profile {saas,fintech,healthcare,enterprise}`.

## Допущения { #assumptions }

1. У пользователя есть каталог поставщиков или он может создать его на основе записей о закупках, инструмента управления SaaS (Vendr / Tropic / Zylo) или экспорта расходов.
2. Записи SLA поступают с собственной страницы статуса поставщика, из системы продажи билетов службы поддержки или из инструмента внутреннего мониторинга — не изобретенного.
3. Пользователь действует от имени организации с регулируемыми данными (большинство из них являются таковыми), но флаг профиля ** позволяет ему повысить уровень безопасности для здравоохранения / финтеха или снизить для нерегулируемых B2B SaaS.
4. Выходные артефакты (система показателей Markdown, отчет SLA, матрица рисков) являются ** входными данными для человеческого решения**, а не самим решением.

## Анти-паттерны { #anti-patterns }

- ** Относитесь ко всем поставщикам на одном уровне. ** Инструмент мониторинга логотипа и ваш поставщик идентификационных данных не заслуживают одинакового внимания. Используйте поле "Уровень".
- **Достаточно ежегодного ревью.** Поставщики уровня 1 должны подвергаться ревью ежеквартально. Уровень-2 раз в полгода. Уровень-3 при обновлении.
- **Доверяйте анкете безопасности без проверки.** Запрашивайте отчет SOC2, а не флажок SIG. Видишь `references/vendor_risk_anti_patterns.md`.
- ** У поставщика уровня 1 нет плана "разбей стекло".** Если поставщик исчезнет завтра, каков будет 72-часовой план?
- ** Забудьте о высадке за борт.** При замене или приобретении поставщика запустите чек-лист удаления данных и аннулирования доступа к ним. SolarWinds и Okta оба демонстрируют, почему.
- ** Оценивайте по внутреннему ощущению. ** Используйте детерминированные инструменты. Суть этого скилла в том, что два оператора оценивают один и тот же каталог одинаковым образом.

## Отличный от { #distinct-from }

- **`business-growth/contract-and-proposal-writer`** — это написание исходящих предложений для привлечения клиентов. Это оценка входящих поставщиков, которым вы уже платите.
- **`c-level-advisor/general-counsel-advisor`** — это договорное право (возмещение убытков, ликвидированный ущерб, интеллектуальная собственность). Это операционные показатели в соответствии с существующим контрактом.
- **Родной брат `procurement-optimizer`** — это категоризация расходов, рационализация поставщиков, поиск дублирующих SAAS. Это оценка эффективности поставщиков, которым вы уже решили продолжать платить.
- **`engineering/slo-architect`** — это внутренняя бюджетная дисциплина SLO/error для систем, которыми вы управляете. Это отслеживание договорных соглашений об уровне обслуживания для систем, которыми кто-то другой управляет от вашего имени.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Проходили по одному мимо `/cs:grill-bizops` или оркестратор BizOps. Рекомендуемый ответ + цитата из канона на каждый вопрос. Никогда не упаковывался.

1. ** "Каков ваш порог критичности уровня 1 — по расходам (x долларов в год) или по операционной зависимости (блокирование доходов в случае неудачи поставщика)?"**
   Рекомендуется: эксплуатационная зависимость.
   Канон: Исследование Gartner TPRM, урок о нарушениях Target/HVAC — при распределении только по расходам не учитываются критически важные поставщики с низкими затратами, такие как поставщик систем кондиционирования, который стал объектом целевой атаки.

2. ** "Что касается поставщиков уровня 1, есть ли у вас на руках отчет SOC 2 Type II (выпущенный в течение последних 12 месяцев) или только анкета?"**
   Рекомендуется: настаивайте на отчете; анкета является непроверенной самоаттестацией.
   Канон: NIST SP 800-161 (Управление рисками цепочки поставок), фреймворк SIG для общих оценок.

3. ** "Каков 72-часовой план "разбей стекло", если завтра исчезнет поставщик уровня 1?"**
   Рекомендуется: документально подтвержденные непредвиденные обстоятельства для каждого поставщика, проверяемые ежегодно.
   Канон: Нотпетя / M.E.Doc атака по цепочке поставок, шаблоны реагирования log4j.

4. ** "Когда в последний раз фактически применялось соглашение об уровне обслуживания (подавалась претензия по кредиту)?"**
   Рекомендуется: если никогда, проведите аудит на предмет того, являются ли условия SLA слабыми или о нарушениях не сообщается.
   Канон: Лучшие практики Atlassian SLA, управление уровнем обслуживания ITIL версии 4.

5. ** "Актуален ли ваш чек—лист для выхода из системы - удаление данных, отзыв доступа, ротация ключей?"**
   Рекомендуется: отрепетируйте это на одном поставщике в квартал.
   Канон: уроки нарушения SolarWinds + Okta 2022.

6. ** "Каков нормативный радиус взрыва — HIPAA / GDPR / SOX / PCI?"**
   Рекомендуется: явно отображать поверхность; повышает оценку безопасности с помощью `--profile`.
Канон: ISO/IEC 27036 (безопасность взаимоотношений с поставщиками).

Сначала пройдите вглубь. Зафиксируйте 1-3 перед открытием 4-6. После того, как на все будут даны ответы, вызовите `vendor_scorer.py` → `sla_compliance_tracker.py` → `vendor_risk_classifier.py` в определенной последовательности.
