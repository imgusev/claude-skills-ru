# Бизнес—операции - Оркестратор домена { #business-operations--domain-orchestrator }

Поверхность BizOps является ** внутренней**: как на самом деле работает компания. Этот оркестратор разветвляет контекст беседы, направляет ваш запрос в один из шести подкаталогов скилла, а затем возвращает сжатый дайджест родительскому потоку. Интенсивный прием информации (каталоги поставщиков, интервью с производителями, прием SOP с несколькими документами) остается в раздвоенном контексте.

## Когда вызывать { #when-to-invoke }

| Симптом | Дополнительный скилл для маршрутизации к |
|---|---|
| "Где работа проводит большую часть своего времени в ожидании?" | `process-mapper` |
| "Этот поставщик осуществляет поставки в соответствии с соглашением об уровне обслуживания?" | `vendor-management` |
| "Достаточно ли у нас людей для отправки в третьем квартале?" | `capacity-planner` |
| "Мне нужно проинформировать компанию о реорганизации" | `internal-comms` |
| "Напишите мне рансбук для процесса реагирования на инциденты" | `knowledge-ops` |
| "Почему расходы на наше программное обеспечение выросли на 40% в годовом исчислении?" | `procurement-optimizer` |

## Логика маршрутизации (детерминированная) { #routing-logic-deterministic }

Оркестратор классифицирует запрос по **сигналам**, обнаруженным в промпте. Двухсигнальный порог для уверенной маршрутизации; один сигнал триггер для уточняющего вопроса.

### Таблица сигналов { #signal-table }

| Класс сигнала | Ключевые слова | Вспомогательный скилл |
|---|---|---|
| **ПРОЦЕСС** | узкое место, время цикла, ожидание, хэндофф, BPMN, карта процесса, воркфлоу | `process-mapper` |
| **ПОСТАВЩИК** | поставщик, supplier, SLA, контракт, сторонняя организация, MSA, подписка SaaS, продление | `vendor-management` |
| **ВМЕСТИМОСТЬ** | численность персонала, производственные мощности, использование, планирование, последовательность найма, FTE | `capacity-planner` |
| **СВЯЗЬ** | общие сведения, внутренний информационный бюллетень, объявление, управление изменениями, часто задаваемые вопросы, ратуша | `internal-comms` |
| **ЗНАНИЯ** | SOP, рансбук, база знаний, wiki, плейбук, документация, онбординг doc | `knowledge-ops` |
| **ЗАКУПКИ** | расходы, закупки, закупочная деятельность, рационализация поставщиков, аудит программного обеспечения, расширение SaaS | `procurement-optimizer` |

Если сигналы смешанные (например, "соглашение об уровне обслуживания поставщика + проведение аудита"), сначала запустите ** вспомогательный скилл с наивысшей степенью достоверности**, затем переходите ко второму в последующем раздвоенном порядке.

### Запасной вариант { #fallback }

Если ни один из классов сигналов не набрал баллов ≥ 2, задайте **один** уточняющий вопрос, назвав двух наиболее вероятных кандидатов. НЕ гадайте молча.

## Воркфлоу (дисциплина Matt Pocock grill) { #workflow-matt-pocock-grill-discipline }

Взято из книги Мэтта Покока `grill-with-docs` шаблон: ** исследуйте, затем задавайте, по одному вопросу за ход с рекомендуемым ответом, сначала пройдитесь по дереву решений в глубину, отслеживайте зависимости, закрепляйте каждую проблему в документированном каноне ** (`references/`).

### Шаг 1 — Исследуйте, прежде чем спрашивать { #step-1--explore-before-asking }

Прежде чем задавать какой-либо уточняющий вопрос, проверьте:
- Содержит ли рабочий каталог пользователя уже карту процессов, каталог поставщиков, SOP или организационную диаграмму, которую мы можем использовать для grep?
- Устраняет ли запрос уже неоднозначность полосы (например, "ревью соглашения об уровне обслуживания поставщика" — это `vendor-management`, вопрос не нужен)?
- Однозначен ли путь из упомянутых имен файлов (`procurement-Q3.csv` → закупки)?

Если кодовая база разрешает полосу движения, **маршрут выполняется автоматически**. Не спрашивай.

### Шаг 2 — Если все еще неясно, задайте ОДИН форсирующий вопрос с рекомендуемым ответом { #step-2--if-still-ambiguous-one-forcing-question-with-a-recommended-answer }

Правило Мэтта: никогда не связывай вопросы воедино. Никогда не задавайте вопрос по умолчанию "что вы думаете?". Всегда предлагайте свои рекомендации.

Узор:
```
Q1/1: [precise question naming the two candidate lanes]
Recommended: [Lane X, because <one-sentence rationale from the signal table>]

(Confirm, or override?)
```

Дождитесь ответа пользователя. **Затем** проложите маршрут. Никогда не угадывайте молча после хода, который задал вопрос.

### Шаг 3 — Разветвление пути принятия решения по дереву (только если запрос пересекает полосы движения) { #step-3--forking-decision-tree-walk-only-if-the-inquiry-crosses-lanes }

Если запрос пользователя законно пересекает две полосы (например, "соглашение об уровне обслуживания поставщика + проведение аудита" = ПОСТАВЩИК + ЗАКУПКИ), сначала пройдитесь по дереву ** в глубину**:

1. Сначала разрешите полосу с более высокой степенью достоверности → запустите этот вспомогательный скилл в раздвоенном контексте → верните дайджест
2. Спросите: "Должны ли мы сейчас бежать [вторая полоса]? Моя рекомендация: да, потому что [причина зависимости]."
3. Только после явного подтверждения пользователя запускайте второй дополнительный скилл

Не цепляйте молча. Каждый форк - это явный шаг, подтвержденный пользователем.

### Шаг 4 — Вызов вспомогательного скилла в раздвоенном контексте { #step-4--invoke-sub-skill-in-forked-context }

Каждый вспомогательный скилл вызывается с исходным промптом + дайджестом любых структурированных входных данных (пути к файлам, входные данные в формате JSON). Разветвление позволяет избежать интенсивного использования (каталог поставщиков, расшифровки процессов, исходные документы SOP) в родительском контексте.

### Шаг 5 — Верните дайджест с цитируемым вызовом по канону { #step-5--return-digest-with-cited-canon-challenge }

Когда под-скилл завершится, верните родительскому потоку дайджест из **≤ 200 слов**:

- Что было проанализировано
- Топ-3 вывода (каждый из которых подкреплен цитатой из справочного материала — например, "Теория ограничений Голдратта: оптимизируйте узкое место, а не отсутствие ограничений")
- Топ-3 следующих действия (по возможности назовите владельцев)
- Путь к созданному артефакту (артефактамам)
- **One grill challenge** для пользователя, цитируется: "Ваш коэффициент полезного действия составляет 12%. Канон бережливого производства (Womack & Jones, 1996) классифицирует <15% как отходы с большим количеством отходов. Что мешает перепроектированию процесса — политическое, техническое или бюджетное?"

Затем родительский агент может запросить последующие действия (каждый триггер запускает новые разветвленные вызовы).

## Библиотека принудительных вопросов (шаблон grill-with-docs) { #forcing-question-library-grill-with-docs-pattern }

Когда пользователь предоставит достаточно контекста для входа в полосу, оркестратор может опросить его о решениях внутри этой полосы** перед вызовом вспомогательного скилла. По одному вопросу за ход, каждый с рекомендуемым ответом + цитата из канона. Примеры:

- **ПОЛОСА обработки**: "Перед составлением карты: у вас есть измеренное время цикла для каждого этапа или только приблизительные данные? Рекомендуется: настаивайте на измеренных данных для трех самых длинных этапов. Анти-паттерн (Голдратт, 1984): сопоставьте оценки, оптимизируйте неправильное ограничение."
- ** Полоса ПОСТАВЩИКОВ **: "Прежде чем оценивать: каков ваш порог критичности уровня 1 — по расходам ($X/year), или по операционной зависимости (блокирование доходов в случае сбоя поставщика)? Рекомендуется: эксплуатационная зависимость. Анти-шаблон (Gartner TPRM): при распределении уровней только по расходам не учитываются критически важные поставщики с низкими расходами, такие как поставщик систем кондиционирования воздуха, в целевом бреши."
- **ПОЛОСА ПРОПУСКАНИЯ**: "Перед моделированием: планируете ли вы использование или пропускную способность? Рекомендуется: пропускная способность (закон Литтла). Анти-шаблон (DORA): планирование использования > 80% снижает пропускную способность из-за постановки в очередь."

Никогда не запускайте вспомогательный скилл до тех пор, пока не будет зафиксировано решение об определении полосы движения.

## Допущения { #assumptions }

1. Пользователь действует от имени организации с числом сотрудников ≥ 10 (небольшим организациям эта поверхность не нужна).
2. Пользователь имеет доступ к данным, необходимым для вспомогательного скилла (документы по обработке, список поставщиков, экспорт расходов и т.д.), или принимает шаблонные фиктивные данные скилла.
3. Пользователю нужен ** детерминированный, повторяемый анализ **, а не проза со вкусом LLM. Каждый вспомогательный скилл предоставляет инструменты Python только для stdlib.

## Нецели { #non-goals }

- Не заменяет ERP, платформу управления поставщиками (Vendr, Tropic) или SaaS для планирования производственных мощностей (Float, Runn).
- Не сохраняет состояние между сеансами — каждый вызов является автономным.
- Не вызывает внешние API-интерфейсы из инструментов Python (только stdlib, по замыслу).

## Отличный от { #distinct-from }

- **`business-growth/*`** — это ** движение внешних продаж** (CSM, инженерия продаж, RevOps). BizOps является ** внутренним**.
- **`c-level-advisor/coo-advisor`** — это стратегическое суждение главного операционного директора ("стоит ли нам проводить реструктуризацию?"). BizOps носит тактический характер ("вот карта процесса с узкими местами").
- **`engineering/slo-architect`** — это надежность системы с SLO/SLI/error бюджеты. `process-mapper` это надежность бизнес-процесса, а не системы.
- **`engineering/llm-wiki`** — это ** личный** ПКМ (паттерн Карпати). `knowledge-ops` является ** общекорпоративной** разработкой SOP.

## Выходные артефакты { #output-artifacts }

Каждый вспомогательный скилл создает по крайней мере один артефакт (Markdown, CSV или JSON), сохраненный в рабочем каталоге пользователя. Оркестратор отображает путь к файлу в дайджесте.

## Анти-паттерны (не делать) { #anti-patterns-do-not }

- ❌ Запустите все 6 вспомогательных скилл "для тщательности" - выберите один на основе сигнала, верните дайджест, дайте пользователю цепочку
- ❌ Автоматическое утверждение изменений в поставщике или процессе — поверхностные выводы; человек принимает решение
- ❌ Редактируйте документы производственного процесса без запроса — записывайте в новый файл, предлагайте разницу
- ❌ Пропустите этап дайджеста — родительскому контексту требуется дайджест из менее чем 200 слов, а не полный вывод вспомогательного скилла
