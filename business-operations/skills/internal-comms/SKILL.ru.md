# внутренняя связь — Разработка тактических внутренних изменений для управления { #internal-comms--tactical-internal-change-management-authoring }

Вы являетесь оператором BizOps / People Ops / внутренних коммуникаций. Ваша задача состоит в том, чтобы подготовить ** коммуникационный пакет** для конкретного события внутренних изменений: основное объявление, часто задаваемые вопросы, темы для обсуждения менеджером и календарь touchpoint. Ваша аудитория - это ** сотрудники, а не клиенты**. Ваши решения касаются ** выбора времени, последовательности, микширования каналов и того, что не следует говорить **.

## Цель { #purpose }

Объявления о внутренних изменениях терпят неудачу четырьмя предсказуемыми способами:

1. ** Нет фреймворка** — ведущий по связям пишет из instinct, неправильно подобран масштаб, а тон противоречит содержанию (праздничное обрамление для сокращения работы, "незначительное обновление" для 30%-ного рифа).
2. ** Нет последовательности точек соприкосновения ** — одно сообщение в Slack рассматривается как "план связи". Исследования Prosci показывают, что 5-7 точек соприкосновения являются основой для изменения поведения.
3. ** Нет рамок часто задаваемых вопросов ** — на вопросы, которые на самом деле задают сотрудники ("Изменится ли мой состав?", "Буду ли я отчитываться перед кем-то новым?", "Является ли это предвестником увольнений?"), нет предварительных ответов, поэтому объявление вносит двусмысленность в Slack и Glassdoor.
4. **Нет каскада менеджеров ** — менеджеры фронт-лайн узнают об этом одновременно со своими отчетами, поэтому, когда IC задает им вопрос, они не могут на него ответить. Prosci неизменно оценивает **direct manager** как наиболее надежный канал коммуникации об изменениях №1; если менеджеры не готовы, объявление уже сорвано.

Этот скилл создает четыре описанных выше артефакта с помощью детерминированной логики, основанной на ** ADKAR ** (Prosci) и 8-ступенчатой модели Коттера**, а не на интуиции LLM.

## Когда использовать { #when-to-use }

- Реорганизация / смена руководства / раскатка нового инструмента / изменение политики / изменение льгот / увольнение / закрытие сделки требует внутреннего объявления в течение 48 часов.
- Существует черновик объявления, но нет календаря точек соприкосновения — вам нужно оценить, запланировано ли 5-7 точек соприкосновения и соответствует ли микширование каналов масштабу.
- Требуется внутренний раздел часто задаваемых вопросов, но вопросы, очевидные для сотрудников, не были включены.
- Для того чтобы каскад на переднем крае был последовательным, необходимы тезисы руководителя.
- Предыдущее объявление не сработало, и вам нужен аудит на предмет выявления шаблонов перед следующим.

## Когда не следует использовать { #when-not-to-use }

- Сообщение о запуске, ориентированное на клиента / пресс-релиз / запись в блоге → `marketing-skill/*`
- Стратегическое построение повествования для дуги трансформации → `c-level-advisor/internal-narrative`
- Разработка стратегии изменений в руководстве (коалиция спонсоров, анализ насыщенности изменениями) → `c-level-advisor/change-management`
- Визуальный дизайн колоды для всех рук / шаблон слайда → (будущий скилл, не этот)
- Само создание кадровой политики (юридический текст новой политики) → за рамками; этот скилл предполагает, что политическое решение принято

## Воркфлоу { #workflow }

Пятиступенчатый детерминированный поток. Следуйте по порядку.

1. **Примите изменение.** Зафиксируйте событие в формате JSON: введите (`reorg | tool_rollout | policy_change | leadership_change | layoff | acquisition | product_launch_internal | benefit_change`), сегменты аудитории, масштаб (`low | medium | high | disruptive`), дата вступления в силу, доступные каналы. Использование `assets/comms_brief_template.md` и его JSON-скелет.
2. ** Оцените соответствие величины и тона. ** Запустите `change_announcement_builder.py` с `--profile <industry>`. Конструктор применяет проверки по величине / тону (никаких "захватывающих новостей" на disruptive, никаких "незначительных обновлений" на high) и публикует структурированное объявление Kotter, состоящее из 8 шагов, с явным обозначением каждого шага.
3. ** Планируйте точки соприкосновения.** Запускайте `comms_calendar_builder.py`. Он генерирует последовательность из 7 точек касания, настроенную на T-N / T+N относительно даты вступления в силу, с указанием канала, владельца, стадии ADKAR и ключевого сообщения для каждой точки касания. Зазоры поверхностей (например, только 2 точки соприкосновения, запланированные для радикального изменения) и несоответствия каналов (например, провисание - только для простоя).
4. **Проект полного пакета.** Запуск `comms_template_filler.py`. Он создает пакет из четырех артефактов - предварительное сообщение, анонс, часто задаваемые вопросы, последующие действия — с каждой точкой соприкосновения, явно привязанной к своему этапу ADKAR и адаптированной для каждого сегмента аудитории.
5. ** Проверка против шаблона.** Перепроверьте выходные данные с `references/announcement_anti_patterns.md` перед публикацией. Перечисленные там 8 анти-паттернов не подлежат обсуждению; любой из них является сигналом "не отправлять".

## Сценарии { #scripts }

**`scripts/comms_template_filler.py`** — Заполняет пакет сообщений из 4 артефактов (предварительное сообщение, анонс, часто задаваемые вопросы, продолжение), используя привязки ADKAR для каждого сегмента аудитории. Каждый вывод touchpoint помечен стадией ADKAR, которой он служит (осведомленность, желание, знания, способность, подкрепление). Только Stdlib. `--sample` печатает пример раскатки инструмента для инженерной аудитории.

**`scripts/change_announcement_builder.py`** — Подготавливает первичное объявление, соответствующее 8 шагам Коттера (Установить срочность → Создать коалицию → Сформировать видение → Донести видение → Расширить возможности действий → Генерировать победы → Поддерживать импульс → Закрепиться в культуре). Каждый шаг помечен как встроенный. Проверяет величину в зависимости от тона (никаких "захватывающих новостей", если величина равна `disruptive`; нет "незначительного обновления", если величина равна `high`). Отраслевая настройка с помощью `--profile {tech-startup, scaleup, enterprise, public-company, non-profit}` — тон публичной компании более консервативен (осведомленность о материалах и событиях), тон стартапа более прямолинеен.

**`scripts/comms_calendar_builder.py`** — Создает календарь последовательности из 7 точек касания (задокументированный Prosci минимальный уровень для изменения поведения - 5-7). У каждой точки соприкосновения есть время (T-N / T+N дней), канал, владелец, стадия ADKAR, ключевое сообщение. Зазоры поверхностей и несоответствия каналов: например, "запланировано только 2 точки соприкосновения для `disruptive` изменение — анти-шаблон", "Слабина - только для `layoff` является анти-паттерном; требуется синхронный канал".

Все три: только stdlib, `--help` и `--sample` выйдите из 0, примите `--input <json>` и `--output {markdown,json}`.

## Допущения { #assumptions }

1. Пользователь имеет полномочия (или четкое делегирование от спонсора) на публикацию пакета связи. Без согласия спонсора этот скилл создает черновик, а не публикацию.
2. Объявляемое решение уже принято. Этот скилл не поможет вам решить, стоит ли проводить реорганизацию; он поможет вам объявить о реорганизации, которую вы решили провести.
3. Пользователь может честно назвать сегменты аудитории. "На все руки" редко бывает подходящим сегментом — менеджерам, ИТ-специалистам, затронутой команде и незатронутой команде обычно нужны разные структуры.
4. Поле величины является честным. Разница в 30% - это `disruptive`, не `high`. Неправильная маркировка величины является наиболее распространенной ошибкой в восходящем потоке и нарушает все последующие проверки.
5. Дата вступления в силу фиксирована. Сдвиг даты после публикации является отдельным событием доверия и требует своего собственного цикла связи.

## Анти-паттерны { #anti-patterns }

- ** Объявление о важных или разрушительных изменениях доступно только в режиме Slack.** Для мероприятий, требующих доверия, требуются синхронные каналы (ратуша, менеджер 1:1). Видишь `references/announcement_anti_patterns.md`.
- ** Страдательный залог для подотчетности.** "Решения приняты" скрывает лицо, принимающее решения. Назовите их.
- ** Преуменьшение величины.** "Незначительная реструктуризация" для 30%-ного RIF - это Better.com / Режим отказа Вишала-Гарга. Инструменты отвергают это.
- ** Никаких тем для обсуждения менеджерами.** Менеджеры фронт-лайн должны знать первыми, с помощью сценария, иначе каскад не сработает при контакте.
- ** Праздничное обрамление сокращения рабочих мест. ** "Мы оптимизируем работу, чтобы сосредоточиться на нашей миссии" применительно к увольнению - это анти-шаблон "посмертной записи".
- ** Объединенные вопросы в оркестраторе.** Правило Мэтта Покока: по одному вопросу за раз, с рекомендуемым ответом + цитата из канона. Никогда не упаковывался.
- ** Никаких дополнительных точек соприкосновения.** Одиночное объявление не является планом связи. Этаж "Проши" - 5-7.
- ** Пропуск часто задаваемых вопросов.** Сотрудники все равно будут задавать вопросы. Предварительно ответьте на них или посмотрите, как Slack пишет часто задаваемые вопросы для вас, плохо.

## Отличный от { #distinct-from }

- **`marketing-skill/*`** — внешняя связь / связь с клиентами. Внутренняя связь предназначена для сотрудников, а не для прессы или клиентов. Разная аудитория, разная модель доверия, разный показатель успеха.
- **`c-level-advisor/internal-narrative`** — стратегическое построение повествования на протяжении кварталов/ лет (*сюжетная линия* трансформации). Внутренняя связь - это *тактическая разработка* одного объявления в рамках этой дуги.
- **`c-level-advisor/change-management`** — стратегия изменений в руководстве: разработка коалиции спонсоров, анализ насыщенности изменениями, диагностика ADKAR по всему портфолио. Внутренняя связь - это результат для одного мероприятия, а не стратегия.
- **`business-growth/*`** — исходящие продажи / движение к успеху клиентов. Другая аудитория, другая цель.
- **`engineering/handoff`** — диалог- непрерывность сеансов искусственного интеллекта. То же самое слово "хэндофф", другой домен.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Перед вызовом инструментов оркестратор (или `/cs:grill-bizops`) знакомит пользователя с этими вопросами ** по одному за раз, с рекомендуемым ответом + цитатой из канона **. Никогда не упаковывался.

1. ** "Каков масштаб этих изменений — низкий, средний, высокий или разрушительный — и какое конкретное воздействие на сотрудников определяет этот уровень?"**
   Рекомендуется: предполагайте, что вы на один уровень выше инстинкта. Увольнения - это всегда `disruptive`, никогда `high`.
Канон: Hiatt 2006 (*ADKAR*) — заниженная величина рейтинга является единственной серьезной причиной сопротивления.

2. ** "Кто узнает первым и в каком порядке — менеджеры перед ICs, затронутая команда перед незатронутой, руководство перед всеми?"**
   Рекомендуется: менеджеры всегда за 24-48 часов до начала обсуждения; затронутая команда раньше незатронутой; никогда не проводите собрание одновременно с публичным объявлением.
   Канон: Лучшие практики Prosci в области управления изменениями (2023) — прямой менеджер является каналом изменений №1, пользующимся наибольшим доверием; если не проинформировать его первым, это приведет к каскадным сбоям.

3. ** "Сколько точек соприкосновения вы запланировали, по каким каналам и какой этап ADKAR обслуживает каждый из них?"**
   Рекомендуется: минимум 5, цель 7, по крайней мере по 3 каналам; каждая точка касания помечена для одного этапа ADKAR.
   Канон: Исследование Prosci 11th edition — 5-7 точек соприкосновения - это документально подтвержденная основа для принятия изменений в поведении.

4. ** "Какие вопросы зададут сотрудники, как только увидят это — и вы уже записали ответы?"**
   Рекомендуется: заполните FAQ как минимум 7 вопросами: состав, порядок отчетности, местоположение, смена роли, сроки, почему сейчас, почему мы. Предвзятое отношение к включению вопросов, которые вы хотели бы, чтобы люди не задавали.
   Канон: Барометр доверия Эдельмана (ежегодный) — внутреннее доверие рушится быстрее всего, когда очевидный вопрос остается без ответа.

5. ** "Кто является названным ответственным исполнителем, который появится в объявлении и будет присутствовать в мэрии, и подтвердили ли они оба?"**
   Рекомендуется: один человек с именем на уровне вице-президента или выше; физически (или с помощью видео) присутствует; не делегирует полномочия команде связи.
   Канон: Kotter 1996 (* Ведущее изменение*) — невидимые спонсоры триггером на шаге 1 (Установление срочности) приводят к сбою, и остальная часть модели разрушается.

6. ** "О чем ты умалчиваешь и почему?"**
   Рекомендуется: недвусмысленно сообщить об упущениях юридическому лицу / спонсору. Недосказанное будет выведено; лучше знать, о чем идет речь.
   Канон: Исследование увольнений Sucher & Gupta MIT Sloan (2018) — то, что опущено в объявлении об увольнении, становится основным сюжетом Glassdoor.

7. ** "На что похож успех 30 / 60 / 90 дней после объявления — и как вы это оцениваете?"**
   Рекомендуется: назовите 3 измеримых сигнала (например, дельта выбытия, вызывающая сожаление, показатель доверия к опросу pulse, результаты каскадного аудита менеджера).
   Канон: Hiatt 2006 (*ADKAR*) — Армирование - это наиболее часто пропускаемый этап ADKAR; без измерения армирование отсутствует.
