# планировщик производственных мощностей { #capacity-planner }

Инструмент определения размера для ** оперативных групп, которые выполняют работу в очереди ** — Поддержка, CX,
успех клиентов, бизнес-операции, ИТ-операции, финансовые операции. Построен на Erlang-C
теория массового обслуживания, закон Литтла и канон оперативного руководства
(Фурнье, Ларсон, Кливленд, Райнерцен). Детерминированный, только для stdlib,
без вызовов LLM.

## Цель { #purpose }

Вы - оперативный руководитель размером 15 на 35 и понятия не имеете, как на самом деле поведет себя организация из 35 человек
при пиковой нагрузке. Или у вас загрузка составляет 88%, а
SLA начинает снижаться. Или у вас утвержден бюджет найма, и вам нужно
распределить его по четырем кварталам, не истощая существующую
команду. Этот скилл отвечает на эти вопросы с помощью арифметики, а не вибраций.

Это приводит к появлению трех артефактов:

1. **Размер емкости** при использовании 70/80/90% по сравнению с P50/P90/P99
   требование, с P (нарушением SLA) в каждой точке и SAFE/WATCH/AT_RISK/CRITICAL
   полоса риска.
2. **Исправность использования** на уровне светофора для каждого участника плюс
   вердикт команды (ЗДОРОВ/ЗАЖАТ/ПЕРЕГРУЖЕН/НЕУРАВНОВЕШЕН).
3. **12-месячный квартальный план найма персонала ** учет кривых роста,
   выбытие персонала, рост спроса по сравнению с предыдущим кварталом и триггеры менеджера по контролю.

## Когда использовать { #when-to-use }

- **Ежегодное планирование производственных мощностей** (октябрь-ноябрь для следующих
  финансовый год).
- ** Ежеквартальный пересмотр размера** если спрос изменился более чем на 15% или выбытие резко возросло.
- ** Предбюджетная оборона** - математика, которая оправдывает спрос на численность персонала.
  вашему финансовому директору.
- ** Диагностика ** когда у оперативной группы отсутствует соглашение об уровне обслуживания и вам необходимо знать
  будь то проблема с размером, проблема с процессом или проблема с узким
местом.
- **Слияния и поглощения / запуск нового сегмента** моделирование — подбор новой команды или
  объединенная организация.

## Воркфлоу { #workflow }

1. **Потребность в потреблении**. Получите ежедневный билет P50/P90/P99/case объем от
   ваша рабочая система (Zendesk, Intercom, JSM, ServiceNow, Salesforce).
   Если у вас есть только средние значения, остановитесь и извлеките распределение. Одинокий-
   точечные оценки спроса - это самый дорогой анти-паттерн в ops.
2. **Пропускная способность модели**. Бежать `capacity_modeler.py` с вашим требованием,
   AHT, целевой показатель SLA, текущий FTE и усадка. Использование `--profile` для
вашей функции (support / cx / bizops / finance-ops / it-ops). Читать
   строка с 80%-ным использованием — это ваша точка отсчета.
3. **Риск использования флага**. Бежать `utilization_analyzer.py` против
   фактические данные об использовании вашей текущей команды. Кто-нибудь получил поддержку >85%
   это риск снижения пропускной способности в расчете на Райнерцена. Спред >30 процентов
   баллы по всей команде означают НЕСБАЛАНСИРОВАННОСТЬ — исправьте это перед приемом на работу.
4. **Последовательность приема на работу**. Бежать `hiring_sequencer.py` с текущим FTE,
   ориентируйтесь на EOY, время нарастания, выбытие и рост. Это будет фронтальная загрузка
   нанимает сотрудников (1 квартал - 35%, 4 квартал - 15%), применяет кривые нарастания и триггер менеджера
   нанимайте, когда диапазон контроля превысит 7 микросхем/manager.
5. ** Пройдитесь по библиотеке принудительных вопросов ** (смотрите ниже). Один вопрос на
   какое-то время. Не забегайте вперед. Ответы должны быть записаны до
того, как вы приступите к выполнению плана.

## Сценарии { #scripts }

- `scripts/capacity_modeler.py` — Калибровка Erlang-C с усадкой
  корректировка и вероятности нарушения P50/P90/P99. `--profile`
  для отраслевых значений по умолчанию.
- `scripts/utilization_analyzer.py` — светофор для каждого участника +
  вердикт о состоянии здоровья на уровне команды с выявлением отклонений.
- `scripts/hiring_sequencer.py` — 12-месячный квартальный план с рампой,
  выбытие, рост, ограничение на максимальное количество сотрудников в квартал и
логика триггера менеджера.

Все трое принимают `--input <path>` (JSON), `--output {markdown,json}`,
`--sample` (встроенный пример), и `--help` Только . Stdlib.

## Краткий пример { #quick-example }

```bash
# Emits an Erlang-C capacity model (required headcount + P50/P90/P99 breach probabilities) for the built-in example
cd business-operations/skills/capacity-planner && python3 scripts/capacity_modeler.py --sample
```

## Допущения { #assumptions }

Этот скилл предполагает:

- Работа ** ставится в очередь** (заявки, кейсы, рабочие элементы) — не в стиле проекта.
  Если работа вашей команды не ставится в очередь, это неправильный скилл.
- Спрос имеет ** достаточно стационарное распределение** в течение квартала.
  Поэтапные изменения (запуск нового продукта, слияния и поглощения, изменение законодательства) требуют
  повторный запуск в середине четверти.
- У вас есть ** по крайней мере 90 дней исторических данных о спросе** для расчета
  P50/P90/P99. Если нет, сгенерируйте распределение на основе ваших продаж /
  сначала прогноз на основе пользовательской базы.
- Услуга является **одноклассовой** внутри очереди. Если у вас трудные
  уровни приоритета (P1/P2/P3 с условиями обслуживания, зависящими от класса), моделируйте каждый как отдельную
очередь и суммируйте.
- **Каналы моделируются согласованно.** Многоканальные команды используют
  соответствующий `--profile` со встроенным премиальным коэффициентом усадки.

## Анти-паттерны { #anti-patterns }

Видишь `references/capacity_anti_patterns.md` для получения полной таксономии с
источниками. Восьмерка лучших:

1. Планируйте использование на 100% (принцип Райнерцена 12)
2. Обработать-рампу-как-мгновенную (Ларсон)
3. Игнорировать-выбытие-за-12-месячный-план (Bersin)
4. Нанимать-ICs-навсегда-без-менеджера-триггер (Фурнье)
5. Размер до P50-только по запросу (Кливленд)
6. Регулировка без усадки (Кливленд, рабочая тетрадь SRE)
7. Одноканальная модель для многоканальной работы (Gartner, Kingman)
8. План "Без всплесков" для мероприятий P99 (Хопп и Спирман, Райнерцен)

## Отличный от { #distinct-from }

- **`c-level-advisor/vpe-advisor`** измерения *проектирование* пропускная способность
  с помощью показателей DORA 4, сюжетных точек, частоты развертывания и
узких мест во времени цикла. Это код доставки для инженерных групп. Этот
скилл предназначен для оперативных групп, обрабатывающих билеты/cases. Другая единица
работы, другая математика (Erlang-C против DORA), другое узкое место
  (организация очередей-слепой подбор персонала по сравнению с НЗП + время выполнения заказа).
- **`c-level-advisor/chro-advisor`** имеет ли *стратегическое значение* рабочая сила
  планирование (портфолио возможностей на 1-5 лет, предложение талантов,
преемственность руководства). Этот скилл позволяет определять *эксплуатационную* мощность на 0-12 месяцев
в зависимости от спроса. Пер Лоулер: объединив их, вы получите работу
  не на ту работу.
- **`project-management/*`** отслеживает пропускную способность проектов
  (Скорость Jira, мощность спринта). Этот скилл
ориентирован на стационарную работу в очереди.
- **Родной брат `process-mapper`** * находит* узкое место. Этот скилл
  * распределяет команду вокруг * известного узкого места. Порядок операций:
  сначала составитель карты процессов → затем планировщик производственных мощностей. Наем в обход
неправильных ограничений приводит к растрате сотрудников впустую.
- **`business-growth/cs-coverage`** (если он существует) размеры заказчика
  Охват успеха по соотношению ARR/CSM и сегменту. Размер этого скилла
зависит от объема работы в очереди (заявки, кейсы, эскалации). Для команды CS
, которая обрабатывает как работу с отношениями, так и очередь заявок, запустите и то, и другое.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

** Дисциплина**: проходите их по одному за раз. Не забегайте вперед. Ответы должны
быть записаны. Если вы не можете ответить ни на один из них, это ваше следующее расследование.

### Вопрос 1 — "В чем заключается ваше узкое место, и подтвердили ли вы это эмпирически?" { #q1--what-is-your-bottleneck-and-have-you-confirmed-it-empirically }

**Рекомендуемый ответ **: именованный, измеряемый этап в воркфлоу с
данными о времени ожидания в очереди, показывающими, где ожидает работа. Ни малейшей вибрации. Не "эскалация
занимает слишком много времени". Фактическая измеренная очередь.

** Почему это первый вопрос**: Голдратт ("Цель", 1984) — каждая
система одновременно имеет ровно одно обязательное ограничение. Ориентируясь на
неправильное ограничение, вы полностью теряете время на наем сотрудников. Если вы не знаете своего
узкого места, запустите `process-mapper` ДО этого скилла.

** Канон**: Эли Голдратт, "Цель" (1984); Райнерцен, "Принципы
потока разработки продукта" (2009).

### Вопрос 2 — "На какой компромисс в отношении услуг вы соглашаетесь?" { #q2--what-service-trade-off-are-you-accepting }

** Рекомендуемый ответ **: письменный, четкий выбор — быстрый или чуткий,
широкий или глубокий, недорогой или нет. высокое качество. Фрэнсис Фрей недвусмысленна:
вы не можете выиграть все четыре. Команда, которая попытается, выиграет ноль.

**Почему это важно**: AHT, SLA и затраты на усадку являются оперативным
выражением этого компромисса. Если они не согласны (например, вы устанавливаете AHT для
"эмпатии", а SLA для "скорости"), план внутренне противоречив.

** Канон**: Фрэнсис Фрей и Энн Моррисс, *Необычное служение* (HBR Press,
2012).

### Вопрос 3 — "Каков ваш спрос на P90 и каков разрыв с вашим P99?" { #q3--whats-your-demand-p90-and-whats-the-gap-to-your-p99 }

** Рекомендуемый ответ **: два конкретных числа из данных за последние 90 дней
с календарным контекстом каждого (например, "P90 было 480 билетов/day
по обычным вторникам; P99 был равен 720 на следующий день после ноябрьского релиза").
Команда размером до P50 пропускает SLA в половине случаев. Команда численностью до P99
превышает штат на 30-50%. P90 - это правильная рабочая точка калибровки для каждого
Кливленд.

** Канон**: Брэд Кливленд, *Управление колл-центром в ускоренной перемотке вперед* (4
-е изд., 2019); А.К. Эрланг, * Теория вероятностей и телефонная связь
Беседы* (1909).

### Вопрос 4 — "При вашем запланированном использовании, что такое P (нарушение SLA) на P90 и на P99?" { #q4--at-your-planned-utilization-what-is-psla-breach-at-p90-and-at-p99 }

** Рекомендуемый ответ **: две вероятности, вычисленные (не угаданные) из
Erlang-C с вашей конкретной целью N, AHT и SLA. Если P (нарушение на P90)
> 10% на момент определения размера у вас не хватает персонала. Если P(нарушение на P99) >
в 50% случаев у вас нет плана повышения производительности, и следующее пиковое событие будет видно
генеральному директору.

** Канон**: Эрланг (1909); Хопп и Спирман, *Заводская физика* (3-е изд.,
2008), уравнение VUT.

### Вопрос 5 — "Заложили ли вы в бюджет наем новых сотрудников в связи с сокращением персонала, которое вы увидите в этом году?" { #q5--have-you-budgeted-replacement-hires-for-the-attrition-youll-see-this-year }

**Рекомендуемый ответ**: да, с определенным номером. При ежегодном
сокращении персонала на 30% (средняя точка BPO Bersin) команда из 20 человек в этом году теряет ~ 6 человек.
Если ваш план "добавить 5 нетто" на самом деле является планом "нанять 11", объем набора
персонала кардинально меняется. Анти-паттерн №3.

**Канон**: Критерии оценки талантов Bersin/Deloitte (2015-2023); Эдвард Лоулер,
*Стратегическое кадровое планирование* (генеральный директор USC, 2008).

### Вопрос 6 — "Когда span of control триггер для найма менеджера и кто является кандидатом?" { #q6--when-does-span-of-control-trigger-a-manager-hire-and-who-is-the-candidate }

**Рекомендуемый ответ**: конкретный квартал (от `hiring_sequencer.py`)
и по крайней мере один идентифицированный кандидат (внутренний руководитель или внешний наймит).
Последние 7 микросхем/manager, время 1:1 ухудшается, циклы обратной связи проскальзывают, износ
возрастает. После 10 у вас кризис с охватом. Наймите менеджера ДО достижения 10-го уровня, а не после.


** Канон**: Камиль Фурнье, *Путь менеджера* (О'Рейли, 2017),
гл. 5; Энди Гроув, *Управление высокой производительностью* (1983).

### Вопрос 7 — "Каков ваш план по увеличению нагрузки на день P99?" { #q7--what-is-your-surge-plan-for-the-p99-day }

** Рекомендуемый ответ **: четкий, документированный план — уровень переполнения,
контрактные мощности BPO, ротация по вызову, дерево эскалации для руководителей,
ИЛИ письменный контракт на снижение производительности, в котором говорится: "в течение 99 дней мы продлеваем SLA
до X минут и заблаговременно уведомляем клиентов". Если ответ "мы
разберемся с этим", то день P99 - это пожар, видимый правлению.

** Канон**: Хопп и Спирман, *Физика фабрики* (2008); Райнерцен (2009)
что касается дисциплины запаса мощности.
