# Оптимизатор закупок — Категоризация расходов + Рационализация поставщиков { #procurement-optimizer--spend-categorization--supplier-rationalization }

Вы являетесь руководителем отдела закупок / руководителем BizOps / вице-президентом по финансам, проводящим ежегодный ревью категории. Ваша работа заключается в том, ** что покупать, у кого, в какой последовательности **, а не в том, как работает поставщик, которого вы уже выбрали (это `vendor-management`). Вы классифицируете расходы в соответствии с таксономией, согласованной с UNSPSC, находите 20% категорий по Парето, на которые приходится 80% затрат, выявляете узкие места в цикле закупок и разрабатываете сбалансированный с учетом рисков план консолидации поставщиков, который отказывается сворачивать категории уровня 1 до единого источника без задокументированное непредвиденное обстоятельство.

## Цель { #purpose }

Типичная компания среднего звена имеет:
- Расходы на программное обеспечение выросли на 40% в годовом исчислении, и ни один владелец не может назвать основные категории роста.
- 3 инструмента мониторинга, 2 платформы учета расходов, 4 инструмента маркетинга по электронной почте - кластеры дублирующих функций, которые никто не объединял, потому что ни у кого не было данных для обоснования рекомендации.
- Цикл закупок, при котором некоторые категории закрываются за 5 дней, а другие - за 90, но "среднее значение" скрывает ограничение.
- Даты продления приходились на один и тот же месяц, что сводило на нет переговорные рычаги.

Этот скилл создает детерминированный, защищаемый артефакт для каждой проблемы: категоризированные расходы по Парето, система показателей времени цикла по категориям и план консолидации с явными флагами рисков.

## Когда использовать { #when-to-use }

- Ежегодный аудит SaaS и ревью расходов на уровне категорий.
- Владелец категории хочет знать, какие 5 категорий привели к росту расходов в этом году.
- Финансы указывают на то, что расходы на программное обеспечение выросли на 40% в годовом исчислении и нуждаются в расчете по Парето по категориям, а не по поставщикам.
- BizOps подозревает дублирующие функции инструментов (мониторинг, расходы, маркетинг по электронной почте) и нуждается в обоснованном плане консолидации.
- Финансовый директор хочет ужесточить пороговые значения одобрения и нуждается в данных о времени цикла для каждой категории, чтобы обосновать это.
- После приобретения двум группам по закупкам необходимо объединить таксономии категорий и дедуплицировать базу поставщиков.

## Когда не следует использовать { #when-not-to-use }

- Оценка или аудит отдельного поставщика, которому вы уже решили продолжать платить → родственник `vendor-management`.
- Закрытие финансового рынка, ежемесячная отчетность или анализ прибыли и убытка → `finance/financial-analysis`.
- Составление или согласование условий контракта → `c-level-advisor/general-counsel-advisor`.
- Формирование предложений по исходящим продажам → `business-growth/contract-and-proposal-writer`.

## Воркфлоу { #workflow }

### Шаг 1 — Расход на потребление { #step-1--intake-spend }

Попросите пользователя заполнить `assets/spend_intake_template.md` (20 минут для типичной компании среднего звена). В скелете ожидаются позиции с `{supplier, description, category_hint, annual_spend, frequency, currency}`. Если имеются данные о расходах за предыдущий год, включите их в анализ за год.

### Шаг 2 — Классифицируйте и найдите Парето { #step-2--categorize-and-find-the-pareto }

Бежать `scripts/spend_categorizer.py --input spend.json --profile <profile> --output categorized.md`.

Классификатор сопоставляет каждую позицию с классом → Семейством → сегментом, не привязанным к SC (встроенная карта из ~ 30 категорий, настроенных для расходов технологических стартапов: Программное обеспечение / SaaS, Аппаратное обеспечение, Облачная инфраструктура, Профессиональные услуги, Маркетинговые услуги, Юридические услуги, Рекрутинг, Путешествия, Офис, страхование, льготы и т.д. — НЕ полная база данных UNSPSC объемом 100 тыс.). Выходные данные включают в себя:

- Категоризированные кампании
- Парето: на какие 20% категорий приходится 80% расходов?
- Топ-10 категорий роста в годовом исчислении (при наличии данных за предыдущий год)

Профили изменяют приоритетность карты категорий: `tech-startup` (тяжелый SaaS / облако), `scaleup` (инструменты продаж / тяжелый набор персонала), `enterprise` (высокий уровень профессиональных услуг / оснащения), `services`, `manufacturing`.

### Шаг 3 — Проанализируйте цикл закупок { #step-3--analyze-the-purchasing-cycle }

Бежать `scripts/purchasing_cycle_analyzer.py --input pos.json --output cycle.md`.

Для каждой записи PO `{category, request_date, approval_date, po_issued_date, goods_received_date, payment_date, approver_hops}`, анализатор вычисляет для каждой категории:

- Время цикла T-запрос → T-PO (медиана, P90)
- T-PO → T-pay (медиана, P90)
- Утверждающий-количество переходов (медиана)

Затем он помечает категории со временем цикла > 2× медиана между категориями как категории с **узким местом**. Это теория ограничений Голдратта, применяемая к закупкам: пропускная способность системы определяется самым медленным шагом, а самый медленный шаг почти всегда относится к одной конкретной категории (юридический ревью контрактов на оказание услуг, ревью безопасности SaaS уровня 1).

### Шаг 4 — Спланируйте консолидацию поставщиков с балансировкой рисков { #step-4--plan-supplier-consolidation-with-risk-balancing }

Бежать `scripts/supplier_consolidation.py --input suppliers.json --profile <profile> --output consolidation_plan.md`.

Планировщик определяет **кластеры дублирующих функций** (например, 3 инструмента мониторинга, 2 платформы учета расходов). Для каждого кластера:

- Выбирает рекомендованного победителя консолидации (сохраняется самый высокий уровень критичности ИЛИ победитель с наименьшими затратами на переключение, если кластер 3-го уровня, в зависимости от типа кластера).
- **Указывает на риск:** НЕ рекомендуется сворачивать до одного источника для любой категории критичности уровня 1, если только входные данные явно не указывают на документированный план по разбиванию стекла. В выходных данных явно указано: "НЕ КОНСОЛИДИРОВАТЬ кластер уровня 1, в записи нет разбитого стекла. Сначала добавьте 72-часовой план действий в чрезвычайных ситуациях."
- Оценки экономии: текущие расходы кластера − расходы победителя − стоимость миграции (сумма оценок затрат на переключение проигравших).
- Анализ кластеризации по дате продления: помечает категории, в которых в течение одного календарного месяца продлевается ≥ 3 контрактов (без кредитного плеча).

### Шаг 5 — Обобщение результатов ревью закупок { #step-5--synthesize-the-procurement-review }

Объедините 3 артефакта в готовый для BizOps дайджест:

- Топ-5 категорий, способствующих росту расходов в годовом исчислении (классификатор)
- Топ-3 категории узких мест, блокирующих пропускную способность (анализатор циклов)
- Топ-5 возможностей консолидации с оценкой экономии и рисков (планировщик консолидации)
- Все кластеры обновления разрушают рычаги воздействия
- Точки воздействия из одного источника уровня 1, нуждающиеся в планах разбивки стекла перед любой консолидацией

## Сценарии { #scripts }

| Сценарий | Цель |
|---|---|
| `scripts/spend_categorizer.py` | Классификация, согласованная с UNSPSC + Парето + рост в годовом исчислении |

## Допущения { #assumptions }

1. Пользователь имеет доступ к экспорту AP / expense / SaaS-management или может вручную составить список расходов из 100-200 основных позиций (действует правило Парето - большая часть расходов приходится на 20% крупнейших поставщиков).
2. Расходы за предыдущий год предпочтительны (в годовом исчислении), но необязательны; классификатор корректно ухудшается, если отсутствует.
3. Данные о цикле закупок предпочтительны, но необязательны; если они отсутствуют, пользователь получает только категоризацию + консолидацию.
4. Критичность поставщика (`tier-1/2/3`) - это ** суждение пользователя **, не основанное только на расходах. Уровень 1 = блокирование доходов в случае исчезновения поставщика. Инструмент отказывается выводить это — пользователь должен отметить это.
5. Выходные артефакты (категоризированный Markdown, система показателей цикла, план консолидации) являются ** входными данными для человеческого решения**, а не самим решением.

## Анти-паттерны { #anti-patterns }

- ** Консолидация до единого источника для критической категории уровня 1 без плана "разбей стекло". ** Экономия затрат ничего не дает, если консолидированный поставщик исчезает. Видишь `references/procurement_anti_patterns.md`.
- ** Классифицируйте по названию поставщика, а не по тому, что было куплено.** Workday может быть "Кадровым программным обеспечением" или "Финансовым программным обеспечением", в зависимости от того, какие модули лицензированы. Позиция `description` и `category_hint` используйте классификацию, а не название поставщика.
- **Игнорируйте кластеризацию по дате обновления.** Двенадцать контрактов уровня 2, которые все продлеваются в марте, означают нулевое влияние на переговоры по любому из них. Разложите их.
- ** Одобрить по умолчанию расходы на сумму менее 5 тысяч долларов.** Это модель "смерть от тысячи SaaS". Классификатор явно отображает кластеры "с небольшими расходами и большим количеством поставщиков".
- **Нет ревью ежеквартального обновления.** Годовой - это слишком грубо для SaaS, который обновляется непрерывно в течение года.
- ** Рационализируйте, не измеряя стоимость переключения. ** Объединение 3 инструментов для экономии 50 тысяч долларов, когда миграция обходится в 200 тысяч долларов, - это не экономия.
- ** Консолидируйте только на основе цены, игнорируя задолженность по интеграции.** Дешевый инструмент, который не интегрируется с вашим хранилищем данных, стоит дороже, чем дорогой, который интегрируется.
- ** Относитесь к теневым расходам на ИТ как к проблеме маркетинга. ** Это проблема закупок. Распространение маркетинговых инструментов является движущей силой №1 роста масштабов расходов на SaaS.

## Отличный от { #distinct-from }

- **Родной брат `vendor-management`** — это оценка производительности (время безотказной работы, соглашение об уровне обслуживания, риски третьих лиц) для поставщиков, которым вы уже решили продолжать платить. Это ** рационализация расходов + консолидация поставщиков** — принятие решения о том, каких поставщиков оставить.
- **`finance/financial-analysis`** — это финансовое закрытие, P&L, отчетность, DCF. Это оперативные закупки: категорийная стратегия и рационализация поставщиков, а не финансовая отчетность.
- **`c-level-advisor/general-counsel-advisor`** — это договорное право (возмещение убытков, интеллектуальная собственность, ликвидированный ущерб). Это стратегия расходов на уровне категории. Как только вы решите, какие 3 инструмента мониторинга объединить в 1, GC ревью ознакомится с условиями контракта с выжившим.
- **`business-growth/contract-and-proposal-writer`** — это исходящие предложения для привлечения клиентов. Это рационализация входящих поставщиков.
- **`finance/budgeting`** — это планирование годового бюджета. Это взгляд изнутри: где на самом деле происходит утечка бюджетных средств.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Проходили по одному мимо `/cs:grill-bizops` или оркестратор BizOps. Рекомендуемый ответ + цитата из канона на каждый вопрос. Никогда не упаковывался.

1. ** "Прежде чем мы классифицируем, есть ли у вас таксономия, не согласованная с SC, или вы классифицируете по названию поставщика?"**
   Рекомендуется: классифицировать по тому, что приобретено (описание позиции + category_hint), а не по поставщику. Один поставщик может охватывать несколько категорий.
   Канон: Официальная документация UNSPSC по таксономии, A.T. Kearney *Управление расходами* по архитектуре категорий.

2. ** "Из 10 ваших лучших категорий по расходам, какие 3 выросли больше всего в годовом исчислении — и знаете ли вы почему?"**
   Рекомендуется: назовите их перед открытием инструмента. Если вы не можете их назвать, это и есть диагноз.
   Канон: Исследование BCG по созданию ценности закупок, Hackett оценивает степень зрелости видимости на уровне категории.

3. ** "Каковы затраты на объединение для каждого кластера с дублирующимися функциями (например, 3 инструмента мониторинга) и превышает ли это экономию?"**
   Рекомендуется: четко оценить стоимость переключения (обучение, доработка интеграции, миграция данных). Отказывайтесь рекомендовать консолидацию без этого.
   Канон: BCG в отношении рисков консолидации поставщиков проводит анализ неудачных инициатив по рационализации.

4. ** "Для любой категории уровня 1, которую вы предлагаете объединить с одним поставщиком, каков 72-часовой план "разбей стекло", если этот поставщик исчезнет?"**
   Рекомендуется: задокументированные непредвиденные обстоятельства для каждой категории, протестированные. Если отсутствует, не консолидируйте.
   Канон: Нотпетя / M.E.Doc уроки атаки на цепочку поставок, NIST SP 800-161, А.Т. Кирни о риске концентрации поставок.

5. ** "Какой % ваших расходов проходит через PO по сравнению с возмещением расходов или теневым ИТ? Где тратится "индивидуалист"?"**
   Рекомендуется: измерьте его. Исследование A.T. Kearney показало, что 10-40% расходов в неконтролируемых компаниях являются индивидуальными.
   Канон: Модель зрелости закупок A.T. Kearney maverick-spend research, ISM (Институт управления поставками).

6. ** "Сколько из ваших топ-20 контрактов продлевается за один и тот же календарный месяц? У вас есть календарь обновления?"**
   Рекомендуется: составьте календарь; сознательно распределяйте обновления. Групповые обновления уничтожают переговорные рычаги.
   Канон: Исследование IACCM/WorldCC по управлению контрактами, посвященное вопросам выбора времени для переговоров.

7. ** "Каков ваш порог одобрения для новых покупок SaaS на сумму менее 5 тысяч долларов? Кому принадлежит проблема со смертельным исходом на тысячу SAAS?"**
   Рекомендуется: повышенный порог + один владелец. Данные Productiv / Zylo показывают, что более 50% роста SaaS приходится на неконтролируемые покупки стоимостью менее 5 тысяч долларов.
