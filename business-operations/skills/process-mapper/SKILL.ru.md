# средство отображения процессов { #process-mapper }

Документирование бизнес-процессов в стиле BPMN, выявление узких мест и анализ времени цикла для руководителей внутренних операций.

## Цель { #purpose }

Работа внутренних операций страдает от трех повторяющихся режимов сбоев:

1. ** Неявный процесс** — этапы существуют только в племенных знаниях, поэтому хэндоффы прекращаются, а онбординг занимает недели.
2. ** Невидимое ожидание** — большая часть времени, затраченного на любой бизнес-процесс, - это время ожидания в очереди / утверждения, а не фактическая работа; команды оптимизируют неправильный этап.
3. ** Локальная оптимизация** — Теория ограничений Голдратта игнорируется; ресурсы добавляются к этапам без ограничений, ничего не получая.

Этот скилл создает документированную карту процесса, определяет, где ожидает выполнения работа, и указывает на ограничение по имени с помощью детерминированной логики, а не интуиции LLM.

## Когда использовать { #when-to-use }

- Документирование нового бизнес-процесса (прием закупок, онбординг поставщика, онбординг сотрудника, хэндофф инцидента, возмещение расходов, онбординг клиента, рассмотрение претензий).
- Существующий процесс "слишком медленный", но никто не может назвать узкое место.
- Время цикла измеряется, но коэффициент полезного действия - нет, поэтому команда не может определить, является ли процесс полезным для здоровья или приводит к большим отходам.
- Межфункциональные хэндоффы сокращают работу, и первопричина неясна.

## Воркфлоу { #workflow }

Пятиступенчатый детерминированный поток:

1. ** Прием.** Запишите процесс в виде файла JSON с одной записью на каждый этап: `name`, `owner`, `type` (`value-add` | `wait` | `rework`), `duration_minutes_p50`, `duration_minutes_p90`. Используйте `assets/process_template.md` и его JSON-скелет.
2. ** Составьте карту этапов.** Запуск `process_documenter.py` для создания диаграммы плавательных дорожек в формате ASCII + нормализованный артефакт JSON. Полоса для плавания разделяет полосы движения по владельцам, так что становятся видны межфункциональные хэндоффы.
3. **Измерьте время цикла.** Запуск `cycle_time_analyzer.py` для вычисления общего P50, общего P90, коэффициента добавленной стоимости (VA%) и оценки пропускной способности по закону Литтла. Вердикт: VA% > 25% = ЗДОРОВЫЙ, 10-25% = ТИПИЧНЫЙ, < 10% = С БОЛЬШИМ КОЛИЧЕСТВОМ ОТХОДОВ.
4. **Выявлять узкие места.** Запуск `bottleneck_detector.py` с соответствующим `--profile` (saas / услуги / производство / здравоохранение). Результатом является ранжированный список с указанием степени тяжести (КРИТИЧЕСКАЯ / ВЫСОКАЯ / СРЕДНЯЯ), гипотезы о первопричине и одного рекомендуемого действия для каждого обнаружения.
5. ** Рекомендовать.** Сопоставьте список узких мест с вердиктом по времени цикла; рекомендуйте единственное вмешательство, ориентированное на ограничение, в соответствии с правилом Голдратта "подчинять все ограничению". Не рекомендуется оптимизировать стадию без ограничений.

## Сценарии { #scripts }

**`scripts/process_documenter.py`** — Считывает JSON-файл процесса, проверяет его и выдает текстовую диаграмму плавательных дорожек в стиле BPMN в Markdown (полосы по владельцу, этапы с аннотацией типа + продолжительность). Также выводит нормализованный артефакт JSON для нижестоящих инструментов. Только Stdlib. `--sample` печатает 6-ступенчатый пример закупки-приема.

**`scripts/bottleneck_detector.py`** — Применяет три детерминированных правила обнаружения: (а) стадия P50 > 2× среднее значение стадий добавления ценности, (б) % состояния ожидания > 40% от общего цикла, (в) % доработки > 15%. Пороговые значения регулируются с помощью `--profile` потому что SaaS, услуги, производство и здравоохранение имеют разные "нормальные" коэффициенты ожидания. Результатом является ранжированный список с указанием серьезности, гипотезы, действия.

**`scripts/cycle_time_analyzer.py`** — Вычисляет общее время циклов P50 и P90, коэффициент добавленной стоимости (VA%), % ожидания, % доработки и оценку пропускной способности по закону Литтла (WIP / время цикла). Согласно канону бережливого производства: VA% > 25% = ПОЛЕЗНО для ЗДОРОВЬЯ, 10-25% = ТИПИЧНО (сюда относится большинство непроизводственных процессов), < 10% = МНОГО ОТХОДОВ.

## Допущения { #assumptions }

1. Пользователь может предоставить данные о времени цикла на уровне этапа (даже приблизительные оценки P50 / P90). Если они не могут, то первым шагом является инструментирование процесса, а не его картографирование.
2. "Процесс" здесь означает повторяемый бизнес-воркфлоу с отдельными этапами, а не разовый проект.
3. Пользователь имеет полномочия устранять узкие места (или может направлять полученные данные тому, кто это делает). Без этого результат будет академическим.
4. Стадия `type` честно говоря: этап "создания дополнительной ценности", обозначенный пользователем как таковой, действительно меняет рабочий продукт с точки зрения заказчика. Неправильное обозначение ожидания как добавляющей ценности является наиболее распространенным сбоем в качестве данных.

## Анти-паттерны { #anti-patterns }

- ** Отображение всех процессов одновременно. ** Выберите один из них. Голдратт: ограничение заключается в одной точке.
- **Оптимизация без ограничений.** Если этап 4 является узким местом, ускорение этапа 2 просто создает запасы перед этапом 4. Подчините все ограничению.
- **Ошибочное принятие общего времени цикла за время обработки.** Они почти никогда не совпадают; VA% выявляет разрыв.
- ** Добавление людей в процесс, связанный с ожиданием.** Время ожидания не определяется увеличением численности персонала; это решается удалением хэндоффа или пакетной обработки.
- ** Рассмотрение переделки как отдельной проблемы. ** циклы переделки относятся к карте процессов. Сокрытие их занижает истинное время цикла.

## Отличный от { #distinct-from }

- **скиллы для роста бизнеса** — движение внешних продаж, конверсия по воронке лидов, удержание успешных клиентов. Process-mapper - это *внутренние* операции.
- **инжиниринг /slo-архитектор** — оценки надежности системы / бюджеты ошибок / предупреждения о частоте выгорания. Process-mapper - это время цикла бизнес-процесса, а не время безотказной работы системы.
- **советник уровня c (главный операционный директор/CEO-распорядитель)** - стратегическое определение приоритетов процессов, которые необходимо исправить. Process-mapper - это тактический инструмент, используемый после принятия решения о расстановке приоритетов.
- ** скиллы управления проектами ** — инструментарий для воркфлоу Jira / Confluence ticket. Process-mapper - это процесс * проектирования*, а не отслеживание заявок *.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Перед вызовом инструментов оркестратор (или `/cs:grill-bizops`) знакомит пользователя с этими вопросами ** по одному за раз, с рекомендуемым ответом + цитатой из канона **. Никогда не упаковывался.

1. ** "Есть ли у вас измеренное время цикла для трех самых длинных этапов или только приблизительные данные?"**
   Рекомендуется: настаивайте на измеренных данных.
   Канон: Голдратт 1984 (*Цель*) — оптимизация предполагаемых узких мест надежно атакует неправильное ограничение.

2. ** "Вы составляете карту *текущего* процесса (как есть) или *предполагаемого* процесса (будущего)?"**
   Рекомендуется: сначала составьте карту как есть. Будет после выявления узкого места.
   Канон: Rother & Shook, 1999 (*Учимся видеть*) — отображение потока создания ценности всегда начинается с текущего состояния.

3. ** "Где происходят хэндоффы между командами и как долго длится ожидание каждой хэндоффы?"**
   Рекомендуется: регистрировать каждый хэндофф с указанием среднего времени ожидания.
   Канон: Reinertsen 2009 (*Принципы процесса разработки продукта*) — время ожидания при хэндоффах является самой большой невидимой стоимостью.

4. ** "Каков размер вашей партии на каждом этапе?"**
   Рекомендуется: по возможности увеличивайте размер партии до 1.
   Канон: Anderson 2010 (*Канбан*) — размер партии коррелирует с разницей во времени цикла 1:1.

5. ** "Какова скорость переделки на каждом этапе?"**
   Рекомендуется: обработать это явно; переделать циклы, принадлежащие карте.
   Канон: Pyzdek (*Руководство по Six Sigma*) — скрытая доработка занимает 30-50% общего времени цикла в процессах обслуживания.

Сначала пройдите вглубь. Не открывайте вопрос 4 до получения ответов на 1-3. После того, как все 5 заблокированы, вызовите `process_documenter.py` → `bottleneck_detector.py` → `cycle_time_analyzer.py` в определенной последовательности.
