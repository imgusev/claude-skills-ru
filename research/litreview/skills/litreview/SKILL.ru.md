# Litreview — Ориентация на академическую литературу { #litreview--academic-literature-orientation }

> ** Переносимость: ** Работает в любом месте с исходящим протоколом HTTPS — поисковая строка по умолчанию - это ** бесплатные API без ключа ** (электронные утилиты PubMed + OpenAlex, без учетной записи, без ключа, без MCP). Согласованный MCP - это необязательный канал расширения**, используемый только при подключении в этом сеансе. Node.js с `docx` пакет необходим для генерации документа, и (в CLI) `bash_tool`. Работает в Claude Code CLI изначально и в Claude.искусственный интеллект с выполнением кода.

Подготовьте ** стартовую площадку** — не законченный ревью литературы, а ориентировочный документ, который даст исследователю, вступающему в незнакомую область, все необходимое для того, чтобы уверенно начать чтение и поиск. Подумайте: что бы сказал вам за чашечкой кофе щедрый коллега, знающий свое дело.

## Поисковые полосы { #search-lanes }

| Полоса движения | Когда | Как |
|---|---|---|
| **Свободная полоса движения (по умолчанию)** | Всегда доступен; нет ключа, нет плана, нет MCP | Электронные утилиты PubMed + OpenAlex через `scripts/free_search.py` или прямой HTTPS (шаблоны URL-адресов приведены ниже) |
| **Полоса консенсуса (дополнительное усовершенствование)** | Только в том случае, если на этом сеансе доступны инструменты согласованного MCP | Запускайте согласованные запросы * в дополнение к* свободной полосе для своих синтезированных карточек ответов |

**Проверка полосы пропускания (одна проверка во время выполнения — заменяет все определения уровней): ** если согласованные инструменты MCP ** недоступны в этом сеансе, используйте бесплатную полосу пропускания — ** не пытайтесь определить уровни **, не анализируйте маркетинговую копию, не спрашивайте пользователя об их Согласованный план. Если консенсус доступен, дополнительно запустите поиск по нему и объедините результаты (дедуплицируйте по DOI/title).

### Шаблоны URL-адресов свободных полос (точные) { #free-lane-url-templates-exact }

**Электронные утилиты PubMed** (без ключа; этикет: ≤3 запроса в секунду):

1. Поиск → PMIDs: `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi?db=pubmed&term=<urlencoded-query>&retmode=json&retmax=20&sort=relevance`
   — читать `esearchresult.idlist` (PMIDs) и `esearchresult.count`.
2. PMIDs → метаданные: `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esummary.fcgi?db=pubmed&id=<pmid1,pmid2,...>&retmode=json`
   — за `result[<pmid>]` читать `title`, `authors[].name`, `pubdate`, `fulljournalname`, `articleids[]` (тот `idtype: "doi"` запись).
3. Гейт для определения эры: добавить `&datetype=pdat&mindate=2021&maxdate=3000` (недавний) или `&maxdate=2015` (исторический).
4. URL-адрес статьи: `https://pubmed.ncbi.nlm.nih.gov/<PMID>/`.

**OpenAlex** (без ключа; добавить `&mailto=<email>` для вежливого пула — быстрее + надежнее):

1. Поиск: `https://api.openalex.org/works?search=<urlencoded-query>&per-page=20&mailto=<email>`
   — за `results[]` читать `display_name` (название), `publication_year`, `cited_by_count`, `doi`, `id` (URL OpenAlex), `authorships[].author.display_name`, `primary_location.source.display_name` (место проведения).
2. Гейт, определяющий эпоху: `&filter=from_publication_date:2021-01-01` или `&filter=to_publication_date:2015-12-31`.
3. Статьи для ревью: `&filter=type:review`.

Openalex's `cited_by_count` является источником подсчета цитирований для интеллектуального уровня перекрестного поиска (PubMed esummary не возвращает подсчетов).

## Правила добросовестности агента (Соглашение об исследовательском пакете) { #agent-integrity-rules-research-pack-convention }

Унаследовано от соглашения research-pack; зафиксировано дословно согласно аудиту согласованности между скиллами PR #657.

- **Дисциплина источника.** Цитируйте только статьи, возвращенные в результате поиска на этой сессии (свободная полоса и / или консенсус). Учебные знания, помеченные `[Not from search — model knowledge]` и исключен из числа цитируемых. Редкие результаты указываются явно, никогда не заполняются автоматически.
- **Дисциплина счета.** Отслеживаются три номера: выполнены поисковые запросы / получены уникальные статьи (дедуплицируются по DOI / названию) / цитируемые статьи. Каждая цитируемая статья имеет доступный для извлечения URL-адрес с этой сессии (PubMed, DOI, OpenAlex или Consensus). Использование `scripts/citation_tracker.py` для детерминированных подсчетов.
- ** Этикет с ограничением скорости.** Электронные утилиты PubMed: ≤3 запроса в секунду без ключа. OpenAlex: вежливый пул через `mailto`. Консенсус (при подключении): 1 запрос в секунду, обязательное последовательное выполнение. Дисциплина по умолчанию: ** последовательный, 1 запрос в секунду по всем полосам.**
- **Политика повторных попыток.** При сбое → подождите 3 секунды → повторите попытку один раз → войдите в систему. После 3 последовательных сбоев: остановитесь, предупредите пользователя, поделитесь тем, что было собрано.
- ** Проверка полосы движения.** Одна проверка во время выполнения при запуске сеанса: доступны согласованные инструменты MCP или нет. Никакого определения уровня, никогда.

Видишь [`references/search_budget_allocation.md`](references/search_budget_allocation.md) для обоснования последовательного исполнения + предельные значения бюджета.

## Обработка ошибок { #error-handling }

| Неудача | Поведение |
|---|---|
| Ограничение скорости / ошибка HTTP на любой полосе | Подождите 3 секунды, повторите попытку один раз, запишите результат |
| Поиск возвращает 0 результатов | Обратите явное внимание; "либо нишевая терминология, либо подлинный пробел"; никогда не заполняйте молча |
| Сеть недоступна (2 выхода со свободной полосы движения) | Остановите, предупредите пользователя — для бесплатной полосы требуется исходящий HTTPS; ничего не нужно обнаруживать или обновлять |
| 3 последовательных сбоя | Прекратите поиск, предупредите пользователя, поделитесь собранным, спросите, как действовать дальше |
| Подобласть возвращает скудные результаты (<5 статей) | Отметьте в аудите; предложите вручную дополнить Google Scholar / Scopus |
| Пользователь хочет настроить вложенные области | Обновите таблицу, повторно подтвердите перед поиском |
| Ошибка проверки DOCX | Распаковать XML, исправить, переупаковать |

## Фаза 0: Прием пищи на гриле (3 форсирующих вопроса, по одному за раз) { #phase-0-grill-me-intake-3-forcing-questions-one-at-a-time }

Каждый вопрос содержит явное "почему я спрашиваю". Условие остановки: максимум 3 перед фазой 1.

### Q1 (корень) — Специфика исследовательского вопроса { #q1-root--research-question-specificity }

> **Сформулируйте исследовательский вопрос в 1-2 предложениях. Конкретнее — "Как магистранты справляются с задачами клинического обоснования по сравнению с врачами?" превосходит "Искусственный интеллект в медицине". Расплывчатые вопросы приводят к расплывчатым ревью.**
>
> *Почему я спрашиваю:* Разведывательный поиск зависит от точной терминологии. Расплывчатые вопросы приводят к скудным результатам разведки, которые не дают полезной разбивки фреймворка.

** Откажитесь от кашицы.** Повторите запрос один раз с примерами, если пользователь слишком широк. Если все еще расплывчато, изложите с явной оговоркой "ориентация на широкий охват, а не на ревью глубины".

### Q2 (зависит от Q1) — подсказка по фреймворку { #q2-depends-on-q1--framework-hint }

> **Фреймворк — выберите один или скажите "выбираете вы".:**
>
> 1. **ПИКО** (Популяция / вмешательство / Сравнение / исход — большинство клинических вопросов)
> 2. **ПАУК** (Образец / феномен / Дизайн / Оценка / Тип исследования — социальный/качественный)
> 3. **Декомпозиция** (Проблема /решение/ Оценка/ ограничения— ориентированные на технологию)
> 4. ** Гибрид** (вы выбираете, какие компоненты из какого фреймворка)
> 5. **Вы выбираете** — проанализируйте Q1 и порекомендуйте
>
> * Почему я спрашиваю: * PICO используется по умолчанию для ~ 70% клинических вопросов, но плохо соотносится с качественной работой или оценкой технологии. Предварительный выбор избавляет поисковую систему от необходимости указывать на несогласованный фреймворк.

Принудительный выбор по умолчанию ("вы выбираете"). Скилл выдает свою собственную рекомендацию по фреймворку после повторного поиска, чтобы пользователь мог ее переопределить. Использование `scripts/framework_recommender.py` для эвристики.

Видишь [`references/framework_selection.md`](references/framework_selection.md) для канона PICO / SPIDER / Decomposition.

### Q3 (зависит от Q1) — Ориентировочная глубина { #q3-depends-on-q1--tentative-depth }

> ** Ориентировочная глубина — выберите одну. Окончательное подтверждение приходит после разбивки фреймворка:**
>
> 1. ** Быстрое сканирование** (5 поисковых запросов)
> 2. ** Стандартный ревью** (10 поисковых запросов)
> 3. ** Глубокое погружение** (20 поисков)
>
> *Почему я спрашиваю:* Я спрашиваю об этом дважды — один раз сейчас, чтобы откалибровать акцент разведывательного поиска, другой раз после разбивки фреймворка для подтверждения. Предварительный ответ влияет на то, какие подобласти будут отображаться в первую очередь; окончательный ответ определяет распределение бюджета поиска.

Вынуждающий выбор. **Повторный запрос** на контрольной точке после фазы 2 после того, как пользователь ознакомился с разбивкой фреймворка.

** Условие остановки:** максимум 3 вопроса перед этапом 1. Контрольная точка после фазы 2 - это отдельный момент для "гриля" (таблица фреймворка + настройка подобласти + повторное подтверждение глубины).

## Фаза 1: Первоначальная разведка { #phase-1-initial-reconnaissance }

** Один широкий разведывательный поиск ** для определения тем, терминологии, методологических различий.

- Запустите проверку полосы движения (доступен консенсус или нет), затем:
  - Свободная полоса движения: `python scripts/free_search.py --query "<broad version of Q1>" --source both --max 20` (или приведенные выше шаблоны URL-адресов esearch/works)
  - **Если консенсус доступен, дополнительно** запустите один общий поиск консенсуса и объедините
- Запрос: расширенная версия Q1 (допустимы варианты терминологии; первый поиск приводит к широкому охвату)
- Запись: `citation_tracker.py --action record_search --session NAME --query "..."`
- Количество полученных записей: `citation_tracker.py --action record_papers_received --session NAME --count N`

Синтезировать для контрольной точки:
- Темы, которые всплыли на поверхность
- Различия в терминологии (например, "LLM" против "модели большого языка" против "модели в стиле GPT")
- Методологические различия (клинические испытания, сравнительная оценка и тематическое исследование)
- Пробелы в охвате (подвопросы, отсутствующие в результатах разведки)

## Этап 2: Выбор фреймворка + Формирование подобласти { #phase-2-framework-selection--sub-area-generation }

Выберите фреймворк (из Q2 или переопределите на основе recon):
- **ПИКО** — большинство клинических вопросов (~70% по умолчанию)
- **ПАУК** — социальный / качественный
- **Декомпозиция** — технологический фокус (проблема / решение / Оценка / ограничения)
- **Гибридный** — явное отображение кросс-фреймворка

Сгенерируйте ** 4-5 вопросов по подразделам**, сопоставленных с компонентами фреймворка. Каждый из них становится объектом целенаправленного поиска на этапе 3.

## Контрольно-пропускной пункт (момент "гриль-я заставляю-варианты") { #checkpoint-grill-me-forcing-options-moment }

После фазы 2 остановитесь и представьте:

### краткое содержание разведки в 3-4 предложениях { #3-4-sentence-recon-summary }
- Какие темы всплыли на поверхность
- Терминологический ландшафт
- Очевидная характеристика ландшафта

### Таблица разбивки фреймворка { #framework-breakdown-table }

| Компонент фреймворка | Как это соотносится с этой темой | Предлагаемая подобласть для изучения |
|---|---|---|
| (Компонент 1) | ... | Подзона 1 |
| (Компонент 2) | ... | Подзона 2 |
| (Компонент 3) | ... | Подзона 3 |
| (Компонент 4) | ... | Подзона 4 |
| Сквозная тема | ... | Подзона 5 |

### Повторное подтверждение глубины (принудительный выбор) { #depth-re-confirmation-forcing-choice }

Обратите внимание на ** практическое ограничение **: используемая полоса поиска (бесплатная / халявная + консенсус) + приблизительный предел в ~ 20 результатов на запрос в каждом источнике.

- Быстрое сканирование (5 поисковых запросов × ~20 результатов = максимум ~ 100 статей на источник)
- Стандартный ревью (10 поисковых запросов × ~20 = ~200 статей на источник)
- Глубокое погружение (20 поисковых запросов × ~20 = ~400 статей на источник)

### Варианты форсирования подобластей { #sub-area-forcing-options }

- "Выглядит хорошо — переходите к этим подразделам"
- "Настроить: добавить подобласть на [X]"
- "Отрегулировать: снять и заменить [Y] с [Z]"
- "Перезапустите с другим фреймворком"

### Почему я спрашиваю (обоснование) { #why-im-asking-the-rationale }

> Неправильный набор фреймворков или подобластей приводит к растрате бюджета поиска. Это **последний дешевый момент**, чтобы скорректировать курс.

**Дождитесь ответа пользователя перед этапом 3.** Откажитесь запускать этап 3 без явного выбора пользователя.

## Этап 3: Целенаправленный поиск { #phase-3-targeted-searches }

Последовательный (1 запрос в секунду), бюджет для каждого уровня глубины. Каждый поиск выполняется на свободной полосе (`free_search.py` или шаблоны URL-адресов); **если консенсус доступен, дополнительно** запустите там тот же запрос и объедините. Видишь [`references/search_budget_allocation.md`](references/search_budget_allocation.md) для полного канона.

### Быстрое сканирование (5 поисковых запросов) { #quick-scan-5-searches }
- 5 поисков по подрайону (по одному на подрайон)
- Пропустить эру-гейт + специфичный для ревью

### Стандартный ревью (10 поисковых запросов) { #standard-review-10-searches }
- 5 поисков по подразделам
- 2 ревью поиска по статьям (топ-2 подраздела): `"systematic review [topic]"` / `"meta-analysis [topic]"` (OpenAlex: добавить `&filter=type:review`)
- 2гейт-поиска с привязкой к эпохе (наиболее важная подобласть): исторический (PubMed `&maxdate=2015` / OpenAlex `to_publication_date:2015-12-31`) + недавние (опубликованные `&mindate=2021` / OpenAlex `from_publication_date:2021-01-01`)
- 1 продолжение статьи, получившей наибольшее цитирование, с использованием ее ключевых терминов + дата, начиная с года ее публикации

### Глубокое погружение (20 поисков) { #deep-dive-20-searches }
- 5 поисков по подразделам
- 5 поисковых запросов по статьям для ревью (по одному для каждой подобласти)
- 4 гейт-поиска с привязкой к эпохе (2 лучшие подобласти, каждая старая + новая)
- 3 продолжения по 3 самым цитируемым статьям
- 3 запасных для появляющихся потоков (неожиданные находки, за которыми нужно следить)

На всем протяжении: ограничение скорости 1 q/сек. Последовательный. Подтвердите ответ перед следующим вызовом. Записывайте каждый с помощью `citation_tracker.py`.

## Интеллектуальный перекрестный поиск { #cross-search-intelligence }

Три трекера по всем результатам поиска — запуск `scripts/cross_search_aggregator.py --session NAME` после завершения фазы 3:

1. ** Статьи с повторным попаданием ** - одна и та же статья появляется в более чем 3 поисковых запросах по подразделам = вероятная основополагающая
2. **Повторяющиеся авторы** — один и тот же автор в нескольких поисковых запросах = доминирующая исследовательская группа; топ-3-5 наиболее часто встречающихся вопросов
3. ** Эвристика цитирования в год** — статья 2023 года со 150 цитированиями >> статья 2008 года со 150 цитированиями. Используйте OpenAlex `cited_by_count` для идентификации исходной работы.

Они содержат разделы DOCX "Начать здесь" + "Ключевые исследовательские группы" + "Библиография".

## Этап 4: Руководство по исследованию DOCX { #phase-4-docx-research-guide }

Генерировать с помощью Node.js + `docx` библиотека. 8 разделов (см. [`references/docx_8_sections.md`](references/docx_8_sections.md) для получения полной спецификации):

1. ** Обзор темы ** — один сжатый абзац (4-6 предложений)
2. ** Начните здесь — Порядок приоритетного чтения ** — заказано 5-7 статей: лучший недавний ревью → основополагающий → 2-3 рубежа → пробел / противоречие. Каждое: название с гиперссылкой + авторы/год + вклад в 1 предложение + 1 предложение "на что обратить внимание"
3. ** Как поле попало сюда ** — хронологическое описание (1-2 абзаца) + таблица временных рамок (5-8 этапов: Год / веха / значимость) + примечание об эволюции терминологии
4. **Руководства по подразделам** (по одному на подраздел, по 4 части в каждом)
   - 4а. Что показывает исследование (обобщение 2-3 предложений со встроенными цитатами)
   - 4b. Ключевые статьи (3-5 статей с гиперссылками с указанием количества цитирований, года, важности 1 предложения)
   - 4c. Ключевые поисковые запросы (6-10 ключевых слов, синонимы, сетка, исторические термины)
   - 4d. Логические строки поиска (2-3 готовые к вставке строки)
5. ** Ключевые исследовательские группы** — 3-5 ведущих авторов/групп с указанием принадлежности, охвата отдельных областей, репрезентативной ссылки на статью (из агрегатора перекрестного поиска)
6. ** Открытые вопросы и пробелы** — три категории: методологические / популяционно-контекстные / концептуально-теоретические. Каждый пробел объясняет, *почему это важно*.
7. **Библиография** — в алфавитном порядке по первому автору. К каждой записи есть интерактивная ссылка: URL-адрес PubMed или DOI (бесплатная полоса) / "Просмотр на основе консенсуса" (Консенсус-источник). Каждая встроенная цитата соответствует библиографической записи.
8. ** Журнал аудита** — сводная таблица поиска (#, запрос, фильтры, возвращенные документы, статус), блок подсчетов, заметки о покрытии, включая то, какая полоса поиска была использована (бесплатно / free+консенсус)

### Технические требования к DOCX { #docx-technical-requirements }

Задокументируйте ключ `docx` библиотечные шаблоны:

- Страница: Американское письмо, поля размером 1 дюйм
- Списки: `LevelFormat.BULLET` (никогда не используйте маркеры в юникоде)
- Гиперссылки: `ExternalHyperlink` с `style: "Hyperlink"`, полный URL-адрес (никогда не усекается)
- Столы: двойной ширины (`columnWidths` + ячейка `width`), `ShadingType.CLEAR`
- Шаг проверки после сохранения (проверка целостности zip-файла: `python3 -c "import zipfile,sys; zipfile.ZipFile(sys.argv[1]).testzip()" output.docx` — нет выходных данных = не поврежден — затем подтвердите наличие необходимых разделов)

Обратитесь к ** скиллу docx** для получения шаблонов настройки и рекомендаций.

## Анти-Паттерны для отклонения { #anti-patterns-to-reject }

- Распараллеливание поисковых вызовов (любая полоса)
- Пропуск интерактивной контрольной точки (выполнение всех поисковых запросов без подтверждения пользователя)
- Дополнять тонкие результаты знаниями о тренировках
- Использование по умолчанию фреймворка, отличного от PICO, без обоснования
- Цитирование статей в чате, которые не были получены в результате поиска в этой сессии
- Попытка определения уровня согласованного плана (удалено - единственная проверка во время выполнения — "доступны ли инструменты согласованного MCP в этом сеансе?")
- Обработка консенсуса по мере необходимости (это необязательное усовершенствование; по умолчанию используется свободная полоса)
- Пропуск поисковых запросов с гейтами, привязанных к эпохе, в стандартных/углубленных бюджетах
- Пропуск результатов перекрестного поиска (повторные обращения, повторяющиеся авторы)
- Усечение исходных URL-адресов в гиперссылках
