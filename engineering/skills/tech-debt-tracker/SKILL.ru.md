# Технический отслеживатель долгов { #tech-debt-tracker }

**Уровень**: МОЩНЫЙ 🔥  
**Категория**: Автоматизация технологических процессов  
**Экспертные знания**: Качество кода, Управление техническими долгами, Разработка программного обеспечения

## Обзор { #overview }

Технический долг является одной из самых коварных проблем в разработке программного обеспечения - со временем он усугубляется, замедляя скорость разработки, увеличивая затраты на обслуживание и снижая качество кода. Этот скилл обеспечивает всеобъемлющий фреймворк для выявления, анализа, расстановки приоритетов и отслеживания технической задолженности в разных кодовых базах.

Технический долг связан не только с беспорядочным кодом - он включает в себя архитектурные сокращения, пропущенные тесты, устаревшие зависимости, пробелы в документации и компромиссы в инфраструктуре. Подобно финансовому долгу, на него начисляются "проценты" за счет увеличения времени разработки, увеличения числа ошибок и снижения скорости работы команды.

## Что дает этот Скилл { #what-this-skill-provides }

Этот скилл предлагает три взаимосвязанных инструмента, которые формируют полноценную техническую систему управления долгом:

1. ** Сканер долгов** - Автоматически идентифицирует сигналы технического долга в вашей кодовой базе
2. ** Система определения приоритетов задолженности** - Анализирует и расставляет приоритеты по статьям задолженности с использованием фреймворков стоимости задержки
3. ** Долговая Дашборд** - Отслеживает тенденции задолженности с течением времени и предоставляет управленческую отчетность

Вместе эти инструменты позволяют инженерным командам принимать решения о технологическом долге на основе данных, сочетая разработку новых функций с работами по техническому обслуживанию.

## Быстрый запуск — сканирование → определение приоритетов → Дашборд { #quick-start--scan--prioritize--dashboard }

Все пути относительно этой папки с скиллами. Выходные данные сканера в формате JSON напрямую передаются в систему определения приоритетов; датированные снимки инвентаризации передаются на дашборд.

### 1. Отсканируйте кодовую базу { #1-scan-the-codebase }

```bash
python3 scripts/debt_scanner.py /path/to/codebase --format json --output debt_inventory.json
```

Испускает `debt_inventory.json` с `scan_metadata`, `summary`, `debt_items[]`, `file_statistics`, и `recommendations`. Сообщить о `summary` засчитывается пользователю. (Сухой пробег: `assets/sample_codebase`.)

### 2. Расставьте приоритеты в невыполненной работе { #2-prioritize-the-backlog }

```bash
python3 scripts/debt_prioritizer.py debt_inventory.json --framework wsjf --team-size 6 --sprint-capacity 20 --format json --output debt_priorities.json
```

Фреймворки: `cost_of_delay` (по умолчанию), `wsjf`, `rice`. Выходные данные содержат `prioritized_backlog` (работа сверху вниз), `sprint_allocation` (вставить в планирование спринта), и `insights`.

### 3. Отслеживайте тенденции с течением времени { #3-track-trends-over-time }

Храните датированные снимки (`debt_YYYY-MM-DD.json`), затем:

```bash
python3 scripts/debt_dashboard.py --input-dir snapshots/ --period monthly --format both --output debt_dashboard
```

Или передавать файлы явно (образцы: `assets/historical_debt_2024-01-15.json assets/historical_debt_2024-02-01.json`). Дашборд сообщает о направлении тренда и сводках, готовых к исполнению - используйте его, чтобы убедиться, что спринт по очистке действительно сократил задолженность.

### Цикл проверки { #verification-loop }

После спринта по исправлению: повторно запустите шаг 1, повторно запустите шаг 3 с новым моментальным снимком и подтвердите, что количество целевых категорий уменьшилось. Очистка, которая не перемещает дашборд, - это переделка, а не погашение долга.

## Распространенные подводные камни и как их избежать { #common-pitfalls-and-how-to-avoid-them }

### 1. Паралич анализа { #1-analysis-paralysis }
**Проблема**: Тратить слишком много времени на анализ долга вместо того, чтобы его исправлять.
** Решение **: Установите временные рамки для анализа, используйте оценку "достаточно хорошо" для большинства элементов.

### 2. Перфекционизм { #2-perfectionism }
**Проблема**: Попытка ликвидировать все долги вместо того, чтобы управлять ими.
** Решение**: Сосредоточьтесь на долгах с высокой отдачей, примите тот факт, что некоторая часть долга приемлема.

### 3. Игнорирование бизнес-контекста { #3-ignoring-business-context }
**Проблема**: Приоритет технической элегантности над ценностью для бизнеса.
** Решение**: Всегда привязывайте работу с долгами к бизнес-результатам и влиянию на клиентов.

### 4. Несогласованное применение { #4-inconsistent-application }
**Проблема**: Некоторые команды перенимают практику, в то время как другие игнорируют ее.
**Решение**: Сделайте отслеживание задолженности частью стандартного воркфлоу разработки.

### 5. Чрезмерная разработка инструментов { #5-tool-over-engineering }
**Проблема**: Создание сложных систем управления долгом, которыми никто не пользуется.
** Решение **: Начните с простого, повторяйте на основе фактических моделей использования.

Техническое управление задолженностью - это не просто написание лучшего кода, это создание методов устойчивого развития, которые уравновешивают краткосрочные трудности с поставками и долгосрочную работоспособность системы. Используйте эти инструменты и фреймворки для принятия обоснованных решений о том, когда и как инвестировать в сокращение задолженности.
