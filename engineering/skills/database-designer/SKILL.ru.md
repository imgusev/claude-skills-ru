# Разработчик баз данных - Скилл высокого уровня { #database-designer---powerful-tier-skill }

## Обзор { #overview }

Комплексный скилл проектирования баз данных, который обеспечивает возможности анализа, оптимизации и миграции на экспертном уровне для современных систем баз данных. Этот скилл сочетает теоретические принципы с практическими инструментами, помогающими архитекторам и разработчикам создавать масштабируемые, производительные и поддерживаемые схемы баз данных.

## Основные компетенции { #core-competencies }

### Проектирование и анализ схемы { #schema-design--analysis }
- **Анализ нормализации**: Автоматическое определение уровней нормализации (от 1NF до BCNF)
- **Стратегия денормализации**: Разумные рекомендации по оптимизации производительности
- **Оптимизация типов данных**: Выявление несоответствующих типов и проблем с размером
- **Анализ ограничений**: Отсутствующие внешние ключи, уникальные ограничения и проверки на null
- ** Проверка соглашения об именовании**: Согласованные шаблоны именования таблиц и столбцов
- ** Генерация ERD**: Автоматическое создание диаграммы русалки из DDL

### Оптимизация индекса { #index-optimization }
- **Анализ пробелов в индексах**: Идентификация отсутствующих индексов по внешним ключам и шаблонам запросов
- **Стратегия составного индекса**: Оптимальное упорядочение столбцов для многоколоночных индексов
- **Обнаружение избыточности индексов**: Устранение перекрывающихся и неиспользуемых индексов
- **Моделирование влияния на производительность**: Оценка избирательности и анализ стоимости запросов
- **Выбор типа индекса**: B-дерево, хэш, частичные, охватывающие и специализированные индексы

### Управление миграцией { #migration-management }
- **Миграция с нулевым временем простоя**: Внедрение модели расширенного контракта
- ** Эволюция схемы**: Безопасные добавления, удаления столбцов и изменения типов
- **Сценарии переноса данных**: Автоматическое преобразование и проверка данных
- **Стратегия отката**: Полные возможности разворота с проверкой
- **Планирование выполнения**: Упорядоченные шаги миграции с разрешением зависимостей

## Инструментальный воркфлоу (запускайте их — не анализируйте схемы вручную) { #tool-workflow-run-these--do-not-analyze-schemas-by-hand }

Все пути относительно этой папки скилла; примеры входных данных в `assets/`.

### 1. Проанализируйте схему { #1-analyze-the-schema }

```bash
python3 schema_analyzer.py --input schema.sql --generate-erd --output-format json -o analysis.json
```

Принимает схему SQL DDL или JSON (`assets/sample_schema.sql` / `sample_schema.json`). Выходные данные включают результаты нормализации, отсутствующие ограничения, проблемы с именованием и Mermaid ERD — покажите ERD пользователю и исправьте отмеченные проблемы перед оптимизацией.

### 2. Оптимизируйте индексы в соответствии с реальными шаблонами запросов { #2-optimize-indexes-against-real-query-patterns }

```bash
python3 index_optimizer.py --schema assets/sample_schema.json --queries assets/sample_query_patterns.json --analyze-existing --format json -o indexes.json
```

Сначала запишите горячие запросы пользователя в JSON с шаблонами запросов (скопируйте `assets/sample_query_patterns.json`). Результатом является упорядоченный по приоритету список рекомендаций по созданию ИНДЕКСА плюс удаление избыточных индексов.

### 3. Сгенерируйте миграцию { #3-generate-the-migration }

```bash
python3 migration_generator.py --current current_schema.json --target target_schema.json --zero-downtime --format sql -o migration.sql
```

`--zero-downtime` выдает план расширения контракта; `--validate-only` проверяет выполнимость без генерации SQL.

### 4. цикл проверки { #4-verification-loop }

Повторно запустите шаг 1 в схеме *target* и подтвердите, что проблемы, обнаруженные при первом проходе, устранены; запустите `migration_generator.py --validate-only` перед передачей миграции.

## Лучшие практики { #best-practices }

### Проектирование схемы { #schema-design }
1. ** Используйте осмысленные имена**: Четкие, непротиворечивые соглашения об именовании
2. **Выберите подходящие типы данных**: Столбцы правильного размера для повышения эффективности хранения
3. **Определите правильные ограничения**: внешние ключи, контрольные ограничения, уникальные индексы
4. **Учитывайте будущий рост**: Планируйте масштабирование с самого начала
5. **Взаимосвязи документов**: Четкие взаимосвязи внешних ключей и бизнес-правила

### Оптимизация производительности { #performance-optimization }
1. ** Стратегически индексируйте **: Охватывайте распространенные шаблоны запросов без чрезмерной индексации
2. ** Мониторинг производительности запросов**: Регулярный анализ медленных запросов
3. **Разбиение больших таблиц на разделы**: Повышение производительности запросов и обслуживания
4. **Используйте соответствующие уровни изоляции**: Сбалансируйте согласованность с производительностью
5. **Внедрить объединение подключений в пул**: эффективное использование ресурсов

### Соображения безопасности { #security-considerations }
1. **Принцип наименьших привилегий**: Предоставляйте минимально необходимые разрешения
2. **Шифрование конфиденциальных данных**: в состоянии покоя и при передаче
3. **Схемы аудита доступа**: Мониторинг и протоколирование доступа к базе данных
4. **Проверка входных данных**: Предотвращение атак с использованием SQL-инъекций
5. ** Регулярные обновления системы безопасности**: Поддерживайте актуальность программного обеспечения базы данных

## Шаблоны генерации запросов { #query-generation-patterns }

### ВЫБЕРИТЕ с помощью соединений { #select-with-joins }

```sql
-- INNER JOIN: only matching rows
SELECT o.id, c.name, o.total
FROM orders o
INNER JOIN customers c ON c.id = o.customer_id;

-- LEFT JOIN: all left rows, NULLs for non-matches
SELECT c.name, COUNT(o.id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name;

-- Self-join: hierarchical data (employees/managers)
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

### Общие табличные выражения (CTE) { #common-table-expressions-ctes }

```sql
-- Recursive CTE for org chart
WITH RECURSIVE org AS (
  SELECT id, name, manager_id, 1 AS depth
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, o.depth + 1
  FROM employees e INNER JOIN org o ON o.id = e.manager_id
)
SELECT * FROM org ORDER BY depth, name;
```

### Оконные функции { #window-functions }

```sql
-- ROW_NUMBER for pagination / dedup
SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
FROM orders;

-- RANK with gaps, DENSE_RANK without gaps
SELECT name, score, RANK() OVER (ORDER BY score DESC) AS rank FROM leaderboard;

-- LAG/LEAD for comparing adjacent rows
SELECT date, revenue,
  revenue - LAG(revenue) OVER (ORDER BY date) AS daily_change
FROM daily_sales;
```

### Шаблоны агрегирования { #aggregation-patterns }

```sql
-- FILTER clause (PostgreSQL) for conditional aggregation
SELECT
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE status = 'active') AS active,
  AVG(amount) FILTER (WHERE amount > 0) AS avg_positive
FROM accounts;

-- GROUPING SETS for multi-level rollups
SELECT region, product, SUM(revenue)
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());
```

## Модели миграции { #migration-patterns }

### Сценарии миграции вверх/вниз { #updown-migration-scripts }

Каждая миграция должна иметь обратимый аналог. Назовите файлы с префиксом временной метки для заказа:

```
migrations/
├── 20260101_000001_create_users.up.sql
├── 20260101_000001_create_users.down.sql
├── 20260115_000002_add_users_email_index.up.sql
└── 20260115_000002_add_users_email_index.down.sql
```

### Миграции с нулевым временем простоя (расширение/сжатие) { #zero-downtime-migrations-expandcontract }

Используйте шаблон expand-contract, чтобы избежать блокировки или нарушения работы кода:

1. **Развернуть** — добавить новый столбец/таблицу (с возможностью обнуления, по умолчанию)
2. **Перенос данных** — обратная заливка пакетами; двойная запись из приложения
3. **Переход** — приложение считывает данные из нового столбца; прекращает запись в старый
4. **Контракт** — удаление старого столбца при последующей миграции

### Стратегии обратного заполнения данных { #data-backfill-strategies }

```sql
-- Batch update to avoid long-running locks
UPDATE users SET email_normalized = LOWER(email)
WHERE id IN (SELECT id FROM users WHERE email_normalized IS NULL LIMIT 5000);
-- Repeat in a loop until 0 rows affected
```

### Процедуры отката { #rollback-procedures }

- Всегда проверяйте `down.sql` в промежуточной стадии перед деплою `up.sql` к производству
- Держите окно отката коротким — если этап контракта выполнен, для отката требуется новая прямая миграция
- Для необратимых изменений (удаление столбцов с данными) сначала создайте логическую резервную копию

## Оптимизация производительности { #performance-optimization }

### Стратегии индексирования { #indexing-strategies }

| Тип индекса | Вариант использования | Пример |
|------------|----------|---------|
| **B-дерево** (по умолчанию) | Равенство, диапазон, ПОРЯДОК ПО | `CREATE INDEX idx_users_email ON users(email);` |
| **ДЖИН** | Полнотекстовый поиск, JSONB, массивы | `CREATE INDEX idx_docs_body ON docs USING gin(to_tsvector('english', body));` |
| **Суть** | Геометрия, типы диапазонов, ближайший сосед | `CREATE INDEX idx_locations ON places USING gist(coords);` |
| **Частичный** | Подмножество строк (уменьшить размер) | `CREATE INDEX idx_active ON users(email) WHERE active = true;` |
| **Покрытие** | Сканирование только по индексу | `CREATE INDEX idx_cov ON orders(customer_id) INCLUDE (total, created_at);` |

### ОБЪЯСНИТЕ чтение плана { #explain-plan-reading }

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;
```

Ключевые сигналы, на которые следует обратить внимание:
- **Последующее сканирование** в больших таблицах — отсутствует индекс
- ** Вложенный цикл ** с высокими оценками строк — рассмотрите возможность объединения хэшем / слиянием или добавления индекса
- **Общее чтение буферов ** намного больше, чем ** попадание** — рабочий набор превышает объем памяти

### Обнаружение N+1 запроса { #n1-query-detection }

Симптомы: приложение выдает по одному запросу на строку (например, выборка связанных записей в цикле).

Исправления:
- Использование `JOIN` или подзапрос для получения за один проход туда и обратно
- Или нетерпеливая загрузка (`select_related` / `includes` / `with`)
- Шаблон загрузки данных для преобразователей GraphQL

### Объединение подключений в пул { #connection-pooling }

| Инструмент | Протокол | Лучше всего подходит для |
|------|----------|----------|
| **PgBouncer -блокировщик** | PostgreSQL | Объединение транзакций/выписок в пул, низкие накладные расходы |
| **ProxySQL** | MySQL | Маршрутизация запросов, разделение на чтение/запись |
| **Встроенный пул** (HikariCP, SQLAlchemy pool) | Любой | Объединение ресурсов на уровне приложений |

** Эмпирическое правило: ** Установите размер пула равным `(2 * CPU cores) + disk spindles`. Для облачных твердотельных накопителей начните с `2 * vCPUs` и настраивайся.

### Чтение реплик и маршрутизация запросов { #read-replicas-and-query-routing }

- Проложите весь маршрут `SELECT` запросы к репликам; запись в первичный
- Учитывайте задержку репликации (обычно <1 с для асинхронности, 0 для синхронизации)
- Использование `pg_last_wal_replay_lsn()` для обнаружения задержки перед считыванием важных данных

## Матрица принятия решений с несколькими базами данных { #multi-database-decision-matrix }

| Критерии | PostgreSQL | MySQL | SQLite | SQL Server |
|----------|-----------|-------|--------|------------|
| **Лучше всего подходит для** | Сложные запросы, JSONB, расширения | Веб-приложения, тяжелые для чтения рабочие нагрузки | Встроенный, разработка/тестирование, edge | Корпоративные .NET-стеки |
| **Поддержка JSON** | Отлично (JSONB + GIN) | Хорошо (тип JSON) | Минимальный | Хорошо (OPENJSON) |
| **Репликация** | Потоковое, логическое | Групповая репликация, кластер InnoDB | Н/Д | Всегда на связи |
| **Лицензирование** | Открытый исходный код (лицензия PostgreSQL) | Открытый исходный код (GPL) / коммерческий | Общественное достояние | Коммерческий |
| **Максимальный практичный размер** | Множественный туберкулез | Множественный туберкулез | ~1 ТБ (для одной записи) | Множественный туберкулез |

**Когда выбирать:**
- **PostgreSQL** — выбор по умолчанию для новых проектов; наилучшая расширяемость и соответствие стандартам
- **MySQL** — существующая экосистема MySQL; простые веб-приложения, требующие большого объема чтения
- **SQLite** — мобильные приложения, инструменты CLI, базы данных модульного тестирования, IoT/edge
- **SQL Server** — требуется корпоративной политикой; глубокая интеграция .NET/Azure

### Соображения по NoSQL { #nosql-considerations }

| База данных | Модель | Используйте, когда |
|----------|-------|----------|
| **MongoDB** | Документ | Гибкость схемы, быстрое прототипирование, управление контентом |
| **Повторный запуск** | Ключ-значение / кэш | Хранилище сеансов, ограничение скорости, таблицы лидеров, паб / саб |
| **DynamoDB** | Широкая колонна | Бессерверные приложения AWS с задержкой в одну цифру в миллисекундах в любом масштабе |

> Используйте SQL по умолчанию. Обращайтесь к NoSQL только тогда, когда шаблон доступа явно выигрывает от этого.

## Сегментирование и репликация { #sharding--replication }

### Разделение по горизонтали и вертикали { #horizontal-vs-vertical-partitioning }

- **Вертикальное разбиение**: Разделение столбцов по таблицам (например, отдельные столбцы больших двоичных объектов). Сокращает ввод-вывод для узких запросов.
- **Горизонтальное секционирование (сегментирование)**: Разделение строк по базам данных/серверам. Требуется, когда один узел не может хранить набор данных или обрабатывать пропускную способность.

### Стратегии сегментирования { #sharding-strategies }

| Стратегия | Как это работает | Плюсы | Минусы |
|----------|-------------|------|------|
| **Хэш** | `shard = hash(key) % N` | Равномерное распределение | Повторная настройка обходится дорого |
| **Диапазон** | Сегментировать по дате или диапазону идентификаторов | Простой, подходит для временных рядов | Горячие точки на последнем осколке |
| **Географический** | Сегмент по региону пользователя | Локальность данных, соответствие требованиям | Межрегиональные запросы сложны |

### Шаблоны репликации { #replication-patterns }

| Узор | Последовательность | Задержка | Вариант использования |
|---------|------------|---------|----------|
| **Синхронный** | Сильный | Более высокая задержка записи | Финансовые операции |
| **Асинхронный** | Возможный | Низкая задержка записи | Веб-приложения, перегруженные чтением |
| **Полусинхронный** | Подтверждена по крайней мере одна реплика | Умеренный | Баланс безопасности и скорости |
