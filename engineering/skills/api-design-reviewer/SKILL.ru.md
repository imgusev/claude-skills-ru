# Рецензент дизайна API { #api-design-reviewer }

**Уровень:** МОЩНЫЙ  
**Категория:** Инженерия / Архитектура  
**Сопровождающий:** Команда Клода по скиллам  

## Обзор { #overview }

Скилл API Design Reviewer обеспечивает всесторонний анализ и ревью проектов API, уделяя особое внимание соглашениям REST, передовым практикам и отраслевым стандартам. Этот скилл помогает инженерным командам создавать согласованные, поддерживаемые и хорошо спроектированные API-интерфейсы с помощью автоматизированной компоновки, обнаружения критических изменений и разработки систем показателей.

## Быстрый запуск — сначала запустите инструменты { #quick-start--run-the-tools-first }

```bash
# 1. Lint an OpenAPI/Swagger spec for convention violations
python3 scripts/api_linter.py openapi.json --format json -o lint.json

# 2. Detect breaking changes between two spec versions (gate: exits non-zero with --exit-on-breaking)
python3 scripts/breaking_change_detector.py openapi-v1.json openapi-v2.json --format json --exit-on-breaking -o breaking.json

# 3. Score overall design quality (gate: --min-grade fails below threshold)
python3 scripts/api_scorecard.py openapi.json --format json --min-grade B -o scorecard.json
```

Процесс ревью: запустите все три, сообщите о результатах линтера + критических изменениях + оценке пользователю, исправьте, затем повторно запускайте, пока линтер не станет чистым, `--exit-on-breaking` проходит (или критические изменения изменяются в зависимости от версии), и система показателей соответствует согласованному `--min-grade`. Никогда не подписывайте ревью API только на prose — прикрепляйте выходные данные инструмента.

## Основные возможности { #core-capabilities }

### 1. Привязка API и анализ соглашений { #1-api-linting-and-convention-analysis }
- **Соглашения об именовании ресурсов**: Применяет регистр kebab для ресурсов, camelCase для полей
- **Использование метода HTTP**: Проверяет правильность использования GET, POST, PUT, PATCH, DELETE
- **Структура URL-адреса**: Анализирует шаблоны конечных точек для обеспечения согласованности и RESTful-дизайна
- **Соответствие коду состояния**: Гарантирует использование соответствующих кодов состояния HTTP
- **Форматы ответов на ошибки**: Проверяет согласованность структур ответов на ошибки
- **Охват документации**: Проверяет наличие отсутствующих описаний и пробелов в документации

### 2. Обнаружение критических изменений { #2-breaking-change-detection }
- **Удаление конечной точки**: Обнаруживает удаленные или устаревшие конечные точки
- **Изменение формы ответа**: Определяет изменения в структурах ответа
- **Удаление полей**: Отслеживает удаленные или переименованные поля в ответах API
- **Изменения типа**: Отслеживает изменения типа поля, которые могут нарушить работу клиентов
- **Обязательные дополнения к полям**: Помечает новые обязательные поля, которые могут нарушить существующую интеграцию
- **Изменения кода состояния**: Обнаруживает изменения в ожидаемых кодах состояния

### 3. Оценка дизайна API по баллам и отзывам { #3-api-design-scoring-and-assessment }
- **Анализ согласованности** (30%): Оценивает соглашения об именовании, шаблоны ответов и структурную согласованность
- **Качество документации** (20%): Оценивает полноту и ясность документации API
- **Внедрение системы безопасности** (20%): Ревью аутентификации, авторизации и заголовков безопасности
- **Дизайн юзабилити** (15%): анализирует простоту использования, доступность для обнаружения и опыт разработчика
- **Шаблоны производительности** (15%): Оценивает шаблоны кэширования, разбивки на страницы и эффективности

## Принципы проектирования REST { #rest-design-principles }

### Соглашения об именовании ресурсов { #resource-naming-conventions }
```
✅ Good Examples:
- /api/v1/users
- /api/v1/user-profiles
- /api/v1/orders/123/line-items

❌ Bad Examples:
- /api/v1/getUsers
- /api/v1/user_profiles
- /api/v1/orders/123/lineItems
```

### Использование метода HTTP { #http-method-usage }
- **ПОЛУЧИТЬ**: Извлекать ресурсы (безопасно, идемпотентно)
- **POST**: Создание новых ресурсов (не идемпотентных)
- **PUT**: Заменить все ресурсы (идемпотентные)
- **ИСПРАВЛЕНИЕ**: Частичные обновления ресурсов (не обязательно идемпотентные)
- **УДАЛИТЬ**: Удалить ресурсы (идемпотентные)

### Лучшие практики в области структуры URL-адресов { #url-structure-best-practices }
```
Collection Resources: /api/v1/users
Individual Resources: /api/v1/users/123
Nested Resources: /api/v1/users/123/orders
Actions: /api/v1/users/123/activate (POST)
Filtering: /api/v1/users?status=active&role=admin
```

## Стратегии управления версиями { #versioning-strategies }

### 1. Управление версиями URL-адресов (рекомендуется) { #1-url-versioning-recommended }
```
/api/v1/users
/api/v2/users
```
** Плюсы**: Четкий, эксплицитный, простой в маршрутизации  
**Минусы**: увеличение количества URL-адресов, сложность кэширования

### 2. Управление версиями заголовков { #2-header-versioning }
```
GET /api/users
Accept: application/vnd.api+json;version=1
```
** Плюсы**: Чистые URL-адреса, согласование контента  
**Минусы**: Менее заметен, сложнее тестировать вручную

### 3. Управление версиями типов носителей { #3-media-type-versioning }
```
GET /api/users
Accept: application/vnd.myapi.v1+json
```
** Плюсы**: RESTful, поддерживает несколько представлений  
**Минусы**: Сложный, более сложный в реализации

### 4. Управление версиями параметров запроса { #4-query-parameter-versioning }
```
/api/users?version=1
```
** Плюсы**: Простота в реализации  
** Минусы**: Не успокаивает, может быть проигнорирован

## Форматы ответов об ошибках { #error-response-formats }

### Стандартная структура ошибок { #standard-error-structure }
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid parameters",
    "details": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "Email address is not valid"
      }
    ],
    "requestId": "req-123456",
    "timestamp": "2026-02-16T13:00:00Z"
  }
}
```

### Использование кода состояния HTTP { #http-status-code-usage }
- **400 Неверный запрос**: Неверный синтаксис запроса или параметры
- **401 Неавторизованный**: Требуется аутентификация
- **403 Запрещено**: Доступ запрещен (аутентифицирован, но не авторизован)
- **404 Не найдено**: Ресурс не найден
- **409 Конфликт**: Конфликт ресурсов (дубликат, несоответствие версии)
- **422 Необрабатываемый объект**: Допустимый синтаксис, но семантические ошибки
- **429 Слишком много запросов**: Превышен лимит скорости
- **500 Внутренняя ошибка сервера**: Непредвиденная ошибка сервера

## Идемпотентность { #idempotency }

### Идемпотентные методы { #idempotent-methods }
- **ПОЛУЧИТЬ**: Всегда безопасно и идемпотентно
- **PUT**: Должно быть идемпотентным (заменить весь ресурс)
- **УДАЛИТЬ**: Должно быть идемпотентным (тот же результат)
- **ИСПРАВЛЕНИЕ**: Может быть идемпотентным, а может и не быть

### Ключи идемпотентности { #idempotency-keys }
```
POST /api/v1/payments
Idempotency-Key: 123e4567-e89b-12d3-a456-426614174000
```

## Рекомендации по обратной совместимости { #backward-compatibility-guidelines }

### Безопасные изменения (неразрушающие) { #safe-changes-non-breaking }
- Добавление необязательных полей в запросы
- Добавление полей к ответам
- Добавление новых конечных точек
- Сделать обязательные поля необязательными
- Добавление новых значений перечисления (с изящной обработкой)

### Критические изменения (требуется изменение версии) { #breaking-changes-require-version-bump }
- Удаление полей из ответов
- Создание обязательных необязательных полей
- Изменение типов полей
- Удаление конечных точек
- Изменение структуры URL-адресов
- Изменение форматов ответов об ошибках

## Проверка OpenAPI/Swagger { #openapiswagger-validation }

### Необходимые компоненты { #required-components }
- **Информация об API**: Название, описание, версия
- **Информация о сервере**: Базовые URL-адреса и описания
- **Определения путей**: Все конечные точки с методами
- **Определения параметров**: Параметры запроса, пути, заголовка
- **Схемы запросов/ответов**: Полные модели данных
- **Определения безопасности**: Схемы аутентификации
- **Ответы на ошибки**: Стандартные форматы ошибок

### Лучшие практики { #best-practices }
- Используйте согласованные соглашения об именовании
- Предоставьте подробные описания для всех компонентов
- Включите примеры для сложных объектов
- Определите повторно используемые компоненты и схемы
- Проверка в соответствии со спецификацией OpenAPI

## Соображения о производительности { #performance-considerations }

### Стратегии кэширования { #caching-strategies }
```
Cache-Control: public, max-age=3600
ETag: "123456789"
Last-Modified: Wed, 21 Oct 2015 07:28:00 GMT
```

### Эффективная передача данных { #efficient-data-transfer }
- Используйте соответствующие HTTP-методы
- Реализовать выбор поля (`?fields=id,name,email`)
- Поддержка сжатия (gzip)
- Внедрить эффективную разбивку на страницы
- Используйте ETags для условных запросов

### Оптимизация ресурсов { #resource-optimization }
- Избегайте N+1 запросов
- Реализовывать пакетные операции
- Используйте асинхронную обработку для тяжелых операций
- Поддержка частичных обновлений (ПАТЧ)

## Лучшие практики обеспечения безопасности { #security-best-practices }

### Проверка входных данных { #input-validation }
- Проверьте все входные параметры
- Очистка пользовательских данных
- Используйте параметризованные запросы
- Ввести ограничения на размер запроса

### Безопасность аутентификации { #authentication-security }
- Используйте HTTPS везде
- Внедрить безопасное хранение токенов
- Поддержка истечения срока действия токена и обновления
- Используйте надежные механизмы аутентификации

### Средства контроля авторизации { #authorization-controls }
- Внедрять принцип наименьших привилегий
- Используйте разрешения, основанные на ресурсах
- Поддержка детального контроля доступа
- Шаблоны доступа к аудиту

## Краткое изложение передовой практики { #best-practices-summary }

1. **Прежде всего согласованность**: Поддерживайте согласованность именования, форматов ответов и шаблонов
2. **Документация**: Предоставьте исчерпывающую, актуальную документацию по API
3. ** Управление версиями**: Планируйте эволюцию с четкими стратегиями управления версиями
4. **Обработка ошибок**: Реализуйте последовательные, информативные ответы на ошибки
5. **Безопасность**: Встроите защиту в каждый уровень API
6. **Производительность**: Проектирование с учетом масштаба и эффективности с самого начала
7. ** Обратная совместимость**: Сведите к минимуму критические изменения и обеспечьте пути миграции
8. **Тестирование**: Внедрить комплексное тестирование, включая контрактное тестирование
9. ** Мониторинг**: Добавьте наблюдаемость за использованием API и производительностью
10. ** Опыт разработчика**: Уделяйте приоритетное внимание простоте использования и понятной документации

## Распространенные анти-паттерны, которых следует избегать { #common-anti-patterns-to-avoid }

1. ** URL-адреса, основанные на глаголах**: Используйте существительные для обозначения ресурсов, а не действий
2. **Несогласованные форматы ответов**: Поддерживайте стандартные структуры ответов
3. **Чрезмерная вложенность**: Избегайте глубоко вложенных иерархий ресурсов
4. **Игнорирование кодов состояния HTTP**: Используйте соответствующие коды состояния для различных сценариев
5. ** Некачественные сообщения об ошибках**: Предоставляйте конкретную информацию об ошибках, пригодную для принятия мер
6. **Отсутствует разбивка на страницы**: Всегда разбивайте список конечных точек на страницы
7. ** Стратегия управления версиями отсутствует**: Планируйте эволюцию API с первого дня
8. ** Раскрытие внутренней структуры**: Разработка API-интерфейсов для внешнего потребления, а не для внутреннего удобства
9. ** Отсутствует ограничение скорости **: Защитите свой API от злоупотреблений и перегрузки
10. **Неадекватное тестирование**: Протестируйте все аспекты, включая случаи ошибок и граничные условия


Регулярное использование инструментов linting, обнаружения критических изменений и подсчета очков обеспечивает непрерывное совершенствование и помогает поддерживать качество API на протяжении всего жизненного цикла разработки.
