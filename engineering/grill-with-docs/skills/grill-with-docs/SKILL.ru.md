# Гриль с документами { #grill-with-docs }

> Полученный из [Гриль Мэтта Покока с документами](https://github.com/mattpocock/skills/tree/main/skills/engineering/grill-with-docs) (Массачусетский технологический институт, © 2026 Мэтт Покок). Дисциплина интервью Мэтта + закрепленные в документах правила приготовления на гриле, дословно сохраненные в Массачусетском технологическом институте. Дополнения в этом репозитории: 3 валидатора stdlib (CONTEXT.md линтер, сканер ADR, глоссарий↔проверка соответствия кода), 3 подробные ссылки, каждая из которых ссылается на более чем 7 авторитетных источников, `cs-grill-with-docs` агент, `/cs:grill-with-docs` команда. Видишь [Дополнения к обертке](#wrapper-additions) ниже.

<what-to-do>

Неустанно расспрашивайте меня о каждом аспекте этого плана, пока мы не придем к общему пониманию. Пройдитесь по каждой ветви дерева проектирования, устраняя зависимости между решениями одно за другим. На каждый вопрос укажите свой рекомендуемый ответ.

Задавайте вопросы по одному за раз, ожидая обратной связи по каждому вопросу, прежде чем продолжить.

Если на вопрос можно ответить, изучив кодовую базу, изучите ее вместо этого.

</what-to-do>

## Осведомленность о предметной области { #domain-awareness }

Во время изучения кодовой базы также ищите существующую документацию:

### Файловая структура { #file-structure }

Большинство репозиториев имеют единый контекст:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

Если бы `CONTEXT-MAP.md` существует в корне, репозиторий имеет несколько контекстов. Карта указывает на то, где живет каждый из них:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

Создавайте файлы лениво — только тогда, когда вам есть что написать. Если нет `CONTEXT.md` существует, создайте его, когда будет разрешен первый термин. Если нет `docs/adr/` существует, создайте его, когда потребуется первый ADR.

## Во время сеанса { #during-the-session }

### Оспаривание глоссария { #challenge-against-the-glossary }

Когда пользователь использует термин, который противоречит существующему языку в `CONTEXT.md`, немедленно объявите об этом. "Ваш глоссарий определяет "отмену" как X, но вы, кажется, имеете в виду Y — что это?"

### Отточите нечеткий язык { #sharpen-fuzzy-language }

Если пользователь использует расплывчатые или перегруженные термины, предложите точный канонический термин. "Вы говорите "учетная запись" — вы имеете в виду Клиента или пользователя? Это разные вещи."

### Обсудите конкретные сценарии { #discuss-concrete-scenarios }

Когда обсуждаются отношения между доменами, проведите их стресс-тестирование с использованием конкретных сценариев. Придумывайте сценарии, которые исследуют крайние случаи и заставляют пользователя быть точным в отношении границ между понятиями.

### Перекрестная ссылка с кодом { #cross-reference-with-code }

Когда пользователь указывает, как что-то работает, проверьте, соответствует ли код. Если вы обнаружите противоречие, укажите его: "Ваш код отменяет все заказы целиком, но вы только что сказали, что возможна частичная отмена — что правильно?"

### Обновление CONTEXT.md встроенный { #update-contextmd-inline }

Когда термин будет разрешен, обновите `CONTEXT.md` прямо здесь. Не собирайте их в пакет — фиксируйте по мере их появления. Используйте формат в [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md).

`CONTEXT.md` должно быть полностью лишено деталей реализации. Не лечите `CONTEXT.md` в качестве спецификации, блокнота для заметок или хранилища решений по внедрению. Это глоссарий и ничего больше.

### Предлагайте ADR экономно { #offer-adrs-sparingly }

Предлагайте создать ADR только в том случае, если все три параметра верны:

1. ** Трудно обратить вспять ** — цена того, что вы передумаете позже, имеет значение
2. ** Удивительно без контекста** — будущий читатель задастся вопросом: "Почему они сделали это таким образом?"
3. ** Результат реального компромисса** - были реальные альтернативы, и вы выбрали одну из них по определенным причинам

Если какой-либо из трех пунктов отсутствует, пропустите ДОПОГ. Используйте формат в [ADR-FORMAT.md](./ADR-FORMAT.md).

## Дополнения к обертке { #wrapper-additions }

Приведенные ниже дополнения **не** являются частью вышестоящего скилла Мэтта. Они реализуют правила восходящего потока в виде детерминированных валидаторов, поддерживающих только stdlib, которые естественным образом сочетаются с циклом опроса.

### Воркфлоу (с инструментами-оболочками) { #workflow-with-wrapper-tools }

1. **Предполетная подготовка (перед первым вопросом):**
   - Бежать `scripts/context_md_linter.py CONTEXT.md` если бы `CONTEXT.md` существует — подтверждает правильность составления глоссария, прежде чем проверять его на гриле.
   - Бежать `scripts/adr_scanner.py docs/adr/` если `docs/adr/` существует — пробелы в нумерации поверхностей, некорректно оформленные ADR, несоответствия status-frontmatter.
   - Бежать `scripts/glossary_code_consistency.py --context CONTEXT.md --code src/` — помечает определенные, но неиспользуемые термины (мертвый глоссарий) и нарицательные существительные только для кода, которые могут нуждаться в определениях. Используйте эти флажки в качестве вводных вопросов для гриля.

2. **Во время сеанса (действуют правила Мэтта):**
   - По одному вопросу за ход, сначала в глубину.
   - Когда термин заостряется: редактировать `CONTEXT.md` немедленно; повторите запуск `context_md_linter.py` если правка носит структурный характер.
   - Когда требуется ДОПОГ: укажите это в разделе `docs/adr/`; повторный запуск `adr_scanner.py` для подтверждения нумерации.

3. **Закрытие:**
   - Окончательный `glossary_code_consistency.py` запустите, чтобы подтвердить, что никаких новых условий-сирот не вводилось.
   - Подведем итог: добавлены термины/refined, написаны ADR, обсуждены сценарии, открыты пункты.

### Инструменты (только для stdlib) { #tools-stdlib-only }

| Инструмент | Однострочная роль |
|---|---|
| `scripts/context_md_linter.py` | Подтверждать `CONTEXT.md` против CONTEXT-FORMAT.md структура. ПЕРЕДАЧА/ПРЕДУПРЕЖДЕНИЕ/СБОЙ по каждому правилу. |
| `scripts/adr_scanner.py` | Прогулка `docs/adr/`, проверьте `NNNN-slug.md` узор, целостность нумерации, завершенность корпуса. |
| `scripts/glossary_code_consistency.py` | Перекрестные ссылки на выделенные жирным шрифтом термины в `CONTEXT.md` против использования кодовой базы. Помечать мертвый глоссарий + код - только нарицательные существительные. |
