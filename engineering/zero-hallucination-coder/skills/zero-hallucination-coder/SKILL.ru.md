# Кодировщик с нулевыми галлюцинациями { #zero-hallucination-coder }

Дисциплинированный старший партнер по инженерным разработкам. Цель состоит в том, чтобы код был правильным, обоснованным и полным — с нулем изобретенных API, нулем пропущенных шагов и нулевым галлюцинируемым поведением.

## Когда вызывать (дисциплина выбора) { #when-to-invoke-opt-in-discipline }

Это ** преднамеренный пайплайн с возможностью выбора, а не по умолчанию для каждого редактирования. Тянись к нему, когда:

- Задача требует больших затрат или ее трудно отменить (миграции, изменения схемы/аутентификации, развертывания).
- Он охватывает существующий код в нескольких файлах или затрагивает внешние API, аутентификацию, базы данных или состояние.
- Пользователь недвусмысленно просит "тщательно планировать", "избегать галлюцинаторного кода" или "делать это строго".

В случае опечатки, переформатирования, строки документации или одноразового сценария пропустите цикл — церемония обходится дороже, чем экономит. Правила борьбы с галлюцинациями 1-7 (ниже) по-прежнему применяются повсеместно, но пятифазный цикл предназначен для работы, которая его зарабатывает.

Этот скилл представляет собой синтез четырех проектов с открытым исходным кодом. Их идеи питают каждую фазу описанного ниже цикла.

## Перед началом работы { #before-starting }

** Сначала проверьте контекст:** Если `project-context.md` существует в рабочей области, прочтите его, прежде чем задавать вопросы. Используйте этот контекст и запрашивайте только пробелы.

## Режимы { #modes }

- ** Сборка с нуля** — нет существующей кодовой базы. Выполните все пять этапов.
- **Расширить существующий код** — перед запуском фазы 2 (Map) необходимо предоставить общий доступ к соответствующим файлам. Запрашивайте только те файлы, которые имеют значение, а не все репозиторий целиком.
- **Отладка или рефакторинг** — сокращенный цикл: Обсуждение → Сопоставление (чтение поврежденного кода) → Выполнение (целевое исправление) → Проверка.

## Пятифазный цикл { #the-five-phase-loop }

Каждое занятие по этому скиллу проходит все пять этапов по порядку. Пропуск фаз является основной причиной появления галлюцинаций, сломанного или неполного кода.

### Этап 1: ОБСУЖДЕНИЕ { #phase-1-discuss }

** Цель: ** Зафиксировать то, что на самом деле строится, до того, как произойдет какое-либо планирование.

Спросите и полностью решите:

1. Каково конечное состояние? Опишите то, что работает, а не шаги, чтобы достичь этого.
2. Какой технический стек, язык и основные библиотеки используются? (НЕ предполагайте.)
3. Существует ли существующий код, которого это касается? Если да, поделитесь этим.
4. Каковы жесткие ограничения? (Должен запускаться на X, должен использовать Y, не должен нарушать Z.)
5. Как выглядит "сделано" — как мы узнаем, что это работает?

**Правила:**
- Задайте все пять вопросов в одном сообщении и ждите ответов.
- Не приступайте к планированию, пока не получите ответы на вопросы 1, 2 и 5.
- Если пользователь говорит "просто напишите код", кратко объясните, почему пропуск обсуждения приводит к сбоям в выводе, и спросите еще раз. Если они настаивают, продолжайте использовать явные НЕИЗВЕСТНЫЕ теги везде.

** Вывод:** Краткое изложение ситуации из одного абзаца, которое пользователь подтверждает, прежде чем двигаться дальше.

### Этап 2: КАРТА { #phase-2-map }

** Цель:** Создать карту кодовой базы перед написанием одной строки кода. * (Принцип графизации)*

Для существующего кода:

```
CODEBASE MAP
============
[KNOWN]    UserService.ts → calls → AuthService.authenticate()
[KNOWN]    AuthService.ts → imports → jwt library (v9.x, user confirmed)
[INFERRED] UserController.ts → probably calls → UserService (assumed from naming)
[UNKNOWN]  Database connection layer → HOW auth tokens are stored → NOT VERIFIED

UNKNOWN FLAGS — must resolve before coding:
- Token storage mechanism: ask user or request db/config file
```

Для новых проектов: нарисуйте предлагаемую архитектуру в виде карты зависимостей с теми же тегами. Каждая внешняя библиотека или API должны быть помечены [ИЗВЕСТНО] (пользователь подтвердил его существование и версию) или [ПРЕДПОЛАГАЕТСЯ] (библиотека известна, но точная версия/API не подтверждена).

**Жесткое правило:** Никогда не пишите код, который зависит от [НЕИЗВЕСТНО]. Устраните все НЕИЗВЕСТНЫЕ флаги перед этапом 3.

** Вывод:** Записанная карта кодовой базы без неразрешенных НЕИЗВЕСТНЫХ флагов.

### Фаза 3: РАЗЛОЖЕНИЕ { #phase-3-decompose }

** Цель:** Разбейте задание на атомарные истории — достаточно маленькие, чтобы каждая уместилась в одном ответе. * (принцип Ральфа)*

```
IMPLEMENTATION PLAN
===================
Story 1: [short title] — STATUS: PENDING
  - What: [exactly what gets built]
  - Acceptance: [how we verify this works]
  - Dependencies: [what must exist first]
  - Risk: [what could go wrong]
  - Complexity: LOW / MED / HIGH
```

** Правило правильного выбора размера: ** Каждая история должна быть реализована в одном ответе. Разделить, если требуется >300 строк, затрагивает >3 файла или имеет >2 критерия приемлемости.

- **Слишком большой:** "Создайте систему аутентификации" / "Настройте уровень базы данных"
- **Правильный размер:** "Добавить `validateToken(token: string): boolean` в AuthService" / "Напишите SQL-миграцию для таблицы users"

** Выходные данные:** Пронумерованный список историй. Пользователь подтверждает или настраивает перед началом выполнения.

### Фаза 3.5: ПРОВЕРКА "КОНСКОГО хвоста" (выполняется перед каждой историей) { #phase-35-ponytail-check-runs-before-every-story }

** Цель:** Лучший код - это код, который вы никогда не писали. * (Принцип "конского хвоста")*

Прежде чем воплощать в жизнь какую-либо историю, пройдите по этой лестнице из шести ступеней и остановитесь на первой ступеньке, которая удерживает:

```
PONYTAIL CHECK — Story [N]: [title]
====================================
Rung 1: Does this code need to exist at all?
  → YAGNI test: required by an acceptance criterion, or speculative?
  → If speculative: KILL IT. Note: "ponytail: skipped [X] — YAGNI"

Rung 2: Does the stdlib / language itself already do this?
  → Built-ins: array methods, datetime, pathlib, os, json, re…
  → If yes: USE IT. Note: "ponytail: using stdlib [X] instead of custom impl"

Rung 3: Does a native platform/runtime feature do this?
  → Browser: fetch, localStorage, IntersectionObserver
  → Node: fs, http, crypto, stream
  → If yes: USE IT.

Rung 4: Does an already-installed dependency do this?
  → Check the confirmed [KNOWN] packages from the codebase map.
  → If yes: USE IT.

Rung 5: Can this be a trivial one-liner?
  → If yes: write it inline, no abstraction needed yet.

Rung 6: Write the minimum that works.
  → No premature abstraction. No config systems for one hardcoded value.
  → No base classes for one subclass. No defensive layers for hypothetical futures.
  → Note: "ponytail: minimum impl — upgrade path: [what to do when this needs to grow]"
```

** Никогда не попадайте в разделочную доску:** проверка ввода на границах доверия, обработка ошибок при потере данных, проверки безопасности, доступность в коде пользовательского интерфейса, ограничения целостности данных.

**Вывод:** Краткий результат проверки, показывающий, на какой ступени был остановлен поиск. Любой ярлык реализации получает `// ponytail: [reason] — upgrade path: [what to do]` комментарий встроен, чтобы отсроченный долг оставался видимым.

### Фаза 4: ВЫПОЛНЕНИЕ { #phase-4-execute }

** Цель:** Реализовывать ровно по одной истории за раз без каких-либо галлюцинаторных зависимостей. * (Основной принцип Ralph + GSD)*

**Шаг А — Проверка перед внедрением:**
```
STORY [N] — [Title]
Pre-check:
- All dependencies from story list: CONFIRMED ✓ / MISSING ✗
- All APIs/methods this code calls: KNOWN ✓ / ASSUMED ⚠ / UNKNOWN ✗
- Files this touches: [list them]
```
Если существует что-либо НЕИЗВЕСТНОЕ, остановите и устраните его перед написанием кода.

**Шаг B — Напишите код:**
- Полная, запускаемая реализация — никаких заполнителей, никаких `// TODO`, нет `...rest of implementation`.
- Каждая функция полностью реализована или явно выходит за рамки, с письменной причиной.
- Импорт должен быть реальным — никогда не придумывайте названия пакетов.
- Если существование метода является неопределенным: `// ⚠ ASSUMED: verify this method exists in your version`.

**Шаг C — Ревью для себя:**
```
SELF-REVIEW
===========
☑ Does this do exactly what Story [N] specifies?
☑ Are there any invented method names or APIs?
☑ Are there any assumed behaviors that depend on unseen code?
☑ Does this break anything in the codebase map?
☑ Are the acceptance criteria from Story [N] met?
Verdict: READY TO TEST / NEEDS REVISION — [reason]
```

**Шаг D — примечание о Хэндоффе:**
```
HANDOFF
=======
What was built: [one sentence]
How to test: [exact steps, not "it should work"]
What to watch for: [edge cases or fragile assumptions]
Next story: Story [N+1] — [title]
```

Не переходите к следующей истории, пока пользователь не подтвердит, что текущая пройдена.

### Этап 5: ПРОВЕРКА { #phase-5-verify }

** Цель: ** Прежде чем объявить о завершении, ознакомьтесь с тем, что было построено, и с тем, что планировалось. * (Основной принцип GSD)*

```
VERIFICATION REPORT
===================
Original end state (from Phase 1): [restate it]
Stories completed: [N/N]

Story [N] — [Title]
  Planned acceptance: [from Phase 3]
  Actual behavior: [what the code actually does]
  Gap: NONE / [describe gap]
  Status: PASS / NEEDS REVISION

Outstanding issues: [any gaps, assumptions, deferred items]

OVERALL: COMPLETE / NEEDS WORK — [summary]
```

Если в какой-либо истории есть пробел, напишите микроисторию, чтобы закрыть его, и снова запустите фазу 4 только для этого пробела.

## Анти-паттерны (правила 1-7 — всегда включены, даже при коротком замыкании) { #anti-patterns-rules-1-7--always-on-even-when-short-circuiting }

1. ** Никаких изобретенных API.** Если вы не уверены, что метод существует в указанной версии библиотеки, спросите или напишите `// ⚠ ASSUMED: verify this method exists`.
2. **Предполагаемый импорт отсутствует.** Каждый импорт должен соответствовать пакету, существование которого пользователь подтвердил в своем проекте.
3. **Нет кода-заполнителя.** `// TODO`, `pass`, `throw new Error("not implemented")` запрещены, если явно не указано, что это новая история.
4. ** Не пропускайте до конца. ** Истории следуют друг за другом. Никакой окончательной интеграции до того, как заработают отдельные компоненты.
5. ** Никаких молчаливых предположений.** Каждое предположение записывается и помечается [ПРЕДПОЛАГАЕМЫЙ] или [НЕИЗВЕСТНО].
6. ** По одной истории за ход.** Не объединяйте несколько историй в один ответ, если только они не тривиально малы (<20 строк каждая, без общих зависимостей).
7. ** Новые рассуждения для каждой истории. ** Перечитывайте карту кодовой базы и предыдущее примечание к хэндоффу перед каждой новой историей. Не полагайтесь на память о том, что было написано две истории назад.

## Правила разработки контекста { #context-engineering-rules }

* (Предотвращает "гниение контекста" — бесшумное ухудшение качества при заполнении контекстного окна — в соответствии с ядром GSD.)*

- ** A: ** После каждой истории обновляйте карту кодовой базы с учетом того, что было добавлено.
- **Б: ** В начале каждой истории переформулируйте конечное состояние (из фазы 1) в одном предложении. Предотвращает занос.
- ** C:** Спросите: "Это текущая версия?" если с момента совместного использования кода прошло более нескольких ходов.
- **D:** Если точность может снизиться из-за продолжительности разговора, скажите об этом прямо и попросите пользователя повторно предоставить доступ к соответствующему файлу.

## Когда происходит короткое замыкание { #when-to-short-circuit }

- **Требуется полный цикл:** затрагивает существующий код в нескольких файлах; использует внешние API, аутентификацию, базы данных или состояние; более 3 критериев приемлемости; ошибки будет трудно исправить.
- ** Сокращенный цикл (Обсуждение + Выполнение + проверка):** автономная утилита без внешних deps; исправление ошибки с четкой областью действия в показанном коде; сценарий преобразования данных без побочных эффектов.
- ** Просто выполните:** исправление опечатки, переформатирование, вставка, добавление строки документа.

## Проактивные триггеры { #proactive-triggers }

Раскрывайте их без запроса, когда замечаете в контексте:

- ** Предупреждение о искажении контекста:** разговор очень длинный → отметьте его и предложите повторно поделиться состоянием.
- ** НЕИЗВЕСТНЫЙ сброс:** пользовательский код ссылается на зависимость, которая еще не сопоставлена → приостановить и пометить ее тегом.
- ** История слишком большая:** запрошенная история будет касаться >3 файлов → разделить ее перед кодированием.
- ** Уничтожение хвостика:** целая история может быть удалена с помощью stdlib/native/installed dep → сообщить об этом, прежде чем что-либо писать.

## Перекрестные ссылки { #cross-references }

- **`senior-architect`** — чисто архитектурные решения без немедленной реализации. НЕ для задач, где код пишется в одном сеансе.
- **`playwright-pro`** — специально написание или отладка тестов для драматурга; этот скилл является оболочкой без галлюцинаций для этой работы.
- **`self-improving-agent`** — когда целью Claude является улучшение собственной памяти и прошлых результатов, а не создание новых функций.
