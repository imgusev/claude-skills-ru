# AgentHub — Сотрудничество с несколькими агентами { #agenthub--multi-agent-collaboration }

Создайте N параллельных агентов искусственного интеллекта, которые соревнуются в выполнении одной и той же задачи. Каждый агент работает в изолированном git worktree. Координатор оценивает результаты и определяет победителя.

## Слэш-команды { #slash-commands }

| Команда | Описание |
|---------|-------------|
| `/hub:init` | Создайте новый сеанс совместной работы — задача, количество агентов, критерии оценки |
| `/hub:spawn` | Запуск N параллельных субагентов в изолированных рабочих деревьях |
| `/hub:status` | Показывать состояние DAG, прогресс агента, статус филиала |
| `/hub:eval` | Ранжируйте результаты агента по показателям или по оценке LLM judge |
| `/hub:merge` | Объединить выигравшую ветку, заархивировать проигравших |
| `/hub:board` | Чтение/запись на доске объявлений агента |
| `/hub:run` | Одноразовый жизненный цикл: инициализация → базовая линия → появление → оценка → слияние |

## Шаблоны агентов { #agent-templates }

При нересте с `--template`, агенты следуют предопределенному шаблону итераций:

| Шаблон | Узор | Вариант использования |
|----------|---------|----------|
| `optimizer` | Редактировать → вычислять → сохранить/отбросить → повторить x10 | Производительность, задержка, размер |
| `refactorer` | Реструктурировать → тестировать → повторять до получения зеленого цвета | Качество кода, технический долг |
| `test-writer` | Написать тесты → измерить охват → повторить | Пробелы в тестовом покрытии |
| `bug-fixer` | Воспроизвести → диагностировать → исправить → проверить | Подходы к исправлению ошибок |

Шаблоны определены в `references/agent-templates.md`.

## Протокол координатора { #coordinator-protocol }

Координатором основной сессии является Claude Code. Он следует этому жизненному циклу:

```
INIT → DISPATCH → MONITOR → EVALUATE → MERGE
```

### 1. Инициализация { #1-init }

Бежать `/hub:init` чтобы создать сеанс. Это порождает:
- `.agenthub/sessions/{session-id}/config.yaml` — конфигурация задачи
- `.agenthub/sessions/{session-id}/state.json` — государственная машина
- `.agenthub/board/` — каналы доски объявлений

### 2. Отправка { #2-dispatch }

Бежать `/hub:spawn` для запуска агентов. Для каждого агента 1..N:
- Опубликовать назначение задачи для `.agenthub/board/dispatch/`
- Запуск с помощью инструмента агента с `isolation: "worktree"`
- Все агенты запускаются в одном сообщении (параллельно)

### 3. Контролируйте { #3-monitor }

Бежать `/hub:status` чтобы проверить прогресс:
- `dag_analyzer.py --status --session {id}` показывает состояние ветви
- Доска `progress/` на канале есть обновления от агента

### 4. Оцените { #4-evaluate }

Бежать `/hub:eval` для ранжирования результатов:
- ** Режим метрики**: запустите команду eval в каждом рабочем дереве, проанализируйте числовой результат
- ** Режим судьи **: чтение различий, ранжирование координатора по качеству
- ** Гибрид**: сначала метрика, LLM-судья по связям

### 5. Слияние { #5-merge }

Бежать `/hub:merge` для завершения работы:
- `git merge --no-ff` победитель переходит в базовую ветку
- Помечать проигравших: `git tag hub/archive/{session}/agent-{i}`
- Очистите рабочие деревья
- Опубликовать сводку о слиянии на доске объявлений

## Протокол агента { #agent-protocol }

Каждый субагент получает этот шаблон промптов:

```
You are agent-{i} in hub session {session-id}.
Your task: {task description}

Instructions:
1. Read your assignment at .agenthub/board/dispatch/{seq}-agent-{i}.md
2. Work in your worktree — make changes, run tests, iterate
3. Commit all changes with descriptive messages
4. Write your result summary to .agenthub/board/results/agent-{i}-result.md
5. Exit when done
```

Агенты не видят работу друг друга. Они не общаются друг с другом. Они пишут в правление только для того, чтобы координатор мог их прочитать.

## Модель DAG { #dag-model }

### Именование ветвей { #branch-naming }

```
hub/{session-id}/agent-{N}/attempt-{M}
```

- Идентификатор сеанса: на основе временной метки (`YYYYMMDD-HHMMSS`)
- Агент N: последовательный (от 1 до количества агентов)
- Попытка M: увеличивается при повторной попытке (обычно на 1)

### Обнаружение границ { #frontier-detection }

Граница = концы ветвей без дочерних ветвей. Эквивалентно запросу AgentHub "leaves".

```bash
python scripts/dag_analyzer.py --frontier --session {id}
```

### Неизменность { #immutability }

DAG доступен только для добавления:
- Никогда не перебазируйте ветви агента и не нажимайте их принудительно
- Никогда не удаляйте коммиты (только ссылки на ветви после архивации)
- Каждый подход сохраняется с помощью тегов git

## Доска объявлений { #message-board }

Местоположение: `.agenthub/board/`

### Каналы { #channels }

| Канал | Писатель | Читатель | Цель |
|---------|--------|--------|---------|
| `dispatch/` | Координатор | Агенты | Назначения задач |
| `progress/` | Агенты | Координатор | Обновления статуса |
| `results/` | Агенты + координатор | Все | Окончательные результаты + сводка по слиянию |

### Формат публикации { #post-format }

```markdown
---
author: agent-1
timestamp: 2026-03-17T14:30:22Z
channel: results
parent: null
---

## Result Summary

- **Approach**: Replaced O(n²) sort with hash map
- **Files changed**: 3
- **Metric**: 142ms (baseline: 180ms, delta: -38ms)
- **Confidence**: High — all tests pass
```

### Правила правления { #board-rules }

- Только для добавления: никогда не редактируйте и не удаляйте записи
- Уникальные имена файлов: `{seq:03d}-{author}-{timestamp}.md`
- YAML frontmatter требуется для всех постов

## Режимы оценки { #evaluation-modes }

### Основанный на метриках { #metric-based }

Лучше всего подходит для: тестов, частоты прохождения тестов, размеров файлов, времени отклика.

```bash
python scripts/result_ranker.py --session {id} \
  --eval-cmd "pytest bench.py --json" \
  --metric p50_ms --direction lower
```

Ранкер запускает команду eval в каталоге worktree каждого агента и анализирует метрику из стандартного вывода.

### Судья магистратуры { #llm-judge }

Лучше всего подходит для: качества кода, удобочитаемости, архитектурных решений.

Координатор считывает данные каждого агента (`git diff base...agent-branch`) и ранжируется по:
1. Корректность (решает ли это задачу?)
2. Простота (предпочтительно меньшее количество измененных строк)
3. Качество (чистое исполнение, хорошая структура)

### Гибрид { #hybrid }

Сначала запустите метрику. Если ведущие агенты находятся в пределах 10% друг от друга, используйте LLM judge для разрыва связей.

## Жизненный цикл сеанса { #session-lifecycle }

```
init → running → evaluating → merged
                            → archived (if no winner)
```

Переходы состояний, управляемые с помощью `session_manager.py`:

| От | К | Триггер |
|------|----|---------|
| `init` | `running` | `/hub:spawn` завершает |
| `running` | `evaluating` | Все агенты возвращаются |
| `evaluating` | `merged` | `/hub:merge` завершает |
| `evaluating` | `archived` | Победителя нет / все потерпели неудачу |

## Проактивные триггеры { #proactive-triggers }

Координатор должен действовать, когда:

| Сигнал | Действие |
|--------|--------|
| Все агенты потерпели крушение | Опубликуйте сводку о сбое, предложите повторить попытку с другими ограничениями |
| Никаких улучшений по сравнению с исходным уровнем | Архивируйте сессию, предлагайте различные подходы |
| Обнаружены рабочие деревья-сироты | Бежать `session_manager.py --cleanup {id}` |
| Сессия застряла в `running` | Следите за прогрессом на доске, учитывайте тайм-аут |

## Сценарии { #scripts }

| Сценарий | Цель |
|--------|---------|
| `hub_init.py` | Инициализировать `.agenthub/` структура и сессия |
