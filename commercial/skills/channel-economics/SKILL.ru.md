# канал-экономика { #channel-economics }

## Цель { #purpose }

Помогите руководителю коммерческого отдела / RevOps / вице-президенту по продажам ответить на три вопроса в ежеквартальном ревью канала:

1. ** Сколько на самом деле стоит обслуживание каждого канала при полной загрузке?** (прямая численность персонала, атрибуция менеджера канала, партнерская скидка, MDF, время включения, нагрузка на службу поддержки, распределенные накладные расходы)
2. ** Какова рентабельность каждого канала при трех объективах?** (денежная рентабельность за год-1, скорректированная на LTV рентабельность инвестиций, предельная рентабельность инвестиций — следующий доллар инвестиций)
3. ** Каков оптимальный набор каналов с учетом наших стратегических ограничений?** (минимальный уровень прямых продаж, максимальный потолок концентрации партнеров, чувствительность к изменениям CAC)

Скилл выдает ** вердикты для каждого канала** (УДВОЕНИЕ / ПОДДЕРЖАНИЕ / ОТМЕНА / ВЫХОД), ** рекомендацию по микшированию, проверенную на чувствительность**, и ** точку перегиба с уменьшением отдачи**. Он не выбирает стратегию — это делают люди, когда цифры загружаются честно в первый раз.

## Когда использовать { #when-to-use }

- Ежеквартальный ревью канала: пайплайн - это прямой канал 60/40 или 50/50 по сравнению с партнерским, и вы на самом деле не знаете, какой из них прибыльный
- Рассматриваете возможность найма менеджера канала — нужно знать, сможет ли канал преодолеть планку загруженных затрат
- Вопрос о рентабельности инвестиций в партнерскую программу от правления ("мы потратили $X на MDF — что мы получили?")
- Сегмент чрезмерно проиндексирован для одного канала, и вы подозреваете, что mix dogma блокирует другой
- Собираетесь расширяться в новом регионе, и вам нужно решить, что лучше - напрямую или сначала с партнером
- Проверка слияний и поглощений: целевая компания утверждает, что "валовая прибыль под руководством партнера составляет 70%" - необходимо подтвердить после загрузки

**Не используйте для:**
- Проектирование уровней партнеров, совместное движение GTM, разделение revshare → `partnerships-architect`
- Маршрутизация SDR-to-AE, оценка потенциальных клиентов, определения MQL → `business-growth/revenue-operations`
- Стратегические решения по CRO ("стоит ли нам нанимать вице-президента по продажам?", разработка бизнес-плана) → `c-level-advisor/cro-advisor`
- Закрытие квартала, признание выручки по GAAP, P&L на уровне канала для исторической отчетности → `finance/financial-analysis`
- Утверждение скидки за каждую сделку → `deal-desk`
- Разработка модели ценообразования → `pricing-strategist`

## Воркфлоу { #workflow }

### Шаг 1 — Данные о канале приема { #step-1--intake-channel-data }

Заполнять `assets/channel_data_template.md` (≈ 20 мин). Учет по каналам: количество сделок TTM, ARR TTM, средний размер сделки, валовая прибыль %, CAC, дни цикла продаж, коэффициент удержания, коэффициент расширения, партнерская скидка %, все сопутствующие расходы (SDR / AE / SE / менеджер канала / CS / поддержка / маркетинг / партнерский MDF / инструментарий / распределение накладных расходов, %).

В шаблоне указаны затраты, о которых команды чаще всего забывают: время на подключение партнеров, инвестиции в сертификацию, накладные расходы на разрешение конфликтов в канале, затраты на численность персонала менеджера канала.

### Шаг 2 — Вычислите стоимость обслуживания для каждого канала { #step-2--compute-cost-to-serve-per-channel }

Бежать `scripts/cost_to_serve_calculator.py --input channel.json --output markdown`.

Результат: полностью загруженные данные о затратах на обслуживание ** за сделку** И ** за доллар ARR**, с разбивкой прямых затрат на распределенные накладные расходы и строкой "истинная валовая прибыль" после загрузки конкретного канала. Выявляет двойной подсчет и выявляет скрытые затраты.

Запускается один раз для каждого канала. Строка "истинная валовая прибыль" - это входные данные, о которых заботятся следующие два сценария.

### Шаг 3 — Вычислите рентабельность инвестиций на канал при использовании трех объективов { #step-3--compute-roi-per-channel-under-three-lenses }

Бежать `scripts/channel_roi_analyzer.py --input roi.json --profile saas --output markdown`.

Выходные данные: для каждого канала три показателя рентабельности инвестиций (кассовый год-1, с поправкой на LTV, маржинальный), точка перегиба убывающей доходности и вердикт: УДВОИТЬ / СОХРАНИТЬ / ОТМЕНИТЬ ФИНАНСИРОВАНИЕ / ВЫЙТИ.

Логика вынесения вердикта является детерминированной и изложена в отчете. Люди могут переопределить; скилл - нет.

### Шаг 4 — Оптимизируйте микширование каналов с учетом ограничений { #step-4--optimize-channel-mix-subject-to-constraints }

Бежать `scripts/channel_mix_optimizer.py --input mix.json --profile saas --output markdown`.

Результат: рекомендуемая смесь, которая максимизирует эффективный ARR с учетом ограничений (минимальный процент прямого воздействия, максимальная концентрация партнера), плюс таблица чувствительности (что, если прямой CAC повысится на 20%? что, если партнерская скидка увеличится на 5 пунктов?).

### Шаг 5 — Примите решение { #step-5--decide }

Включите эти три отчета в ежеквартальный ревью канала. Скилл рекомендует; человек берет на себя обязательства.

## Сценарии { #scripts }

- `scripts/cost_to_serve_calculator.py` — полностью загруженная стоимость обслуживания за сделку и за $ в год, с выявлением скрытых затрат
- `scripts/channel_roi_analyzer.py` — 3-линзовый показатель рентабельности инвестиций (Cash / LTV / Marginal) с вердиктами и тенденцией к уменьшению доходности
- `scripts/channel_mix_optimizer.py` — оптимизатор ограниченного микширования со сценариями чувствительности

Все скрипты: только stdlib. `--help`, `--sample`, `--input`, `--output` поработайте над всеми тремя. Отраслевая настройка с помощью `--profile {saas,api,enterprise-software,marketplace,hardware}` на двух анализаторах.

## Допущения { #assumptions }

- Экономика канала - это ** перспективный** вопрос. Исторический канал P&L - это работа финансиста; этот скилл позволяет использовать перспективную экономику для принятия решения.
- "Канал" означает последовательный выход на рынок (прямой исходящий, под руководством партнера, маркетплейс, реселлер, OEM-производитель). Это не означает, что это маркетинговый источник.
- Соотношение затрат на обслуживание требует ** честного распределения накладных расходов**. Сценарий проверяет, что процент накладных расходов согласован по всем каналам — ложное повышение маржи партнера из-за несогласованного распределения - это анти-паттерн № 1.
- Входные данные LTV (сохранение, расширение) распределяются по каждому каналу, а не объединяются в пул. Клиенты, привлеченные партнерами, часто удерживаются иначе, чем клиенты, привлеченные напрямую, - эта разница обычно является самой большой экономической переменной и чаще всего игнорируется.
- Отраслевые профили (`--profile`) настройте значения по умолчанию для бенчмарков (например, SaaS direct CAC payback target ~12mo, enterprise ~ 18mo) — они не переопределяют ваши цифры.
- Это скилл для поддержки принятия решений. Результатом являются вердикты и рекомендуемое сочетание, а не автоматическое перераспределение ресурсов.

## Анти-паттерны { #anti-patterns }

- **Отношение к сделкам, на которые "повлияли", как к сделкам, полученным от "источника".** Партнер, который заключил сделку, которая уже была заключена вашим AE, не получает доход от канала. Загрузка этого в качестве дохода партнера увеличивает рентабельность инвестиций партнера и одновременно увеличивает прямой CAC.
- **Несогласованное распределение накладных расходов.** Распределение 25% накладных расходов на прямые сделки и 5% на партнерские сделки, поскольку "партнер берет на себя накладные расходы" является ложным. Партнерский менеджер, партнерская программа, MDF, сертификация и разрешение конфликтов - все это находится в вашем P&L.
- ** Игнорирование времени включения в качестве затрат. ** Каждый час, который ваш AE тратит на совместные продажи с партнером, - это прямые затраты, взимаемые с партнерского канала — большинство команд забывают его загрузить.
- **MDF без отслеживания рентабельности инвестиций.** Средства на развитие рынка, выделяемые без соответствующего пайплайна рентабельности инвестиций, являются просто расширением партнерской скидки. Скилл помечает MDF без возврата.
- ** Догма смешивания каналов.** "Мы - компания, ориентированная в первую очередь на партнеров" / "мы не продаем напрямую" блокирует прибыльные сегменты. Микс должен соответствовать математике, а не слогану.
- ** Расчет рентабельности канала без учета разницы в удержании. ** Если отток клиентов из партнерских источников на 5 пунктов выше, чем у прямых, игнорирование этого приводит к завышению LTV партнера на 30-50%. Сохранение данных для каждого канала является обязательным вводом.
- **Нет привязки затрат к численности персонала менеджера канала.** Менеджер канала стоимостью 200 тыс. долларов, управляющий партнерским доходом в размере 4 млн долларов, - это 50 долларов расходов менеджера канала за 1 тыс. долларов дохода — материал для вердикта.
- ** Путаете этот скилл с партнерством-архитектор.** Этот скилл разрабатывает партнерскую программу. Этот скилл подсказывает вам, окупается ли программа сама по себе.

## Отличный от { #distinct-from }

- **коммерческий/partnerships-architect** — дизайн уровня партнеров, совместное движение GTM, разделение revshare, поддержка партнеров. Партнерская программа *структура*, а не партнерская программа *экономика*. Этот скилл использует структуру программы в качестве входных данных и выносит экономический вердикт.
- **рост бизнеса/revenue-operations** — маршрутизация выводов, перемещение SDR, определение MQL, операции пайплайна. RevOps владеет механикой воронки; этот скилл влияет на экономический результат на уровне канала.
- **советник c-уровня/cro-advisor** — стратегическое решение CRO: когда нанимать вице-президента по продажам, философия составления плана, дизайн территории, многолетняя стратегия получения дохода. Советник CRO использует выходные данные channel-economics как один из многих входных данных.
- **финансы/financial-analysis** — закрытие и отчет о прибылях и убытках за предыдущий период по каналам в соответствии с GAAP. Этот скилл - ориентированная на будущее поддержка принятия решений; финансы - это исторический рекорд. Другой временной горизонт, другая аудитория, другой результат.
- **коммерческий/deal-desk** — одобрение скидки за каждую сделку. Действует ежедневно; этот скилл действует ежеквартально.
- **коммерческий/pricing-strategist** — модель ценообразования и дизайн уровней. Ценообразование - это входные данные; экономика канала - это то, что происходит при таком ценообразовании по всем каналам.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Проходили по одному мимо `/cs:grill-commercial` или оркестратор. Рекомендуемый ответ + цитата из канона на каждый вопрос. Никогда не упаковывался.

1. ** "Какова ваша полная стоимость обслуживания на каждом канале, включая численность персонала менеджера канала, MDF, время подключения партнеров и распределение накладных расходов?"**
   Рекомендуется: загрузите все четыре. Большинство команд используют партнерскую скидку, но забывают о численности персонала менеджера канала и времени подключения, увеличивая маржу партнера на 8-15 пунктов.
   Канон: Kaplan & Cooper (HBR, 1988) — *Правильно оценивайте затраты: принимайте правильные решения*. Калькуляция затрат на основе видов деятельности была изобретена именно потому, что затраты на канал скрываются за накладными расходами и искажают сравнение маржи.

2. ** "Какова разница в удержании клиентов из прямых источников и партнеров?"**
   Рекомендуется: удержание прибора для каждого канала ПЕРЕД запуском ROI канала. Разрыв в удержании в 5 пунктов увеличивает LTV на 30-50%.
   Канон: Дэвид Скок (*Для предпринимателей* — SaaS Metrics 2.0). LTV = (ARPA × валовая прибыль) / отток. Отток без учета каналов является наиболее распространенным источником ложной рентабельности инвестиций в канал.

3. ** "Какую долю пайплайна, основанного на "канальных источниках", на самом деле создала ваша команда?"**
   Рекомендуется: если у вашего AE уже была учетная запись, это не связано с источником канала - это зависит от канала. Влияние и источник - это разные экономические направления.
   Канон: SiriusDecisions / Forrester channel attribution research — путаница между источником и влиянием - причина № 1, по которой рентабельность инвестиций партнеров завышена во всей отрасли.

4. ** "Какова предельная рентабельность следующего доллара, вложенного в партнерскую программу, по сравнению с прямыми продажами?"**
   Рекомендуется: вычислите кривую убывающей доходности для обоих. Средняя рентабельность инвестиций скрывает тот факт, что следующий доллар может принести 0,3 х, в то время как средний заработок составляет 2,1 х.
   Канон: Томаш Тунгуз (*Блог Томаша Тунгуза* — канал CAC analysiss). Средняя рентабельность инвестиций - это показатель тщеславия; предельная рентабельность инвестиций определяет инвестиционные решения.

5. ** "Каково ваше соотношение MDF к пайплайну за последние 4 квартала?"**
   Рекомендуется: < 5:1 (каждый 1 доллар MDF должен генерировать ≥5 долларов соответствующего пайплайна в течение 2 кварталов). Все, что дешевле, - это театр со скидкой для партнеров.
   Канон: Джей Макбейн (Canalys) — *Состояние канала* исследование. MDF без соблюдения дисциплины атрибуции является самой дорогостоящей формой субсидирования канала.

6. ** "Ваша догма о микшировании каналов блокирует прибыльный сегмент?"**
   Рекомендуется: четко сформулируйте догму ("мы в первую очередь партнеры", "мы не продаем напрямую в SMB"). Смешивание должно осуществляться в соответствии с математикой сегмента.
   Канон: Ревью менеджмента MIT Sloan — *Когда конфликт каналов означает рост*. Догматические одноканальные стратегии теряют 15-25% прибыли, особенно на среднем рынке.

7. ** "Какую методологию распределения накладных расходов вы применяете — и согласована ли она между директорами и партнерами?"**
   Рекомендуется: та же методология, тот же знаменатель, оба канала. Несогласованное распределение - это молчаливый убийца анализа экономики каналов.
   Канон: Чарльз Хорнгрен (*Учет затрат: акцент руководства*) — согласованность распределения является предварительным условием для сравнения маржи между сегментами. Без этого любое заключение будет искажено.

Сначала пройдите вглубь. Зафиксируйте 1-3 перед открытием 4-7. После того, как будут даны ответы на все 7 вопросов, вызовите `cost_to_serve_calculator.py` → `channel_roi_analyzer.py` → `channel_mix_optimizer.py` в определенной последовательности.
