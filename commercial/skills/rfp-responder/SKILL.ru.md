# rfp-ответчик { #rfp-responder }

## Цель { #purpose }

Помогите менеджерам по заявкам, лидерам по предложениям и директорам по продажам ответить на пять вопросов в момент принятия решения о стратегии:

1. ** О чем на самом деле спрашивает это предложение? ** (проанализируйте разделы, пометьте каждое требование как ОБЯЗАТЕЛЬНОЕ / ВЗВЕШЕННОЕ / ПРИЯТНОЕ К исполнению, извлеките критерии оценки, крайние сроки и ограничения формата)
2. ** Каково наше истинное соответствие? ** (матрица контрольных точек для каждого требования: СИЛЬНОЕ / ЧАСТИЧНОЕ / НЕСООТВЕТСТВИЕ, каждое из которых подкреплено проверяемым источником - тематическим исследованием, сертификацией, предложением заказчика, технической аттестацией, эталоном)
3. ** Какова наша стратегия выбора выигрышной темы? ** (метод Шипли: 3-5 тем, которые соответствуют требованиям, а не общие маркеры, указывающие на ценность)
4. ** Каков наш реалистичный коэффициент выигрыша?** (факторная модель, разработанная Шипли: соответствие требованиям, занимаемая должность, сила отношений, соответствие критериям принятия решений, поздний вход, количество конкурентов, размер сделки — дает оценку + доверительный интервал)
5. ** Должны ли мы делать ставку?** (детерминированный вердикт: СТАВКА / ПАРТНЕР-СТАВКА / НЕ-СТАВКА с указанием названных факторов, определяющих колл)

Скилл явно выявляет пробелы. Руководство решает, закрывать ли их, сотрудничать с ними или не участвовать в торгах. ** Он никогда не выдумывает претензий.**

## Когда использовать { #when-to-use }

- Поступило более чем 30-страничное предложение / RFI / RFQ с крайним сроком ответа 7-14 дней
- Анкета безопасности (SIG, CAIQ, custom-buyer) нуждается в структурированных вопросах и ответах, а не в прозе
- Команда готовит ревью заявки / отказа от участия в конкурсе, и ей нужна обоснованная оценка винрейта
- У Sales Engineering есть библиотека пробных точек, но нет системы для сопоставления пробных точек с требованиями
- Руководство хочет видеть приемлемый процент (СИЛЬНЫЙ / ЧАСТИЧНЫЙ / РАЗРЫВ), прежде чем выделять бюджет на реализацию
- Возможность позднего вступления требует честной оценки дефицита отношений

**Не используйте для:**
- Создание повествовательного предложения в свободной форме → `business-growth/contract-and-proposal-writer`
- Красная строка контракта ПОСЛЕ присуждения → `c-level-advisor/general-counsel-advisor`
- Маркетинговое обеспечение / содержание категории → `marketing-skill/*`
- Одобрение скидки по заключенной сделке → `commercial/deal-desk`
- Ценообразование-разработка модели нового продукта → `commercial/pricing-strategist`

## Воркфлоу { #workflow }

### Шаг 1 — Проанализируйте запрос предложения { #step-1--parse-the-rfp }

Поместите Markdown / текст запроса предложений в `scripts/rfp_parser.py`. Вывод: структурированный JSON-файл с перечислением каждого требования, помеченный как ОБЯЗАТЕЛЬНЫЙ / ВЗВЕШЕННЫЙ / ПРИЯТНЫЙ для ИСПОЛЬЗОВАНИЯ на основе ключевых слов (must / shall = ОБЯЗАТЕЛЬНЫЙ; should / взвешенные балльные числа = ВЗВЕШЕННЫЕ; may / preferred / desired = ПРИЯТНЫЙ ДЛЯ использования). Фиксирует структуру раздела, критерии оценки, если они раскрыты, крайний срок, ограничения формата подачи.

```bash
python scripts/rfp_parser.py --input rfp.md --output json > parsed.json
```

### Шаг 2 — Оценка соответствия требованиям { #step-2--score-fit-per-requirement }

Заполнять `assets/rfp_intake_template.md` с вашей библиотекой пробных точек (каждое доказательство помечено типом + проверяемым источником + какие теги требований оно охватывает) и предлагаемыми выигрышными темами. Подайте проанализированный RFP + вход в `scripts/response_drafter.py`. Результат: матрица контрольных точек для каждого требования с СИЛЬНЫМ / ЧАСТИЧНЫМ / разрывом, внедрение выигрышной темы, аудит разрыва.

```bash
python scripts/response_drafter.py --input draft_input.json --output markdown > matrix.md
```

** Жесткое правило: ** Требования к разрывам появляются на поверхности, а не придумываются заново. Руководство проводит аудит пробелов и принимает решение: устранить пробел, участвовать в тендере с партнером или не участвовать.

### Шаг 3 — Примените стратегию выигрышной темы { #step-3--apply-win-theme-strategy }

Метод Шипли: 3-5 тем, которые охватывают требования. Каждая тема отвечает на вопрос "почему мы лучше действующего поставщика / конкурента по критериям, названным покупателем". `response_drafter.py` показывает, какие темы пронизывают какие требования — тема, появляющаяся в <2 требованиях, является декоративной, а не стратегической, и помечается.

### Шаг 4 — Оцените коэффициент выигрыша { #step-4--estimate-winrate }

Введите контекст сделки (процент соответствия, численность действующих сотрудников, взаимоотношения, соответствие критериям принятия решений, поздний вход, количество конкурентов, размер сделки в сравнении со средним) в `scripts/winrate_predictor.py`. Результат: оценка, полученная по методу Шипли, 0-100% + доверительный интервал + разбивка по факторам + вердикт о предложении / ПАРТНЕРСКОЙ СТАВКЕ / отказе от предложения.

```bash
python scripts/winrate_predictor.py --input deal_context.json --profile enterprise-software --output markdown
```

** Порог отсутствия ставок:** оценка < 20% триггеров автоматической рекомендации об отказе от ставок.

### Шаг 5 — Примите решение { #step-5--decide }

Возьмите проанализированный запрос предложений + матрицу контрольных точек + аудит пробелов + оценку винрейта в ревью "Можно / нельзя". Скилл не обязывает к соблюдению бюджета — это делает лидерство.

## Сценарии { #scripts }

- `scripts/rfp_parser.py` — раздел + экстрактор требований (регулярное выражение + эвристика ключевого слова, только stdlib)
- `scripts/response_drafter.py` — матрица пробных точек + внедрение выигрышной темы + аудит пробелов
- `scripts/winrate_predictor.py` — Факторная модель, полученная по методу Шипли + ставка/no-bid вердикт, адаптированный к отраслевому профилю

Все скрипты: только stdlib (argparse, json, sys, pathlib, re, коллекции, статистика). `--help` и `--sample` поработайте над всеми тремя.

## Допущения { #assumptions }

- ** Предложение — это основная истина. ** Если покупатель задал его, ответьте на него - в том порядке, в котором он задал, в указанном им формате. Реорганизация повествовательного потока предназначена для предложений, а не для запросов.
- ** Доказательства должны поддаваться проверке.** Претензия является убедительной только в том случае, если она подкреплена тематическим исследованием, сертификацией, рекомендацией клиента или технической аттестацией. Неподтвержденные заявки становятся пробелами.
- ** Выигрышные темы ориентированы на покупателя, а не на продавца.** "Мы являемся лидером в области X" - это маркетинговое заявление; "Ваша оперативная группа сокращает количество инцидентов на 60% при той же численности персонала" - это выигрышная тема. Канон Шипли, необязательный.
- ** Оценки винрейта носят направленный характер.** Модель является дисциплинирующим инструментом для обеспечения честного прохождения квалификации, а не оракулом. Доверительный интервал всегда шире, чем предполагает точечная оценка.
- ** Отраслевые профили настраивают базовые ставки ** — правительственные запросы поощряют соблюдение дисциплины; корпоративный SaaS поощряет справочные аккаунты; здравоохранение поощряет регулирование + уровень безопасности.
- **Поздний въезд является структурным недостатком.** При подаче заявки после получения запроса, без истории отношений, базовая ставка снижается на ~ 15%. Скилл называет это, а не скрывает.

## Анти-паттерны { #anti-patterns }

- ** Придумывание доказательства, чтобы заполнить пробел.** Нарушение жестких правил. Пробелы возникают для принятия лидерских решений, а не для отмывания денег. Видишь `references/rfp_anti_patterns.md`.
- ** Реагирование на каждое предложение.** Без гейта квалифицированной заявки / без участия в торгах команда расходует ресурсы на гонках с винрейтом менее 20% и проигрывает гонкам с более чем 50% из-за отсутствия концентрации. Исследование в области коммерческих дисциплин.
- ** Общий ответ без выигрышной темы.** Предложение, которое может быть отправлено дословно любым участником, носит декоративный характер. Режим сбоя Шипли #1.
- ** Опоздание с обязательной дисквалификацией.** FedRAMP / HIPAA / ISO 27001 / SOC 2 / резидентство данных на берегу обнаружено на 12-й день из 14-дневного ответа = напрасная погоня. Синтаксический анализатор обнаруживает их на 1-й день.
- ** Отвечая на вопрос, который ВЫ хотели задать. ** Дисциплина ответчика RFP: отвечайте на то, что они спросили, их словами, в их порядке. Повторное обрамление относится к сопроводительным письмам, а не к матрице соответствия требованиям.
- ** Нет матрицы соответствия.** Каждое требование должно быть сопоставлено с разделом ответа + номером страницы. Оценщики выставляют баллы по матрице; респонденты, которые не предоставляют ни одного балла, самостоятельно дисквалифицируются в отношении прослеживаемости.
- ** Поздний вход без признания дефицита отношений. ** Холодный вход против действующего игрока с 3-летними отношениями и без чемпиона = винрейт ниже 20%. Притворяясь, что это не так, вы тратите впустую возможности отдела продаж.
- ** Отношение к ВЗВЕШЕННЫМ требованиям как к ОБЯЗАТЕЛЬНЫМ. ** Требования, взвешенные по баллам, вознаграждают за глубину по предметам с высоким весом, а не за одинаковую посредственность по всем. Метод захвата Шипли.

## Отличный от { #distinct-from }

- **`business-growth/contract-and-proposal-writer`** — описательные предложения свободной формы, в которых ВЫ задаете структуру (краткие инструкции для руководителей, заявления о возможностях, незапрашиваемые предложения). RFP-ответчик обрабатывает ** продиктованные покупателем структурированные вопросы и ответы **, в которых покупатель задает вопросы, разделы, критерии оценки и формат. Другой артефакт, другая логика принятия решений.
- **`c-level-advisor/general-counsel-advisor`** — красная линия контракта и IP/risk ревью ПОСЛЕ присуждения премии. RFP-ответчик действует ДО присуждения премии в соответствии со стратегией реагирования.
- **`marketing-skill/*`** — внешние маркетинговые ресурсы (веб-копирование, контент, ASO, SEO, озвучивание бренда) для широкой аудитории. RFP-ответчик создает артефакт **для одного покупателя** с детерминированными требованиями соответствия.
- **`commercial/deal-desk`** — предоставление скидки за каждую сделку при возможности закрытия. Ответчик на запрос предложений находится на стадии преследования; отдел заключения сделок находится на стадии закрытия.
- **`commercial/pricing-strategist`** — ценообразование -разработка модели нового продукта. RFP-ответчик использует существующие цены в качестве входных данных для раздела коммерческих условий.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Проходите по одному перед запуском любого скрипта. Рекомендуемый ответ + цитата из канона на каждый вопрос. Никогда не упаковывался.

1. ** "Каково ваше СИЛЬНОЕ / ЧАСТИЧНОЕ / НЕДОСТАТОЧНОЕ разделение по ОБЯЗАТЕЛЬНЫМ требованиям?"**
   Рекомендуется: перед началом торгов ОБЯЗАТЕЛЬНО УВЕЛИЧЬТЕ количество на ≥ 70%. ЧАСТИЧНЫЙ/ПРОБЕЛ по любому ОБЯЗАТЕЛЬНОМУ = либо закрыть пробел предварительной подачей заявки, либо не подавать заявку.
   Канон: Шипли * Руководство по предложениям v6* — дисциплина управления захватом, "Pgw (вероятность выигрыша) ограничена вашим самым слабым ОБЯЗАТЕЛЬСТВОМ".

2. ** "Есть ли действующий президент и насколько сильна его позиция?"**
   Рекомендуется: сильный игрок (более 3 лет, без смещения) снижает базовый винрейт на ~30%. Не делайте ставку без именованного триггера смещения.
   Канон: Forrester B2B-RFP research — сотрудники выигрывают 70-80% заявок на продление при отсутствии названного события сбоя.

3. ** "Вы вступили в разговор до или после отправки запроса?"**
   Рекомендуется: поздняя заявка (после получения запроса, без предварительного участия) снижает винрейт на ~15% и сигнализирует о том, что запрос был сделан с учетом чьих-то сильных сторон.
   Канон: Том Сирси + Генри Деврис *Как выиграть в большом бизнесе* — "Если вы не помогали писать предложение, вы - материал для колонки".

4. ** "Каковы ваши 3-5 выигрышных тем и соответствует ли каждая тема требованиям ≥2?"**
   Рекомендуется: темы, которые отображаются только в одном требовании, являются декоративными. Темы должны располагаться в порядке возрастания по ОБЯЗАТЕЛЬНЫМ + ВЗВЕШЕННЫМ разделам.
   Канон: Shipley * Руководство по захвату* — темы-победители - это ответ покупателя на вопрос "почему мы" по критериям оценки, а не списки функций со стороны продавца.

5. ** "По каждому утверждению в ответе можете ли вы назвать проверяемый источник?"**
   Рекомендуется: каждая претензия → тематическое исследование / сертификация / рекомендации для клиентов / техническая аттестация / эталон. Заявки без источников = пробелы.
   Канон: APMP BoK — "Обоснование: каждое утверждение в предложении должно быть подкреплено доказательствами, которые оценщик может независимо проверить".

6. ** "Каков порог предложения / отказа от предложения, который вы установили ДО того, как увидели это предложение?"**
   Рекомендуется: предварительно установленный порог (например, винрейт ≥ 25%, СИЛА ≥ 70% в ОБЯЗАТЕЛЬНОМ порядке, названный чемпион). Рационализация Post-hoc - это то, как команды в конечном итоге назначают 5% заданий.
   Канон: Запрос предложений от Bain- исследование коэффициента выигрыша — дисциплинированная заявка/no-bid Гейты повышают коэффициент выигрыша с ~15% до ~35%.

7. ** "По каким показателям на самом деле оценивает команда оценки покупателя?"**
   Рекомендуется: если в запросе предложений указаны критерии оценки, пропорционально взвесьте свои усилия по реагированию. Если не разглашается, спросите. Если вы не можете спросить, это само по себе является сигналом дефицита отношений.
   Канон: Стратегические предложения - исследование по управлению предложениями — оценщики оценивают по той рубрике, которую им дали, а не по вашему описанию.

Сначала пройдите вглубь. Зафиксируйте 1-3 перед открытием 4-7. После того, как будут даны ответы на все 7 вопросов, вызовите `rfp_parser.py` → `response_drafter.py` → `winrate_predictor.py` в определенной последовательности. Если в вопросе 6 будет ответ "у нас нет порога", установите его сейчас или не делайте ставку.
