# /plugin-audit

<div class="page-meta" markdown>
<span class="meta-badge">:material-console: Слэш-команда</span>
<span class="meta-badge">:material-github: <a href="https://github.com/imgusev/claude-skills-ru/tree/main/commands/plugin-audit.md">Источник</a></span>
</div>


Полный пайплайн аудита для любого скилла, плагина, агента или команды в этом репозитории. Запускает 8 этапов проверки, автоматически исправляет все, что может, и останавливается только для ввода пользователем критических решений (критические изменения, новые зависимости).

## Использование { #usage }

```bash
/plugin-audit product-team/code-to-prd
/plugin-audit engineering/agenthub
/plugin-audit engineering-team/playwright-pro
```

## Что он делает { #what-it-does }

Выполните все 8 этапов последовательно. Остановитесь на критических сбоях. Автоматическое исправление некритических проблем. Сообщите о результатах в конце.

---

## Фаза 1: Открытие { #phase-1-discovery }

Определите, что содержит в себе скилл, и классифицируйте его.

1. Проверить `{skill_path}` существует и содержит `SKILL.md`
2. Читать `SKILL.md` frontmatter — извлечение `name`, `description`, `Category`, `Tier`
3. Определение типа скилла:
   - Имеет `scripts/` → имеет инструменты Python
   - Имеет `references/` → содержит справочные материалы
   - Имеет `assets/` → содержит шаблоны/образцы
   - Имеет `expected_outputs/` → имеет тестовые приспособления
   - Имеет `agents/` → имеет встроенных агентов
   - Имеет `skills/` → обладает дополнительными скиллами (составной скилл)
   - Имеет `.claude-plugin/plugin.json` → является автономным плагином
   - Имеет `settings.json` → имеет регистрацию команд
4. Определить домен по пути: `engineering/`, `product-team/`, `marketing-skill/` и т.д.
5. Проверьте наличие соответствующей команды: поиск `commands/` для `.md` файл, соответствующий названию скилла

Отобразите сводку обнаружения, прежде чем продолжить:
```
Auditing: code-to-prd
  Domain: product-team
  Type: STANDARD skill with standalone plugin
  Scripts: 2 | References: 2 | Assets: 1 | Expected outputs: 3
  Command: /code-to-prd (found)
  Plugin: .claude-plugin/plugin.json (found)
```

## Этап 2: Валидация структуры { #phase-2-structure-validation }

Запустите валидатор скилла-тестера.

```bash
python3 engineering/skills/skill-tester/scripts/skill_validator.py {skill_path} --tier {detected_tier} --json
```

Проанализируйте выходные данные в формате JSON. Выдержка:
- Общий балл и уровень соответствия требованиям
- Неудачные проверки (перечислите каждую)
- Ошибки и предупреждения

** Правило гейта: ** Оценка должна быть ≥ 75 (ХОРОШО). Если ниже 75:
- Ознакомьтесь со списком ошибок
- Автоматическое исправление того, что возможно:
  - Отсутствующие поля frontmatter → добавьте их из SKILL.md содержание
  - Отсутствующие разделы → добавить заголовки-заглушки
  - Отсутствующие каталоги → создайте пустые каталоги с примечанием
- Повторите запуск после исправления. Если все еще ниже 75, сообщите о сбое и продолжайте собирать оставшиеся результаты.

## Этап 3: Оценка качества { #phase-3-quality-scoring }

Запустите программу оценки качества.

```bash
python3 engineering/skills/skill-tester/scripts/quality_scorer.py {skill_path} --detailed --json
```

Проанализируйте выходные данные в формате JSON. Выдержка:
- Общий балл и оценка по буквам
- Оценки по каждому измерению (Документация, качество кода, полнота, удобство использования)
- Пункты дорожной карты улучшения

**Правило гейта: ** Оценка должна быть ≥ 60 (C). Если ниже 60, укажите пункты дорожной карты улучшений в качестве пунктов действий.

## Этап 4: Тестирование скрипта { #phase-4-script-testing }

Если у скилла есть `scripts/` с `.py` файлы, запустите тестер скриптов.

```bash
python3 engineering/skills/skill-tester/scripts/script_tester.py {skill_path} --json --verbose
```

Проанализируйте выходные данные в формате JSON. Для каждого сценария извлеките:
- Статус пройден/частичен/Сбой
- Индивидуальные результаты тестирования

**Правило гейта:** Все скрипты должны проходить. Любая неудача - это блокиратор. ЧАСТИЧНЫЙ триггер выдает предупреждение.

**Автоматическое исправление:** Если скрипт выходит из строя, то `--help` протестируйте, проверьте, есть ли у него `argparse` — если нет, то это реальная проблема. Если тест только для stdlib не прошел, отметьте импорт и ** спросите пользователя**, приемлема ли зависимость (это критическое решение).

## Этап 5: Аудит безопасности { #phase-5-security-audit }

Запустите аудитора безопасности по скиллу.

```bash
python3 engineering/skills/skill-security-auditor/scripts/skill_security_auditor.py {skill_path} --strict --json
```

Проанализируйте выходные данные в формате JSON. Выдержка:
- Вердикт (ПРОЙДЕН/ПРЕДУПРЕЖДЕН/НЕ ПРОЙДЕН)
- Критические выводы (должны быть равны нулю)
- Высокие результаты (должны быть равны нулю в строгом режиме)
- Информационные выводы (только консультативные)

** Правило гейта: ** Ноль КРИТИЧЕСКИХ выводов. Ноль ВЫСОКИХ результатов. Любой КРИТИЧЕСКИЙ или ВЫСОКИЙ уровень является блокирующим — сообщите точный файл, строку, шаблон и рекомендуемое исправление.

** Не устраняйте проблемы безопасности автоматически. ** Сообщайте о них и предоставьте пользователю принимать решение.

## Этап 6: Соответствие требованиям маркетплейса и плагинов { #phase-6-marketplace--plugin-compliance }

### 6a. Проверка плагина.json { #6a-pluginjson-validation }

Если `{skill_path}/.claude-plugin/plugin.json` существует:

1. Разобрать как JSON — должно быть допустимым
2. Проверяйте только разрешенные поля: `name`, `description`, `version`, `author`, `homepage`, `repository`, `license`, `skills`
3. Версия должна соответствовать версии репозитория (`2.1.2`)
4. `skills` должно быть `"./"`
5. `name` должно совпадать с именем каталога скилла

** Автоматическое исправление: ** Если версия неверна, обновите ее. Если существуют дополнительные поля, удалите их.

### 6b. настройки.проверка json { #6b-settingsjson-validation }

Если `{skill_path}/settings.json` существует:

1. Разобрать как JSON — должно быть допустимым
2. Версия должна соответствовать версии репозитория
3. Если `commands` поле существует, убедитесь, что у каждой команды есть соответствующий файл в `commands/`

### 6c. Вход на маркетплейс { #6c-marketplace-entry }

Проверьте, есть ли запись о скилле в `.claude-plugin/marketplace.json`:

1. Обыщите `plugins` массив для записи с `source` соответствие `./` + путь к скиллу
2. Если найдено: проверьте `version`, `name`, и это `source` путь существует
3. Если не найдено: проверьте, есть ли у скилла пакет доменов (например, `product-skills`) включил бы его через свой `source` путь

### 6d. плагин для домена.json { #6d-domain-pluginjson }

Проверьте родительский домен `.claude-plugin/plugin.json`:
- Убедитесь, что количество скилл, указанное в описании, соответствует действительности
- Проверьте, совпадает ли версия с версией репозитория

** Автоматическое исправление:** Обновите количество устаревших данных. Исправьте несоответствия версий.

## Этап 7: Интеграция экосистемы { #phase-7-ecosystem-integration }

### 7a. Кроссплатформенная синхронизация { #7a-cross-platform-sync }

Убедитесь, что скилл отображается в индексах платформы:

```bash
grep -l "{skill_name}" .codex/skills-index.json .gemini/skills-index.json
```

Если отсутствует в любом из индексов:
```bash
python3 scripts/sync-codex-skills.py --verbose
python3 scripts/sync-gemini-skills.py --verbose
```

### 7b. Интеграция команд { #7b-command-integration }

Если у скилла есть связанные команды (из settings.json `commands` поле или соответствующее имя в `commands/`):
- Проверьте выполнение команды `.md` файл имеет допустимый YAML frontmatter (`name`, `description`)
- Убедитесь, что команда ссылается на правильный путь к скиллу
- Убедитесь, что команда введена `mkdocs.yml` навигационная система

** Автоматическое исправление:** Добавьте отсутствующие навигационные записи mkdocs.yml.

### 7c. Интеграция с агентом { #7c-agent-integration }

Если у скилла есть встроенные агенты (`{skill_path}/agents/*.md`):
- Убедитесь, что у каждого агента есть действительный YAML frontmatter
- Проверка разрешения ссылок на агентов (относительные пути к скиллам)

Поиск `agents/` для любого агента cs-*, который ссылается на этот скилл:
```bash
grep -rl "{skill_name}\|{skill_path}" agents/
```

Если найдено, проверьте правильность ссылок на скиллы агента.

### 7d. Зависимости между скиллами { #7d-cross-skill-dependencies }

Прочтите SKILL.md для получения ссылок на другие скиллы (ищите `../` пути, названия скилл-систем в разделах "Связанные скиллы"):
- Убедитесь, что существует каждый указанный скилл
- Проверьте скиллы, на которые ссылается ссылка SKILL.md существует

## Этап 8: Ревью кода, соответствующего домену { #phase-8-domain-appropriate-code-review }

Основываясь на области применения скилла, воспользуйтесь подходящей точкой зрения ревью агента:

| Домен | Агент | Фокус на Ревью |
|--------|-------|-------------|
| `engineering/` или `engineering-team/` | cs-старший инженер | Архитектура, качество кода, интеграция CI/CD |
| `product-team/` | cs-менеджер по продукту | Качество PRD, охват пользовательских историй, выравнивание рисунка |
| `marketing-skill/` | cs-создатель контента | Качество контента, SEO-оптимизация, голос бренда |
| `ra-qm-team/` | cs-контроль качества-нормативный | Чек-лист соответствия требованиям, журнал аудита, согласование нормативных требований |
| `business-growth/` | cs-стратег по росту | Показатели роста, влияние на выручку, успех клиентов |
| `finance/` | cs-финансовый аналитик | Точность финансовой модели, определения показателей |
| Другое | cs-старший инженер | Общий ревью кода и архитектуры |

**Как вызвать:** Прочитайте инструкцию агента `.md` файл, чтобы понять его критерии ревью. Примените эти критерии для ревью скилла SKILL.md , сценарии и ссылки. Это не создание субагента — это использование документированной точки зрения агента для структурирования вашего ревью.

Чек-лист для ревью (примените объектив, соответствующий домену):
- [ ] SKILL.md Воркфлоу являются действенными и полными
- [ ] Скрипты корректно решают заявленную проблему
- [ ] Ссылки содержат точные знания предметной области
- [ ] Шаблоны/ресурсы готовы к производству
- [ ] Нет неработающих внутренних ссылок
- [ ] Указание авторства присутствует там, где это требуется

### Логика вынесения вердикта { #verdict-logic }

| Условие | Вердикт |
|-----------|---------|
| Все этапы проходят | **PASS** — Готов к объединению/публикации |
| Только предупреждения (без блокировок) | **ПЕРЕДАВАТЬ С ПРЕДУПРЕЖДЕНИЯМИ** — Ревью предупреждений перед слиянием |
| У любой фазы есть блокиратор | **ОШИБКА** — Список блокировщиков с инструкциями по исправлению |

### Блокировщики (любой из них = СБОЙ) { #blockers-any-of-these--fail }

- Оценка структуры < 75
- Оценка качества < 60 (после ознакомления с дорожной картой)
- Любой сбой скрипта
- Любая КРИТИЧЕСКАЯ находка или находка с высоким уровнем безопасности
- плагин.json недействителен или содержит запрещенные поля
- Несоответствие версии с репозиторием

### Неблокирующие (только предупреждения) { #non-blockers-warnings-only }

- Оценка качества в диапазоне 60-75
- Частичные результаты скрипта
- Отсутствует в индексе одной платформы (автоматически исправлено)
- Отсутствующая навигационная запись mkdocs.yml (автоматически исправлена)
- Полученные данные о безопасности
