**$ARGUMENTS**

## Пять правил (сохранено от Мэтта Покока, Массачусетский технологический институт) { #five-rules-preserved-from-matt-pocock-mit }

1. ** По одному вопросу за ход. ** Никогда не связывайтесь.
2. ** Рекомендуйте ответ на каждый вопрос.**
3. ** Изучите рабочее пространство, прежде чем задавать вопросы ** — протоколы, бухгалтерские книги, модели рынка, руководства по проведению собеседований.
4. ** Сначала пройдите по глубине.**
5. ** Отслеживание зависимостей** — конечная точка → мощность → осуществимость; бюджет → сжигание → лечение; определение размера → обследование → сегментация; метод → насыщение → синтез.

## Дерево решений для исследовательских операций (сначала в глубину) { #the-research-ops-decision-tree-depth-first }

### Ответвление 1 — Какая полоса движения? { #branch-1--which-lane }

- КЛИНИЧЕСКИЙ / RD_FINANCE / РЫНОК / ПРОДУКТ

### Ветвь 2 — Форсирующий вопрос для каждой полосы { #branch-2--the-forcing-question-per-lane }

** КЛИНИЧЕСКИЙ: ** "Является ли ваша основная конечная точка клиническим исходом или суррогатной — и если суррогатной, подтверждена ли она по данному показанию?"
Рекомендуется: клинический исход, если суррогатная мать не указана в таблице, утвержденной FDA.
Канон: Таблица суррогатных конечных точек FDA; ЛУЧШИЙ глоссарий; ICH E9.

**RD_FINANCE:** "Находятся ли эти расходы на стадии исследования или разработки, и можете ли вы подтвердить техническую осуществимость?"
Рекомендуется: исследование = расходы; разработка = капитализация - кандидат только с подтверждением технико-экономического обоснования, направляемым указанному финансовому владельцу.
Канон: МСФО (IAS) 38; ASC 730.

** РЫНОК: ** "Является ли ваш TAM нисходящим или восходящим снизу вверх - и вычислили ли вы его обоими способами для триангуляции?"
Рекомендуется: и то, и другое; выверяйте дельту, прежде чем указывать число.
Канон: Оценка рынка Bessemer / a16z; оценка Ферми.

** ПРОДУКТ: ** "Является ли это исследование генеративным (выявление проблем) или оценочным (тестирование решения)?"
Рекомендуется: сначала назовите его; далее следует метод.
Канон: Ландшафт методов UX-исследования Рорера (NN/g).

### Ветвь 3 — Проверка достоверности и предположений { #branch-3--confidence--assumptions-check }

"Каков ваш уровень уверенности и на каких трех предположениях основывается ответ?"
Рекомендуется: доверие государства (высокое/moderate/low) и выдвигать предположения перед любым числом.

### Филиал 4 — Названный владелец { #branch-4--named-owner }

"Кто является владельцем-человеком, который подписывает этот вывод?"
Рекомендуется: именованный клиницист/biostatistician (клинический), назначенный финансовый контролер (финансы), назначенное лицо, принимающее решения (рынок/product) — не "команда".

### Ветвь 5 — Теперь вызываем дополнительный скилл { #branch-5--now-invoke-the-sub-skill }

Только после того, как ветви 1-4 будут заблокированы, вызовите `/cs:research-ops` с помощью синтезированного запроса.

## Формат вывода за оборот { #output-format-per-turn }

```
Q[i]/[total]: [precise question]
Recommended: [answer + canon-cited rationale]

(Confirm, or override?)
```

## Условия остановки { #stop-conditions }

- Все ветви разрешены → вызвать `/cs:research-ops <synthesized>`
- Пользователь говорит "прекратите гриль, просто запустите его" → вызвать с тем, что решено, пометить неразрешенные ветви в дайджесте
- Пользователь отказывается → нет вспомогательной скиллы, сохраните частичный гриль для `research-ops-grill-{timestamp}.md`

## Отличный от { #distinct-from }

- `engineering/grill-me` (Мэтт Покок) — универсальный.
- `engineering/grill-with-docs` (Мэтт Покок) — кодовая база + ADR-привязка для разработки. Это ** Проверка домена Research-Ops** в соответствии с исследовательским каноном.
- `/cs:research-ops` — **выполняет** маршрутизацию. Это ** сначала опрашивает**.
