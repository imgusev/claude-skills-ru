Скиллы по эксплуатации на уровне внутреннего аудита в соответствии с ISO/IEC 42001:2023. **Три решения, никакой исполнительной стратегии искусственного интеллекта:**

1. ** Где имеются пробелы в целях по сравнению с пунктами 4-10?** — оценка охвата по каждому пункту + приоритет исправления
2. **Что такое реестр рисков искусственного интеллекта и какие средства контроля относятся к каждому риску?** — Приложение A.2–A.10 сопоставление контроля в соответствии с методом оценки рисков ISO 23894
3. **Каков план внутреннего аудита, предусмотренный пунктом 9.2?** — 12- месячный график с указанием объема, периодичности проверок независимости аудитора

Этот скилл ** НЕ является заменой главному специалисту по искусственному интеллекту-советнику **. CAIO решает, создавать ли/покупать ли модель и на какой бизнес-риск пойти. Этот скилл управляет дисциплиной системы менеджмента, которая фиксирует эти решения в готовых к аудиту доказательствах.

Этот скилл ** НЕ является скиллам, соответствующим Закону ЕС об искусственном интеллекте **. ISO 42001 - это добровольный стандарт системы менеджмента; Закон ЕС об искусственном интеллекте является обязательным регламентом по безопасности продукции. Они частично совпадают (система ИИ с высоким уровнем риска в соответствии со статьей 6(2) Закона об ИИ обычно требует СМК в статье 17, которой частично может соответствовать ISO 42001), но артефакты различаются. Видишь `compliance-team-eu-ai-act` для оценки соответствия на уровне изделия.

Этот скилл ** НЕ заменяет ISO 23894 + 38507** . 42001 - это система управления; 23894 - методология оценки рисков ИИ, которая соответствует пункту 6.1; 38507 - объектив управления. Тот `ai_risk_register_builder.py` инструмент реализует процесс 23894; рассматривайте ссылки как методологический мост.

## Ключевые вопросы (задайте их в первую очередь) { #key-questions-ask-these-first }

- ** Содержит ли в заявлении о сфере применения AIMS (пункт 4.3) название каждой системы искусственного интеллекта, включая встроенные модели и сторонние сервисы искусственного интеллекта?** Если "Функции искусственного интеллекта, добавленные нашими поставщиками SaaS" не входят в сферу применения, AIMS является неполным.
- ** Предусматривает ли политика в области искусственного интеллекта (пункт 5.2) законное использование И полезные цели, А ТАКЖЕ человеческий надзор И постоянное совершенствование? ** Отсутствие любого из четырех = несоответствие при сертификации.
- **Проводилась ли повторная оценка рисков ИИ (пункт 6.1.2) с момента последнего изменения модели материала?** Изменение концепции - это не разовое событие.
- **Кто подписывает оценку воздействия ИИ для систем с высокой отдачей (приложение A.5.4)?** Если отчетность не подписана, контроль отсутствует.
- ** Какова периодичность проведения внутреннего аудита (пункт 9.2)?** Стандарты системы менеджмента ISO предполагают проведение не реже одного раза в 3-летний цикл по каждому пункту; зрелые программы проводят ежегодно.
- **Существует ли документированная процедура для инцидентов с ИИ (приложение A.9.3)?** Необработанный мониторинг после развертывания - это несоответствие № 1 у первых пользователей.

## Основные обязанности { #core-responsibilities }

### 1. Анализ пробелов в целях (пункты 4-10) { #1-aims-gap-analysis-clauses-410 }

** Фреймворк: ** ISO 42001 соответствует структуре высокого уровня приложения SL, совместно используемой с ISO 9001 / 27001 / 13485 . Пункты 4-10 представляют собой требования к системе управления; элементы управления A.1-A.10 приложения A представляют собой операционные элементы управления, специфичные для ИИ.

| Оговорка | Что для этого требуется | Общий разрыв |
|---|---|---|
| **4. Контекст** | Сфера применения искусственного интеллекта, заинтересованные стороны, внешний контекст | Сфера применения не включает сторонние сервисы искусственного интеллекта |
| **5. Лидерство** | Политика в области искусственного интеллекта, роли, подотчетность | Политика рассматривает "этику искусственного интеллекта" как маркетинговую копию, а не как обязательство |
| **6. Планирование** | Оценка рисков и воздействия искусственного интеллекта, цели | Реестр рисков не связан с элементами управления |
| **7. Поддержка** | Ресурсы, компетентность, осведомленность, документированная информация | Требования к компетентности инженеров ML не определены |
| **8. Операция** | Оперативное планирование, жизненный цикл системы искусственного интеллекта | Этапы жизненного цикла, не отображенные в элементах управления приложения А |
| **9. Производительность** | Мониторинг, внутренний аудит, ревью руководства | Мониторинг дрейфа существует в коде, но не во входных данных для ревью со стороны руководства |
| **10. Улучшение** | Несоответствие, корректирующие действия, постоянное совершенствование | Цикл CAPA, отдельный от существующего 13485/9001 CAPA — дублирования |

**Запуск** `aims_gap_analyzer.py` с помощью JSON-файла инвентаризации доказательств можно оценить каждое предложение (полное / частичное / отсутствующее) и получить список приоритетных исправлений.

Видишь `references/iso42001_clauses.md` смотрите полное пошаговое руководство по каждому пункту с ожидаемыми доказательствами аудита.

### 2. Реестр рисков искусственного интеллекта + Приложение A Контрольная карта { #2-ai-risk-register--annex-a-control-mapping }

** Фреймворк:** Пункт 6.1.2 требует оценки рисков ИИ; пункт 6.1.3 требует учета рисков. В приложении А приведены 38 средств контроля, сгруппированных по 10 категориям контроля (A.2–A.10). В реестре рисков должен быть указан каждый идентифицированный риск, связанный с ≥ 1 элементом управления, который его обрабатывает.

**Контрольные категории приложения А (10):**

| ИДЕНТИФИКАТОР | Категория | Примеры элементов управления |
|---|---|---|
| **A.2** | Политика в области искусственного интеллекта | A.2.2 Политика в области искусственного интеллекта, A.2.3 согласование с другими политиками |
| **A.3** | Внутренняя организация | A.3.2 Роли и обязанности ИИ, A.3.3 проблемы с отчетностью |
| **A.4** | Ресурсы для систем искусственного интеллекта | A.4.2 информационные ресурсы, A.4.3 инструментарий, A.4.4 людские ресурсы |
| **A.5** | Оценка воздействий | A.5.2 Оценка воздействия системы искусственного интеллекта, A.5.4 документация по оценке воздействия |
| **A.6** | Жизненный цикл системы искусственного интеллекта | A.6.2.2 цели, A.6.2.3 фазы жизненного цикла, A.6.2.4 проверка и валидация |
| **A.7** | Данные для систем искусственного интеллекта | A.7.2 управление данными, A.7.3 качество данных, A.7.4 источник данных, A.7.5 подготовка данных |
| **A.8** | Информация для заинтересованных сторон | A.8.2 системная документация, A.8.3 информация о пользователях, A.8.4 сообщение об инцидентах |
| **A.9** | Использование систем искусственного интеллекта | A.9.2 использование по назначению, A.9.3 мониторинг работы, A.9.4 регистрация системных событий |
| **A.10** | Отношения с третьими лицами и клиентами | A.10.2 взаимоотношения с поставщиками, A.10.3 взаимоотношения с клиентами |

ISO/IEC 23894:2023 обеспечивает процесс управления рисками, специфичными для ИИ (методология); приложение A 42001 обеспечивает средства контроля. Реестр рисков - это связующее звено.

**Запуск** `ai_risk_register_builder.py` с помощью JSON-файла идентифицированных рисков для создания структурированного реестра с сопоставленными элементами управления + вердикт об остаточном риске в соответствии с вариантами обработки рисков по стандарту ISO 23894.

Видишь `references/aims_controls_annex_a.md` для получения полного каталога из 38 элементов управления с доказательствами аудита для каждого элемента управления.

### 3. Пункт 9.2 Плана внутреннего аудита { #3-clause-92-internal-audit-plan }

** Фреймворк:** Пункт 9.2 требует "проведения внутренних аудитов с запланированными интервалами для предоставления информации о том, соответствуют ли цели требованиям организации и эффективно ли они реализуются и поддерживаются в рабочем состоянии". Это требование системы управления; **как часто** и **насколько глубоко** принимаются организационные решения.

**Зрелый - настройки программы по умолчанию:**

- Охватывать каждый пункт + каждое применимое приложение Контроль в течение 3-летнего цикла (скользящий)
- Ежегодный полносистемный аудит, охватывающий пункты 4, 5, 9, 10 (пункты "всегда актуальны")
- Ежеквартальные или полугодовые глубокие погружения по пунктам 6, 7, 8 в разбивке по доменам (для каждой системы искусственного интеллекта или для каждой фазы жизненного цикла)
- Независимость аудитора: никто не проводит аудит своей собственной работы; Владелец жизненного цикла A.6 не может проводить аудит операции, предусмотренной пунктом 8

**Запуск** `aims_audit_scheduler.py` с помощью scope JSON (системы искусственного интеллекта в области применения, результаты за предыдущий год, фаза цикла сертификации) для составления 12-месячного плана с назначениями аудиторов и проверками независимости.

Видишь `references/aims_implementation_guide.md` для модели зрелости и последовательности раскатки (1-й год создания, 2-й год сертификации, 3-й год + постоянное совершенствование).

## Воркфлоу { #workflows }

### Воркфлоу 1: Устранение пробелов в целях сертификации (4-8 недель) { #workflow-1-aims-gap-closure-for-certification-48-weeks }
**Цель:** Выявить пробелы; определить приоритетность устранения; завершить до проведения сертификационного аудита 1-го этапа.

```bash
# 1. Inventory current AIMS evidence (policies, procedures, records)
python scripts/aims_gap_analyzer.py aims_evidence.json
# 2. Review gap matrix; group by clause
# 3. For each gap, identify owner + due date (target: close before stage 1)
# 4. Cross-check against ISO 27001 / 13485 existing artifacts — many can be reused
# 5. Cross-check against EU AI Act obligations (use compliance-team-eu-ai-act)
# 6. Output: prioritized remediation plan with owners + dates
```

### Воркфлоу 2: Построение реестра рисков искусственного интеллекта (1-2 недели) { #workflow-2-ai-risk-register-build-12-weeks }
**Цель:** Создать реестр рисков, предусмотренный пунктом 6.1.2, с полным охватом контроля в приложении А.

```bash
# 1. Run ISO 23894 risk identification across AI lifecycle (data, model, deployment, decommission)
# 2. Capture each risk with: source, event, consequence, likelihood, impact
python scripts/ai_risk_register_builder.py risks.json
# 3. For each high/critical risk, confirm ≥ 1 Annex A control is selected as treatment
# 4. Document residual risk acceptance with management signoff
# 5. Cross-check with cs-caio-advisor on executive risk acceptance for "tolerate" decisions
# 6. Log via management review (Clause 9.3)
```

### Воркфлоу 3: Годовой план внутреннего аудита (1 день) { #workflow-3-annual-internal-audit-plan-1-day }
**Цель:** Разработать 12-месячный план, предусмотренный пунктом 9.2, с независимостью аудитора.

```bash
# 1. Pull last year's audit findings and certification cycle status (year 1/2/3)
python scripts/aims_audit_scheduler.py audit_scope.json
# 2. Confirm auditor independence per assignment
# 3. Confirm coverage hits every clause and every applicable Annex A control over rolling 3 years
# 4. Submit plan for management review approval (Clause 9.3 input)
```

### Воркфлоу 4: Сопоставление повторного использования кросс-фреймворка (для онбординга каждой системы) { #workflow-4-cross-framework-reuse-mapping-per-system-onboarded }
** Цель:** При добавлении новой системы искусственного интеллекта сопоставьте данные ISO 42001 с существующими данными 27001 + 13485, чтобы избежать дублирования.

1. Использовать существующие элементы управления в приложении A к стандарту ISO 27001 + процедуры ISO 13485, относящиеся к системе
2. Для каждого элемента управления, включенного в приложение A к стандарту ISO 42001, определите, удовлетворяет ли ему уже существующий артефакт (например, 27001 A.8.16 мероприятия по мониторингу могут распространяться на мониторинг системы искусственного интеллекта).
3. Добавляйте наложение, специфичное для искусственного интеллекта, только там, где существующий элемент управления его не покрывает
4. Сопоставление документов в описании области применения AIMS (пункт 4.3)
