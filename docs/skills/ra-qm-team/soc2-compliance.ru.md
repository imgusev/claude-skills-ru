## Обзор { #overview }

### Что такое SOC 2? { #what-is-soc-2 }

SOC 2 (System and Organization Controls 2) - это фреймворк для аудита, разработанный AICPA, который оценивает, как сервисная организация управляет данными клиентов. Это применимо к любой технологической компании, которая хранит, обрабатывает или передает информацию о клиентах — в первую очередь к SaaS, облачной инфраструктуре и поставщикам управляемых услуг.

### Тип I против типа II { #type-i-vs-type-ii }

| Аспект | Тип I | Тип II |
|--------|--------|---------|
| **Сфера применения** | Проектирование элементов управления в определенный момент времени | Проектирование И эффективность эксплуатации в течение определенного периода |
| **Продолжительность** | Моментальный снимок (одна дата) | Период наблюдения (3-12 месяцев, обычно 6) |
| **Доказательства** | Описания элементов управления, политики | Описания элементов управления + доказательства работы (журналы, тикеты, скриншоты) |
| **Стоимость** | $20 тыс.-$50 тыс. (плата за аудит) | $30 тыс.-$100 тыс.+ (плата за аудит) |
| **Временная шкала** | 1-2 месяца (этап аудита) | 6-12 месяцев (наблюдение + аудит) |
| **Лучше всего подходит для** | Соответствие требованиям с первого раза, быстрая потребность рынка | Зрелые организации, корпоративные клиенты |

### Кому нужен SOC 2? { #who-needs-soc-2 }

- **SaaS-компании** продажи корпоративным клиентам
- **Поставщики облачной инфраструктуры** обработка рабочих нагрузок клиентов
- **Обработчики данных** управление PII, PHI или финансовыми данными
- **Управляемые поставщики услуг** с доступом к клиентским системам
- **Любой поставщик**, чьи клиенты нуждаются в гарантиях третьей стороны

### Типичное путешествие { #typical-journey }

```
Gap Assessment → Remediation → Type I Audit → Observation Period → Type II Audit → Annual Renewal
    (4-8 wk)      (8-16 wk)     (4-6 wk)       (6-12 mo)          (4-6 wk)       (ongoing)
```

## Критерии доверительного обслуживания { #trust-service-criteria }

SOC 2 организован на основе пяти категорий Критериев доверительного обслуживания (TSC). **Безопасность** требуется для каждого отчета SOC 2; остальные четыре являются необязательными и выбираются в зависимости от потребностей бизнеса.

### Безопасность (общие критерии CC1-CC9) — Требуется { #security-common-criteria-cc1-cc9--required }

Основа каждого отчета SOC 2. Соответствует принципам COSO 2013.

| Критерии | Домен | Ключевые элементы управления |
|----------|--------|-------------|
| **СС1** | Управляющая среда | Добросовестность/этика, надзор совета директоров, организационная структура, компетентность, подотчетность |
| **СС2** | Коммуникация и информация | Внутренняя/внешняя коммуникация, качество информации |
| **CC3** | Оценка рисков | Идентификация рисков, риск мошенничества, анализ влияния изменений |
| **CC4** | Деятельность по мониторингу | Постоянный мониторинг, оценка недостатков, корректирующие действия |
| **CC5** | Контрольные мероприятия | Политики/процедуры, технологический контроль, развертывание с помощью политик |
| **CC6** | Логический и физический доступ | Предоставление доступа, аутентификация, шифрование, физические ограничения |
| **CC7** | Системные операции | Управление уязвимостями, обнаружение аномалий, реагирование на инциденты |
| **CC8** | Управление изменениями | Разрешение на внесение изменений, тестирование, одобрение, экстренные изменения |
| **CC9** | Снижение рисков | Управление рисками поставщика/делового партнера |

### Доступность (A1) — необязательно { #availability-a1--optional }

| Критерии | Сосредоточься | Ключевые элементы управления |
|----------|-------|-------------|
| **A1.1** | Управление производительностью | Масштабирование инфраструктуры, мониторинг ресурсов, планирование производственных мощностей |
| **A1.2** | Восстановительные операции | Процедуры резервного копирования, аварийного восстановления, тестирования BCP |
| **A1.3** | Тестирование восстановления | Тренировки DR, тестирование на отказоустойчивость, проверка RTO/RPO |

** Выберите, когда:** Клиенты зависят от вашего времени безотказной работы; у вас есть соглашения об уровне обслуживания; время простоя оказывает прямое влияние на бизнес.

### Конфиденциальность (C1) — необязательно { #confidentiality-c1--optional }

| Критерии | Сосредоточься | Ключевые элементы управления |
|----------|-------|-------------|
| **C1.1** | Идентификация | Политика классификации данных, инвентаризация конфиденциальных данных |
| **C1.2** | Защита | Шифрование в состоянии покоя и при передаче, DLP, ограничения доступа |
| **C1.3** | Утилизация | Безопасные процедуры удаления, дезинфекция носителей, принудительное хранение |

**Выберите, когда:** Вы обрабатываете коммерческую тайну, служебные данные или конфиденциальную по контракту информацию.

### Целостность обработки (PI1) — необязательно { #processing-integrity-pi1--optional }

| Критерии | Сосредоточься | Ключевые элементы управления |
|----------|-------|-------------|
| **PI1.1** | Точность | Проверка входных данных, проверки обработки, проверка выходных данных |
| **PI1.2** | Полнота | Мониторинг транзакций, сверка, обработка ошибок |
| **PI1.3** | Своевременность | Мониторинг SLA, оповещения о задержке обработки, мониторинг пакетных заданий |
| **PI1.4** | Авторизация | Контроль за обработкой разрешений, разделение обязанностей |

** Выберите, когда:** Точность данных имеет решающее значение (обработка финансовых данных, медицинские записи, аналитические платформы).

### Конфиденциальность (P1-P8) — Необязательно { #privacy-p1-p8--optional }

| Критерии | Сосредоточься | Ключевые элементы управления |
|----------|-------|-------------|
| **P1** | Обратите внимание | Политика конфиденциальности, уведомление о сборе данных, ограничение цели |
| **P2** | Выбор и согласие | Регистрация/отказ от участия, управление согласием, отслеживание предпочтений |
| **P3** | Коллекция | Минимальный сбор, законное основание, указание цели |
| **P4** | Использование, хранение, утилизация | Ограничение по назначению, сроки хранения, надежная утилизация |
| **P5** | Доступ | Запросы субъекта данных на доступ, права на исправление |
| **P6** | Раскрытие информации и уведомление | Обмен информацией с третьими лицами, уведомление о нарушении |
| **P7** | Качество | Проверка точности данных, механизмы коррекции |
| **P8** | Мониторинг и правоприменение | Мониторинг программы обеспечения конфиденциальности, рассмотрение жалоб |

** Выберите, когда:** Вы обрабатываете персональные данные, и клиенты ожидают гарантий конфиденциальности (дополняет соблюдение GDPR).

## Генерация управляющей матрицы { #control-matrix-generation }

Контрольная матрица сопоставляет каждый критерий TSC с конкретными элементами управления, владельцами, доказательствами и процедурами тестирования.

### Матричная структура { #matrix-structure }

| Поле | Описание |
|-------|-------------|
| **Идентификатор элемента управления** | Уникальный идентификатор (например, SEC-001, AVL-003) |
| **Отображение TSC** | Каким критериям соответствует элемент управления (например, CC6.1, A1.2) |
| **Описание элемента управления** | Что делает элемент управления |
| **Тип управления** | Превентивный, детективный или корректирующий |
| **Владелец** | Ответственное лицо/команда |
| **Частота** | Непрерывный, Ежедневный, еженедельный, Ежемесячный, Ежеквартальный, Годовой |
| **Тип доказательства** | Скриншот, Журнал, Политика, конфигурация, Тикет |
| **Процедура тестирования** | Как аудитор проверяет систему контроля |

### Соглашение об именовании элементов управления { #control-naming-convention }

```
{CATEGORY}-{NUMBER}
SEC-001 through SEC-NNN  → Security
AVL-001 through AVL-NNN  → Availability
CON-001 through CON-NNN  → Confidentiality
PRI-001 through PRI-NNN  → Processing Integrity
PRV-001 through PRV-NNN  → Privacy
```

### Воркфлоу { #workflow }

1. Выберите применимые категории TSC в зависимости от потребностей бизнеса
2. Бежать `control_matrix_builder.py` для создания базовой матрицы
3. Настройте элементы управления в соответствии с вашей реальной средой
4. Назначение владельцев и требования к доказательствам
5. Проверка покрытия — каждый выбранный критерий TSC должен иметь по крайней мере один элемент управления

## Воркфлоу-анализ пробелов в работе { #gap-analysis-workflow }

### Этап 1: Оценка текущего состояния { #phase-1-current-state-assessment }

1. **Документирование существующих средств контроля** — инвентаризация всех политик безопасности, процедур и технических средств контроля
2. **Сопоставление с TSC** — приведение существующих элементов управления в соответствие с критериями доверительного обслуживания
3. ** Сбор образцов доказательств** — сбор доказательств того, что средства контроля существуют и функционируют
4. ** Опросите владельцев контроля** — проверьте понимание и выполнение

### Этап 2: Выявление пробелов { #phase-2-gap-identification }

Бежать `gap_analyzer.py` сопоставьте с вашими текущими элементами управления, чтобы идентифицировать:

- **Отсутствующие элементы управления** — критерии TSC без соответствующего элемента управления
- **Частично внедрено** — Контроль существует, но ему не хватает доказательств или последовательности
- **Пробелы в проектировании** — Система управления разработана, но неадекватно соответствует критериям
- **Рабочие зазоры** (только тип II) — Система управления спроектирована правильно, но работает неэффективно.

### Этап 3: Планирование восстановительных работ { #phase-3-remediation-planning }

Для каждого промежутка определите:

| Поле | Описание |
|-------|-------------|
| Идентификатор пробела | Ссылочный идентификатор |
| Критерии TSC | Затронутые критерии |
| Описание разрыва | Чего не хватает или чего недостаточно |
| Меры по восстановлению | Конкретные шаги по устранению этого разрыва |
| Владелец | Лицо, ответственное за устранение последствий |
| Приоритет | Критический / Высокий / Средний/ Низкий |
| Намеченная дата | Крайний срок завершения |
| Зависимости | Другие пробелы или проекты, которые необходимо завершить в первую очередь |

### Этап 4: Планирование сроков { #phase-4-timeline-planning }

| Приоритет | Целевое восстановление |
|----------|--------------------|
| Критический | 2-4 недели |
| Высокий | 4-8 недель |
| Средний | 8-12 недель |
| Низкий | 12-16 недель |

| Зона управления | Первичные доказательства | Вторичные доказательства |

| Подтверждение конфигурации | Моментальные снимки инфраструктуры в виде кода, инструменты обеспечения соответствия требованиям в виде кода |

### Непрерывный мониторинг { #continuous-monitoring }

Переход от сбора доказательств в определенный момент времени к постоянному соблюдению требований:

1. ** Автоматический сбор доказательств** — скрипты, которые собирают доказательства по расписанию
2. **Дашборды управления** — отображение состояния управления в режиме реального времени
3. **Мониторинг на основе предупреждений ** - уведомляет, когда элемент управления выходит из—под контроля
4. **Хранилище доказательств** — централизованное хранилище доказательств с отметками времени

## Чек-лист готовности к аудиту - "Контрольный список Readiness Readiness { #audit-readiness-checklist }

### Подготовка к предварительному аудиту (за 4-6 недель до проведения) { #pre-audit-preparation-4-6-weeks-before }

- [ ] Все элементы управления задокументированы с описаниями, владельцами и частотами
- [ ] Доказательства, собранные за весь период наблюдения (тип II)
- [ ] Ревью контрольной матрицы и устранение пробелов
- [ ] Полисы, подписанные и распространенные в течение последних 12 месяцев
- [ ] Доступ к ревью, выполненным с требуемой периодичностью
- [ ] Текущее сканирование уязвимостей (нет критических/ высокий уровень не исправлен > SLA)
- [ ] План реагирования на инциденты, протестированный в течение последних 12 месяцев
- [ ] Оценки рисков поставщиков актуальны для всех организаций, предоставляющих вспомогательные услуги
- [ ] DR/BCP протестирован и задокументирован в течение последних 12 месяцев
- [ ] Обучение сотрудников по вопросам безопасности завершено для всего персонала

### Оценка готовности { #readiness-scoring }

| Оценка | Рейтинг | Значение |
|-------|--------|---------|
| 90-100% | Готовность к аудиту | Действуйте уверенно |
| 75-89% | Незначительные пробелы | Обращайтесь перед планированием аудита |
| 50-74% | Значительные пробелы | Требуется исправление |
| < 50% | Не готов | Необходима масштабная разработка программы |

### Общие выводы аудита { #common-audit-findings }

| Поиск | Первопричина | Предотвращение |
|---------|-----------|-----------|
| Неполный доступ к ревью | Ручной процесс, никаких напоминаний | Автоматизировать ежеквартальный ревью триггеров |
| Отсутствующие утверждения изменений | Процесс обхода аварийных изменений | Определите процедуру экстренного изменения с последующим утверждением |
| Устаревшие проверки уязвимостей | Неправильно сконфигурирован сканер | Автоматическое еженедельное сканирование с предупреждением |
| Политика не признана | Нет механизма отслеживания | Ежегодный воркфлоу для электронной подписи |
| Отсутствующие оценки поставщиков | Нет инвентаря поставщика | Ведение реестра поставщиков с расписанием ревью |

## Управление поставщиками { #vendor-management }

### Оценка рисков третьей стороной { #third-party-risk-assessment }

Каждый поставщик, который получает доступ, хранит или обрабатывает данные клиентов, должен быть оценен:

1. ** Инвентаризация поставщиков** — ведение реестра всех поставщиков услуг
2. **Классификация рисков** — категоризация поставщиков по уровню доступа к данным
3. **Комплексная проверка** — сбор отчетов SOC 2, анкет безопасности, сертификатов
4. **Договорная защита** — обеспечение DPA, требований безопасности, положений об уведомлении о нарушениях
5. **Постоянный мониторинг** — ежегодная переоценка, непрерывный мониторинг новостей

### Уровни рисков поставщиков { #vendor-risk-tiers }

| Уровень | Доступ к данным | Частота оценки | Требования |
|------|-------------|---------------------|-------------|
| Критический | Обрабатывает/хранит данные клиентов | Ежегодный + непрерывный мониторинг | SOC 2 Type II, тест на проникновение, ревью безопасности |
| Высокий | Получает доступ к клиентской среде | Ежегодный | SOC 2 Тип II или эквивалент, анкета |
| Средний | Косвенный доступ, инструменты поддержки | Ежегодный вопросник | Сертификаты безопасности, анкета |
| Низкий | Нет доступа к данным | Вопросник за двухгодичный период | Базовый опросник по вопросам безопасности |

### Организации, предоставляющие вспомогательные услуги { #subservice-organizations }

Когда ваш отчет SOC 2 основан на элементах управления в организации-субсервисе (например, AWS, GCP, Azure):

- **Инклюзивный метод** — ваш отчет охватывает элементы управления вспомогательной организации (требуется их сотрудничество)
- ** Метод исключения** — ваш отчет исключает их элементы управления, но ссылается на их отчет SOC 2
- Большинство компаний используют ** выделение** и включают дополнительные элементы управления пользовательскими объектами (CUECs).

## Постоянное соблюдение требований { #continuous-compliance }

### От мгновенного к непрерывному { #from-point-in-time-to-continuous }

| Аспект | Момент времени | Непрерывный |
|--------|---------------|-----------|
| Сбор доказательств | Руководство перед аудитом | Автоматизированный, непрерывный |
| Контрольный мониторинг | Периодический ревью | Дашборды в режиме реального времени |
| Обнаружение дрейфа | Обнаружено в ходе аудита | Основанный на предупреждении, немедленный |
| Восстановление | Реактивный | Активный |
| Подготовка к аудиту | схватка на 4-8 недель | Всегда готов |

### Этапы реализации { #implementation-steps }

1. **Автоматизировать сбор доказательств** — задания cron, интеграция API, моментальные снимки IaC
2. **Создание дашбордов управления ** — объединение состояния управления в единое представление
3. ** Настройка оповещений о дрейфе ** — уведомляет, когда элементы управления выходят из-под контроля.
4. **Установить частоту ревью** — еженедельные контрольные проверки владельцев, ежемесячное управление
5. **Поддерживать хранилище фактических данных** — централизованное, с отметками времени, доступное аудитору

### Ежегодный цикл переоценки { #annual-re-assessment-cycle }

| Четверть | Деятельность |
|---------|-----------|
| Вопрос 1 | Ежегодная оценка рисков, обновление политики, запуск повторной оценки поставщиков |
| Q2 | Тестирование системы внутреннего контроля, исправление выявленных нарушений |
| Вопрос 3 | Ревью готовности к предварительному аудиту, проверка полноты доказательств |
| Q4 | Внешний аудит, утверждение руководства, рассылка отчетов |

## Анти-паттерны { #anti-patterns }

| Анти-паттерн | Почему это терпит неудачу | Лучший подход |
|--------------|-------------|----------------|
| Соответствие требованиям на определенный момент времени | Средства контроля ухудшаются между аудитами; пробелы, обнаруженные в ходе аудита | Внедрить непрерывный мониторинг и автоматизированную сборку данных |
| Ручной сбор доказательств | Отнимающий много времени, непоследовательный, подверженный ошибкам | Автоматизируйте с помощью скриптов, IaC и платформ соответствия требованиям |
| Отсутствующие оценки поставщиков | Аудиторы отмечают неполную проверку поставщиков | Ведение реестра поставщиков с многоуровневым графиком оценки рисков |
| Правила копирования и вставки | Общие политики не соответствуют фактическим операциям | Адаптируйте политику к вашей реальной среде и технологическому стеку |
| Театр безопасности | Средства контроля существуют на бумаге, но не соблюдаются | Проверка операционной эффективности; встраивание элементов управления в воркфлоу |
| Пропуск типа I | Переход ко второму типу без фундаментальной готовности | Начните с типа I, чтобы проверить конструкцию элемента управления перед наблюдением |
| Чрезмерный охват TSC | Включая все 5 категорий, когда требуется только безопасность | Выбирайте категории на основе фактических требований заказчика/ бизнеса |
| Отношение к аудиту как к проекту | Соответствие требованиям ухудшается после публикации отчета | Внедрите соответствие требованиям в повседневную деятельность и инженерную культуру |

## Инструменты { #tools }

### Построитель управляющих матриц { #control-matrix-builder }

Генерирует управляющую матрицу SOC 2 из выбранных категорий TSC.

```bash
# Generate full security matrix in markdown
python scripts/control_matrix_builder.py --categories security --format md

# Generate matrix for multiple categories as JSON
python scripts/control_matrix_builder.py --categories security,availability,confidentiality --format json

# All categories, CSV output
python scripts/control_matrix_builder.py --categories security,availability,confidentiality,processing-integrity,privacy --format csv
```

### Отслеживатель улик { #evidence-tracker }

Отслеживает статус сбора доказательств для каждого элемента управления.

```bash
# Check evidence status from a control matrix
python scripts/evidence_tracker.py --matrix controls.json --status

# JSON output for integration
python scripts/evidence_tracker.py --matrix controls.json --status --json
```

### Анализатор зазоров { #gap-analyzer }

Анализирует текущие средства контроля в соответствии с требованиями SOC 2 и выявляет пробелы.

```bash
# Type I gap analysis
python scripts/gap_analyzer.py --controls current_controls.json --type type1

# Type II gap analysis (includes operating effectiveness)
python scripts/gap_analyzer.py --controls current_controls.json --type type2 --json
```
