Корпоративный SOP + разработка внутреннего рансбука, проверка полноты 5W2H и отчетность по гигиене KB для руководителей подразделений / менеджеров знаний / TPM-внутренних сотрудников.

## Цель { #purpose }

Оперативная организация, работающая три года, разрастается: 600 концептуальных страниц, 200 рансбуков Confluence, три хранилища Obsidian, `Drive/SOPs/` папка, а также `Slack #ops-questions` канал, который существует потому, что никто не может найти канонический документ. Предсказуемые режимы отказа:

1. **Нет владельца** — 40% СОП называют "команду" вместо человека. Когда документ гниет, никто не несет ответственности.
2. ** Нет даты последнего ревью** - в SOP, разработанном много лет назад для сторонних поставщиков, по—прежнему упоминается инструмент закупок, который был закрыт более года назад.
3. ** Неопределенные сигналы об успехе** — в рансбуке на шаге 4 написано "убедитесь, что служба запущена". Новый оператор не может сказать, что это значит.
4. **Нет пути отката** — инцидент - рансбук каскадной связи сообщает вам, как отправить предупреждение. В нем не указано, как отозвать его, если предупреждение было неправильным.
5. **Страницы-сироты** — половина КБАЙТ не содержит входящих ссылок. Никто не находит их с помощью навигации; они существуют только потому, что кто-то знал URL-адрес.
6. ** Изменение глоссария** — "CSM" означает "Менеджер по работе с клиентами" в трех документах и "Менеджер по решениям для клиентов" в пяти. Новые сотрудники ошибаются в своих предположениях в течение шести месяцев.
7. ** SOPs только для счастливого пути ** - в документе описано, что происходит, когда все работает. Это не распространяется на 30% случаев, когда это не так.

Этот скилл отвечает на актуальный вопрос оператора: ** "Какие 20 документов я исправляю в первую очередь и что конкретно в каждом из них не так?"** — с помощью детерминированной логики, а не интуиции.

## Когда использовать { #when-to-use }

- Разработка нового SOP для межфункционального процесса компании (прием заказов, увольнение поставщика, каскад связи с инцидентами, онбординг сотрудников, возмещение расходов, плейбук для эскалации клиентов, связь с инцидентами безопасности, предоставление доступа к системе).
- Проверка существующего внутреннего рансбука перед его запуском в ротацию (у каждого шага должен быть именованный владелец, ожидаемая продолжительность, наблюдаемый сигнал успеха, наблюдаемый сигнал сбоя, путь отката, контакт для эскалации).
- Выполнение экспорта из нескольких документов в формате KB (zip-файл Concept, экспорт пространства слияния, Obsidian vault, `Drive/SOPs/` каталог) и выявляем то, что не работает: страницы-сироты, устаревшие страницы (не редактировались более 12 месяцев), смещение глоссария, страницы с отсутствующими владельцами, карта перекрестных ссылок.
- Онбординг нового сотрудника ops путем создания страниц SOPs и ops-handbook, которые они должны прочитать на первой неделе.
- Спринты по очистке вики — ежеквартальная гигиеническая работа, в ходе которой организация решает, какие 30 документов заархивировать, переписать или объединить.

## Воркфлоу { #workflow }

Четырехэтапный детерминированный поток (соответствует фактическому воркфлоу операционной организации, а не абстрактному процессу):

1. **Проглотить КБАЙТ.** Запустить `kb_ingester.py --input <vault-dir>` на существующем вики-экспорте. Результатом является отчет о состоянии Markdown: потерянные страницы, устаревшие страницы, смещение глоссария, страницы с отсутствующими владельцами, карта перекрестных ссылок, список приоритетной очистки. В отчете представлены 20 документов, которые необходимо исправить в первую очередь - обычно это смесь устаревших документов с высоким трафиком и документов о пропавших владельцах, соответствующих требованиям. Отнесите этот список в спринт по очистке.
2. **Проверьте существующие рансбуки.** Для каждого рансбука в списке очистки (или для любого нового рансбука до того, как он поступит в ротацию) запустите `runbook_validator.py --input <runbook.md>`. Валидатор оценивает каждый шаг по шести проверкам (имя владельца, ожидаемая продолжительность, наблюдаемый сигнал успеха, наблюдаемый сигнал сбоя, путь отката, контакт для эскалации) и выдает для каждого шага значение светофора + общий балл валидности 0-100 + список проблем, которые необходимо устранить. Рансбук, набравший менее 60 баллов, небезопасен для использования в инциденте.
3. ** Сгенерируйте отсутствующие SOP.** Для SOP, которые необходимо написать с нуля (или переписать заново, поскольку существующий не подлежит восстановлению), запустите `sop_generator.py --input <metadata.json> --profile <ops|support|finance|hr|it|regulated>`. На выходе получается структурированный по 5W2H каркас SOP: Кто (RACI), что (этапы процесса), когда (триггеры + частота), Где (система + инструмент), почему (цель + нормативная база), Как (пошагово), Сколько (затраты + время на каждый казнь). Тот `regulated` профиль добавляет разделы контроля версий, выхода из системы и аудита (ISO 9001 / FDA 21 CFR Part 211 / SOC 2 / HIPAA).
4. **Перекрестная ссылка + завершение цикла.** Повторный запуск `kb_ingester.py` после спринта по очистке, чтобы убедиться, что количество потерянных страниц уменьшилось, и смещение глоссария устранено. Важными показателями являются ** "недоступные документы"** (сироты) и ** "небезопасные рансбуки"** (оценка достоверности < 60), а не количество страниц.

## Сценарии { #scripts }

**`scripts/sop_generator.py`** — Считывает файл метаданных JSON, описывающий SOP (владелец процесса, событие триггера, роль аудитории, частота, наложение правил, входы, выходы, схема шагов) и выдает полный SOP со структурой 5W2H в Markdown (или нормализованный JSON). Тот `--profile` флаг настраивает выходной сигнал: `ops` (общие внутренние операции), `support` (стиль рансбука службы поддержки клиентов), `finance` (контроль + фокус на согласовании), `hr` (помечены конфиденциальные данные), `it` (система + фокус доступа), `regulated` (добавляет контроль версий, матрицу выхода из системы, отслеживание аудита). Нормативные накладки (`SOC2`, `HIPAA`, `ISO13485`, `GDPR`, `SOX`) приложите соответствующую преамбулу о соблюдении требований. `--sample` печатает полный пример SOP для сторонних поставщиков. Только Stdlib.

**`scripts/runbook_validator.py`** — Считывает рансбук (файл Markdown или JSON) и проверяет каждый шаг на соответствие шести обязательным атрибутам: (1) имя владельца (не "команда", не "операции"), (2) ожидаемая продолжительность (конкретное число + единица измерения), (3) наблюдаемый сигнал успеха (например, "HTTP 200 от `/healthz`" — не "служба запущена"), (4) наблюдаемый сигнал сбоя, (5) путь отката (или явное "этот шаг не может быть откатан, эскалация до X"), (6) контакт для эскалации (названное лицо или именованная ротация по вызову). Результатом является значение светофора для каждого шага (ЗЕЛЕНЫЙ / ЖЕЛТЫЙ / КРАСНЫЙ), общая оценка достоверности от 0 до 100 и список проблем, которые необходимо устранить. Вердикт: ≥ 80 = БЕЗОПАСЕН В ИСПОЛЬЗОВАНИИ, 60-79 = ИСПОЛЬЗУЙТЕ С ОСТОРОЖНОСТЬЮ, < 60 = НЕБЕЗОПАСЕН. `--sample` печатает намеренно поврежденный рансбук связи с инцидентами для демонстрации обнаружения сбоев. Только Stdlib.

**`scripts/kb_ingester.py`** — Просматривает каталог файлов Markdown (экспорт понятий, экспорт пространства слияния, Obsidian vault, `Drive/SOPs/` каталог). Выдержки: (а) карта перекрестных ссылок (какая страница ссылается на какую, с помощью Markdown `[link](path)` синтаксис), (б) кандидаты в глоссарий (часто используемые имена собственные и аббревиатуры, которые повторяются в более чем 3 документах без единой страницы канонического определения), (в) страницы-сироты (нет входящих ссылок из любой точки хранилища), (г) смещение глоссария (один и тот же термин определяется или используется непоследовательно в разных документах — например, "CSM" расширен по-разному в двух местах), (e) устаревшие страницы (не редактировались более 12 месяцев, обнаружены с помощью файловой системы mtime или YAML `last_reviewed` frontmatter), (f) отсутствующие страницы владельца (нет `owner:` поле в frontmatter). Выдает отчет о работоспособности KB в Markdown с приоритетным списком из топ-20 по очистке, ранжированным по `staleness × inbound-link-count` (сначала устаревшие документы с высоким трафиком). `--sample` создает крошечное синтетическое хранилище на 8 страниц в tmpdir и запускает на нем полный пайплайн. Только Stdlib.

## Краткий пример { #quick-example }

```bash
# Builds a synthetic 8-page vault and emits a KB health report (orphans, stale pages, glossary drift, top-20 cleanup list)
```

## Допущения { #assumptions }

1. КБ находится в Markdown (или может быть экспортирован в Markdown — все это поддерживают Notion, Confluence, Obsidian и Google Docs). Для KBS, поддерживающих только HTML или PDF, сначала требуется выполнить преобразование; это выходит за рамки.
2. Пользователь имеет право заказывать перезапись или архивирование. Создание списка очистки, с которым никто не работает, является пустой тратой времени — направляйте результаты поиска указанному владельцу перед запуском программы ingester.
3. Метаданные владельца хранятся в YAML frontmatter (`owner: alex@company.com`) или в строке "Владелец:" в верхней части страницы. Владелец племенных знаний (человек, который последним редактировал страницу) считается отсутствующим.
4. Значение "Устаревший" по умолчанию равно 12 месяцам. Переопределить с помощью `--stale-days` на `kb_ingester.py`. Некоторые режимы соблюдения требований (FDA, ISO 13485) требуют более коротких циклов ревью; используйте `--profile regulated` и `--stale-days 365`.
5. Пользователь не запрашивает персональный PKM. Личная работа второго мозга в стиле Карпатии относится к `engineering/llm-wiki`.

## Анти-паттерны { #anti-patterns }

- ** Массовое создание SOP без владельцев.** Период полураспада документа без владельца составляет 6 месяцев. Откажитесь генерировать пакет из 30 SOP, если каждый из них не назначен указанному человеку.
- **Использование `runbook_validator.py` в качестве флажка.** Валидатор улавливает отсутствующую структуру. Он не улавливает неправильный контент. Рансбук может набрать 100 баллов и все равно сообщить оператору неправильную информацию.
- ** По умолчанию страницы—сироты рассматриваются как мусор.** Некоторые страницы-сироты являются справочными страницами, которые можно найти только с помощью поиска - не все страницы-сироты следует архивировать. Список очистки - это *приоритетная очередь*, а не список удаления.
- **Путать операции со знаниями с `process-mapper`.** Process-mapper документирует *поток* работ между этапами (BPMN, время цикла, узкое место). Knowledge-ops документирует *артефакты*, используемые операторами для выполнения работы (SOP, рансбук, глоссарий). И то, и другое может применяться к одному и тому же процессу.
- ** Позволяя глоссарию накапливаться. ** Два определения "CSM" за три года превращаются в семь определений за пять. Исправьте смещение глоссария в тот момент, когда он появляется в `kb_ingester.py` вывод.
- **Пропуск регулируемого профиля при регулируемой рабочей нагрузке.** Если процесс касается PHI, финансового контроля, относящегося к SOX, или СМК устройств по стандарту ISO 13485, используйте `--profile regulated`. Отсутствие контроля версий в регулируемом SOP является результатом аудита.
- ** Рукописное написание разделов 5W2H по памяти.** Каркас 5W2H существует потому, что операторы забывают "Сколько". Используйте генератор; отредактируйте выходные данные.

## Отличный от { #distinct-from }

- **`engineering/llm-wiki`** — Персональный PKM second brain в стиле Карпатии, где один человек собирает источники в свое собственное взаимосвязанное хранилище. Knowledge-ops является *организационным*: много авторов, много читателей, названные владельцы для каждого документа, формальные циклы ревью, накладки на соответствие требованиям.
- **`engineering-team/runbook-generator`** — system-ops рансбук для отладки производственной системы (журналы, оповещения, k8s, on-call). Рансбуки Knowledge-ops - это рансбуки операторов для бизнес-процессов (каскад инцидентов-связи, увольнение поставщика, онбординг сотрудников). Аудитория - коллеги-операторы, а не инженеры, собирающие бревна.
- **`project-management/*`** — Отслеживание доставки Jira / Confluence, воркфлоу заявок на спринт, отчеты о состоянии проекта. Knowledge-ops - это *контент* на этих страницах слияния, а не *отслеживание* того, кто их редактирует.
- **`business-operations/process-mapper`** (родственный) — процесс BPMN *проектирование*: где находятся этапы, где предстоит работа, какой этап является узким местом. Knowledge-ops - это процесс * документация*: артефакты SOP и рансбук, которые сообщают оператору, как выполнить процесс, описанный картографом.
- **`business-operations/internal-comms`** (брат или сестра) — широковещательные объявления, обмен сообщениями в режиме реального времени, связь для управления изменениями. Knowledge-ops - это долговременный справочный артефакт; internal-commms - это широковещательная передача.
- **`ra-qm-team/*`** — официальное подтверждение соответствия нормативным требованиям (СМК ISO 13485, технические файлы MDR, 21 CFR, часть 820). Knowledge-ops заимствует нормативный чек-лист, но не является заменой аудита уполномоченного органа.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Перед вызовом инструментов оркестратор (или `/cs:grill-bizops`) знакомит пользователя с этими вопросами ** по одному за раз, с рекомендуемым ответом + цитатой из канона **. Никогда не упаковывался. Сначала пройдите вглубь - не открывайте вопрос 4, пока не будут заблокированы пункты 1-3.

1. ** "Кто является названным владельцем этого SOP / рансбука, и знают ли они, что он им принадлежит?"**
   Рекомендуется: один человек (не "команда"), и да — они договорились в письменной форме.
   Канон: Gawande 2009 (* Манифест Чек—листа*) - чек-листы без владельца гниют в течение 12 месяцев. Ответственность - это дисциплина.

2. ** "Когда этот документ в последний раз подвергался ревью и какова частота ревью?"**
   Рекомендуется: ревью проводился в течение последних 12 месяцев (90 дней, если `--profile regulated`); интонация написана в заголовке.
   Канон: ISO 9001:2015 §7.5.3 — контролируемые документы требуют метаданных цикла ревью. ITIL v4 повторяет это для сервисных операций рансбуков.

3. ** "Для каждого шага рансбука: каков наблюдаемый сигнал успеха — под которым я подразумеваю, какой конкретный результат говорит вам о том, что шаг сработал?"**
   Рекомендуется: конкретная наблюдаемая ("HTTP 200 от `/healthz`", "Провисшая нить закрыта с помощью `done` реакция", "Salesforce opportunity перешла на `Closed-Won` стадия") — не "служба запущена" или "это работает".
   Канон: Beyer et al., 2018 (*Руководство по надежности сайта*, гл. 8) — наблюдаемые сигналы - это весь смысл рансбука. Расплывчатые критерии успеха являются основной причиной неправильного использования рансбука во время инцидентов.

4. ** "Каков путь отката для каждого шага рансбука, который может завершиться неудачей?"**
   Рекомендуется: каждый шаг, изменяющий состояние, имеет либо путь отката, либо явную строку "невозможно выполнить откат — эскалация до X".
   Канон: Хорошо спроектированный фреймворк AWS, основа операционного совершенства - "вы не можете запустить процесс, который вы не можете обратить вспять, предварительно не согласовав, что означает "обратить вспять"".

5. ** "Где находится этот документ и какие другие документы ссылаются на него?"**
   Рекомендуется: в канонической вики и по крайней мере 2 входящие ссылки из соответствующих документов. Бесхозная ПОДАЧКА - это подачка, которую невозможно найти.
   Канон: Плейбук команды Atlassian по исправности документации — показатель "бесхозности" > 20% является основным показателем проблемы разрастания вики.

6. ** "Какие нормативные требования накладываются на этот процесс — SOC 2, HIPAA, ISO 13485, GDPR, SOX, отсутствуют?"**
   Рекомендуется: четкий ответ. Если "нет", подтвердите, проверив классы данных, к которым прикасается процесс.
   Канон: FDA 21 CFR, часть 211.100 (Письменные процедуры; отклонения) — регулируемые SOP требуют контроля версий, истории изменений и выхода из системы. Пропустите этот шаг, и документ станет результатом аудита.

7. ** "Задокументирован ли счастливый путь как *единственный* путь, или также задокументированы 2-3 наиболее распространенных режима отказа?"**
   Рекомендуется: 2 основных режима сбоя для каждого процесса задокументированы с помощью их собственной подпроцедуры восстановления.
   Канон: Fowler 2016 (*Готовые к производству микросервисы*) - операционные документы, которые охватывают только "счастливый путь", ответственны за более чем 60% потерь времени на инциденты.

После того, как все 7 будут заблокированы, вызовите `kb_ingester.py` → `runbook_validator.py` → `sop_generator.py` в определенной последовательности.
