Исследование продукта / пользователя как операционная дисциплина: выбор правильного метода, его честная оценка и обобщение результатов в управляемые идеи. Основное правило: ** метод должен соответствовать цели**, и ** понимание требует повторения среди независимых участников** — единственная цитата - это анекдот.

## Цель { #purpose }

Исследователям продуктов, командам ResearchOps и руководителям, выполняющим discovery, нужна строгость методов и хранилище информации, которому они могут доверять. Этот скилл формирует три решения:

Три детерминированных инструмента:

1. `study_designer.py` — Сопоставляет (цель исследования × стадия продукта) с соответствующим методом и выдает соответствующий методу каркас плана (цель, критерии участников, структура руководства, критерии успеха). Перенаправляет прямой эфир A/B на `product-team/experiment-designer`.
2. `saturation_planner.py` — Руководство по выборке, основанное на методе, с явной ** меткой достоверности**: Проблема Нильсена-обнаружение (5/segment), Гест и др. тематическая насыщенность (~12) и оценочный охват. Никогда не претендует на показатель распространенности по результатам юзабилити-теста small-n.
3. `insight_synthesizer.py` — Группирует закодированные наблюдения по тегам, подсчитывает отдельных участников, ранжирует по повторяемости между участниками и помечает любого кандидата ниже порогового значения источника как ** АНЕКДОТ **, никогда не повышая его до уровня инсайта.

## Когда использовать { #when-to-use }

Используйте этот скилл, когда:

- Вы планируете исследование, и вам нужен метод, соответствующий цели (генеративный, оценочный и валидационный).
- Вам нужно обоснованное обоснование размера выборки / насыщенности с заявленной уверенностью.
- У вас есть необработанные закодированные наблюдения, и вам нужно синтезировать идеи, не переоценивая их.
- Вы настраиваете или проводите аудит исследовательского хранилища и нуждаетесь в дисциплине "понимание против наблюдения".

** Не используйте этот скилл для**: создания персонажей / карт путешествий (используйте `product-team/ux-researcher-designer`), спланируйте спринт по обнаружению или подтвердите возможность (используйте `product-team/product-discovery`), спроектируйте или проанализируйте эксперимент A/B с живым продуктом (используйте `product-team/experiment-designer`), или проводить оценку рынка / опросы (используйте `market-research` родной брат).

## Воркфлоу { #workflow }

1. **Обрамите исследование** — Заполните `assets/research_plan_template.md` (вопросы исследования, обоснование метода, критерии участия, план анализа, схема маркировки репозитория).
2. **Выберите метод** — Запустите `study_designer.py --goal {discovery|evaluative|validation} --stage {concept|prototype|beta|live} --profile {b2b-saas|consumer-app|enterprise|marketplace|hardware|platform}`. Соблюдайте перенаправление, если оно ведет к experiment-designer.
3. **Определите его размер ** — Запустите `saturation_planner.py --method {usability|thematic|evaluative-coverage} --segments N`. Запишите метку достоверности и пределы.
4. **Синтезировать** — После заполнения, закодируйте наблюдения и запустите `insight_synthesizer.py --input observations.json --min-sources 3`. Рассматривайте кластеры, помеченные как анекдотические, как сигналы для исследования, а не как результаты для отправки.
5. **Файл в репозитории** — Помечайте идеи для атомной схемы во время синтеза с их доказательствами и уверенностью.

## Сценарии { #scripts }

| Сценарий | Цель | Профили |
|---|---|---|
| `scripts/study_designer.py` | (цель × этап) → метод + каркас плана | b2b-saas, потребительское приложение, предприятие, маркетплейс, оборудование, платформа |
| `scripts/saturation_planner.py` | Руководство по выборке на основе метода + уверенность | n/a (зависит от метода) |
| `scripts/insight_synthesizer.py` | Кластерные наблюдения, отмеченные анекдоты | n/a (на основе фактических данных) |

Все три: только для stdlib, `--help`, `--sample`, `--output {human,json}`.

## Онбординг и кастомизация { #onboarding--customization }

Запустите анкету для онбординга ** один раз перед началом работы ** — она фиксирует ваши настройки по умолчанию, поэтому каждый инструмент в этом скилле предварительно настроен. Суть в настройке: ответы фактически изменяют поведение инструмента (например, источник информации-порог).

```bash
python3 scripts/onboard.py            # interactive (also: --defaults, --set key=value, --reset)
python3 scripts/onboard.py --show     # see the questions + current effective config
```

Ответы сохраняются в `~/.config/research-ops/product-research.json` (глобальный) или `./.research-ops/product-research.json` (`--scope project`) и считываются автоматически `config_loader.py`. Они устанавливают ** профиль продукта ** по умолчанию, **порог источника инсайта** (количество независимых участников делает вывод инсайтом, а не анекдотом), ** метод насыщения по умолчанию ** и флаг **высокие ставки**. Флаги CLI всегда переопределяют сохраненную конфигурацию; `RESEARCH_OPS_NO_CONFIG=1` игнорирует это.

** Четыре вопроса: ** профиль продукта · источник информации - порог · метод насыщения · флаг высоких ставок.

## Оптимизация с помощью автоматического поиска (опция) { #optimize-with-autoresearch-opt-in }

Этот скилл предоставляет ** изолированный, согласованный** мост для `engineering/autoresearch-agent`. Только когда вы просите "оптимизировать синтез" / "запустить цикл", эксперимент с автоматическим поиском итеративно уточняет кодирование/clustering из фиксированного набора доказательств, чтобы выявлялось больше взаимосвязей между участниками. `scripts/ar_evaluator.py` является основным средством оценки истинности; он печатает `validated_insights: <int>` (чем выше, тем лучше). Он оптимизирует ** кодирование**, никогда не фальсифицирует доказательства.

```bash
/ar:setup --domain custom --name insight-synthesis \
  --target observations.json \
  --eval "python3 ar_evaluator.py --target observations.json" \
  --metric validated_insights --direction higher
/ar:loop custom/insight-synthesis
```

Изолированный: нет жесткой зависимости — автоматический поиск выполняется только по запросу, а цикл редактируется `observations.json`, но никогда не оценщик.

## Допущения { #assumptions }

- Выбор метода предполагает, что вы можете честно назвать цель; если цель нечеткая, сначала определите ее (цель определяет все).
- Рекомендации по насыщению основаны на методе, а не на расчете мощности - тесты удобства использования выявляют проблемы, а не показатели распространенности.
- Синтезатор учитывает предоставленные вами доказательства; качество кодирования зависит от него. Теги мусора → кластеры мусора.
- Порог проницательности (`--min-sources`) по умолчанию равно 3; увеличьте его для игроков с высокими ставками или разнородных групп населения.

## Анти-паттерны { #anti-patterns }

- ** Несоответствие метода цели.** Юзабилити-тест не может выявить неудовлетворенные потребности; собеседование не может измерить успешность выполнения задачи.
- ** Отчет о проблемах с удобством использования в процентах.** Small-n тестирует поверхностные проблемы, а не показатели численности населения.
- ** Продвижение анекдота к пониманию. ** Один участник - это сигнал для исследования, а не находка.
- ** Формулируйте вопросы интервью как характерные реакции.** Изучите предстоящую работу и недавнее реальное поведение, а не гипотетические мнения.
- **Синтезирование без схемы хранилища.** Помечайте во время синтеза, иначе информацию будет невозможно найти.

## Отличный от { #distinct-from }

| Сосед | Сфера применения | Разница |
|---|---|---|
| `product-team/ux-researcher-designer` | Персонажи, карты путешествий, фреймворки юзабилити, привязанные к результатам проектирования | Который создает **артефакты**; это ** метод + дисциплина хранилища** |
| `product-team/product-discovery` | Проверка возможностей, обнаружение-планирование спринта | Который планирует ** спринты по открытиям**; он проектирует и обобщает ** исследования** |

## Краткие примеры { #quick-examples }


Сэмпл синтезатора корректно продвигает "import-confusion" (3 независимых участника) к ПОНИМАНИЮ и помечает "wants-slack" (1 участник) как АНЕКДОТ.

## Библиотека принудительных вопросов (дисциплина Matt Pocock grill) { #forcing-question-library-matt-pocock-grill-discipline }

Проходили по одному мимо `/cs:grill-research-ops` или оркестратор. Рекомендуемый ответ + цитата из канона на каждый вопрос. Никогда не упаковывался.

1. ** "Является ли это исследование генеративным (выявление проблем) или оценочным (тестирование решения)?"**
   Рекомендуется: сначала назовите его — метод вытекает из цели.
   Канон: Рорер, *Когда использовать какие методы исследования пользовательского опыта* (NN/g).

2. ** "Каков ваш обоснованный размер выборки и насыщенность — и с какой степенью уверенности?"**
   Рекомендуется: основанный на методе n (5/segment удобство использования; ~12 для тематической насыщенности), выразите уверенность.
   Канон: Нильсен; Гость, Банс и Джонсон (2006); Фолкнер (2003).

3. ** "Сколько независимых участников поддерживают каждое предположение — или это анекдот из одного источника?"**
   Рекомендуется: требуйте повторения в ≥3 источниках, прежде чем называть это инсайтом; отмечайте синглтоны.
   Канон: атомные исследования / ResearchOps; тематический анализ Braun & Clarke.

4. ** "Сформулированы ли ваши задачи по собеседованию /юзабилити как результаты (задания) или как реакции на особенности?"**
   Рекомендуется: ориентируйтесь на работу, которую предстоит выполнить, и недавнее реальное поведение, а не на гипотетическое мнение.
   Канон: Кристенсен/Улвик выполняют задания, которые необходимо выполнить; Портигал * Проводит собеседования с пользователями*.

5. ** "Где это попадает в хранилище и как оно помечается для повторного использования?"**
   Рекомендуется: прикреплять теги к атомной схеме во время синтеза, не позже.
   Канон: Томер Шарон, *Polaris* / Практика репозиториев ResearchOps.

Сначала пройдите вглубь. Зафиксируйте 1-2 перед открытием 3-5. После того, как на все будут даны ответы, вызовите `study_designer.py` → `saturation_planner.py` → (после выставления) `insight_synthesizer.py`.
