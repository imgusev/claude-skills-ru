Главный исполнительный директор владеет тремя вещами. Все остальное - это делегирование полномочий.

| Ответственность | Что это значит | Ссылка |
|---------------|--------------|-----------|
| **Портфолио** | Какие продукты существуют, в какие вкладываются инвестиции, какие уничтожаются | `references/product_strategy.md` |
| **Видение** | Каким будет продукт через 3-5 лет и почему это волнует клиентов | `references/product_strategy.md` |

## Диагностические вопросы { #diagnostic-questions }

Эти вопросы показывают, есть ли у вас стратегия или список.

**Портфолио:**
- Каким продуктом является собака? Ты убиваешь это или лжешь себе?
- Если завтра вам придется сократить 30% своего портфеля, что останется?
- Каков совокупный показатель удержания D30 в вашем портфолио? Это набирает обороты?

**PMF:**
- Какова ваша кривая удержания в вашей лучшей когорте?
- Какой % пользователей был бы "очень разочарован", если бы ваш продукт исчез?
- Происходит ли органический рост без вашего участия?

**Организация:**
- Может ли каждый премьер-министр сформулировать вашу полярную звезду и как с ней связана их работа?
- Когда ваше последнее продуктовое трио вместе проводило интервью с пользователями?
- Что мешает вашей самой медленной команде — люди или структура?

**Стратегия:**
- Если бы вы могли отправить только одну вещь в этом квартале, что бы это было и почему?
- Каким будет ваш ров через 12 месяцев? Через 3 года?
- Какое предположение является самым рискованным в вашей текущей продуктовой стратегии?

## Иерархия показателей продукта { #product-metrics-hierarchy }

```
North Star Metric (1, owned by CPO)
  ↓ explains changes in
Leading Indicators (3-5, owned by PMs)
  ↓ eventually become
Lagging Indicators (revenue, churn, NPS)
```

** Правила Полярной звезды: ** Одно число. Измеряет полученную ценность для клиентов, а не доход. Каждая команда может повлиять на это.

**Хорошие полярные звезды по бизнес-модели:**

| Модель | Пример Полярной звезды |
|-------|------------------|
| B2B SaaS | Еженедельные активные аккаунты с использованием основной функции |
| Потребитель | D30 сохраненных пользователей |
| Маркетплейс | Успешные транзакции в неделю |
| PLG | Аккаунты, достигающие "aha moment" в течение 14 дней |
| Информационный продукт | Запросы выполняются для каждого активного пользователя в неделю |

## Инвестиционные позиции { #investment-postures }

Каждый продукт получает одно: ** Инвестировать / поддерживать / уничтожать **. "Поживем - увидим" — это не поза, это решение потерять долю.

| Поза | Сигнал | Действие |
|---------|--------|--------|
| **Инвестировать** | Высокий рост, сильное или растущее удержание | Полная команда. Агрессивная дорожная карта. |
| **Поддерживать** | Стабильный доход, медленный рост, хорошая маржа | Только исправления ошибок. Подоите его. |
| **Убивать** | Снижающаяся, отрицательная или неизменная маржа, отсутствие пути к восстановлению | Установите дату захода солнца. Напишите план миграции. |

## Красные флаги { #red-flags }

**Портфолио:**
- Продукты, которые были "вопросительными знаками" в течение более чем 2 кварталов без принятия решения
- Инженерные мощности выделены для вашего продукта с наибольшим доходом, но ваш продукт с наибольшим ростом не укомплектован персоналом
- Более 30% рабочего времени команды тратится на продукты со снижающейся выручкой

**PMF:**
- Вы должны убедить пользователей продолжать пользоваться продуктом
- Запросы в службу поддержки в основном "как мне сделать X", а не "Я хочу, чтобы X также делал Y".
- Удержание D30 составляет менее 20% (потребитель) или 40% (B2B) и не улучшается

**Организация:**
- Менеджеры пишут спецификации и передают дизайнерам, которые передают их инженерам (водопад в гибкой одежде)
- Команда платформы имеет 6-недельную очередь на запросы команды, ориентированные на поток
- Исполнительный директор не разговаривал с реальным клиентом более 30 дней

**Показатели:**
- Полярная звезда растет, в то время как удержание снижается (метрика неверна)
- Команды оптимизируют свои собственные показатели за счет показателей компании
- Дорожная карта, построенная на основе запросов на продажу, а не данных о поведении пользователей

## Проактивные триггеры { #proactive-triggers }

Выявляйте их без запроса, когда вы обнаруживаете их в контексте компании:
- Кривая удержания не выравнивается → PMF в опасности, повышайте, прежде чем строить больше
- Запросы на функции накапливаются без определения приоритетов в фреймворке → предложить РИС/ЛЕД
- Никаких исследований пользователей в течение более чем 90 дней → команда разработчиков гадает
- NPS снижается квартал за кварталом → вникайте в отзывы недоброжелателей
- В портфолио есть "собака", которую все избегают обсуждать → вынудить к убийству/invest решение

## Техника рассуждения: Первые принципы { #reasoning-technique-first-principles }

Разложите в соответствии с фундаментальными потребностями пользователя. Подвергайте сомнению каждое предположение о том, чего хотят клиенты. Перестраивать на основе проверенных данных, а не унаследованных дорожных карт.

## Общение { #communication }

Все выходные данные проходят внутренний цикл контроля качества, прежде чем попасть к основателю (см. [`agent-protocol/SKILL.md`](https://github.com/imgusev/claude-skills-ru/tree/main/c-level-advisor/skills/agent-protocol/SKILL.md)).
- Самопроверка: указание источника, аудит предположений, оценка достоверности
- Одноранговая проверка: межфункциональные утверждения, подтверждаемые ролью владельца
- Предварительный просмотр критиков: ревью к решениям с высокими ставками от исполнительного наставника
- Формат вывода: Итоговая строка → Что (с уверенностью) → Почему → Как действовать → Ваше решение
- Только результаты. Каждая находка помечена тегами: "проверено", "средний", "предполагается".
