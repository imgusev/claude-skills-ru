Руководство стратегическими инженерными операциями для вице-президентов стартапов и основателей без такового. **Четыре решения, никаких общих инженерных изысканий:**

1. **Обеспечиваем ли мы правильную пропускную способность?** — Показатели DORA 4 + выявление узких мест (где работа ждет своего часа)
2. ** Как мы масштабируем воронку найма в Англии?** — математика воронки + разрыв в пайплайне + дисциплина, требующая времени для заполнения
3. ** Какова структура нашей команды — и когда мы добавим технического руководителя?** - дизайн отряда/племени/главы + менеджер—триггер
4. ** Какова наша производственная дисциплина?** — ротация по вызову, частота развертывания, культура вскрытия (только для справки)

Этот скилл не относится к скиллу технического директора **. Технический директор владеет *тем, что строить* (архитектура, масштабирование скал, "строить против покупки"). VPE владеет *методами надежной доставки* (доставка, наем, структура команды, производственные операции). На ранней стадии это часто один и тот же человек; в масштабе это разные роли.

Этот скилл ** НЕ является заменой cs-engineering-lead**. Ведущий инженер отвечает за повседневную координацию инцидентов и действий по вызову. VPE владеет операционной моделью, которую реализует ведущий инженер.

## Ключевые вопросы (задайте их в первую очередь) { #key-questions-ask-these-first }

- ** Каково время вашего цикла и где работа проводит большую часть времени в ожидании?** (Если вы не знаете, вы не сможете улучшить это).
- ** Сколько времени проходит от принятия решения до производства?** (DORA "время подготовки к изменениям" — лучший показатель общего состояния команды.)
- ** Каков процент выхода? ** (Ошибки, обнаруженные в процессе производства, по сравнению с ошибками, обнаруженными в CI/staging. > 15% = нарушена дисциплина качества.)
- **Когда менеджер eng в последний раз писал код?** (соотношение менеджеров и IC неверно, если менеджеры вообще не могут ревью кода.)
- ** Какова конверсия воронки найма на каждом этапе?** (Источник → экран → на месте → предложение → принять. Утечка - вот ответ на этот вопрос.)
- ** Какова ротация по вызову и кто в ней участвует?** (Если всегда вызываются одни и те же 3 человека, операционная модель нарушена.)

## Основные обязанности { #core-responsibilities }

### 1. Пропускная способность доставки (показатели DORA) { #1-delivery-throughput-dora-metrics }

** Фреймворк:** 4 ключевых показателя Google DORA (из "Accelerate", Форсгрен /Хамбл/Ким, 2018).

| Метрика | Что он измеряет | Элита | Высокий | Средний | Низкий |
|---|---|---|---|---|---|
| **Частота развертывания** | Как часто код достигает prod | Несколько раз в день | Ежедневно-еженедельно | Еженедельно-ежемесячно | < ежемесячно |
| **Время, необходимое для внесения изменений** | Фиксация → производство | < 1 час | 1 день-1 неделя | 1 неделя-1 месяц | > 1 месяц |
| **Среднее время до восстановления (MTTR)** | Обнаружение инцидента → устранено | < 1 час | < 1 день | 1-7 дней | > 7 дней |
| **Изменение частоты отказов** | % от числа деплою, приводящих к инцидентам | 0-15% | 16-30% | 16-45% | 46-60% |

**Выявление узких мест — где ожидает работа?**

Время цикла = (создание PR → первый ревью) + (ревью → утверждение) + (утверждение → слияние) + (слияние → депло). Самый длинный сегмент - это узкое место.

Распространенные узкие места:
- ** Очередь на ревью PR ** (ожидание рецензентов-людей) — исправлено: ротация рецензентов + SLA
- ** Неустойчивость теста ** (CI периодически выходит из строя, требуется повторный запуск) — исправлено: неустойчивый бюджет тестирования + карантин
- **Деплей гейтов** (ручное утверждение, панель управления изменениями) - исправлено: прогрессивная доставка + фич—флаги
- ** Миграция базы данных** (блокировка, запланированные окна) — исправлено: шаблоны миграции с нулевым временем простоя

**Запуск** `delivery_throughput_analyzer.py` с данными спринта, чтобы получить вердикт DORA + верхнее узкое место.

Видишь `references/delivery_throughput.md` для получения полной информации о фреймворке DORA, анти-шаблонах и о том, что нужно исправить в первую очередь.

### 2. Воронка найма инженеров { #2-engineering-hiring-funnel }

** Ловушка: ** "Мы не можем найти хороших инженеров".

Реальность: воронка состоит из 4-6 этапов, каждый из которых имеет свой коэффициент конверсии. Найдите, какая ступень наиболее негерметична; исправьте ее. "Не удается найти хороших инженеров" обычно означает, что объем работы в верхней части воронки слишком мал или критерии отбора неверны.

**Стандартные этапы воронки:**

| Стадия | Здоровое преобразование | Что он измеряет |
|---|---|---|
| Применено → Экран источника | 30-50% | Качество резюме |
| Источник → Экран рекрутера | 50-70% | Базовая посадка |
| Рекрутер → Менеджер по найму | 60-80% | Соответствие требованиям команды |
| Менеджер по найму → Техническое собеседование | 70-85% | Техническая база |
| Техническое обслуживание → на месте (полный цикл) | 30-50% | Техническая глубина |
| На месте → Предложение | 25-40% | Окончательный вариант "идти"/"не идти" |
| Предложение → Принять | 70-90% | Комп + строгая дисциплина |

** Математика воронки: ** чтобы нанять N инженеров, вам нужно N / (произведение всех коэффициентов конверсии) кандидатов в верхней части воронки.

Пример: требуется 4 сотрудника × 100 кандидатов на каждом этапе (при условии 30% × 60% × 70% × 75% × 40% × 35% × 80% = ~0.7% сквозной) = ~570 кандидатов в верхней части воронки.

**Запуск** `eng_hiring_funnel_calculator.py` с данными воронки для расчета конверсии на каждом этапе, времени заполнения и промежутка между пайплайнами.

Видишь `references/engineering_hiring_funnel.md` для полного фреймворка воронки, общих точек утечки и диверсификации каналов поставок.

### 3. Структура инженерной команды { #3-engineering-team-structure }

** Правильный вопрос: ** "Как нам организовать людей, чтобы они могли отправлять заказы без накладных расходов на координацию?"

** Трехосевая модель (адаптирована из Spotify, доработана с учетом реальности):**

- ** Команда: ** небольшая автономная команда (5-9 инженеров), полностью владеющая сервисной или продуктовой областью.
- ** Глава:** функциональная дисциплина, охватывающая все подразделения (бэкенд—глава, фронтенд-глава и т.д.) - для развития скилла, а не для владения
- **Племя:** группа связанных отрядов, работающих над достижением общей цели (например, "племя платформы" = 3 отряда на infra)

**Когда эволюционировать:**

| Стадия | Структура |
|---|---|
| 1-5 инженеров | Одна команда. Никакой структуры. |
| 6-15 инженеров | 2-3 неформальных группы по основным направлениям работы. Основатель-технический директор по-прежнему может знать всех. |
| 16-40 инженеров | 4-6 отрядов. Первый нанятый менеджер по английскому языку. Появляется структура глав для выравнивания скилла между отрядами. |
| 41-100 инженеров | 2-3 племени (скопления отрядов). Директор инженерного отдела. Главы носят формальный характер. |
| более 100 инженеров | Несколько племен + групповой администратор /директор для каждого племени. Вице-президент + директор(ы) + EMS + технические руководители. |

**Менеджер- пороговые значения триггера:**
- 5-7 ICS без менеджера = первый наем EM (или внутреннее продвижение по службе)
- 3+ EMS без директора = наем директора
- 8+ команд в одном племени = разделение племени

**Запуск** `eng_team_structure_designer.py` с профилем команды для рекомендации структуры + менеджер-триггер.

Видишь `references/eng_team_structure.md` для получения полной информации о фреймворке, последствиях закона Конвея и разделении EM-vs-tech-lead.

### 4. Производственная дисциплина { #4-production-discipline }

Производственная дисциплина - это операционная модель, которая позволяет команде спать спокойно. Четыре столпа:

- **Ротация по вызову: ** достаточно широкая, чтобы избежать выгорания (≥ 6 человек на смену; первичный + вторичный персонал)
- **Реагирование на инциденты: ** Рансбуки, определения степени тяжести, безупречные вскрытия
- ** Частота развертывания: ** непрерывное развертывание ИЛИ запланированные выпуски; оба варианта работают; неожиданные выпуски - нет
- ** Дисциплина SLO:** каждая служба, работающая с клиентами, имеет задокументированные бюджеты SLO + ошибок (в сочетании с `engineering/slo-architect/`)

Видишь `references/production_discipline.md` для полной операционной модели.

## Воркфлоу { #workflows }

### Воркфлоу 1: Ревью состояния доставки ежеквартально (4 часа) { #workflow-1-quarterly-delivery-health-review-4-hours }
**Цель:** Диагностика пропускной способности + выявление главного узкого места.

```bash
# 1. Pull sprint metrics: deployment frequency, lead time, MTTR, change failure rate
python ../../skills/vpe-advisor/scripts/delivery_throughput_analyzer.py sprint_metrics.json
# 2. Review DORA verdict per metric
# 3. Identify top bottleneck (longest wait stage)
# 4. Cross-check with cs-cto-advisor on architectural causes
# 5. Output: 90-day fix plan with one bottleneck owned by one engineer
# 6. Log via /cs:decide
```

### Воркфлоу 2: Диагностика воронки найма (1 день) { #workflow-2-hiring-funnel-diagnosis-1-day }
** Цель:** Определить утечку в воронке + рассчитать разрыв в пайплайне для цели найма.

```bash
# 1. Pull funnel data from ATS for last 90 days
python ../../skills/vpe-advisor/scripts/eng_hiring_funnel_calculator.py funnel.json
# 2. Identify weakest conversion stage
# 3. Compute pipeline volume needed for next quarter's hiring target
# 4. Cross-check with cs-chro-advisor on comp/leveling competitiveness
# 5. Cross-check with cs-cfo-advisor on cost-per-hire envelope
# 6. Output: top-3 fixes + sourcing channel diversification plan
```

### Воркфлоу 3: Аудит структуры команды (1 день) { #workflow-3-team-structure-audit-1-day }
** Цель:** Подтвердить, что структура команды соответствует численности персонала + рабочим потокам.

```bash
# 1. Build team.json: headcount, work streams, manager count, IC distribution
python ../../skills/vpe-advisor/scripts/eng_team_structure_designer.py team.json
# 2. Check manager-trigger thresholds (5-7 IC rule)
# 3. Identify squad sizes outside 5-9 range
# 4. Cross-check with cs-cto-advisor on Conway's Law alignment
# 5. Output: structure recommendations + manager hire plan
```

### Воркфлоу 4: Аудит производственной дисциплины (1 неделя) { #workflow-4-production-discipline-audit-1-week }
**Цель:** Подтвердить, что операционная модель может масштабироваться за счет текущего роста.

1. Инвентаризация: охват по вызову, частота инцидентов в разбивке по степени тяжести, тенденция MTTR
2. Убедитесь, что у каждой службы, работающей с клиентами, есть SLO (сопряжение с `engineering/slo-architect/`)
3. Ревью последние 5 вскрытий — безупречны ли они? Закрыты ли элементы действия?
4. Перепроверьте частоту развертывания с вердиктом DORA
5. Результат: оценка зрелости производственной дисциплины + 90-дневный план совершенствования
