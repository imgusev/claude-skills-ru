## Обзор { #overview }

### Что делает этот Скилл { #what-this-skill-does }

Этот скилл предоставляет методологию и инструменты для ** проактивного обнаружения угроз** — определения активности злоумышленника с помощью структурированных гипотез поиска, анализа IOC и обнаружения статистических аномалий до срабатывания оповещений.

### Отличие от других Скилл по обеспечению безопасности { #distinction-from-other-security-skills }

| Скилл | Сосредоточься | Подход |
|-------|-------|----------|
| **обнаружение угроз** (это) | Поиск скрытых угроз | Упреждающий поиск перед предупреждениями |
| реагирование на инцидент | Активные инциденты | Реагирование — сдерживание и расследование заявленных инцидентов |
| красная команда | Имитация наступления | Наступление — проверка защиты с точки зрения атакующего |
| облачная безопасность | Неправильные настройки облака | Положение — IAM, S3, доступ к сети |

### Предварительные условия { #prerequisites }

Доступ на чтение к телеметрии SIEM/EDR, журналам конечных точек и данным сетевого потока. Корма IOC должны быть свежими в течение 30 дней, чтобы избежать ложноположительных результатов. Поисковые гипотезы должны быть привязаны к среде перед выполнением.

## Анализатор сигналов угрозы { #threat-signal-analyzer }

Тот `threat_signal_analyzer.py` инструмент поддерживает три режима: `hunt` (оценка гипотез), `ioc` (генерация развертки), и `anomaly` (статистическое обнаружение).

```bash
# Hunt mode: score a hypothesis against MITRE ATT&CK coverage
python3 scripts/threat_signal_analyzer.py --mode hunt \
  --hypothesis "Lateral movement via PtH using compromised service account" \
  --actor-relevance 3 --control-gap 2 --data-availability 2 --json

# IOC mode: generate sweep targets from an IOC feed file
python3 scripts/threat_signal_analyzer.py --mode ioc \
  --ioc-file iocs.json --json

# Anomaly mode: detect statistical outliers in telemetry events
python3 scripts/threat_signal_analyzer.py --mode anomaly \
  --events-file telemetry.json \
  --baseline-mean 100 --baseline-std 25 --json

# List all supported MITRE ATT&CK techniques
python3 scripts/threat_signal_analyzer.py --list-techniques
```

### Формат файла IOC { #ioc-file-format }

```json
{
  "ips": ["1.2.3.4", "5.6.7.8"],
  "domains": ["malicious.example.com"],
  "hashes": ["abc123def456..."]
}
```

### Формат файла событий телеметрии { #telemetry-events-file-format }

```json
[
  {"timestamp": "2024-01-15T14:32:00Z", "entity": "host-01", "action": "dns_query", "volume": 450},
  {"timestamp": "2024-01-15T14:33:00Z", "entity": "host-02", "action": "dns_query", "volume": 95}
]
```

### Коды выхода { #exit-codes }

| Код | Значение |
|------|---------|
| 0 | Никаких высокоприоритетных выводов |
| 1 | Обнаружены сигналы среднего приоритета |
| 2 | Подтвержденные выводы с высоким приоритетом |

## Методология поиска угроз { #threat-hunting-methodology }

Структурированный поиск угроз осуществляется по пятиэтапному циклу: гипотеза → идентификация источника данных → выполнение запроса → сортировка результатов поиска → обратная связь с инженерами обнаружения.

### Оценка гипотез { #hypothesis-scoring }

| Фактор | Вес | Описание |
|--------|--------|-------------|
| Значимость актера | ×3 | Насколько точно этот TTP соответствует известным субъектам угроз в вашем секторе? |
| Контрольный зазор | ×2 | Сколько из ваших существующих элементов управления пропустили бы такое поведение? |
| Доступность данных | ×1 | Есть ли у вас телеметрические данные, необходимые для проверки этой гипотезы? |

Оценка приоритета = (actor_relevance × 3) + (control_gap × 2) + (data_availability × 1)

### Ценные гипотезы поиска с помощью тактики { #high-value-hunt-hypotheses-by-tactic }

| Гипотеза | ИДЕНТИФИКАТОР МИТРЫ | Источники данных | Сигнал приоритета |
|-----------|----------|--------------|-----------------|
| Боковое перемещение WMI с помощью удаленного выполнения | T1047 | Журналы WMI, телеметрия процесса EDR | Процесс WMI, созданный из WINRM, необычная цепочка "родитель-потомок" |
| Казнь Лолбина за уклонение от обороны | T1218 | Создание процесса, аргументы команд-строки | certutil.exe , regsvr32.exe , mshta.exe с сетевой активностью |
| Подача сигнала C2 с помощью интервалов с высоким уровнем дрожания | T1071.001 | Журналы прокси-серверов, журналы DNS | Исходящие соединения с регулярными интервалами ±10% дрожания |
| Боковое движение при передаче хэша | T1550.002 | Событие безопасности Windows 4624 тип 3 | Авторизация NTLM с неожиданного исходного хоста на общий доступ администратора |
| Доступ к памяти LSASS | T1003.001 | События доступа к памяти EDR | Откройте процесс на lsass.exe из несистемного процесса |
| Разгон по керберу | T1558.003 | Событие Windows 4769 | Большой объем запросов TGS для учетных записей служб |
| Сохранение запланированной задачи | T1053.005 | Системное событие 1/11, Windows 4698 | Запланированная задача, созданная в нестандартном каталоге |

## Анализ МОК { #ioc-analysis }

Анализ IOC определяет, являются ли индикаторы свежими, сопоставляет их с требуемыми целевыми показателями проверки и фильтрует устаревшие данные, которые генерируют ложноположительные результаты.

### Типы IOC и приоритет развертки { #ioc-types-and-sweep-priority }

| Тип IOC | Порог затхлости | Цель зачистки | УГЛОВОЕ покрытие |
|---------|--------------------|--------------|----|
| IP-адреса | 30 дней | Журналы брандмауэра, NetFlow, прокси-сервера | T1071, T1105 |
| Домены | 30 дней | Журналы распознавателя DNS, журналы прокси-сервера | T1568, T1583 |
| Хэши файлов | 90 дней | Создание EDR-файла, журналы AV-сканирования | T1105, T1027 |
| URL-адреса | 14 дней | Журналы доступа к прокси-серверу, история браузера | T1566.002 |
| Имена мьютексов | 180 дней | Артефакты среды выполнения EDR | T1055 |

### Обработка застоя IOC { #ioc-staleness-handling }

IOC, возраст которых превышает их пороговое значение, помечаются как `stale` и исключен из генерации цели развертки. Проведение проверок устаревших IOC приводит к увеличению числа ложноположительных результатов и снижает доверие к SOC. Обновляйте каналы IOC с платформ анализа угроз (MISP, OpenCTI, commercial TI) перед каждым циклом поиска.

## Обнаружение аномалий { #anomaly-detection }

Обнаружение статистических аномалий выявляет поведение, которое отклоняется от установленных базовых показателей, не полагаясь на заведомо неверные сигнатуры.

### Пороговые значения Z-баллов { #z-score-thresholds }

| Z-Оценка | Классификация | Ответ |
|---------|---------------|----------|
| < 2.0 | Нормальный | Никаких действий не требуется |
| 2.0–2.9 | Мягкая аномалия | Регистрируйте и контролируйте — увеличивайте выборку |
| ≥ 3.0 | Жесткая аномалия | Эскалация до поиска аналитика — объекта расследования |

### Базовые требования { #baseline-requirements }

Для эффективного обнаружения аномалий требуется не менее 14 дней телеметрии за прошлые периоды, чтобы установить достоверную базовую линию. Исходные показатели должны быть пересчитаны после:
- Инциденты безопасности (изменение поведения после инцидента)
- Основные изменения в инфраструктуре (миграция в облако, новые развертывания SaaS)
- Сезонные изменения в структуре использования (конец квартала, праздничные периоды)

### Высокоценные цели-аномалии { #high-value-anomaly-targets }

| Тип объекта | Метрика | Индикатор аномалии |
|-------------|--------|--------------------|
| Распознаватель DNS | Количество запросов в час на один хост | Установка маяков, прокладка туннелей, DGA |
| Конечная точка | Выполнение уникальных процессов в день | Установка вредоносного ПО, злоупотребление LOLBin |
| Учетная запись службы | Авторизация событий в час | Заполнение учетных данных, боковое перемещение |
| Шлюз электронной почты | Типы насадок в час | Всплеск фишинговой кампании |
| Облачный ЯМ | Вызовы API для каждого идентификатора в час | Компрометация учетных данных, эксфильтрация |

## Приоритезация сигналов MITRE ATT&CK { #mitre-attck-signal-prioritization }

Каждая гипотеза поиска соотносится с одним или несколькими методами ATT&CK. Методы с несколькими подтвержденными сигналами в вашей среде имеют более высокий приоритет.

### Матрица тактического охвата { #tactic-coverage-matrix }

| Тактика | Ключевые методы | Первичный источник данных |
|--------|---------------|--------------------|-|
| Первоначальный доступ | T1190, T1566, T1078 | Журналы веб-доступа, шлюз электронной почты, журналы авторизации |
| Исполнение | T1059, T1047, T1218 | Создание процесса, команда-строка, выполнение скрипта |
| Настойчивость | T1053, T1543, T1098 | Запланированные задачи, службы, изменения учетной записи |
| Уклонение от защиты | T1027, T1562, T1070 | Выдалбливание процесса, очистка журнала, кодирование |
| Доступ с использованием учетных данных | T1003, T1558, T1110 | Сбои LSASS, Kerberos, аутентификации |
| Боковое перемещение | T1550, T1021, T1534 | Авторизация NTLM, удаленные службы, внутренний spearphish |
| Коллекция | T1074, T1560, T1114 | Промежуточные каталоги, создание архива, доступ к электронной почте |
| Эксфильтрация | T1048, T1041, T1567 | Необычный исходящий объем, туннелирование DNS, облачное хранилище |
| Команда и контроль | T1071, T1572, T1568 | Маячок, туннелирование по протоколу, DNS C2 |

## Интеграция обмана и приманки { #deception-and-honeypot-integration }

Средства обмана генерируют высокоточные оповещения - любое взаимодействие с приманкой является недвусмысленным сигналом, требующим расследования.

### Типы активов для обмана и их размещение { #deception-asset-types-and-placement }

| Тип актива | Размещение | Сигнал | Техника ATT&CK |
|-----------|-----------|--------|-----------------|
| Учетные данные Honeypot в хранилище паролей | Хранилище секретов хранилища | Попытка доступа к учетным данным | T1555 |
| Токены Honey (поддельные ключи доступа AWS) | Git-репозитории, объекты S3 | Разведка или эксфильтрация | T1552.004 |
| Файлы Honey (названные: passwords.xlsx ) | Общие файловые ресурсы, конечные точки | Постановка коллекции | T1074 |
| Учетные записи Honey (неактивные пользователи рекламы) | Активный каталог | Ось бокового перемещения | T1078.002 |
| Сетевые сервисы Honeypot | Демилитаризованная зона, сегменты плоской сети | Сканирование сети, эксплуатация сервиса | T1046, T1190 |

Оповещения Honeypot обходят стандартный пайплайн подсчета очков — любое попадание автоматически засчитывается как SEV2, пока не доказано обратное.

## Воркфлоу { #workflows }

### Воркфлоу 1: Быстрая охота (30 минут) { #workflow-1-quick-hunt-30-minutes }

Для реагирования на новый отчет об аналитической информации об угрозах или предупреждение о CVE:

```bash
# 1. Score hypothesis against environment context
python3 scripts/threat_signal_analyzer.py --mode hunt \
  --hypothesis "Exploitation of CVE-YYYY-NNNNN in Apache" \
  --actor-relevance 2 --control-gap 3 --data-availability 2 --json

# 2. Build IOC sweep list from threat intel
echo '{"ips": ["1.2.3.4"], "domains": ["malicious.tld"], "hashes": []}' > iocs.json
python3 scripts/threat_signal_analyzer.py --mode ioc --ioc-file iocs.json --json

# 3. Check for anomalies in web server telemetry from last 24h
python3 scripts/threat_signal_analyzer.py --mode anomaly \
  --events-file web_events_24h.json --baseline-mean 80 --baseline-std 20 --json
```

**Решение**: Если приоритет поиска ≥ 7 или какая-либо проверка IOC сработает, эскалация до полной охоты.

### Воркфлоу 2: Полный поиск угроз (многодневный) { #workflow-2-full-threat-hunt-multi-day }

**День 1 — Выработка гипотезы:**
1. Ревью аналитических данных об угрозах для ТТП, относящихся к сектору
2. Сопоставьте предупреждения о безопасности за последние 30 дней с тактикой ATT&CK, чтобы выявить пробелы
3. Оцените топ-5 гипотез с помощью threat_signal_analyzer.py режим охоты
4. Расставляйте приоритеты по баллам — начинайте с самого высокого

**День 2 — Сбор данных и выполнение запроса:**
1. Извлеките соответствующую телеметрию из SIEM (диапазон дат: последние 14 дней)
2. Запустите обнаружение аномалий по базовым линиям объектов
3. Выполните проверку IOC на наличие всех свежих кормов в течение 30 дней
4. Ревью плейбуков для охоты в `references/hunt-playbooks.md`

**День 3 — Сортировка и отчетность:**
1. Сортируйте все обнаруженные аномалии — подтверждайте или отклоняйте
2. Эскалация подтвержденной активности до уровня реагирования на инцидент
3. Документируйте новые правила обнаружения на основе результатов охоты
4. Отправляйте ложноположительные IOCS обратно поставщику TI

### Воркфлоу 3: Непрерывный мониторинг (автоматизированный) { #workflow-3-continuous-monitoring-automated }

Настройте обнаружение повторяющихся аномалий по базовым показателям ключевых объектов с 6-часовой периодичностью:

```bash
# Run as cron job every 6 hours — auto-escalate on exit code 2
python3 scripts/threat_signal_analyzer.py --mode anomaly \
  --events-file /var/log/telemetry/events_6h.json \
  --baseline-mean "${BASELINE_MEAN}" \
  --baseline-std "${BASELINE_STD}" \
  --json > /var/log/threat-detection/$(date +%Y%m%d_%H%M%S).json

# Alert on exit code 2 (hard anomaly)
if [ $? -eq 2 ]; then
  send_alert "Hard anomaly detected — threat_signal_analyzer"
fi
```

## Анти-паттерны { #anti-patterns }

1. ** Поиск без гипотезы** — Выполнение широких запросов по всей телеметрии без целенаправленного вопроса генерирует шум, а не сигнал. Каждая охота должна начинаться с проверяемой гипотезы, охватывающей один или два метода ATT&CK.
2. **Использование устаревших IOCs** — IOCs старше 30 дней генерируют ложные срабатывания, которые приучают аналитиков игнорировать предупреждения. Всегда проверяйте свежесть IOC перед подметанием; исключите индикаторы несвежести из автоматических подметаний.
3. **Пропуск установления базовой линии** — Обнаружение аномалий без действительной базовой линии приводит к появлению предупреждений в обычные дни большого объема. Требуется более 14 дней исходных данных, прежде чем включать статистическое оповещение для любого типа объектов.
4. ** Охота только на известные приемы** — Охота исключительно на задокументированные приемы ATT &CK не учитывает новое поведение противника. Регулярно включайте открытый анализ аномалий, который может выявить неизвестные TTP.
5. ** Не замыкать цикл обратной связи для разработки средств обнаружения** — Результаты поиска, подтверждающие вредоносное поведение, должны создавать новые правила обнаружения. Охота, которая не улучшает охват обнаружения, не имеет долговременной ценности.
6. ** Рассматривать каждую аномалию как подтвержденную угрозу** — Высокие z-баллы указывают на отклонение от исходного уровня, а не на подтвержденный злой умысел. Все аномалии требуют сортировки человеком для подтверждения или отклонения перед эскалацией.
7. ** Игнорирование предупреждений honeypot** — Любое взаимодействие с объектом обмана является высокоточным сигналом. Рассмотрение предупреждений honeypot как шума сводит на нет все инвестиции в обман.
