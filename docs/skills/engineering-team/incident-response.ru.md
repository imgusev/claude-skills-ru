## Обзор { #overview }

### Что делает этот Скилл { #what-this-skill-does }

Этот скилл предоставляет методологию и инструменты для ** сортировки инцидентов и реагирования на них** — классификации событий безопасности по типизированным инцидентам, оценки степени серьезности, фильтрации ложных срабатываний, определения путей эскалации и инициирования сбора криминалистических доказательств в рамках контроля цепочки поставок.

### Отличие от других Скилл по обеспечению безопасности { #distinction-from-other-security-skills }

| Скилл | Сосредоточься | Подход |
|-------|-------|----------|
| **инцидент-реагирование** (это) | Активные инциденты | Реагирование — классификация, эскалация, сбор доказательств |
| обнаружение угроз | Охота до инцидента | Упреждающий — обнаружение угроз до срабатывания оповещений |
| облачная безопасность | Оценка положения облаков | Профилактика — IAM, S3, неправильная настройка сети |
| красная команда | Имитация наступления | Способность к обнаружению наступательных испытаний и реагированию |

### Предварительные условия { #prerequisites }

Перед сортировкой необходимо принять меры безопасности. События могут поступать из предупреждений SIEM, обнаружений EDR, информационных каналов об угрозах или пользовательских отчетов. Инструмент сортировки принимает полезную нагрузку событий JSON; смотрите схему ввода ниже.

## Инструмент для сортировки инцидентов { #incident-triage-tool }

Тот `incident_triage.py` инструмент классифицирует события, проверяет ложные срабатывания, оценивает степень серьезности, определяет эскалацию и выполняет предварительный судебно-медицинский анализ.

```bash
# Classify an event from JSON file
python3 scripts/incident_triage.py --input event.json --classify --json

# Classify with false positive filtering enabled
python3 scripts/incident_triage.py --input event.json --classify --false-positive-check --json

# Force a severity level for tabletop exercises
python3 scripts/incident_triage.py --input event.json --severity sev1 --json

# Read event from stdin
echo '{"event_type": "ransomware", "host": "prod-db-01", "raw_payload": {}}' | \
  python3 scripts/incident_triage.py --classify --false-positive-check --json
```

### Схема входного события { #input-event-schema }

```json
{
  "event_type": "ransomware",
  "host": "prod-db-01",
  "user": "svc_backup",
  "source_ip": "10.1.2.3",
  "timestamp": "2024-01-15T14:32:00Z",
  "raw_payload": {}
}
```

### Коды выхода { #exit-codes }

| Код | Значение | Требуемый ответ |
|------|---------|-------------------|
| 0 | SEV3/SEV4 или чистый | Стандартная обработка на основе билетов |
| 1 | SEV2 — повышенный | 1-часовой вызов по мостику, асинхронная координация |
| 2 | SEV1 — критический | Немедленная 15-минутная боевая рубка, все в сборе |

## Классификация инцидентов { #incident-classification }

События безопасности классифицируются по 14 типам инцидентов. Классификация определяет степень серьезности по умолчанию, сопоставление методов MITRE и SLA для реагирования.

### Таксономия инцидентов { #incident-taxonomy }

| Тип Инцидента | Серьезность по умолчанию | Техника МИТРЫ | Соглашение об уровне обслуживания в ответ |
|--------------|-----------------|-----------------|--------------|
| программа-вымогатель | СЕВ1 | T1486 | 15 минут |
| фильтрация данных | СЕВ1 | T1048 | 15 минут |
| apt_интрузия | СЕВ1 | T1566 | 15 минут |
| поставка_цепи_компрометации | СЕВ1 | T1195 | 15 минут |
| domain_controller_breach | СЕВ1 | T1078.002 | 15 минут |
| учетные данные_компрометируют | СЕВ2 | T1110 | 1 час |
| боковое движение | СЕВ2 | T1021 | 1 час |
| заражение вредоносной программой | СЕВ2 | T1204 | 1 час |
| внутренняя угроза | СЕВ2 | T1078 | 1 час |
| cloud_account_compromise облачный аккаунт | СЕВ2 | T1078.004 | 1 час |
| несанкционированный доступ | СЕВ3 | T1190 | 4 часа |
| политика_нарушения | СЕВ3 | Н/Д | 4 часа |
| фишинговая попытка | СЕВ4 | T1566.001 | 24 часа |
| предупреждение о безопасности | СЕВ4 | Н/Д | 24 часа |

### Триггеры для эскалации SEV { #sev-escalation-triggers }

Любое из следующих действий автоматически повторно объявляет более высокий уровень серьезности:

| Триггер | Новая суровость |
|---------|-------------|
| Найдена заметка о программе-вымогателе | СЕВ1 |
| Подтверждена активная эксфильтрация | СЕВ1 |
| Отключен CloudTrail или SIEM | СЕВ1 |
| Доступ к контроллеру домена подтвержден | СЕВ1 |
| Вторая система скомпрометирована | СЕВ1 |
| Объем эксфильтрации превышает 1 ГБ | Минимум SEV2 |
| Доступ к учетной записи C-suite | Минимум SEV2 |

## Фреймворк для определения степени серьезности { #severity-framework }

### Матрица седьмого уровня { #sev-level-matrix }

| Уровень | Имя | Критерии | Вызываемые скиллы | Путь эскалации |
|-------|------|----------|---------------|-----------------|
| СЕВ1 | Критический | Подтвержденная программа-вымогатель; активная эксфильтрация PII/PHI (>10 тыс. записей); взлом контроллера домена; уклонение от защиты (CloudTrail отключен); компрометация цепочки поставок | Все скиллы (параллельные) | Руководитель SOC → CISO → Генеральный директор → Председатель правления |
| СЕВ2 | Высокий | Подтвержден несанкционированный доступ к конфиденциальным системам; компрометация учетных данных с повышенными привилегиями; подтверждено боковое перемещение; индикаторы программ-вымогателей без подтвержденного выполнения | сортировка + изоляция + судебно-медицинская экспертиза | Лидер SOC → CISO |
| СЕВ3 | Средний | Подозрение на несанкционированный доступ (неподтвержденный); вредоносное ПО обнаружено и локализовано; компрометация одной учетной записи (без эскалации конфиденциальности) | сортировка + сдерживание | Руководитель SOC → Менеджер по безопасности |
| СЕВ4 | Низкий | Предупреждение системы безопасности без подтвержденного воздействия; информационный индикатор; нарушение политики без риска для данных | только сортировка | Очередь аналитиков L3 |

## Фильтрация ложноположительных результатов { #false-positive-filtering }

Инструмент сортировки применяет пять фильтров перед эскалацией, чтобы предотвратить ложноположительное повышение.

### Типы ложноположительных фильтров { #false-positive-filter-types }

| Фильтр | Описание | Пример шаблона |
|--------|-------------|----------------|
| Активность агента CI/CD | Известные агенты по сборке/деплою, помеченные как аномалии | дженкинс, github-действия, circleci, gitlab-runner |
| Маркировка тестовой среды | Активы, помеченные как непроизводственные | тестирование, промежуточная обработка, разработка, песочница- |
| Запланированные схемы выполнения заданий | Ожидаемые пакетные процессы, вызывающие предупреждения о триггерах | cron, scheduled_task, пакетное задание, резервное копирование_ |
| Личности, занесенные в белый список | Явно одобренные учетные записи служб | svc_monitoring, svc_backup, datadog-агент |
| Активность сканера | Известные сканеры безопасности и средства защиты от уязвимостей | nessus, qualys, rapid7, aws_inspector |

Подтвержденный ложноположительный результат подавляет эскалацию и регистрирует причину подавления для целей аудита. Повторяющиеся ложные срабатывания из одного и того же источника следует отключать на уровне обнаружения, а не повторно фильтровать при сортировке.

## Сбор судебно-медицинских доказательств { #forensic-evidence-collection }

Сбор доказательств осуществляется в соответствии с шестиэтапной фреймворком DFRWS и принципом сбора данных в первую очередь.

### DFRWS проходит шесть этапов { #dfrws-six-phases }

| Фаза | Деятельность | Приоритет |
|-------|----------|----------|
| Идентификация | Определите, какие доказательства существуют и где | Немедленный |
| Сохранение | Предотвращение модификации — блокировка записи, моментальный снимок, законное удержание | Немедленный |
| Коллекция | Собирайте доказательства в порядке изменчивости | Немедленный |
| Обследование | Технический анализ собранных доказательств | В течение 2 часов |
| Анализ | Интерпретировать полученные результаты в контексте расследования | В течение 4 часов |
| Презентация | Подготовьте отчет о результатах с использованием цепочки поставок | До закрытия инцидента |

### Изменчивые доказательства — Соберите в первую очередь { #volatile-evidence--collect-first }

1. Оперативная память (дамп оперативной памяти) — теряется при перезагрузке
2. Запущенные процессы и открытые сетевые подключения (`netstat`, `ps`)
3. Вошедшие в систему пользователи и активные сеансы
4. Время безотказной работы системы и текущее время (для привязки к временной шкале)
5. Переменные окружения и загруженные модули ядра

### Требования к цепочке поставок { #chain-of-custody-requirements }

Каждое вещественное доказательство должно быть зафиксировано с:
- Хэш SHA-256 во время получения
- Временная метка получения в UTC со смещением часового пояса
- Происхождение инструмента (FTK Imager, Volatility, dd, экспорт AWS CloudTrail)
- Личность исследователя
- Журнал передачи (у кого была опека и когда)

## Пути эскалации { #escalation-paths }

### По степени тяжести { #by-severity }

| Серьезность | Немедленный контакт | Вызов на мостик | Внешнее уведомление |
|----------|------------------|-------------|----------------------|
| СЕВ1 | Руководство SOC + CISO (15 мин) | Непосредственная боевая рубка | Правовой режим + режим PR в режиме ожидания; уведомление регулирующих органов в соответствии с таблицей крайних сроков |
| СЕВ2 | Вывод SOC (30 мин асинхронно) | 1-часовой мост | Юридическое уведомление, если задействованы личные данные |
| СЕВ3 | Менеджер по безопасности (4 часа) | Только асинхронный | Нет, если область действия не расширяется |
| СЕВ4 | Очередь аналитиков L3 (24 часа) | Нет | Нет |

### По типу Инцидента { #by-incident-type }

| Тип Инцидента | Первичная эскалация | Вторичный |
|--------------|-------------------|-----------|
| Программа-вымогатель / APT | CISO + генеральный директор | Совет директоров, если данные находятся под угрозой |
| Нарушение PII/PHI | Юридический + CISO | Регулирующий орган (согласно таблице крайних сроков) |
| Компрометация облачной учетной записи | Команда облачной безопасности | CISO |
| Внутренняя угроза | Отдел кадров + юриспруденция + CISO | Правоохранительные органы, если преступник |
| Цепочка поставок | CISO + Управление поставщиками | Доска |

## Обязательства по уведомлению регулирующих органов { #regulatory-notification-obligations }

Отсчет времени уведомления начинается с момента объявления о инциденте, а не с завершения расследования.

| Фреймворк | Тип Инцидента | Крайний срок | Штраф |
|-----------|--------------|----------|---------|
| GDPR (ЕС 2016/679) | Нарушение персональных данных | через 72 часа после обнаружения | До 4% мирового дохода |
| PCI-DSS v4.0 | Утечка данных о владельце карты | 24 часа до получения | Штрафы за бренд карты |
| HIPAA (45 CFR 164) | Нарушение PHI (>500 человек) | через 60 дней после обнаружения | До 1,9 млн долларов за каждую категорию нарушений |
| NY DFS 23 NYCRR 500 | Мероприятие по кибербезопасности | 72 часа до DFS | Нормативные санкции |
| Правило SEC (17 CFR 229.106) | Существенный инцидент в области кибербезопасности | через 4 рабочих дня после определения существенности | Обеспечение соблюдения правил SEC |
| CCPA / CPRA | Нарушение конфиденциальных данных | Без необоснованных задержек | Принудительное исполнение закона; частное право на иск |
| NIS2 (ЕС 2022/2555) | Значительный инцидент (основные службы) | 24-часовое раннее предупреждение; 72-часовое уведомление | Санкции национальных властей |

** Оперативное правило: ** Если область применения неясна при объявлении, используйте наиболее ограничительный применимый крайний срок и подтвердите область применения в течение первого окна ответа.

Ссылка на полный крайний срок: `references/regulatory-deadlines.md`

## Воркфлоу { #workflows }

### Воркфлоу 1: Быстрая сортировка (15 минут) { #workflow-1-quick-triage-15-minutes }

Для одиночного предупреждения, требующего классификации перед принятием решения об эскалации:

```bash
# 1. Classify the event with false positive filtering
python3 scripts/incident_triage.py --input alert.json \
  --classify --false-positive-check --json

# 2. Review severity, escalation_path, and false_positive_flag in output
# 3. If severity = sev1 or sev2, page SOC Lead immediately
# 4. If false_positive_flag = true, document and close
```

**Решение**: Код выхода 2 = боевая комната SEV1 сейчас. Код выхода 1 = вызов на мост SEV2 в течение 30 минут.

### Воркфлоу 2: Полное реагирование на инцидент (SEV1) { #workflow-2-full-incident-response-sev1 }

```
T+0   Detection arrives (SIEM alert, EDR, user report)
T+5   Classify with incident_triage.py --classify --false-positive-check
T+10  If SEV1: page CISO, open war room, start regulatory clock
T+15  Initiate forensic collection (volatile evidence first)
T+15  Containment assessment (parallel with forensics)
T+30  Human approval gate for any containment action
T+45  Execute approved containment
T+60  Assess containment effectiveness, brief Legal if PII/PHI scope
T+4h  Final forensic evidence package, dwell time estimate
T+8h  Eradication and recovery plan
T+72h Regulatory notification submission (if GDPR/NIS2 triggered)
```

```bash
# Full classification with forensic context
python3 scripts/incident_triage.py --input incident.json \
  --classify --false-positive-check --severity sev1 --json > incident_triage_output.json

# Forensic pre-analysis
python3 scripts/incident_triage.py --input incident.json --json | \
  jq '.forensic_findings, .chain_of_custody_steps'
```

### Воркфлоу 3: Имитация настольных упражнений { #workflow-3-tabletop-exercise-simulation }

Имитировать инциденты с определенными уровнями серьезности без учета реальных событий:

```bash
# Simulate SEV1 ransomware incident
echo '{"event_type": "ransomware", "host": "prod-db-01", "user": "svc_backup"}' | \
  python3 scripts/incident_triage.py --classify --severity sev1 --json

# Simulate SEV2 credential compromise
echo '{"event_type": "credential_compromise", "user": "admin_user", "source_ip": "203.0.113.5"}' | \
  python3 scripts/incident_triage.py --classify --false-positive-check --json

# Verify escalation paths for all 14 incident types
for type in ransomware data_exfiltration credential_compromise lateral_movement; do
  echo "{\"event_type\": \"$type\"}" | python3 scripts/incident_triage.py --classify --json
done
```

## Анти-паттерны { #anti-patterns }

1. ** Запуск часов уведомления по завершении расследования ** — Нормативные часы (GDPR 72 часа, PCI 24 часа) начинаются с момента обнаружения, а не завершения расследования. Опоздание с объявлением влечет за собой максимальное наказание для организации, даже если сам инцидент был незначительным.
2. **Хранение перед сбором изменчивых данных** — Перезагрузка или изоляция системы приводит к уничтожению оперативной памяти, запущенных процессов и активных подключений. Судебно-медицинский сбор летучих улик должен осуществляться параллельно с локализацией, но ни в коем случае после нее.
3. **Пропуск проверки с ложным срабатыванием перед эскалацией** — эскалация каждого предупреждения до SEV1 снижает доверие к SOC и вызывает усталость от оповещений. Всегда запускайте фильтры ложноположительных результатов перед вызовом CISO.
4. **Недокументированные решения команды по инциденту** — Каждое решение, принятое в ходе SEV1, включая решения, принятые в условиях неопределенности, должно быть занесено в цепочку доказательств с отметкой времени и обоснованием. Недокументированные решения не могут быть защищены в ходе расследований регулирующих органов.
5. **Рассматривать закрытие инцидента как завершение расследования** — инциденты закрываются после завершения ликвидации и восстановления, а не после завершения расследования. Подготовка отчета судебно-медицинской экспертизы и нормативных документов может быть продолжена после завершения операционной деятельности.
6. **Классификация по одному источнику** - Классификация инцидента по одному источнику данных (одно предупреждение SIEM) без подтверждающих доказательств часто приводит к неправильной классификации. Соберите по крайней мере два независимых сигнала, прежде чем объявлять SEV1.
7. ** Обход гейтов для локализации, одобренных человеком** — Автоматизированные действия по локализации (изоляция сети, отзыв учетных данных), предпринятые без одобрения человека, могут привести к перебоям в производстве, уничтожению доказательств и возникновению ответственности. Одобрение человека не подлежит обсуждению в отношении всех действий по сдерживанию мутаций.
