### Основные инструменты { #core-tools }

```bash
# Generate pipeline orchestration config
python scripts/pipeline_orchestrator.py generate \
  --type airflow \
  --source postgres \
  --destination snowflake \
  --schedule "0 5 * * *"

# Validate data quality
python scripts/data_quality_validator.py validate \
  --input data/sales.parquet \
  --schema schemas/sales.json \
  --checks freshness,completeness,uniqueness

# Optimize ETL performance
python scripts/etl_performance_optimizer.py analyze \
  --query queries/daily_aggregation.sql \
  --engine spark \
  --recommend
```

## Фреймворк архитектурных решений { #architecture-decision-framework }

Используйте этот фреймворк, чтобы выбрать правильный подход для вашего пайплайна данных.

### Пакетная передача против потоковой { #batch-vs-streaming }

| Критерии | Партия | Потоковое вещание |
|----------|-------|-----------|
| **Требование к задержке** | От часов до дней | Секунды превращаются в минуты |
| **Объем данных** | Большие исторические наборы данных | Непрерывные потоки событий |
| **Сложность обработки** | Сложные преобразования, МЛ | Простые агрегации, фильтрация |
| **Чувствительность к затратам** | Более экономичный | Более высокие затраты на инфраструктуру |
| **Обработка ошибок** | Легче поддается повторной обработке | Требует тщательного проектирования |

**Дерево решений:**
```
Is real-time insight required?
├── Yes → Use streaming
│   └── Is exactly-once semantics needed?
│       ├── Yes → Kafka + Flink/Spark Structured Streaming
│       └── No → Kafka + consumer groups
└── No → Use batch
    └── Is data volume > 1TB daily?
        ├── Yes → Spark/Databricks
        └── No → dbt + warehouse compute
```

### Архитектура Lambda vs Kappa { #lambda-vs-kappa-architecture }

| Аспект | Лямбда | Каппа |
|--------|--------|-------|
| **Сложность** | Две кодовые базы (пакетная + потоковая) | Единая кодовая база |
| **Техническое обслуживание** | Выше (логика пакетной/потоковой синхронизации) | Более низкий |
| **Переработка** | Собственный пакетный слой | Воспроизведение из исходного кода |
| **Вариант использования** | Обучение ML + подача в режиме реального времени | Чисто управляемый событиями |

**Когда выбирать Лямбда:**
- Необходимость обучения ML-моделей на исторических данных
- Сложные пакетные преобразования невозможны при потоковой передаче
- Существующая пакетная инфраструктура

**Когда выбирать Kappa:**
- Архитектура, основанная на событиях
- Вся обработка может быть выражена в виде потоковых операций
- Начинать все сначала без устаревших систем

### Хранилище данных против Data Lakehouse { #data-warehouse-vs-data-lakehouse }

| Особенность | Склад (Snowflake/BigQuery) | Домик на озере (Дельта/Айсберг) |
|---------|-------------------------------|---------------------------|
| **Лучше всего подходит для** | BI, SQL-аналитика | ML, неструктурированные данные |
| **Стоимость хранения** | Более высокий (проприетарный формат) | Нижний (открытые форматы) |
| **Гибкость** | Схема при записи | Схема-при-чтении |
| **Производительность** | Отлично подходит для SQL | Хороший, улучшающийся |
| **Экосистема** | Зрелые инструменты BI | Инструмент для выращивания ML |
