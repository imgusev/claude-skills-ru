Систематически проводите ревью тестовых файлов Драматурга на предмет наличия антишаблонов, пропущенных рекомендаций и пробелов в охвате.

## Входной сигнал { #input }

`$ARGUMENTS` может быть:
- Путь к файлу: ревью к этому конкретному тестовому файлу
- Каталог: ревью все тестовые файлы в каталоге
- Пусто: ревью все тесты в проекте `testDir`

## Шаги { #steps }

### 1. Соберите контекст { #1-gather-context }

- Читать `playwright.config.ts` для настройки проекта
- Перечислите все `*.spec.ts` / `*.spec.js` файлы в области видимости
- При ревью отдельного файла также проверьте связанные объекты страницы и приспособления

### 2. Проверьте каждый файл на наличие Анти-Шаблонов { #2-check-each-file-against-anti-patterns }

Нагрузка `anti-patterns.md` из этого справочника по скиллам. Проверьте наличие всех 20 анти-паттернов.

**Критический (необходимо исправить):**
1. `waitForTimeout()` использование
2. Утверждения, не относящиеся к web-first (`expect(await ...)`)
3. Жестко закодированные URL-адреса вместо `baseURL`
4. Селекторы CSS/XPath при существовании на основе ролей
5. Пропавший без вести `await` о вызовах драматурга
6. Общее изменяемое состояние между тестами
7. Зависимости от порядка выполнения теста

**Предупреждение (должно быть исправлено):**
8. Тесты длиннее 50 строк (рассмотрите возможность разделения)
9. Магические строки без именованных констант
10. Пропущенная ошибка/edge тематические тесты
11. `page.evaluate()` для того, что могут делать локаторы
12. Вложенный `test.describe()` глубина более 2 уровней
13. Общие названия тестов ("должно сработать", "тест 1")

**Информация (рассмотреть):**
14. Нет объектов страницы для страниц с более чем 5 локаторами
15. Встроенные тестовые данные вместо заводских/fixture
16. Отсутствующие утверждения о доступности
17. Отсутствие визуальных регрессионных тестов для страниц с большим количеством пользовательского интерфейса
18. Утверждения об ошибках консоли не проверены
19. Ожидания простоя сети вместо конкретных утверждений
20. Пропавший без вести `test.describe()` группировка

### 3. Оцените каждый файл { #3-score-each-file }

Оцените 1-10 в зависимости от:
- **9-10**: Готов к производству, соблюдает все золотые правила
- **7-8**: Хорошо, возможны незначительные улучшения
- **5-6**: Функционален, но имеет анти-паттерны
- **3-4**: Существенные проблемы, вероятно, шелушащиеся
- **1-2**: Требуется переписать

### 4. Сгенерируйте отчет о ревью { #4-generate-review-report }

Для каждого файла:
```
## <filename> — Score: X/10

### Critical
- Line 15: `waitForTimeout(2000)` → use `expect(locator).toBeVisible()`
- Line 28: CSS selector `.btn-submit` → `getByRole('button', { name: "submit" })`

### Warning
- Line 42: Test name "test login" → "should redirect to dashboard after login"

### Suggestions
- Consider adding error case: what happens with invalid credentials?
```

### 5. Для ревью в рамках всего проекта { #5-for-project-wide-review }

При ревью всего набора тестов:
- Запуск саб-агентов для каждого файла для параллельного ревью (до 5 одновременных)
- Или использовать `/batch` для очень больших апартаментов
- Сведите результаты в сводную таблицу

### 6. Предлагайте исправления { #6-offer-fixes }

Для каждой критической проблемы укажите исправленный код. Спросите пользователя: "Применить эти исправления? [Да/нет]"

Если да, примените все исправления с помощью `Edit` инструмент.

## Выход { #output }

- Ревью файла за файлом с оценками
- Сводка: общее количество файлов, средний балл, количество критических проблем
- Список исправлений, подлежащих действию
- Выявленные пробелы в охвате (страницы/features без каких-либо тестов)
