Диагностируйте и исправьте тест драматурга, который не прошел или проходит с перерывами, используя систематическую таксономию.

## Входной сигнал { #input }

`$ARGUMENTS` содержит:
- Путь к тестовому файлу: `e2e/login.spec.ts`
- Тестовое имя: ""должно перенаправляться после входа в систему"`
- Описание: `"the checkout test fails in CI but passes locally"`

## Шаги { #steps }

### 1. Воспроизведите сбой { #1-reproduce-the-failure }

Запустите тест, чтобы зафиксировать ошибку:

```bash
npx playwright test <file> --reporter=list
```

Если тест пройден, то, скорее всего, он шелушащийся. Запуск выгорания:

```bash
npx playwright test <file> --repeat-each=10 --reporter=list
```

Если это все еще проходит, попробуйте с параллельными рабочими:

```bash
npx playwright test --fully-parallel --workers=4 --repeat-each=5
```

### 2. Захват трассировки { #2-capture-trace }

Запуск с полной трассировкой:

```bash
npx playwright test <file> --trace=on --retries=0
```

Прочитайте выходные данные трассировки. Использование `/debug` для анализа файлов трассировки, если таковые имеются.

### 3. Классифицируйте неудачу { #3-categorize-the-failure }

Нагрузка `flaky-taxonomy.md` из этого справочника по скиллам.

Каждый проваленный тест относится к одной из четырех категорий:

| Категория | Симптом | Диагностика |
|---|---|---|
| **Синхронизация/асинхронность** | Периодически происходит сбой везде | `--repeat-each=20` размножается локально |
| **Тестовая изоляция** | Терпит неудачу в номере люкс, проходит в одиночку | `--workers=1 --grep "test name"` проходит |
| **Окружающая среда** | Сбой в CI, проходит локально | Сравните скриншоты CI и local/traces |
| **Инфраструктура** | Случайный, без закономерности | Ошибка ссылается на внутренние компоненты браузера |

### 4. Примените целевое исправление { #4-apply-targeted-fix }

**Синхронизация/асинхронность:**
- Заменить `waitForTimeout()` с помощью веб-первых утверждений
- Добавить `await` на звонки пропавшего драматурга
- Дождитесь конкретных ответов сети, прежде чем утверждать
- Использование `toBeVisible()` перед взаимодействием с элементами

**Тестовая изоляция:**
- Удалить общее изменяемое состояние между тестами
- Создавайте тестовые данные для каждого теста с помощью API или приспособлений
- Используйте уникальные идентификаторы (временные метки, случайные строки) для тестовых данных
- Проверьте, нет ли утечек состояния базы данных

**Окружающая среда:**
- Сопоставьте размеры видового экрана между локальным и CI
- Учитывайте различия в отображении шрифтов на скриншотах
- Использование `docker` локально, чтобы соответствовать среде CI
- Проверьте утверждения, зависящие от часового пояса

**Инфраструктура:**
- Увеличьте время ожидания для медленных пользователей CI
- Добавьте повторные попытки в конфигурацию CI (`retries: 2`)
- Проверьте наличие OOM в браузере (уменьшите количество параллельных рабочих процессов)
- Убедитесь, что установлены зависимости от браузера

### 5. Проверьте исправление { #5-verify-the-fix }

Запустите тест 10 раз, чтобы подтвердить стабильность:

```bash
npx playwright test <file> --repeat-each=10 --reporter=list
```

Все 10 должны пройти. Если что-либо не сработает, вернитесь к шагу 3.

### 6. Предотвратите повторение { #6-prevent-recurrence }

Предложить:
- Добавить в CI с помощью `retries: 2` если еще не сделали
- Включить `trace: 'on-first-retry'` в конфигурации
- Добавьте шаблон исправления в документ о тестовых соглашениях проекта

## Выход { #output }

- Категория первопричины и конкретная проблема
- Примененное исправление (с разницей)
- Результат проверки (10/10 проходов)
- Рекомендация по профилактике
