## Обзор { #overview }

Используйте этот скилл для перемещения промптов из специальных черновиков в производственные ресурсы с возможностью повторного тестирования, управления версиями и безопасности регрессии. Это делает акцент на измеримом качестве, а не на интуиции. Применяйте его при запуске новой функции LLM, требующей надежных выходных данных, когда качество промптов ухудшается после изменения модели или инструкции, когда несколько членов команды редактируют промпты и им нужна история/diffs, когда вам нужен основанный на фактических данных выбор промпта для раскатки на производстве или когда вам требуется согласованное управление промптом в разных средах.

## Основные возможности { #core-capabilities }

- Промпт-оценка A/B на основе структурированных тестовых примеров
- Количественная оценка за соблюдение требований, актуальность и проверки безопасности
- Отслеживание версий промпта с неизменяемой историей и списком изменений
- Промпт различий для ревью изменений, влияющих на поведение
- Многоразовые шаблоны промптов и рекомендации по выбору
- Воркфлоу для модели, ориентированный на регрессию/prompt обновления

## Ключевые Воркфлоу { #key-workflows }

### 1. Запустите Промпт A/B-тест { #1-run-prompt-ab-test }

Подготовьте тестовые примеры JSON и запустите:

```bash
python3 scripts/prompt_tester.py \
  --prompt-a-file prompts/a.txt \
  --prompt-b-file prompts/b.txt \
  --cases-file testcases.json \
  --runner-cmd 'my-llm-cli --prompt {prompt} --input {input}' \
  --format text
```

Входные данные также могут поступать из stdin/`--input` Полезная нагрузка в формате JSON.

### 2. Выберите Победителя с помощью Доказательств { #2-choose-winner-with-evidence }

Тестировщик оценивает выходные данные по каждому случаю и суммирует их:

- ожидаемый охват контента
- нарушения, связанные с запрещенным контентом
- регулярное выражение/format соответствие требованиям
- допустимая длина выходного сигнала

Используйте промпт с более высокой оценкой в качестве потенциальной базовой линии, затем запустите regression suite.

### 3. Промпт версии { #3-version-prompts }

```bash
# Add version
python3 scripts/prompt_versioner.py add \
  --name support_classifier \
  --prompt-file prompts/support_v3.txt \
  --author alice

# Diff versions
python3 scripts/prompt_versioner.py diff --name support_classifier --from-version 2 --to-version 3

# Changelog
python3 scripts/prompt_versioner.py changelog --name support_classifier
```

### 4. Цикл регрессии { #4-regression-loop }

1. Сохраните базовую версию.
2. Предлагайте промпт-правки.
3. Повторно запустите A/B-тест.
4. Продвигайте только в том случае, если оценка и ограничения по безопасности улучшатся.

## Интерфейсы сценариев { #script-interfaces }

- `python3 scripts/prompt_tester.py --help`
  - Считывает промпты/cases из stdin или `--input`
  - Дополнительная команда внешнего исполнителя
  - Генерирует текстовые или JSON-метрики
- `python3 scripts/prompt_versioner.py --help`
  - Управляет историей промптов (`add`, `list`, `diff`, `changelog`)
  - Хранит метаданные и моментальные снимки содержимого локально

## Подводные камни, лучшие практики и чек-лист для ревью ( Review Review { #pitfalls-best-practices--review-checklist }

**Избегайте этих ошибок:**
1. Выбор промптов из выходных данных для одного случая - используйте реалистичный набор тестов с расширенными возможностями.
2. Одновременное изменение промпта и модели — всегда изолируйте переменные.
3. Пропавший без вести `must_not_contain` (запрещенный контент) проверяется по критериям оценки.
4. Редактирование промптов без метаданных версии, автора или обоснования изменений.
5. Пропуск семантических различий перед деплою новой версии промпта.
6. Оптимизация одного бенчмарка при одновременном нанесении ущерба крайним случаям — отслеживайте весь набор.
7. Замена модели без повторного запуска базового набора A/B.

**Прежде чем продвигать какую-либо промпту, подтвердите:**
- [ ] Цель задачи является явной и недвусмысленной.
- [ ] Схема вывода/format является явным.
- [ ] Ограничения безопасности и исключения являются явными.
- [ ] Никаких противоречивых инструкций.
- [ ] Никаких ненужных знаков многословия.
- [ ] Оценка A/B улучшается, а количество нарушений остается на нулевом уровне.

## Дизайн оценки { #evaluation-design }

Каждый тестовый пример должен определять:

- `input`: реалистичные производственные данные
- `expected_contains`: необходимые маркеры/content
- `forbidden_contains`: запрещенные фразы или небезопасный контент
- `expected_regex`: требуемые структурные модели

Это позволяет детерминированно оценивать варианты промптов.

## Политика управления версиями { #versioning-policy }

- Используйте идентификаторы семантических промптов для каждой функции (`support_classifier`, `ad_copy_shortform`).
- Автор записи + примечание об изменении для каждой редакции.
- Никогда не перезаписывайте исторические версии.
- Diff перед запуском нового промпта в производство.

## Стратегия раскатки { #rollout-strategy }

1. Создайте базовую версию промпта.
2. Предложите промпт кандидата.
3. Запустите пакет A/B для тех же случаев.
4. Продвигайте только в том случае, если победитель улучшит среднее значение и сохранит количество нарушений на нулевом уровне.
5. Отслеживайте отзывы после выпуска и добавляйте новые случаи сбоев обратно в набор тестов.
