## Инструменты анализа и их использование { #analysis-tools--usage }

### 1. Анализатор скорости (`scripts/velocity_analyzer.py`) { #1-velocity-analyzer-scriptsvelocity_analyzerpy }

Использует скользящие средние, определение тренда с помощью линейной регрессии и моделирование методом Монте-Карло по истории спринта.

```bash
# Text report
python velocity_analyzer.py sprint_data.json --format text

# JSON output for downstream processing
python velocity_analyzer.py sprint_data.json --format json > analysis.json
```

**Выходные данные**: тренд скорости (улучшающийся/стабильный/снижающийся), коэффициент вариации, прогноз на 6 спринтов по методу Монте-Карло на 50 / 70 / 85 / 95 % доверительных интервалов, флаги аномалий с предложениями о первопричинах.

**Проверка**: Если во входных данных присутствует менее 3 спринтов, остановитесь и промпт пользователя: * "Для анализа скорости требуется как минимум 3 спринта. Пожалуйста, предоставьте дополнительные данные о спринте".* Для получения статистически значимых результатов по методу Монте-Карло рекомендуется провести более 6 спринтов.

---

### 2. Показатель здоровья в спринте (`scripts/sprint_health_scorer.py`) { #2-sprint-health-scorer-scriptssprint_health_scorerpy }

Оценивает здоровье команды по 6 взвешенным параметрам, получая общую оценку от 0 до 100 баллов.

| Измерение | Вес | Цель |
|---|---|---|
| Приверженность и надежность | 25% | >85% целей в спринте выполнены |
| Стабильность области применения | 20% | <15% изменений в середине спринта |
| Разрешение блокировщика | 15% | в среднем <3 дней |
| Церемония помолвки | 15% | >90% участников |
| Распределение по завершению истории | 15% | Высокий процент полностью завершенных историй |
| Предсказуемость скорости | 10% | CV <20% |

```bash
python sprint_health_scorer.py sprint_data.json --format text
```

**Результаты**: общий показатель состояния здоровья + оценка, баллы по каждому измерению с рекомендациями, тенденция к спринту за спринтом, матрица приоритетов вмешательства.

** Проверка**: Требуется более 2-х спринтов с данными о церемонии и завершении истории. Если данные отсутствуют, сообщите, какие измерения не могут быть оценены, и попросите пользователя указать пробелы.

---

### 3. Анализатор ретроспективы (`scripts/retrospective_analyzer.py`) { #3-retrospective-analyzer-scriptsretrospective_analyzerpy }

Отслеживает выполнение действий, повторяющиеся темы, тенденции настроений и прогресс зрелости команды.

```bash
python retrospective_analyzer.py sprint_data.json --format text
```

** Результаты **: процент выполнения действий по приоритету/владельцу, показатели постоянства повторяющейся темы, уровень зрелости команды (формирование / штурм / нормирование / выполнение), тенденция к скорости улучшения.

** Проверка**: Требуется более 3 ретроспективы с отслеживанием действий по элементам. Если их меньше, обратите внимание на ограничение и предлагайте только частичный анализ темы.

## Входные требования { #input-requirements }

Все скрипты принимают JSON, следуя схеме в `assets/sample_sprint_data.json`:

```json
{
  "team_info": { "name": "string", "size": "number", "scrum_master": "string" },
  "sprints": [
    {
      "sprint_number": "number",
      "planned_points": "number",
      "completed_points": "number",
      "stories": [...],
      "blockers": [...],
      "ceremonies": {...}
    }
  ],
  "retrospectives": [
    {
      "sprint_number": "number",
      "went_well": ["string"],
      "to_improve": ["string"],
      "action_items": [...]
    }
  ]
}
```

Jira и аналогичные инструменты могут экспортировать данные спринта; сопоставьте экспортированные поля с этой схемой перед запуском скриптов. Видишь `assets/sample_sprint_data.json` для полного примера из 6 спринтов и `assets/expected_output.json` для получения соответствующих ожидаемых результатов (средняя скорость 20,2 балла, CV 12,7%, показатель здоровья 78,3/100, выполнение действия-пункта 46,7%).

## Спринт-выполнение воркфлоу { #sprint-execution-workflows }

### Планирование спринта { #sprint-planning }

1. Анализ скорости выполнения: `python velocity_analyzer.py sprint_data.json --format text`
2. Используйте 70%-ный доверительный интервал в качестве рекомендуемого верхнего предела обязательств для невыполненной работы в спринте.
3. Проведите ревью по показателям надежности обязательств и стабильности сферы применения, чтобы согласовать их с владельцем продукта.
4. Если результаты по методу Монте-Карло показывают высокую волатильность (CV >20%), доведите это до сведения стейкхолдеров с помощью оценок диапазона, а не одноточечных прогнозов.
5. Задокументируйте допущения о пропускной способности (отпуск, зависимости) для сравнения в ретроспективе.

### Ежедневный стендап { #daily-standup }

1. Отслеживайте схемы участия и обращения за помощью - вводите данные о церемониях в `sprint_health_scorer.py` в конце спринта.
2. Регистрируйте каждый блокиратор с указанием даты открытия; время разрешения определяет измерение разрешения блокиратора.
3. Если блокировка не устранена по истечении 2 дней, проведите эскалацию в упреждающем порядке и внесите это в данные спринта.

### Ревью к спринту { #sprint-review }

1. Представьте тенденцию скорости и оценку работоспособности вместе с демонстрацией, чтобы предоставить стейкхолдерам контекст реализации.
2. Фиксируйте запросы на изменение области, возникшие во время ревью; записывайте как события изменения области в данные спринта для следующего цикла подсчета очков.

### Ретроспектива спринта { #sprint-retrospective }

1. Запустите все три скрипта перед началом сеанса:
   ```bash
   python sprint_health_scorer.py sprint_data.json --format text > health.txt
   python retrospective_analyzer.py sprint_data.json --format text > retro.txt
   ```
2. Начните с оценки состояния здоровья и отмеченных сверху параметров, чтобы сфокусировать обсуждение.
3. Используйте показатель выполнения действий-элементов анализатора ретроспективы, чтобы определить, сколько новых действий-элементов команда реально может освоить (цель: ≤3, если показатель выполнения <60%).
4. Назначьте каждому элементу действия владельца и измеримый критерий успеха перед закрытием сеанса.
5. Записывайте новые элементы действий в `sprint_data.json` для отслеживания в следующем цикле.

## Воркфлоу командной разработки { #team-development-workflow }

### Оценка { #assessment }

```bash
python sprint_health_scorer.py team_data.json > health_assessment.txt
python retrospective_analyzer.py team_data.json > retro_insights.txt
```

- Сопоставьте выходные данные анализатора зрелости ретроспективы с соответствующей стадией разработки.
- Дополните анонимным опросом "Пульс психологической безопасности" (7-балльная шкала Эдмондсона) и индивидуальными наблюдениями в соотношении 1:1.
- Если результат зрелости равен `forming` или `storming`, уделяйте приоритетное внимание мерам по обеспечению безопасности и разрешению конфликтов перед оптимизацией процесса.

### Вмешательство { #intervention }

Применяйте фасилитацию для конкретного этапа (подробности в `references/team-dynamics-framework.md`):

| Стадия | Сосредоточься |
|---|---|
| Формирование | Структура, обучение процессу, укрепление доверия |
| Штурмующий | Облегчение конфликтов, поддержание психологической безопасности |
| Нормирование | Создание автономии, передача права собственности на процесс |
| Выполняющий | Внедрение сложных задач, поддержка инноваций |

### Измерение прогресса { #progress-measurement }

- ** Частота спринта**: повторно запустите показатель здоровья; планируйте улучшение общего балла на ≥5 баллов за квартал.
- **Ежемесячно**: опрос "Пульс психологической безопасности"; цель >4,0/5,0.
- **Ежеквартально**: повторная оценка полной зрелости с помощью анализатора ретроспективы.
- Если показатели стабилизируются или регрессируют в течение 2 последовательных спринтов, примените стратегию эскалации вмешательства (см. `references/team-dynamics-framework.md`).

## Ключевые показатели и целевые показатели { #key-metrics--targets }

| Метрика | Цель |
|---|---|
| Общий показатель состояния здоровья | >80/100 |
| Индекс психологической безопасности | >4.0/5.0 |
| Скорость CV (предсказуемость) | <20% |
| Приверженность и надежность | >85% |
| Стабильность области применения | <15% изменений в середине спринта |
| Время разрешения блокировки | <3 дней |
| Церемония помолвки | >90% |
| Завершение действия ретроспективы | >70% |

## Ограничения { #limitations }

- **Размер выборки**: менее 6 спринтов снижают достоверность по методу Монте-Карло; всегда указывайте доверительные интервалы, а не точечные оценки.
- ** Полнота данных**: отсутствующие поля "Церемония" или "завершение истории" подавляют затронутые параметры оценки - явно сообщайте о пробелах.
- **Чувствительность к контексту**: рекомендации скрипта должны интерпретироваться наряду с организационным и командным контекстом, не отраженным в данных JSON.
- **Количественный уклон**: показатели не заменяют качественное наблюдение; сочетайте оценки с непосредственным взаимодействием команды.
- ** Размер команды**: методы оптимизированы для команд из 5-9 человек; для больших групп может потребоваться адаптация.
- **Внешние факторы**: межкомандные зависимости и организационные ограничения не полностью моделируются показателями одной команды.
