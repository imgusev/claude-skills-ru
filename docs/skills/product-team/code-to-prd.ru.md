## Имя { #name }

Код → PRD

## Описание { #description }

Преобразуйте любую интерфейсную, серверную или fullstack-кодовую базу в полный документ требований к продукту (PRD). Анализирует маршруты, компоненты, модели, API и пользовательские взаимодействия для создания бизнес-читаемой документации, достаточно подробной, чтобы инженеры или агенты искусственного интеллекта могли полностью реконструировать каждую страницу и конечную точку.

# Код → PRD: Реинжиниринг любой кодовой базы в соответствии с требованиями к продукту { #code--prd-reverse-engineer-any-codebase-into-product-requirements }

## Особенности { #features }

- **трехэтапный воркфлоу**: глобальное сканирование → постраничный анализ → генерация структурированного документа
- **Поддержка интерфейса **: React, Vue, Angular, Svelte, Next.js (App + Pages Router), Nuxt, SvelteKit, Remix
- ** Поддержка серверной части **: NestJS, Express, Django, фреймворк Django REST, FastAPI, Flask
- ** Поддержка Fullstack**: Комбинированный анализ интерфейса + серверной части с унифицированным выводом PRD
- ** Обнаружение макета **: Автоматически отличает реальную интеграцию API от макета/fixture данные
- **Извлечение перечисления**: Исчерпывающий список всех кодов состояния, сопоставлений типов и констант
- **Извлечение модели**: Анализирует модели Django, объекты NestJS, схемы Pydantic
- **Сценарии автоматизации**: `codebase_analyzer.py` для сканирования, `prd_scaffolder.py` для создания каталога
- **Чек-лист качества**: Чек-лист проверки полноты, точности, удобочитаемости

## Использование { #usage }

```bash
# Analyze a project and generate PRD skeleton
python3 scripts/codebase_analyzer.py /path/to/project -o analysis.json
python3 scripts/prd_scaffolder.py analysis.json -o prd/ -n "My App"

# Or use the slash command
/code-to-prd /path/to/project
```

## Примеры { #examples }

### Интерфейс (React) { #frontend-react }
```bash
/code-to-prd ./src
# → Scans components, routes, API calls, state management
# → Generates prd/ with per-page docs, enum dictionary, API inventory
```

### Серверная часть (Django) { #backend-django }
```bash
/code-to-prd ./myproject
# → Detects Django via manage.py, scans urls.py, views.py, models.py
# → Documents endpoints, model schemas, admin config, permissions
```

### Полный набор (Next.js ) { #fullstack-nextjs }
```bash
/code-to-prd .
# → Analyzes both app/ pages and api/ routes
# → Generates unified PRD covering UI pages and API endpoints
```

## Роль { #role }

Вы являетесь старшим аналитиком по продуктам и техническим архитектором. Ваша задача состоит в том, чтобы прочитать кодовую базу интерфейса, понять бизнес-назначение каждой страницы и создать полный PRD на ** языке, удобном для менеджера по продукту **.

### Двойная аудитория { #dual-audience }

1. **Менеджеры по продуктам / стейкхолдеры бизнеса** — должны понимать, *что* делает система, а не *как*
2. **Инженерам / агентам искусственного интеллекта** — требуется достаточно деталей, чтобы ** полностью реконструировать ** поля, взаимодействия и взаимосвязи каждой страницы

В вашем документе функциональность должна описываться нетехническим языком, при этом не должно быть никаких бизнес-деталей.

### Поддерживаемые стеки { #supported-stacks }

| Стопка | Фреймворки |
|-------|-----------|
| **Интерфейс** | Реагировать, Vue, Угловатый, стройный, Next.js (Маршрутизатор приложений / страниц), Nuxt, SvelteKit, Remix, Astro |
| **Серверная часть** | NestJS, Express, Fastify, Django, фреймворк Django REST, FastAPI, Flask |
| **Полный пакет** | Next.js (Маршруты API + страницы), Nuxt (сервер/ + страницы/), Django (представления + шаблоны) |

Для проектов **только для серверной части** концепция "страницы" соответствует **группам ресурсов API** или ** представлениям администратора**. Применяется тот же трехэтапный воркфлоу - маршруты становятся конечными точками, компоненты — контроллерами/views, и взаимодействия становятся запросом/response течет.

## Воркфлоу { #workflow }

### Фаза 1 — Глобальное сканирование проекта { #phase-1--project-global-scan }

Создайте глобальный контекст, прежде чем погружаться в страницы.

#### 1. Определите структуру проекта { #1-identify-project-structure }

Просканируйте корневой каталог и разберитесь в организации:

```
Frontend directories:
- Pages/routes (pages/, views/, routes/, app/, src/pages/)
- Components (components/, modules/)
- Route config (router.ts, routes.ts, App.tsx route definitions)
- API/service layer (services/, api/, requests/)
- State management (store/, models/, context/)
- i18n files (locales/, i18n/) — field display names often live here

Backend directories (NestJS):
- Modules (src/modules/, src/*.module.ts)
- Controllers (*.controller.ts) — route handlers
- Services (*.service.ts) — business logic
- DTOs (dto/, *.dto.ts) — request/response shapes
- Entities (entities/, *.entity.ts) — database models
- Guards/pipes/interceptors — auth, validation, transformation

Backend directories (Django):
- Apps (*/apps.py, */views.py, */models.py, */urls.py)
- URL config (urls.py, */urls.py)
- Views (views.py, viewsets.py) — route handlers
- Models (models.py) — database schema
- Serializers (serializers.py) — request/response shapes
- Forms (forms.py) — validation and field definitions
- Templates (templates/) — server-rendered pages
- Admin (admin.py) — admin panel configuration
```

**Определить фреймворк** из `package.json` (Node.js фреймворки) или файлы проекта (`manage.py` для Джанго, `requirements.txt`/`pyproject.toml` для Python). Маршрутизация, шаблоны компонентов и управление состоянием существенно различаются в разных фреймворках — идентификация обеспечивает точный синтаксический анализ.

#### 2. Создайте список маршрутов и страниц { #2-build-route--page-inventory }

Извлеките все страницы из конфигурации маршрута в полный список **страниц**:

| Поле | Описание |
|-------|-------------|
| Путь маршрута | например, `/user/list`, `/order/:id` |
| Заголовок страницы | Из конфигурации маршрута, хлебных крошек или компонента страницы |
| Уровень модуля/ меню | Где он находится в навигации |
| Путь к файлу компонента | Исходные файлы, реализующие эту страницу |

Для маршрутизации в файловой системе (Next.js , Nuxt), выводится из структуры каталогов.

**Для серверных проектов** список страниц становится конечной точкой **/resource инвентарь**:

| Поле | Описание |
|-------|-------------|
| Путь к конечной точке | например, `/api/users`, `/api/orders/:id` |
| HTTP-метод | ПОЛУЧИТЬ, ОПУБЛИКОВАТЬ, ПОМЕСТИТЬ, УДАЛИТЬ, ИСПРАВЛЯТЬ |
| Контроллер/view | Исходный файл, обрабатывающий этот маршрут |
| Модуль/app | Какому модулю NestJS или приложению Django он принадлежит |
| Требуется авторизация | Является ли аутентификация/permissions необходимы |

Для NestJS: выдержка из `@Controller` + `@Get/@Post/@Put/@Delete` декораторы.
Для Django: извлечение из `urls.py` → `urlpatterns` и `viewsets.py` → регистрация маршрутизатора.

#### 3. Отобразите глобальный контекст { #3-map-global-context }

Прежде чем анализировать отдельные страницы, захватите:

- ** Глобальное состояние** — информация о пользователе, разрешения, фич-флаги, конфигурация
- **Общие компоненты** — макет, навигация, защита от аутентификации, границы ошибок
- **Перечисления и константы** — коды состояния, сопоставления типов, определения ролей
- **Базовая конфигурация API** — базовый URL, перехватчики, заголовки аутентификации, обработка ошибок
- **Модели баз данных** (серверная часть) — отношения сущностей, типы полей, ограничения
- **Промежуточное программное обеспечение** (серверная часть) — промежуточное программное обеспечение для аутентификации, ограничение скорости, ведение журнала, CORS
- **DTO/сериализаторы** (серверная часть) — формы проверки запросов, форматы ответов

На них будут ссылки по всей странице/endpoint анализ.

### Этап 2 — Постраничный глубокий анализ { #phase-2--page-by-page-deep-analysis }

Проанализируйте каждую страницу в инвентаре. **Каждая страница создает свой собственный файл Markdown.**

#### Параметры анализа { #analysis-dimensions }

Для каждой страницы ответьте:

##### A. Обзор страницы { #a-page-overview }
- Что делает эта страница? (одно предложение)
- Как это вписывается в систему?
- Какой сценарий приводит пользователя сюда?

##### B. Планировка и регионы { #b-layout--regions }
- Основные регионы: область поиска, таблица, панель сведений, панель действий, вкладки и т.д.
- Пространственное расположение: верхняя часть/bottom, слева/right, вложенный

##### C. Инвентаризация на местах (основная — должна быть исчерпывающей) { #c-field-inventory-core--be-exhaustive }

**Для страниц форм** перечислите все поля:

| Имя поля | Тип | Требуемый | Значение по умолчанию | Проверка подлинности | Описание бизнеса |
|-----------|------|----------|---------|------------|---------------------|
| Имя пользователя | Ввод текста | Да | — | Максимум 20 символов | Учетная запись для входа в систему |

**Для стола/list страницы**, список:
- Поиск/filter поля (тип, обязательные, параметры перечисления)
- Столбцы таблицы (название, формат, возможность сортировки, фильтрации)
- Кнопки действий в строке (что делает каждая из них)

**Приоритет извлечения имени поля:**
1. Жестко запрограммированный текст отображения в коде
2. значения перевода i18n
3. Компонент `placeholder` / `label` / `title` реквизит
4. Имена переменных (в крайнем случае — укажите разумное отображаемое имя)

##### D. Логика взаимодействия { #d-interaction-logic }

Опишите как ** "действие пользователя → реакция системы"**:

```
[Action]     User clicks "Create"
[Response]   Modal opens with form fields: ...
[Validation] Name required, phone format check
[API]        POST /api/user/create with form data
[Success]    Toast "Created successfully", close modal, refresh list
[Failure]    Show API error message
```

**Охватывать все типы взаимодействий:**
- Загрузка / инициализация страницы (запросы по умолчанию, предварительно загруженные данные)
- Поиск / фильтр / сброс
- Операции CRUD (создание, чтение, обновление, удаление)
- Таблица: разбивка на страницы, сортировка, выбор строк, массовые действия
- Отправка и проверка формы
- Переходы статуса (например, потоки утверждений: ожидание → одобрено → отклонено)
- Импорт / экспорт
- Взаимозависимости полей (выбор значения A изменяет параметры в поле B)
- Элементы управления разрешениями (кнопки/fields виден только для определенных ролей)
- Опрос / автоматическое обновление / обновления в режиме реального времени

##### E. Зависимости API { #e-api-dependencies }

**Пример 1: API интегрирован ** (реальные HTTP-вызовы в коде)

| Имя API | Способ | Путь | Триггер | Ключевые параметры | Примечания |
|----------|--------|------|---------|-----------|-------|
| Получить пользователей | ПОЛУЧИТЬ | /api/user/list | Загрузка, поиск | страница, размер, ключевое слово | Разбит на страницы |

**Случай 2: API не интегрирован** (макет/hardcoded данные)

Когда страница использует фиктивные данные, жестко закодированные приспособления, `setTimeout` моделирования, или `Promise.resolve()` заглушки — API еще не создан. **Перепроектируйте требуемую спецификацию API** на основе функциональности страницы и формы данных.

Для каждого необходимого API документируйте:
- Метод, предлагаемый путь, триггер
- Входные параметры (имя, тип, обязательно, описание)
- Выходные поля (название, тип, описание)
- Описание основной бизнес-логики

**Сигналы обнаружения:**
- `setTimeout` / `Promise.resolve()` возвращаемые данные → макет
- Данные, определенные в компоненте или `*.mock.*` файлы → макет
- Реальные HTTP-вызовы (`axios`, `fetch`, уровень обслуживания) с реальными путями → интегрированный
- `__mocks__` каталог → макет

##### F. Взаимосвязи страниц { #f-page-relationships }

- **Входящие**: На какие страницы здесь есть ссылки? Какие параметры они передают?
- **Исходящий**: Куда пользователи могут перейти отсюда? Какие параметры?
- **Связь данных**: Какие страницы совместно используют данные или триггеры обновления друг в друге?

## Ключевые принципы { #key-principles }

### 1. Сначала деловой язык { #1-business-language-first }
Не пишите "звонки `useState` для управления состоянием загрузки." Напишите "кнопка поиска показывает счетчик для предотвращения дублирования отправок".

Не пишите "useEffect извлекает данные при монтировании". Напишите "страница автоматически загружает первую страницу результатов при открытии".

Включайте технические детали только тогда, когда они ** непосредственно влияют на поведение продукта**: пути к API (они нужны инженерам), правила проверки (влияют на UX), условия разрешений (влияют на видимость).

### 2. Не упустите скрытую логику { #2-dont-miss-hidden-logic }
Код содержит логику, о существовании которой PMS может не подозревать:
- Взаимозависимости полей (тип A показывает поле X; тип B показывает поле Y)
- Условная видимость кнопки
- Форматирование данных (валюта с 2 десятичными знаками, форматы дат, сопоставления меток состояния)
- Порядок сортировки и размер страницы по умолчанию
- Разоблачать/throttle влияние на пользовательский ввод
- Интервалы опроса/автоматического обновления

### 3. Исчерпывающий список перечислений { #3-exhaustively-list-enums }
Когда код определяет перечисления (коды состояния, коды типов, типы ролей), перечислите ** каждое значение и его значение**. Они часто разбросаны по файлам констант, компонентам `valueEnum` конфигурации или средства отображения ответов API.

### 4. Отметьте неопределенность — Не гадайте { #4-mark-uncertainty--dont-guess }
Если бизнес-значение поля или логики не может быть определено из кода (например, сокращенные имена переменных, чрезмерно сложные условия), отметьте это `[TBC]` и объясните, что вы наблюдали и почему вы не уверены. Никогда не выдумывайте деловой смысл.

### 5. Сохраняйте файлы подкачки автономными { #5-keep-page-files-self-contained }
Markdown каждой страницы должен быть **автономным** — чтение только этого файла дает полное представление. Используйте относительные ссылки при ссылках на другие страницы или записи приложений.

## Стратегии по набору страниц { #page-type-strategies }

### Интерфейсные страницы { #frontend-pages }

| Тип страницы | Приоритетные области |
|-----------|------------|
| **Список / таблица** | Условия поиска, действия со столбцами, строками, разбивка на страницы, массовые операции |
| **Форма / Создание-Редактирование** | Каждое поле, проверка, взаимозависимости, поведение после отправки |
| **Подробная информация / Просмотр** | Отображаемая информация, вкладка/section организация, доступные действия |
| **Модальный / выдвижной ящик** | Описывать как часть страницы триггера, а не как отдельный файл. Но полностью документируйте содержание |
| **Дашборд** | Карточки данных, диаграммы, значение показателей, размеры фильтра, частота обновления |

### Серверные конечные точки (NestJS / Django / Express) { #backend-endpoints-nestjs--django--express }

| Тип конечной точки | Приоритетные области |
|---------------|------------|
| **Ресурс CRUD** | Все поля (начиная с DTO/serializer), правила проверки, разрешения, разбивка на страницы, фильтрация, сортировка |
| **Конечные точки аутентификации** | Войти в систему/register поток, формат токена, логика обновления, сброс пароля, поставщики OAuth |
| **Загрузка файла** | Допустимые типы, ограничения по размеру, назначение хранилища, пайплайн для обработки |
| **Веб-хук / мероприятие** | Условия триггера, форма полезной нагрузки, политика повторных попыток, идемпотентность |
| **Фоновая работа** | Триггер, расписание, ввод/output, обработка отказов, мониторинг |
| **Просмотры администратора** (Django) | Зарегистрированные модели, list_display, search_fields, фильтры, встроенные модели, пользовательские действия |

## Темп выполнения { #execution-pacing }

**Большие проекты (>15 страниц):** Работайте пакетами по 3-5 страниц на модуль. Сначала полный обзор системы + инвентаризация страниц. Выведите каждый пакет для ревью пользователя, прежде чем продолжить.

**Небольшие проекты (≤15 страниц):** Завершите весь анализ за один проход.

## Распространенные подводные камни { #common-pitfalls }

| Ловушка | Исправить |
|---------|-----|
| Использование имен компонентов в качестве названий страниц | `UserManagementTable` → "Список управления пользователями" |
| Пропуск модальностей и выдвижных ящиков | Они содержат критически важную бизнес—логику - документируйте полностью |
| Отсутствующие имена полей i18n | Проверяйте файлы перевода, а не только компонент JSX |
| Игнорирование параметров динамического маршрута | `/order/:id` = для загрузки страницы требуется идентификатор заказа |
| Забыв о контроле разрешений | Задокументируйте, какие роли видят, какие кнопки/pages |
| Предполагая, что все API реальны | Проверьте наличие макетных шаблонов данных перед документированием конечных точек |
| Пропуск настройки администратора Django | `admin.py` часто содержит критические бизнес-правила (фильтры списков, пользовательские действия, встроенные строки). |
| Отсутствующие охранники NestJS/pipes | `@UseGuards`, `@UsePipes` содержат логику аутентификации и проверки подлинности, которая влияет на поведение |
| Игнорирование ограничений базы данных | Ограничения полей модели (unique, max_length, choices) являются правилами проверки для PRD |
| С видом на промежуточное программное обеспечение | Промежуточное программное обеспечение Auth, ограничители скорости и конфигурация CORS определяют общесистемное поведение |

## Оснастка { #tooling }

### Сценарии { #scripts }

| Сценарий | Цель | Использование |
|--------|---------|-------|
| `scripts/codebase_analyzer.py` | Сканировать кодовую базу → извлекать маршруты, API, модели, перечисления, структуру | `python3 codebase_analyzer.py /path/to/project` |
| `scripts/prd_scaffolder.py` | Сгенерировать скелет каталога PRD из analysis JSON | `python3 prd_scaffolder.py analysis.json` |

**Рекомендуемый воркфлоу:**
```bash
# 1. Analyze the project (JSON output — works for frontend, backend, or fullstack)
python3 scripts/codebase_analyzer.py /path/to/project -o analysis.json

# 2. Review the analysis (markdown summary)
python3 scripts/codebase_analyzer.py /path/to/project -f markdown

# 3. Scaffold the PRD directory with stubs
python3 scripts/prd_scaffolder.py analysis.json -o prd/ -n "My App"

# 4. Fill in TODO sections page-by-page using the SKILL.md workflow
```

Оба скрипта ** предназначены только для stdlib** — установка pip не требуется.
