Полученный из [Наблюдения Андрея Карпати](https://x.com/karpathy/status/2015883857489522876) о подводных камнях в кодировании LLM. Это ** не просто рекомендации ** — в него входят инструменты Python, которые обнаруживают нарушения, агент ревью, слэш-команда и функция предварительной фиксации.

> "Модели делают неверные предположения от вашего имени и просто следуют им, не проверяя. Они не справляются со своим замешательством, не ищут разъяснений, не выявляют несоответствий, не предлагают компромиссов, не дают отпор, когда следовало бы".
>
> "Им действительно нравится чрезмерно усложнять код и API, раздувать абстракции, не убирать мертвый код... внедрять раздутую конструкцию из 1000 строк, когда хватило бы и 100".
>
> "LLM исключительно хороши в создании циклов до тех пор, пока не достигнут конкретных целей... Не указывайте ему, что делать, дайте ему критерии успеха и наблюдайте, как он работает".
>
> — Андрей Карпати

## Четыре принципа { #the-four-principles }

### 1. Подумайте, прежде чем кодировать { #1-think-before-coding }

** Не предполагайте. Не скрывайте замешательства. Поверхностные компромиссы.**

- Явно формулируйте предположения. Если вы не уверены, спросите.
- Если существует множество интерпретаций, представьте их — не выбирайте молча.
- Если существует более простой подход, скажите об этом. Отодвигайтесь, когда это необходимо.
- Если что-то непонятно, остановитесь. Назовите то, что сбивает с толку. Спрашивай.

### 2. Простота прежде всего { #2-simplicity-first }

**Минимальный код, который решает проблему. Ничего умозрительного.**

- Никаких функций, выходящих за рамки того, что было задано.
- Никаких абстракций для одноразового кода.
- Никакой "гибкости" или "настраиваемости", которые не запрашивались.
- Нет обработки ошибок для невозможных сценариев.
- Если вы пишете 200 строк, а их может быть 50, перепишите это.

** Тест:** Сказал бы старший инженер, что это слишком сложно? Если да, то упростите.

### 3. Хирургические изменения { #3-surgical-changes }

** Прикасайтесь только к тому, к чему вы должны. Убирайте только свой собственный беспорядок.**

- Не "улучшайте" соседний код, комментарии или форматирование.
- Не реорганизовывайте то, что не сломано.
- Соответствуйте существующему стилю, даже если вы бы сделали это по-другому.
- Если вы заметили несвязанный мертвый код, упомяните об этом — не удаляйте его.
- Удалить импорт/variables/functions что ВАШИ изменения остались неиспользованными.
- Не удаляйте ранее существовавший мертвый код, если вас об этом не попросят.

** Тест:** Каждая измененная строка должна быть связана непосредственно с запросом пользователя.

### 4. Целенаправленное выполнение { #4-goal-driven-execution }

**Определите критерии успеха. Цикл повторяется до тех пор, пока не будет проверено.**

| Вместо этого... | Преобразовать в... |
|---|---|
| "Добавить проверку" | "Напишите тесты для недопустимых входных данных, а затем заставьте их пройти" |
| "Исправьте ошибку" | "Напишите тест, который воспроизводит это, а затем заставьте его пройти" |
| "Рефакторинг X" | "Убедитесь, что тесты прошли до и после" |

Для многоэтапных задач составьте краткий план:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

## Слэш-команда { #slash-command }

`/karpathy-check` — Выполните полный ревью по 4-м принципам для ваших поэтапных изменений.

## Инструменты Python (`scripts/`) { #python-tools-scripts }

Все инструменты доступны только для stdlib. Бегать с `--help`.

| Сценарий | Что он обнаруживает |
|---|---|
| `complexity_checker.py` | Чрезмерная инженерия: слишком много классов, глубокая вложенность, высокая цикломатическая сложность, неиспользуемые параметры, преждевременные абстракции |
| `diff_surgeon.py` | Различный шум: строки, которые не соответствуют заявленной цели — изменения комментариев, смещение стиля, рефакторинг по ходу движения |
| `assumption_linter.py` | Скрытые допущения в плане: незаданные функции, отсутствующие пояснения, варианты интерпретации, о которых умалчивается |
| `goal_verifier.py` | Слабые критерии успеха: расплывчатые планы без поддающихся проверке проверок, отсутствующие тестовые утверждения |

## Саб-агент { #sub-agent }

`karpathy-reviewer` — Сопоставляет все 4 принципа с diff. Отправлено `/karpathy-check` или вручную перед фиксацией.

## Крючок для предварительной фиксации { #pre-commit-hook }

`hooks/karpathy-gate.sh` — пробеги `complexity_checker.py` и `diff_surgeon.py` на промежуточных файлах. Предупреждает (не блокирует) при обнаружении нарушений. Подключите его через `.claude/settings.json` или хриплый.

## Когда нужно расслабиться { #when-to-relax }

Эти принципы смещены в сторону **осторожности, а не скорости**. Для тривиальных задач (исправления опечаток, очевидные однострочники) используйте суждение. Принципы имеют наибольшее значение на:

- Нетривиальные реализации (изменено >20 строк)
- Код, который вы не до конца понимаете
- Многоэтапные задачи с неясными требованиями
- Все, что будет подвергнуто ревью со стороны людей
