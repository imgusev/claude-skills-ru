## Описание { #description }

Самооценка - это скилл Клода Кода, который позволяет проводить честную, выверенную оценку работы. Он заменяет стандартную тенденцию ИИ оценивать все на 4/5 структурированной двухосевой системой подсчета очков, обязательными рассуждениями адвоката дьявола и межсессионным выявлением антиинфляции.

Основная идея: самооценка ИИ сводится к "все на 4", потому что оценка по одной оси связывает сложность задачи с качеством выполнения. Самостоятельная оценка разделяет эти оси, затем объединяет их с помощью фиксированной матрицы, которую модель не может переопределить.

## Особенности { #features }

- ** Оценка по двум осям** - независимо оценивает амбициозность задачи (низкая / средняя / высокая) и качество выполнения (плохое / адекватное / сильное), затем объединяет с помощью матрицы поиска.
- ** Обязательный "адвокат дьявола" ** — Перед окончательным подведением итогов необходимо аргументировать как более высокие, так и более низкие баллы, затем разрешить возникшую напряженность
- ** Постоянство оценки ** — Добавляет баллы к `.self-eval-scores.jsonl` в рабочем каталоге, создавая историю между сеансами
- ** Обнаружение антиинфляции ** — Считывает прошлые оценки и помечает кластеризацию (4+ из последних 5 идентичных)
- ** Оценка с привязкой к матрице ** - Сводная оценка берется из матрицы, а не из прямого отбора. Низкие амбиции на уровне 2/5 независимо от качества исполнения

## Использование { #usage }

После завершения работы в сеансе Claude Code:

```
/self-eval
```

С контекстом о том, что следует оценивать:

```
/self-eval the authentication refactor we just completed
```

Скилл ревью просматривает историю разговоров, определяет, что было достигнуто, оценивает это по обеим осям, запускает проверку "Адвоката дьявола" и добавляет результат в файл истории оценок.

## Примеры { #examples }

### Пример 1: Реализация функции { #example-1-feature-implementation }

```
/self-eval added pagination to the user list API
```

Выход:
```
## Self-Evaluation

**Task:** Added cursor-based pagination to the user list API endpoint
**Ambition:** Medium — New feature with established patterns, but required careful backwards compatibility
**Execution:** Strong — All tests pass, handles edge cases, existing clients unaffected

**Devil's Advocate:**
- Lower: Pagination is well-documented. The pattern was copied from another endpoint with minor changes. Could argue Low ambition.
- Higher: The backwards-compat requirement made this harder than a greenfield implementation. Had to support both offset and cursor modes.
- Resolution: Medium ambition holds — the backwards-compat constraint added real complexity beyond copy-paste.

**Score: 4** — Solid execution on meaningful work with real constraints.
```

### Пример 2: Исправление ошибки { #example-2-bug-fix }

```
/self-eval
```

Выход:
```
## Self-Evaluation

**Task:** Fixed race condition in the checkout flow causing duplicate orders
**Ambition:** Medium — Required debugging across 3 services to find the root cause
**Execution:** Adequate — Fix works but the test only covers the exact scenario reported, not the general class of race conditions

**Devil's Advocate:**
- Lower: The fix was a single line (adding a mutex). Once found, it was trivial.
- Higher: Finding the root cause across 3 services took real investigation. The mutex placement required understanding the full flow.
- Resolution: Medium ambition is correct for the investigation, but execution drops to Adequate — a more thorough fix would address the pattern, not just the instance.

**Score: 3** — Good debugging work but the fix is narrow.
```

## Что оценивать { #what-to-evaluate }

$АРГУМЕНТЫ

Если аргументов не представлено, ревью полную историю разговоров, чтобы определить, что было выполнено на этом сеансе. Обобщите работу в одном предложении, прежде чем выставлять оценку.

## Как оценить — Двухосевая модель { #how-to-score--two-axis-model }

Проведите оценку по двум независимым осям, затем объедините с помощью матрицы. Не выбирайте сначала число и не рационализируйте его — оцените каждую ось отдельно, а затем прочитайте матрицу.

### Ось 1: Амбициозность задачи (что было предпринято) { #axis-1-task-ambition-what-was-attempted }

Оцените сложность и риск того, над чем была проведена работа. НЕ то, насколько хорошо это было сделано.

- **Низкий (1)** — Безопасный, привычный, рутинный. Никакого реального риска неудачи. Примеры: незначительные изменения конфигурации, простые рефакторинги, копирование-вставка с небольшими изменениями, задачи, в выполнении которых вы были уверены перед началом работы.
- **Средний уровень (2)** — Значимая работа с новизной или вызовом. Частичный сбой был возможен. Примеры: реализация новой функции, интеграция незнакомого API, архитектурные изменения, отладка сложной проблемы.
- **Высокий (3)** — Амбициозный, незнакомый или с высокими ставками. Реальный риск полного провала. Примеры: создание чего-либо с нуля в незнакомой предметной области, редизайн сложной системы, оптимизация, критически важная для производительности, отправка в производство под давлением.

** Самопроверка:** Если вы были уверены в успехе до начала работы, значит, амбиции низкие или средние, а не высокие.

### Ось 2: Качество исполнения (насколько хорошо это было сделано) { #axis-2-execution-quality-how-well-it-was-done }

Оцените качество фактического результата, независимо от того, насколько амбициозной была задача.

- **Плохой (1)** — Серьезные сбои, неполный, неправильный вывод или отказ от выполнения задачи в середине. Результат не соответствует собственным заявленным критериям.
- ** Адекватный (2)** — Завершенный, но с пробелами, сокращениями или отсутствующей строгостью. Сделал свое дело, но оставил очевидные улучшения на столе.
- **Сильный (3)** — Хорошо выполненный, тщательный, качественный результат. Учитывая масштаб, никаких очевидных улучшений сделано не было.

### Составная матрица оценок { #composite-score-matrix }

|                        | Плохой руководитель (1) | Адекватный руководитель (2) | Сильный руководитель (3) |
|------------------------|:---:|:---:|:---:|
| **Низкие амбиции (1)**   |  1  |  2  |  2  |
| **Средние амбиции (2)**|  2  |  3  |  4  |
| **Высокие амбиции (3)**  |  2  |  4  |  5  |

** Прочитайте матрицу, не переопределяйте ее. ** Составная часть - это ваш результат. Приведенный ниже "Адвокат дьявола" может заставить вас повторно оценить ось, но вы не можете напрямую переопределить результат матрицы.

Ключевые свойства:
- Низкий уровень амбиций - 2. Безопасная работа, выполненная идеально, по-прежнему остается безопасной работой.
- Оценка "5" требует КАК высоких амбиций, ТАК И четкого исполнения. Это должно быть редкостью.
- Высокие амбиции + плохое исполнение = 2. Смелая неудача причиняет боль.
- Наиболее распространенная честная оценка за добросовестную работу - 3 (средние амбиции, адекватное исполнение).

## Адвокат дьявола (ОБЯЗАТЕЛЬНО) { #devils-advocate-mandatory }

Прежде чем написать свой окончательный результат, вы должны написать все три из этих:

1. ** Аргументы в пользу БОЛЕЕ НИЗКОЙ оценки:** Почему эта работа может заслуживать более низкой оценки? Что было легко, чего удалось избежать, что было менее амбициозным, чем кажется? Согласился бы скептически настроенный рецензент с вашими оценками axis?
2. ** Аргументы в пользу БОЛЕЕ ВЫСОКОЙ оценки: ** Почему эта работа может заслуживать более высокой оценки? Что было действительно сложным, неожиданным или выходило за рамки первоначального плана?
3. ** Разрешение: ** Если в любом случае окажется, что вы неправильно оценили ось, повторно оцените ее и пересчитайте результат матрицы. Затем укажите свой окончательный результат с обоснованием в 1-2 предложениях, в котором учитывается по крайней мере один балл в каждом случае.

Если в вашем "Адвокате дьявола" меньше 3 предложений, значит, вы с ним не справляетесь — старайтесь усерднее.

## Проверка на антиинфляцию { #anti-inflation-check }

Проверьте наличие файла истории оценок по адресу `.self-eval-scores.jsonl` в текущем рабочем каталоге.

Если файл существует, прочтите его и проверьте последние 5 баллов. Если 4+ из последних 5 - это одно и то же число, отметьте его:
> ** Предупреждение: Обнаружена кластеризация баллов.** Последние 5 баллов: [список]. Подумайте, привязываетесь ли вы к значению по умолчанию.

Если файл не существует, спросите себя: "Оценил бы это сторонний наблюдатель так же, как я?"

## Постоянство оценки { #score-persistence }

После представления вашей оценки добавьте одну строку к `.self-eval-scores.jsonl` в текущем рабочем каталоге:

```json
{"date":"YYYY-MM-DD","score":N,"ambition":"Low|Medium|High","execution":"Poor|Adequate|Strong","task":"1-sentence summary"}
```

Это позволяет антиинфляционной проверке работать в течение нескольких сеансов. Если файл не существует, создайте его.

## Выходной формат { #output-format }

Представьте свою оценку в виде:

## Самооценка { #self-evaluation }

**Задача:** [краткое изложение того, что было предпринято, в 1 предложении]
**Амбиции:** [Низкий/Средний/высокий] — [1-обоснование предложения]
**Исполнение:** [Плохой/Адекватный/Сильный] — [1-обоснование предложения]

** Адвокат дьявола:**
- Более низкий: [почему это может заслуживать меньшего]
- Более высокий: [почему это может заслуживать большего]
- Разрешение: [заключительное рассуждение]

**Оценка: [1-5]** — [1-окончательное обоснование предложения]
