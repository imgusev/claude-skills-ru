## Обзор { #overview }

Управляйте гигиеной окружающей среды и безопасностью секретов в рамках местных воркфлоу-процессов разработки и производства. Этот скилл фокусируется на практическом аудите, осознании дрейфа и готовности к ротации.

## Основные возможности { #core-capabilities }

- `.env` и `.env.example` руководство по жизненному циклу
- Обнаружение секретных утечек для рабочих деревьев репозитория
- Выводы на основе серьезности для вероятных учетных данных
- Рабочие указатели поворота и удержания
- Готовые к интеграции выходные данные для проверок CI

---

## Когда использовать { #when-to-use }

- Перед отправкой коммитов, которые касались файлов env/config
- Во время аудита безопасности и сортировки инцидентов
- При онбординге участников, которым нужны соглашения о безопасной среде
- При проверке того, что никакие очевидные секреты не закодированы жестко

---

## Быстрый старт { #quick-start }

```bash
# Scan a repository for likely secret leaks
python3 scripts/env_auditor.py /path/to/repo

# JSON output for CI pipelines
python3 scripts/env_auditor.py /path/to/repo --json
```

---

## Рекомендуемый воркфлоу { #recommended-workflow }

1. Бежать `scripts/env_auditor.py` в корневом каталоге репозитория.
2. Расставлять приоритеты `critical` и `high` сначала выводы.
3. Измените реальные учетные данные и удалите открытые значения.
4. Обновление `.env.example` и `.gitignore` по мере необходимости.
5. Добавьте или затяните гейты секретного сканирования pre-commit/CI.

## Распространенные подводные камни { #common-pitfalls }

- Закрепление реальных ценностей в `.env.example`
- Замена одной системы, но отсутствие нижестоящих потребителей
- Протоколирование секретов во время отладки или реагирования на инцидент
- Отнесение подозрительных утечек к категории малой срочности без подтверждения

## Лучшие практики { #best-practices }

1. Используйте секретного менеджера в качестве производственного источника истины.
2. Сохраняйте файлы dev env локальными и gitignored.
3. Принудительное обнаружение в CI перед слиянием.
4. Повторно протестируйте пути приложения сразу после смены учетных данных.

## Интеграция с облачным секретным хранилищем { #cloud-secret-store-integration }

Производственные приложения никогда не должны считывать секреты из `.env` файлы или переменные окружения, запеченные в образах контейнеров. Вместо этого используйте специальное секретное хранилище.

### Сравнение поставщиков { #provider-comparison }

| Поставщик | Лучше всего подходит для | Ключевая особенность |
|----------|----------|-------------|
| **Хранилище HashiCorp** | Мультиоблачный / гибридный | Динамические секреты, механизм политик, подключаемые серверные части |
| **Менеджер секретов AWS** | AWS-собственные рабочие нагрузки | Встроенная интеграция Lambda/ECS/EKS, автоматическое переключение RDS |
| **Хранилище ключей Azure** | Собственные рабочие нагрузки Azure | Управляемый HSM, Azure AD RBAC, управление сертификатами |
| **Секретный менеджер GCP** | GCP-собственные рабочие нагрузки | Доступ на основе IAM, автоматическая репликация, управление версиями |

### Руководство по выбору { #selection-guidance }

- **Единый облачный провайдер ** — используйте встроенный в облако secret manager. Он тесно интегрируется с IAM, снижает операционные издержки и стоит дешевле, чем самостоятельный хостинг.
- **Мультиоблачный или гибридный** — используйте хранилище HashiCorp. Он предоставляет единый API для всех сред и поддерживает динамическую генерацию секретов (учетные данные базы данных, облачные ключи IAM), срок действия которых истекает автоматически.
- ** Kubernetes-тяжелый ** — объедините оператор внешних секретов с любым бэкендом, описанным выше, для синхронизации секретов в K8s `Secret` объекты без жесткого кодирования.

### Шаблоны доступа к приложениям { #application-access-patterns }

1. ** SDK / API pull ** — приложение извлекает секрет при запуске или по требованию через SDK поставщика.
2. **Внедрение Sidecar** — контейнер sidecar (например, агент хранилища) записывает секреты в общий том или вводит их в качестве переменных среды.
3. **Контейнер инициализации** — контейнер инициализации Kubernetes извлекает секреты перед запуском основного контейнера.
4. **Драйвер CSI** — secrets монтируется как том файловой системы с помощью драйвера Secrets Store CSI.

> **Перекрестная ссылка:** Смотрите `engineering/secrets-vault-manager` для шаблонов инфраструктуры производственного хранилища, развертывания HA и процедур аварийного восстановления.

## Секретный воркфлоу ротации { #secret-rotation-workflow }

Устаревшие секреты - это помеха. Ротация гарантирует, что даже в случае утечки учетных данных срок их полезного использования ограничен.

### Фаза 1: Обнаружение { #phase-1-detection }

- Отслеживайте даты создания секрета и истечения срока его действия в метаданных вашего секретного хранилища.
- Устанавливайте оповещения за 30, 14 и 7 дней до истечения срока действия.
- Использование `scripts/env_auditor.py` чтобы пометить секреты без записанной даты ротации.

### Фаза 2: Вращение { #phase-2-rotation }

1. **Сгенерируйте** новые учетные данные (ключ API, пароль базы данных, сертификат).
2. *Деплей** новые учетные данные для всех пользователей (приложений, служб, пайплайнов) параллельно.
3. ** Проверьте** каждый пользователь может пройти аутентификацию, используя новые учетные данные.
4. ** Отозвать** старые учетные данные можно только после подтверждения работоспособности всех пользователей.
5. ** Обновите ** метаданные с новой временной меткой ротации и датой следующей ротации.

### Этап 3: Автоматизация { #phase-3-automation }

- **AWS Secrets Manager** — используйте встроенную ротацию на основе лямбда для RDS, Redshift и DocumentDB.
- **HashiCorp Vault** — настройка динамических секретов с помощью TTLS; учетные данные генерируются по запросу и автоматически истекают.
- **Хранилище ключей Azure** — используйте уведомления о сетке событий для триггера функций ротации.
- ** GCP Secret Manager ** — используйте уведомления Pub / Sub, привязанные к облачным функциям, для логики ротации.

### Чек-лист для экстренной ротации в случае необходимости. { #emergency-rotation-checklist }

Когда утечка секрета подтверждается:

1. **Немедленно отозвать** скомпрометированные учетные данные на уровне поставщика.
2. Сгенерируйте и деплою заменяющие учетные данные для всех пользователей.
3. Аудит журналов доступа на предмет несанкционированного использования в течение периода экспозиции.
4. Просканируйте историю git, журналы CI и реестры артефактов на предмет утечки значения.
5. Отправьте отчет об инциденте, документирующий объем, временные рамки и шаги по устранению неполадок.
6. Ревью и ужесточите меры контроля за обнаружением, чтобы предотвратить повторение.

## Секретная инъекция CI/CD { #cicd-secret-injection }

Секреты в пайплайнах CI/CD требуют тщательного обращения, чтобы избежать раскрытия в журналах, артефактах или контекстах запроса на извлечение.

### Действия на GitHub { #github-actions }

- Используйте **секреты хранилища** или ** секреты среды** с помощью `${{ secrets.SECRET_NAME }}`.
- Предпочитаю **Федерацию OIDC** (`aws-actions/configure-aws-credentials` с `role-to-assume`) по долгоживущим ключам доступа.
- Секреты среды с обязательными проверяющими добавляют гейты утверждения для производственных развертываний.
- GitHub автоматически маскирует секреты в журналах, но избегает `echo` или `toJSON()` о секретных ценностях.

### GitLab CI { #gitlab-ci }

- Храните секреты в виде **переменных CI/CD** с помощью `masked` и `protected` флаги включены.
- Используйте ** Интеграцию с хранилищем HashiCorp** (`secrets:vault`) для динамического внедрения секрета без сохранения значений в GitLab.
- Переменные области видимости для конкретных сред (`production`, `staging`) для обеспечения наименьших привилегий.

### Универсальные паттерны { #universal-patterns }

- **Никогда не повторяйте и не печатайте** секретные значения в выводе пайплайна, даже для отладки.
- **Используйте недолговечные токены** (OIDC, STS AssumeRole) вместо статических учетных данных везде, где это возможно.
- **Ограничить доступ PR** — не раскрывайте секреты пайплайнам, триггерам форков или ненадежных ветвей.
- ** Чередуйте секреты CI** по тому же расписанию, что и секреты приложений; учетные данные пайплайна также являются векторами атак.
- **Периодически проводите аудит журналов пайплайна** на предмет случайного раскрытия секретов, которые могли быть пропущены при маскировке.

## Обнаружение секрета перед фиксацией { #pre-commit-secret-detection }

Улавливание секретов до того, как они попадут в систему контроля версий, является наиболее экономичной защитой. Два ведущих инструмента охватывают это пространство.

### гитлаки { #gitleaks }

```toml
# .gitleaks.toml — minimal configuration
[extend]
useDefault = true

[[rules]]
id = "custom-internal-token"
description = "Internal service token pattern"
regex = '''INTERNAL_TOKEN_[A-Za-z0-9]{32}'''
secretGroup = 0
```

- Установить: `brew install gitleaks` или скачайте с релизов GitHub.
- Крючок для предварительной фиксации: `gitleaks git --pre-commit --staged`
- Сканирование базовой линии: `gitleaks detect --source . --report-path gitleaks-report.json`
- Управление ложными срабатываниями в `.gitleaksignore` (по одному отпечатку пальца на строку).

### обнаружение-секреты { #detect-secrets }

```bash
# Generate baseline
detect-secrets scan --all-files > .secrets.baseline

# Pre-commit hook (via pre-commit framework)
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.5.0
    hooks:
      - id: detect-secrets
        args: ['--baseline', '.secrets.baseline']
```

- Поддерживает ** пользовательские плагины ** для шаблонов, специфичных для организации.
- Аудит воркфлоу: `detect-secrets audit .secrets.baseline` интерактивно помечает истинные/ложные срабатывания.

### Управление ложноположительными результатами { #false-positive-management }

- Поддерживать `.gitleaksignore` или `.secrets.baseline` в системе управления версиями, таким образом, вся команда разделяет исключения.
- Ревью списки ложноположительных результатов во время аудита безопасности — шаблоны могут со временем маскировать реальные утечки.
- Предпочитайте ужесточать шаблоны регулярных выражений, а не широко игнорировать файлы.

## Ведение журнала аудита { #audit-logging }

Знание того, кто получил доступ к какому секрету и когда, имеет решающее значение для расследования инцидентов и соблюдения требований законодательства.

### Собственные маршруты аудита в облаке { #cloud-native-audit-trails }

| Поставщик | Обслуживание | Что он запечатлевает |
|----------|---------|-----------------|
| **AWS** | Облачный след | Каждый `GetSecretValue`, `DescribeSecret`, `RotateSecret` Вызов API |
| **Лазурный** | Журнал действий + Диагностические журналы | События доступа к хранилищу ключей, включая идентификатор вызывающего абонента и IP-адрес |
| **GCP** | Журналы облачного аудита | Журналы доступа к данным для Secret Manager с именем участника и отметкой времени |
| **Хранилище** | Серверная часть аудита | Полное ведение журнала запросов/ответов (файл, системный журнал или серверная часть сокета) |

### Стратегия оповещения { #alerting-strategy }

- Предупреждение о ** доступе с неизвестных диапазонов IP-адресов** или учетных записях служб за пределами ожидаемого набора.
- Предупреждение о **массовом считывании секретов** (доступ к более чем N секретам осуществляется в течение временного интервала).
- Предупреждение о **доступе за пределами windows развертывания**, когда пайплайн CI/CD не запущен.
- Загружайте журналы аудита в ваш SIEM (Splunk, Datadog, Elastic) для корреляции с другими событиями безопасности.
- Ежеквартально ревью журналы аудита в рамках повторной сертификации доступа.
