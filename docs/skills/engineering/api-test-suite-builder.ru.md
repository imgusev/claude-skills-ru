## Обзор { #overview }

Сканирует определения маршрутов API в разных фреймворках (Next.js App Router, Express, FastAPI, Django REST) и
автоматически генерирует комплексные наборы тестов, охватывающие аутентификацию, проверку ввода, коды ошибок, разбиение на страницы,
загрузку файлов и ограничение скорости. Выводит готовые к запуску тестовые файлы для Vitest+Supertest (Node) или Pytest+httpx
(Python).

---

## Основные возможности { #core-capabilities }

- ** Определение маршрута** — сканирование исходных файлов для извлечения всех конечных точек API
- **Авторизационное покрытие** — действительное/invalid/expired токены, отсутствующий заголовок auth
- **Проверка ввода** — отсутствующие поля, неправильные типы, граничные значения, попытки ввода
- **Матрица кодов ошибок** — 400/401/403/404/422/500 для каждого маршрута
- **Разбивка на страницы** — первая/last/empty/oversized страницы
- **Загрузка файлов** — допустимый размер, неправильный тип MIME, пустой
- ** Ограничение скорости ** — обнаружение пакетов для каждого пользователя в сравнении с глобальными ограничениями

## Когда использовать { #when-to-use }

- Добавлен новый API — сгенерировать тестовый каркас перед написанием реализации (TDD)
- Устаревший API без тестов — сканирование и создание базового покрытия
- Ревью контракта API — проверка соответствия существующих тестов текущим определениям маршрутов
- Регрессионная проверка перед выпуском - убедитесь, что на всех маршрутах есть как минимум тесты на дым
- Подготовка к аудиту безопасности — создание состязательных входных тестов

## Определение маршрута { #route-detection }

### Next.js Маршрутизатор приложений { #nextjs-app-router }
```bash
# Find all route handlers
find ./app/api -name "route.ts" -o -name "route.js" | sort

# Extract HTTP methods from each route file
grep -rn "export async function\|export function" app/api/**/route.ts | \
  grep -oE "(GET|POST|PUT|PATCH|DELETE|HEAD|OPTIONS)" | sort -u

# Full route map
find ./app/api -name "route.ts" | while read f; do
  route=$(echo $f | sed 's|./app||' | sed 's|/route.ts||')
  methods=$(grep -oE "export (async )?function (GET|POST|PUT|PATCH|DELETE)" "$f" | \
    grep -oE "(GET|POST|PUT|PATCH|DELETE)")
  echo "$methods $route"
done
```

### Выражать { #express }
```bash
# Find all router files
find ./src -name "*.ts" -o -name "*.js" | xargs grep -l "router\.\(get\|post\|put\|delete\|patch\)" 2>/dev/null

# Extract routes with line numbers
grep -rn "router\.\(get\|post\|put\|delete\|patch\)\|app\.\(get\|post\|put\|delete\|patch\)" \
  src/ --include="*.ts" | grep -oE "(get|post|put|delete|patch)\(['\"][^'\"]*['\"]"

# Generate route map
grep -rn "router\.\|app\." src/ --include="*.ts" | \
  grep -oE "\.(get|post|put|delete|patch)\(['\"][^'\"]+['\"]" | \
  sed "s/\.\(.*\)('\(.*\)'/\U\1 \2/"
```

### FastAPI { #fastapi }
```bash
# Find all route decorators
grep -rn "@app\.\|@router\." . --include="*.py" | \
  grep -E "@(app|router)\.(get|post|put|delete|patch)"

# Extract with path and function name
grep -rn "@\(app\|router\)\.\(get\|post\|put\|delete\|patch\)" . --include="*.py" | \
  grep -oE "@(app|router)\.(get|post|put|delete|patch)\(['\"][^'\"]*['\"]"
```

### Фреймворк Django REST { #django-rest-framework }
```bash
# urlpatterns extraction
grep -rn "path\|re_path\|url(" . --include="*.py" | grep "urlpatterns" -A 50 | \
  grep -E "path\(['\"]" | grep -oE "['\"][^'\"]+['\"]" | head -40

# ViewSet router registration
grep -rn "router\.register\|DefaultRouter\|SimpleRouter" . --include="*.py"
```

## Шаблоны генерации тестов { #test-generation-patterns }

### Матрица проверки подлинности { #auth-test-matrix }

Для каждой прошедшей проверку подлинности конечной точки сгенерируйте:

| Тестовый пример | Ожидаемый статус |
|-----------|----------------|
| Нет заголовка авторизации | 401 |
| Недопустимый формат токена | 401 |
| Действительный токен, неправильная роль пользователя | 403 |
| Истекший токен JWT | 401 |
| Действительный токен, правильная роль | 2xx |
| Токен от удаленного пользователя | 401 |

### Матрица проверки входных данных { #input-validation-matrix }

Для каждой конечной точки POST/PUT/PATCH с телом запроса:

| Тестовый пример | Ожидаемый статус |
|-----------|----------------|
| Пустое тело `{}` | 400 или 422 |
| Отсутствующие обязательные поля (по одному за раз) | 400 или 422 |
| Неправильный тип (строка, где ожидается значение int) | 400 или 422 |
| Граница: значение при min-1 | 400 или 422 |
| Граница: минимальное значение | 2xx |
| Граница: максимальное значение | 2xx |
| Граница: максимальное значение+1 | 400 или 422 |
| SQL-инъекция в строковое поле | 400 или 200 (продезинфицированных) |
| Полезная нагрузка XSS в строковом поле | 400 или 200 (продезинфицированных) |
| Нулевые значения для обязательных полей | 400 или 422 |

## Генерация тестов на основе сканирования маршрута { #generating-tests-from-route-scan }

Получив кодовую базу, следуйте этому процессу:

1. **Сканируйте маршруты**, используя приведенные выше команды обнаружения
2. ** Прочтите каждый обработчик маршрута **, чтобы понять:
   - Ожидаемая схема тела запроса
   - Требования к авторизации (промежуточное программное обеспечение, декораторы)
   - Типы возвращаемых данных и коды состояния
   - Бизнес-правила (владение, проверка ролей)
3. **Сгенерируйте тестовый файл** для каждой группы маршрутов, используя приведенные выше шаблоны
4. **Назовите тесты описательно**: `"returns 401 when token is expired"` не `"auth test 3"`
5. **Используйте фабрики/fixtures** для тестовых данных — никогда не вводите жесткие идентификаторы
6. **Утверждайте форму ответа**, а не только код состояния

## Распространенные подводные камни { #common-pitfalls }

- ** Тестируем только счастливые пути ** — 80% ошибок живут в путях ошибок; сначала протестируйте их
- **Жестко закодированные идентификаторы тестовых данных** — используйте фабрики/fixtures; Идентификаторы меняются в зависимости от среды
- ** Общее состояние между тестами** — всегда выполняйте очистку после каждого теста/afterВсе
- ** Тестирование реализации, а не поведения ** — тестируйте то, что возвращает API, а не то, как он это делает
- ** Пропущенные граничные тесты ** — единичные ошибки чрезвычайно распространены при разбивке на страницы и ограничениях
- **Не проверяется истечение срока действия токена ** — токены с истекшим сроком действия ведут себя иначе, чем недействительные токены
- **Игнорирование Content-Type** — проверка того, что API отклоняет неправильные типы контента (xml при ожидаемом json)

## Лучшие практики { #best-practices }

1. Один блок описания на конечную точку — позволяет изолировать сбои и сделать их читаемыми
2. Ввод минимальных данных — не загружайте всю базу данных; создавайте только то, что нужно тесту
3. Использование `beforeAll` для общей настройки, `afterAll` для очистки — не `beforeEach` для дорогостоящих операций
4. Утверждать конкретные сообщения об ошибках/fields, а не только коды состояния
5. Проверьте, чтобы конфиденциальные поля (пароль, секрет) никогда не появлялись в ответах
6. Для проверки подлинности всегда проверяйте регистр "отсутствующий заголовок" отдельно от "недопустимый токен".
7. Добавьте тесты с ограничением скорости в последнюю очередь — они могут мешать другим наборам тестов, если выполняются параллельно
