## Обзор { #overview }

Используйте этот скилл для безопасного запуска параллельной функциональной работы с Git worktrees. Он стандартизирует изоляцию ветвей, распределение портов, синхронизацию среды и очистку, поэтому каждое рабочее дерево ведет себя как независимое локальное приложение, не переходя на другую ветвь.

Этот скилл оптимизирован для воркфлоу с несколькими агентами, где каждому агенту или сеансу терминала принадлежит одно рабочее дерево.

## Основные возможности { #core-capabilities }

- Создавайте рабочие деревья из новых или существующих ветвей с детерминированным именованием
- Автоматическое выделение неконфликтующих портов для каждого рабочего дерева и сохранение назначений
- Копирование файлов локальной среды (`.env*`) из основного репозитория в новое рабочее дерево
- Необязательно устанавливать зависимости, основанные на обнаружении файла блокировки
- Обнаруживать устаревшие рабочие деревья и незафиксированные изменения перед очисткой
- Идентифицируйте объединенные ветви и безопасно удаляйте устаревшие рабочие деревья

## Когда использовать { #when-to-use }

- Вам нужно более 2 одновременных филиалов, открытых локально
- Вам нужны изолированные серверы разработки для проверки функций, исправлений и PR
- Вы работаете с несколькими агентами, которые не должны совместно использовать ветку
- Ваша текущая ветка заблокирована, но вам нужно отправить быстрое исправление прямо сейчас
- Вам нужна повторяемая очистка вместо разовой `rm -rf` операции

## Ключевые Воркфлоу { #key-workflows }

### 1. Создайте полностью подготовленное рабочее дерево { #1-create-a-fully-prepared-worktree }

1. Выберите название ветви и название рабочего дерева.
2. Запустите скрипт менеджера (создает ветку, если она отсутствует).
3. Ревью сгенерированную карту порта.
4. Запустите приложение, используя выделенные порты.

```bash
python scripts/worktree_manager.py \
  --repo . \
  --branch feature/new-auth \
  --name wt-auth \
  --base-branch main \
  --install-deps \
  --format text
```

Если вы используете автоматизированный ввод JSON:

```bash
cat config.json | python scripts/worktree_manager.py --format json
# or
python scripts/worktree_manager.py --input config.json --format json
```

### 2. Запускайте параллельные сеансы { #2-run-parallel-sessions }

Рекомендуемое соглашение:

- Основное хранилище: ветвь интеграции (`main`/`develop`) на порту по умолчанию
- Рабочее дерево A: функциональная ветвь + смещенные порты
- Рабочее дерево B: ветвь исправления + следующее смещение

Каждое рабочее дерево содержит `.worktree-ports.json` с назначенными портами.

### 3. Очистка с проверкой безопасности { #3-cleanup-with-safety-checks }

1. Отсканируйте все рабочие деревья и их устаревший возраст.
2. Проверьте состояние грязных деревьев и слияния ветвей.
3. Удаляйте только объединенные + чистые рабочие деревья или применяйте явную силу.

```bash
python scripts/worktree_cleanup.py --repo . --stale-days 14 --format text
python scripts/worktree_cleanup.py --repo . --remove-merged --format text
```

### 4. Шаблон создания Docker { #4-docker-compose-pattern }

Используйте переопределение файлов для каждого рабочего дерева, сопоставленных с выделенными портами. Скрипт выводит детерминированную карту портов; примените ее к `docker-compose.worktree.yml`.

Видишь [docker-compose-patterns.md](https://github.com/imgusev/claude-skills-ru/tree/main/engineering/skills/git-worktree-manager/references/docker-compose-patterns.md) для конкретных шаблонов.

### 5. Стратегия распределения портов { #5-port-allocation-strategy }

Стратегия по умолчанию - это `base + (index * stride)` с проверками на столкновение:

- Приложение: `3000`
- Постгрес: `5432`
- Переделать: `6379`
- Шагать: `10`

Видишь [port-allocation-strategy.md](https://github.com/imgusev/claude-skills-ru/tree/main/engineering/skills/git-worktree-manager/references/port-allocation-strategy.md) для полной стратегии и крайних случаев.

## Интерфейсы сценариев { #script-interfaces }

- `python scripts/worktree_manager.py --help`
  - Создание/перечисление рабочих деревьев
  - Выделять/сохранять порты
  - Копия `.env*` файлы
  - Необязательная установка зависимостей
- `python scripts/worktree_cleanup.py --help`
  - Обнаружение устаревания по возрасту
  - Обнаружение "грязного" состояния
  - Обнаружение объединенной ветви
  - Дополнительное безопасное извлечение

Оба инструмента поддерживают stdin JSON и `--input` файловый режим для автоматизации пайплайнов.

## Распространенные подводные камни { #common-pitfalls }

1. Создание рабочих деревьев внутри основного каталога репозитория
2. Повторное использование `localhost:3000` по всем ветвям
3. Совместное использование одного URL-адреса базы данных в изолированных ветвях объектов
4. Удаление рабочего дерева с незафиксированными изменениями
5. Забыв обрезать старые метаданные после удаления ветки
6. Принятие статуса объединенного без проверки целевой ветви

## Лучшие практики { #best-practices }

1. Одна ветвь на рабочее дерево, один агент на рабочее дерево.
2. Сохраняйте рабочие деревья недолговечными; удаляйте после слияния.
3. Используйте детерминированный шаблон именования (`wt-<topic>`).
4. Сохраняйте сопоставления портов в файле, а не в примечаниях к памяти или терминалу.
5. Еженедельно запускайте очистительное сканирование в активных репозиториях.
6. Использование `--format json` для машинных потоков и `--format text` для ревью со стороны людей.
7. Никогда не удаляйте принудительно грязные рабочие деревья, если только изменения не были намеренно отменены.

## Чек-лист для проверки подлинности (#) { #validation-checklist }

Прежде чем заявить о завершении настройки:

1. `git worktree list` показывает ожидаемый путь + ветвь.
2. `.worktree-ports.json` существует и содержит уникальные порты.
3. `.env` файлы скопированы успешно (если они присутствуют в исходном репозитории).
4. Команда установки зависимостей завершает работу с кодом `0` (если включено).
5. Проверка очистки не сообщает об отсутствии непреднамеренных устаревших грязных деревьев.

## Матрица принятия решений { #decision-matrix }

Используйте этот быстрый выбор перед созданием нового рабочего дерева:

- Нужны изолированные зависимости и серверные порты -> создайте новое рабочее дерево
- Нужен только быстрый ревью локальных различий -> оставайтесь на текущем дереве
- Требуется исправление, пока ветка функций загрязнена -> создать выделенное рабочее дерево исправлений
- Нужна ветка эфемерного воспроизведения для сортировки ошибок -> создать временное рабочее дерево и очистить в тот же день

## Оперативный чек-лист { #operational-checklist }

### До сотворения мира { #before-creation }

1. Подтвердите, что в основном репозитории есть чистые базовые данные или намеренные фиксации WIP.
2. Подтвердите соглашение об именовании целевой ветви.
3. Подтвердите существование требуемой базовой ветви (`main`/`develop`).
4. Убедитесь, что ни один зарезервированный локальный порт не занят службами, не являющимися репозиториями.

### После создания { #after-creation }

1. Проверить `git status` ветвь соответствует ожидаемой ветви.
2. Проверить `.worktree-ports.json` существует.
3. Убедитесь, что приложение загружается через выделенный порт приложения.
4. Убедитесь, что конечные точки базы данных и кэша нацелены на изолированные порты.

### Перед удалением { #before-removal }

1. Убедитесь, что ветвь имеет восходящий поток и объединена по назначению.
2. Убедитесь, что не осталось незафиксированных файлов.
3. Убедитесь, что никакие запущенные контейнеры/процессы не зависят от этого пути к рабочему дереву.

## Интеграция CI и команды { #ci-and-team-integration }

- Используйте имя пути к рабочему дереву, которое соответствует идентификатору задачи (`wt-1234-auth`).
- Включите путь к рабочему дереву в заголовок терминала, чтобы избежать фиксации в неправильном окне.
- При автоматизированных настройках сохраняйте метаданные создания в артефактах/журналах CI.
- Запустите отчет об очистке триггера в запланированных заданиях и опубликуйте сводку на командном канале.

## Восстановление после сбоя { #failure-recovery }

- Если `git worktree add` сбой из-за существующего пути: проверьте путь, не перезаписывайте.
- Если установка зависимостей завершается неудачей: сохраните созданное рабочее дерево, отметьте статус и продолжите восстановление вручную.
- Если копирование env завершается неудачно: продолжайте с предупреждением и явным списком отсутствующих файлов.
- Если при распределении портов возникают проблемы с внешней службой: повторите запуск с настроенными базовыми портами.
