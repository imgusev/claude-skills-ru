## Обзор { #overview }

Управление секретной инфраструктурой производства для команд, использующих HashiCorp Vault, облачные хранилища секретов или гибридные архитектуры. Этот скилл охватывает разработку политики, настройку метода аутентификации, автоматическую ротацию, динамические секреты, ведение журнала аудита и реагирование на инциденты.

**Отличается от env-secrets-manager**, который обрабатывает локальные `.env` гигиена файлов и обнаружение утечек. Этот скилл работает на уровне инфраструктуры — кластеры хранилищ, облачные KMS, центры сертификации и внедрение секретных данных CI/CD.

### Когда использовать { #when-to-use }

- Создание нового кластера хранилищ или миграция в управляемое секретное хранилище
- Разработка методов аутентификации для служб, исполнителей CI и людей-операторов
- Внедрение автоматической ротации учетных данных (база данных, ключи API, сертификаты)
- Аудит шаблонов секретного доступа на соответствие требованиям (SOC 2, ISO 27001, HIPAA)
- Реагирование на секретную утечку, которая требует массового отзыва
- Интеграция секретов в рабочие нагрузки Kubernetes или пайплайны CI/CD

## Шаблоны хранилищ HashiCorp { #hashicorp-vault-patterns }

### Архитектурные решения { #architecture-decisions }

| Решение | Рекомендация | Обоснование |
|----------|---------------|-----------|
| Режим развертывания | ГА с плотным хранилищем | Отсутствие внешней зависимости, встроенные выборы лидера |
| Автоматическое вскрытие | Облачная KMS (AWS KMS / Azure Key Vault / GCP KMS) | Исключает ручное вскрытие, обеспечивает автоматический перезапуск |
| Пространства имен | По одному на среду (dev/staging/prod) | Изоляция в радиусе взрыва, независимая политика |
| Устройства для аудита | Файл + системный журнал (двойной) | Хранилище отклоняет запросы, если все устройства аудита выходят из строя — dual предотвращает перебои в работе |

### Методы аутентификации { #auth-methods }

**AppRole** — Межмашинная аутентификация для служб и пакетных заданий.

```hcl
# Enable AppRole
path "auth/approle/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}

# Application-specific role
vault write auth/approle/role/payment-service \
  token_ttl=1h \
  token_max_ttl=4h \
  secret_id_num_uses=1 \
  secret_id_ttl=10m \
  token_policies="payment-service-read"
```

**Kubernetes** — Pod-встроенная аутентификация с помощью токенов учетной записи службы.

```hcl
vault write auth/kubernetes/role/api-server \
  bound_service_account_names=api-server \
  bound_service_account_namespaces=production \
  policies=api-server-secrets \
  ttl=1h
```

**OIDC** — доступ человека-оператора через провайдера единого входа (Okta, Azure AD, Google Workspace).

```hcl
vault write auth/oidc/role/engineering \
  bound_audiences="vault" \
  allowed_redirect_uris="https://vault.example.com/ui/vault/auth/oidc/oidc/callback" \
  user_claim="email" \
  oidc_scopes="openid,profile,email" \
  policies="engineering-read" \
  ttl=8h
```

### Секретные двигатели { #secret-engines }

| Двигатель | Вариант использования | Стратегия TTL |
|--------|----------|-------------|
| КВ v2 | Статические секреты (ключи API, конфигурация) | Версионное, ручное вращение |
| База данных | Учетные данные динамической базы данных | по умолчанию 1 час, максимум 24 часа |
| PKI | Сертификаты TLS | сертификаты leaf 90d, 5-летний промежуточный CA |
| Транзит | Шифрование как услуга | Поворот ключа каждые 90 секунд |
| SSH | Подписанные SSH-сертификаты | 30 м для интерактивности, 8 часов для автоматизации |

### Разработка политики { #policy-design }

Следуйте принципу наименьших привилегий с детализацией на основе пути:

```hcl
# payment-service-read policy
path "secret/data/production/payment/*" {
  capabilities = ["read"]
}

path "database/creds/payment-readonly" {
  capabilities = ["read"]
}

# Deny access to admin paths explicitly
path "sys/*" {
  capabilities = ["deny"]
}
```

**Соглашение об именовании политики:** `{service}-{access-level}` (например,, `payment-service-read`, `api-gateway-admin`).

## Интеграция с облачным секретным хранилищем { #cloud-secret-store-integration }

### Матрица сравнения { #comparison-matrix }

| Особенность | Менеджер секретов AWS | Хранилище ключей Azure | Секретный менеджер GCP |
|---------|--------------------|-----------------|--------------------|
| Вращение | Встроенный лямбда- | Пользовательская логика с помощью функций | Облачные функции |
| Управление версиями | Автоматический | Ручной или автоматический | Автоматический |
| Шифрование | AWS KMS (по умолчанию или CMK) | Поддерживаемый HSM | Управляемый Google или CMEK |
| Контроль доступа | Политика IAM + политика в отношении ресурсов | Политики доступа RBAC + | Привязки IAM |
| Межрегиональный | Поддерживается репликация | Гео-резервирование по умолчанию | Поддерживается репликация |
| Аудит | Облачный след | Монитор Azure + Диагностические журналы | Журналы облачного аудита |
| Модель ценообразования | Для каждого секрета + для каждого вызова API | Для каждой операции + для каждого ключа | Для каждой секретной версии + для каждого доступа |

### Когда использовать, какой { #when-to-use-which }

- **AWS Secrets Manager**: Ротация учетных данных RDS/Aurora "из коробки". Лучше всего, когда вы полностью подключены к AWS.
- **Хранилище ключей Azure**: Надежность управления сертификатами. Требуется для интегрированных рабочих нагрузок Azure AD.
- **GCP Secret Manager**: Простейший интерфейс API. Лучше всего подходит для рабочих нагрузок, основанных на GKE, с идентификацией рабочей нагрузки.
- ** Хранилище HashiCorp**: Мультиоблачное, динамические секреты, PKI, транзитное шифрование. Лучше всего подходит для сложных или гибридных сред.

### Шаблоны доступа к SDK { #sdk-access-patterns }

** Принцип: ** Всегда извлекайте секреты при запуске или через sidecar — никогда не загружайте в изображения или конфигурационные файлы.

```python
# AWS Secrets Manager pattern
import boto3, json

def get_secret(secret_name, region="us-east-1"):
    client = boto3.client("secretsmanager", region_name=region)
    response = client.get_secret_value(SecretId=secret_name)
    return json.loads(response["SecretString"])
```

```python
# GCP Secret Manager pattern
from google.cloud import secretmanager

def get_secret(project_id, secret_id, version="latest"):
    client = secretmanager.SecretManagerServiceClient()
    name = f"projects/{project_id}/secrets/{secret_id}/versions/{version}"
    response = client.access_secret_version(request={"name": name})
    return response.payload.data.decode("UTF-8")
```

```python
# Azure Key Vault pattern
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

def get_secret(vault_url, secret_name):
    credential = DefaultAzureCredential()
    client = SecretClient(vault_url=vault_url, credential=credential)
    return client.get_secret(secret_name).value
```

## Секретный воркфлоу ротации { #secret-rotation-workflows }

### Стратегия ротации по секретному типу { #rotation-strategy-by-secret-type }

| Секретный тип | Частота вращения | Способ | Риск простоя |
|-------------|-------------------|--------|---------------|
| Пароли к базе данных | 30 дней | Обмен на два счета | Ноль (вращение A/B) |
| Ключи API | 90 дней | Генерировать новое, отвергать старое | Ноль (окно перекрытия) |
| Сертификаты TLS | за 60 дней до истечения срока годности | ACME или Vault PKI | Ноль (плавная перезагрузка) |
| SSH-ключи | 90 дней | Сертификаты, подписанные хранилищем | Ноль (на основе CA) |
| Сервисные токены | 24 часа | Динамическая генерация | Ноль (недолговечный) |
| Ключи шифрования | 90 дней | Изменение версии ключа (перемотка) | Ноль (сосуществование версий) |

### Ротация учетных данных базы данных (двойная учетная запись) { #database-credential-rotation-dual-account }

1. Существуют две учетные записи базы данных: `app_user_a` и `app_user_b`
2. Приложение в настоящее время использует `app_user_a`
3. Вращение вращает `app_user_b` пароль, обновления секретного хранилища
4. Приложение переключается на `app_user_b` при следующей выборке учетных данных
5. После льготного периода, `app_user_a` пароль изменен
6. Цикл повторяется

### Поворот ключа API (окно перекрытия) { #api-key-rotation-overlap-window }

1. Сгенерируйте новый ключ API с помощью поставщика
2. Сохраните новый ключ в секретном хранилище как `current`, переместить старое в `previous`
3. Деплою приложений — они читают `current`
4. После перезапуска всех экземпляров (или истечения срока действия TTL) отмените `previous`
5. Мониторинг подтверждает нулевое использование старого ключа перед отзывом

## Динамические секреты { #dynamic-secrets }

Динамические секреты генерируются по требованию с автоматическим истечением срока действия. По возможности предпочитайте динамические секреты статическим учетным данным.

### Динамические учетные данные базы данных (хранилище) { #database-dynamic-credentials-vault }

```hcl
# Configure database engine
vault write database/config/postgres \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db.example.com:5432/app" \
  allowed_roles="app-readonly,app-readwrite" \
  username="vault_admin" \
  password="<admin-password>"

# Create role with TTL
vault write database/roles/app-readonly \
  db_name=postgres \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl=1h \
  max_ttl=24h
```

### Динамические учетные данные Cloud IAM { #cloud-iam-dynamic-credentials }

Vault может генерировать недолговечные учетные данные AWS IAM, пароли участников службы Azure или ключи учетной записи службы GCP, полностью устраняя долговременные учетные данные в облаке.

### Центр сертификации SSH { #ssh-certificate-authority }

Замените распространение ключей SSH моделью сертификата, подписанного хранилищем:

1. Хранилище действует как SSH-центр сертификации
2. Пользователи/машины запрашивают подписанные сертификаты с коротким TTL (30 мин)
3. SSH—серверы доверяют открытому ключу центра сертификации - нет `authorized_keys` управление
4. Срок действия сертификатов истекает автоматически — для нормальной работы отзыв не требуется

## Ведение журнала аудита { #audit-logging }

### Что регистрировать { #what-to-log }

| Событие | Приоритет | Удержание |
|-------|----------|-----------|
| Секретный доступ для чтения | ВЫСОКИЙ | минимум 1 год |
| Секретное создание/обновление | ВЫСОКИЙ | минимум 1 год |
| Вход в систему методом аутентификации | СРЕДНИЙ | 90 дней |
| Изменения в политике | КРИТИЧЕСКИЙ | 2 года (соответствие требованиям) |
| Неудачные попытки доступа | КРИТИЧЕСКИЙ | 1 год |
| Создание/отзыв токена | СРЕДНИЙ | 90 дней |
| Операции по запечатыванию/вскрытию | КРИТИЧЕСКИЙ | Неопределенный |

### Сигналы обнаружения аномалий { #anomaly-detection-signals }

- Секретный доступ с нового диапазона IP/CIDR
- Скачок объема доступа (>3-кратный базовый уровень для пути)
- Доступ в нерабочее время для методов аутентификации человека
- Служба, получающая доступ к секретам, выходящим за рамки ее политики (отклоненные запросы)
- Несколько неудачных попыток аутентификации из одного источника
- Токен, созданный с необычно длинным TTL

### Отчетность о соблюдении требований { #compliance-reporting }

Создавать периодические отчеты, охватывающие:

1. **Доступ к инвентарю** — Какие идентификаторы получили доступ к каким секретам, когда
2. ** Соответствие требованиям ротации** — Секреты, просроченные для ротации
3. ** Изменение политики** — Политики, измененные с момента последнего ревью
4. ** Потерянные секреты** — Секреты, к которым недавно не было доступа (>90 дней)

Использование `audit_log_analyzer.py` для анализа журналов аудита хранилища или облака на наличие этих сигналов.

## Процедуры в чрезвычайных ситуациях { #emergency-procedures }

### Реагирование на утечку секретной информации (немедленное) { #secret-leak-response-immediate }

** Целевое время: Задержать в течение 15 минут с момента обнаружения.**

1. **Определить область применения ** — Какие секреты просочились, где (репозиторий, журнал, сообщение об ошибке, третья сторона)
2. **Немедленно отозвать** — Изменить скомпрометированные учетные данные в источнике (provider API, Vault, cloud SM).
3. **Аннулировать токены** — Отозвать все токены хранилища, которые получили доступ к утечке секрета
4. **Аудит радиуса поражения** — Запрос журналов аудита на предмет использования скомпрометированного секрета в окне раскрытия
5. **Уведомлять стейкхолдеров** — службу безопасности, владельцев затронутых сервисов, соответствие требованиям (если PII/регулируемые данные)
6. **Вскрытие** — Документирование первопричины, обновление элементов управления для предотвращения повторения

### Операции по опечатыванию хранилища { #vault-seal-operations }

**Когда закрывать:** Активный инцидент с безопасностью, затрагивающий инфраструктуру хранилища, подозрение на компрометацию ключа.

**Опечатывание** останавливает все операции с хранилищем. Используйте только в крайнем случае.

**Процедура вскрытия:**
1. Соберите кворум владельцев открытых ключей (порог Шамира)
2. Или подтвердите, что ключ KMS для автоматического снятия печати доступен
3. Распечатать с помощью `vault operator unseal` или перезапустите с автоматическим распечатыванием
4. Проверка повторного подключения устройств аудита
5. Проверьте активные договоры аренды и срок действия токена

Видишь `references/emergency_procedures.md` для получения полных плейбуков.

## Интеграция CI/CD { #cicd-integration }

### Коляска агента хранилища (Kubernetes) { #vault-agent-sidecar-kubernetes }

Агент Vault работает вместе с модулями приложений, обрабатывает аутентификацию и секретный рендеринг:

```yaml
# Pod annotation for Vault Agent Injector
annotations:
  vault.hashicorp.com/agent-inject: "true"
  vault.hashicorp.com/role: "api-server"
  vault.hashicorp.com/agent-inject-secret-db: "database/creds/app-readonly"
  vault.hashicorp.com/agent-inject-template-db: |
    {{- with secret "database/creds/app-readonly" -}}
    postgresql://{{ .Data.username }}:{{ .Data.password }}@db:5432/app
    {{- end }}
```

### Оператор внешних секретов (Kubernetes) { #external-secrets-operator-kubernetes }

Для команд, предпочитающих декларативные GitOps, а не коляски агентов:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: api-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: api-credentials
  data:
    - secretKey: api-key
      remoteRef:
        key: secret/data/production/api
        property: key
```

### Действия на GitHub OIDC { #github-actions-oidc }

Устраните долгоживущие секреты в CI с помощью федерации OIDC:

```yaml
- name: Authenticate to Vault
  uses: hashicorp/vault-action@v2
  with:
    url: https://vault.example.com
    method: jwt
    role: github-ci
    jwtGithubAudience: https://vault.example.com
    secrets: |
      secret/data/ci/deploy api_key | DEPLOY_API_KEY ;
      secret/data/ci/deploy db_password | DB_PASSWORD
```

## Анти-паттерны { #anti-patterns }

| Анти-паттерн | Риск | Правильный подход |
|-------------|------|-----------------|
| Жестко закодированные секреты в исходном коде | Утечка через репозиторий, журналы, вывод ошибок | Выборка из секретного хранилища во время выполнения |
| Долговечные статические токены (>30 дней) | Устаревшие учетные данные, отсутствие подотчетности | Динамические секреты или короткий TTL + поворот |
| Общие учетные записи служб | Отсутствие следа аудита для каждого потребителя | Идентификатор для каждой службы с уникальными учетными данными |
| Отсутствие политики ротации | Скомпрометированные сертификаты сохраняются на неопределенный срок | Автоматическая ротация по расписанию |
| Секреты в переменных окружения в CI | Отображается в журналах сборки, таблице процессов | Агент Vault или инъекция на основе OIDC |
| Одиночный незапечатываемый держатель для ключей | Коэффициент шины равен 1, восстановление заблокировано | Разделение Шамира (3 из 5) или автоматическое вскрытие |
| Устройство аудита не настроено | Нулевая видимость доступа | Устройства двойного аудита (файл + системный журнал) |
| Правила использования подстановочных знаков (`path "*"`) | Чрезмерно разрешенный, нарушает наименьшие привилегии | Явные политики на основе путей для каждой службы |
