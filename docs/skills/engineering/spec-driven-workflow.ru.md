## Обзор { #overview }

Воркфлоу, основанный на спецификациях, применяет единственное, не подлежащее обсуждению правило: ** напишите спецификацию ПЕРЕД написанием любого кода.** Не параллельно. Не после. Раньше.

Это не документация. Это контракт. Спецификация определяет, что должна делать система, что она ДОЛЖНА делать и чего она явно не будет делать. Каждая строка кода, которую вы пишете, восходит к требованию в спецификации. Каждый тест основан на определенном критерии приемлемости. Если его нет в спецификации, он не будет создан.

### Почему важна спецификация в первую очередь { #why-spec-first-matters }

1. ** Исключает переделки.** 60-80% дефектов возникают из-за требований, а не из-за реализации. Обнаружение двусмысленности в спецификации требует минут; обнаружение ее в процессе производства требует дней.
2. ** Обеспечивает ясность.** Если вы не можете написать, что должна делать система, простым языком, вы недостаточно хорошо понимаете проблему, чтобы писать код.
3. ** Включает параллелизм.** Как только спецификация утверждена, интерфейс, серверная часть, контроль качества и документация могут запускаться одновременно.
4. ** Создает подотчетность.** Спецификация - это определение "сделано". Никаких аргументов о том, является ли функция "завершенной" — либо она удовлетворяет критериям приемлемости, либо нет.
5. ** Напрямую передает TDD.** Критерии приемлемости в заданном формате /When/Then преобразуют 1:1 в тестовые примеры. Спецификация - ЭТО план тестирования.

### Железный закон { #the-iron-law }

```
NO CODE WITHOUT AN APPROVED SPEC.
NO EXCEPTIONS. NO "QUICK PROTOTYPES." NO "I'LL DOCUMENT IT LATER."
```

Если спецификация не написана, не ревью-рована и не одобрена, внедрение не начинается. Точка.

## Формат спецификации { #the-spec-format }

Каждая спецификация соответствует этой структуре. Никакие разделы не являются необязательными — если какой-либо раздел неприменим, напишите "N/A — [причина]", чтобы рецензенты знали, что это было рассмотрено, а не забыто.

### Обязательные разделы { #mandatory-sections }

| # | Раздел | Ключевые правила |
|---|---------|-----------|
| 1 | **Название и метаданные** | Автор, дата, статус (Черновик/на ревью/Одобрено/заменено), рецензенты |
| 2 | **Контекст** | Почему существует эта функция. 2-4 абзаца с доказательствами (метрики, билеты). |
| 3 | **Функциональные требования** | Ключевые слова RFC 2119 (MUST/ДОЛЖЕН/МОЖЕТ). Пронумерованный FR-N. Каждый из них является атомарным и поддается тестированию. |
| 4 | **Нефункциональные требования** | Производительность, безопасность, доступность, масштабируемость, надежность — все это имеет измеримые пороговые значения. |
| 5 | **Критерии приемлемости** | Заданный формат/When/Then. Каждый AC ссылается по крайней мере на один FR-* или NFR-*. |
| 6 | **Крайние случаи** | Пронумерованный EC-N. Охватите режимы сбоя для каждой внешней зависимости. |
| 7 | **Контракты API** | Интерфейсы в стиле TypeScript. Опишите ответы на вопросы об успехах и ошибках. |
| 8 | **Модели данных** | Формат таблицы с указанием поля, типа, ограничений. У каждого объекта из требований должна быть модель. |
| 9 | **Выходит за рамки** | Явные исключения с указанием причин. Предотвращает расползание области видимости во время реализации. |

### Ключевые слова RFC 2119 { #rfc-2119-keywords }

| Ключевое слово | Значение |
|---------|---------|
| **ДОЛЖЕН** | Абсолютное требование. Неконформен без этого. |
| **НЕ ДОЛЖЕН** | Абсолютный запрет. |
| **СЛЕДУЕТ** | Рекомендуется. Опускать только при наличии документально подтвержденного обоснования. |
| **МОЖЕТ** | Необязательно. Усмотрение исполнителя. |

Видишь [spec_format_guide.md](https://github.com/imgusev/claude-skills-ru/tree/main/engineering/skills/spec-driven-workflow/references/spec_format_guide.md) для получения полного шаблона с примерами по разделам, хорошо/bad шаблоны требований и шаблоны функционального типа (CRUD, интеграция, миграция).

Видишь [acceptance_criteria_patterns.md](https://github.com/imgusev/claude-skills-ru/tree/main/engineering/skills/spec-driven-workflow/references/acceptance_criteria_patterns.md) для получения полной библиотеки шаблонов с заданными критериями/When/Then в сценариях аутентификации, CRUD, поиска, загрузки файлов, оплаты, уведомления и доступности.

## Правила ограниченной автономии { #bounded-autonomy-rules }

Эти правила определяют, когда агент (человек или искусственный интеллект) ДОЛЖЕН остановиться и запросить указания. когда они смогут действовать независимо.

### ОСТАНОВИТЕСЬ и спросите, когда: { #stop-and-ask-when }

1. **Обнаружено смещение прицела.** Для реализации требуется что-то, чего нет в спецификации. Даже если это кажется очевидным, ОСТАНОВИТЕСЬ. Возможно, спецификация намеренно исключила это.

2. **Неоднозначность превышает 30%.** Если вы не можете определить правильное поведение из спецификации более чем для 30% заданного требования, спецификация является неполной. Не гадай.

3. ** Требуются критические изменения.** Реализация изменит существующий контракт API, схему базы данных или общедоступный интерфейс. Всегда проводите эскалацию.

4. **Последствия для безопасности.** Любое изменение, касающееся аутентификации, авторизации, шифрования или обработки персональных данных, требует явного одобрения.

5. ** Характеристики производительности неизвестны.** Если в требовании указано "ДОЛЖНО быть выполнено за < 500 мс", но у вас нет возможности измерить или гарантировать это, выполните эскалацию, прежде чем реализовывать предположение.

6. **Межкомандные зависимости.** Если спецификация требует согласования с другой командой или службой, подтвердите зависимость, прежде чем строить на ее основе.

### Продолжайте автономно, когда: { #continue-autonomously-when }

1. **Спецификация ясна и недвусмысленна** для текущей задачи.
2. ** Все критерии приемлемости имеют проходные тесты **, и вы проводите рефакторинг внутренних компонентов.
3. ** Изменения не являются нарушающими ** — никаких изменений в общедоступном API, схеме или поведении.
4. **Внедрение - это прямой перевод** четко определенного критерия приемлемости.
5. **Обработка ошибок выполняется в соответствии с установленными шаблонами**, уже задокументированными в базе кода.

### Протокол эскалации { #escalation-protocol }

Когда вы должны остановиться, обеспечьте:

```markdown
## Escalation: [Brief Title]

**Blocked on:** [requirement ID, e.g., FR-3]
**Question:** [Specific, answerable question — not "what should I do?"]
**Options considered:**
  A. [Option] — Pros: [...] Cons: [...]
  B. [Option] — Pros: [...] Cons: [...]
**My recommendation:** [A or B, with reasoning]
**Impact of waiting:** [What is blocked until this is resolved?]
```

Никогда не повышайте эскалацию без рекомендации. Никогда не задавайте открытых вопросов. Всегда предлагайте варианты.

Видишь `references/bounded_autonomy_rules.md` для получения полной матрицы принятия решений.

## Воркфлоу — 6 этапов { #workflow--6-phases }

### Этап 1: Сбор требований { #phase-1-gather-requirements }

** Цель:** Понять, что нужно построить и почему.

1. ** Опросите пользователя.** Спросите:
   - Какую проблему это решает?
   - Кто такие пользователи?
   - На что похож успех?
   - Что явно не должно быть построено?
2. **Прочтите существующий код.** Разберитесь в текущей системе, прежде чем предлагать изменения.
3. **Определите ограничения.** Бюджеты производительности, требования к безопасности, обратная совместимость.
4. ** Перечислите неизвестные.** Каждое неизвестное - это риск. Выявляйте их сейчас, а не во время реализации.

** Критерии выхода: ** Вы можете объяснить эту функцию кому-то, незнакомому с проектом, за 2 минуты.

### Фаза 2: Запись спецификации { #phase-2-write-spec }

**Цель:** Подготовить полный технический документ в соответствии с приведенным выше форматом спецификации.

1. Заполните каждый раздел шаблона. Ни один раздел не остался пустым.
2. Пронумеруйте все требования (FR-*, NFR-*, AC-*, EC-*, OS-*).
3. Точно используйте ключевые слова RFC 2119.
4. Напишите критерии приемлемости в заданном формате/When/Then.
5. Определите контракты API с помощью типов в стиле TypeScript.
6. Перечислите явные исключения в поле "Вне области видимости".

** Критерии выхода: ** Спецификация может быть передана разработчику, который не соответствовал требованиям, и он может реализовать функцию, не задавая уточняющих вопросов.

### Этап 3: Проверка спецификации { #phase-3-validate-spec }

**Цель:** Убедиться, что спецификация является полной, непротиворечивой и выполнимой.

Бежать `spec_validator.py` в соответствии со спецификационным файлом:

```bash
python spec_validator.py --file spec.md --strict
```

Чек-лист для проверки вручную validation validation:
- [ ] Каждое функциональное требование имеет по крайней мере один критерий приемлемости
- [ ] Каждый критерий приемлемости поддается проверке (никаких субъективных формулировок)
- [ ] Контракты API охватывают все конечные точки, упомянутые в требованиях
- [ ] Модели данных охватывают все объекты, упомянутые в требованиях
- [ ] Пограничные случаи охватывают режимы сбоя для каждой внешней зависимости
- [ ] Вне сферы охвата прямо указывает на то, что было рассмотрено и отклонено
- [ ] Нефункциональные требования имеют измеримые пороговые значения

** Критерии выхода: ** Спецификация набирает более 80 баллов на валидаторе, и все пункты ручного чек-листа проходят проверку.

### Этап 4: Создание тестов { #phase-4-generate-tests }

**Цель:** Извлечь тестовые примеры из критериев приемлемости перед написанием кода реализации.

Бежать `test_extractor.py` в соответствии с утвержденной спецификацией:

```bash
python test_extractor.py --file spec.md --framework pytest --output tests/
```

1. Каждый критерий приемлемости становится одним или несколькими тестовыми примерами.
2. Каждый граничный случай становится тестовым.
3. Тесты — это заглушки - они определяют утверждение, но не реализацию.
4. Изначально все тесты должны завершиться неудачей (красная фаза TDD).

** Критерии выхода: ** У вас есть тестовый файл, в котором каждый тест завершается неудачей с пометкой "не реализовано" или эквивалентом.

### Этап 5: Внедрение { #phase-5-implement }

** Цель:** Написать код, который позволяет проходить неудачные тесты по одному критерию приемлемости за раз.

1. Выберите один критерий приемлемости (начните с самого простого).
2. Сделайте так, чтобы его тесты проходили с минимальным количеством кода.
3. Запустите полный набор тестов — никаких регрессий.
4. Совершить.
5. Выберите следующий критерий приемлемости. Повторите.

**Правила:**
- НЕ реализовывайте ничего, чего нет в спецификации.
- НЕ проводите оптимизацию до выполнения всех критериев приемлемости.
- Не проводите рефакторинг до выполнения всех критериев приемлемости.
- Если вы обнаружите отсутствующее требование, сначала остановитесь и обновите спецификацию.

**Критерии выхода:** Все тесты пройдены. Все критерии приемлемости выполнены.

### Этап 6: Ревью для себя { #phase-6-self-review }

** Цель:** Проверьте соответствие реализации спецификации перед выполнением разметки.

Ознакомьтесь с приведенным ниже чек-листом для ревью. Если какой-либо элемент выходит из строя, исправьте его, прежде чем объявлять задачу завершенной.

---

## Чек-лист для ревью для самостоятельной работыReviewReview { #self-review-checklist }

Прежде чем отмечать какую-либо реализацию как выполненную, проверьте ВСЕ следующее:

- [ ] ** Каждый критерий приемлемости имеет проходной тест.** Исключений нет. Если AC-3 существует, то тест для AC-3 существует и проходит успешно.
- [ ] ** У каждого граничного случая есть тест.** У всех EC-1 по EC-N есть соответствующие тестовые случаи.
- [ ] ** Нет расширения области видимости.** Реализация не включает функции, отсутствующие в спецификации. Если вы что-то добавили, либо обновите спецификацию, либо удалите это.
- [ ] ** Контракты API соответствуют реализации.** Запрос/response формы в коде точно соответствуют спецификации. Названия полей, типы, коды состояния — все это.
- [ ] ** Протестированы сценарии ошибок.** У каждого ответа на ошибку, определенного в спецификации, есть тест, который его триггер.
- [ ] **Проверены нефункциональные требования.** Если в спецификации указано < 500 мс, у вас есть доказательства (бенчмарк, нагрузочный тест, профилирование) того, что он соответствует пороговому значению.
- [ ] **Модель данных совпадает.** Схема базы данных соответствует спецификации. Никаких дополнительных столбцов, никаких пропущенных ограничений.
- [ ] ** Элементы, находящиеся вне области видимости, не созданы.** Дважды проверьте, что ничего из раздела "Вне области видимости" не просочилось в реализацию.

## Интеграция с руководством по TDD { #integration-with-tdd-guide }

Управляемый спецификациями воркфлоу и TDD дополняют друг друга, а не конкурируют:

```
Spec-Driven Workflow          TDD (Red-Green-Refactor)
─────────────────────         ──────────────────────────
Phase 1: Gather Requirements
Phase 2: Write Spec
Phase 3: Validate Spec
Phase 4: Generate Tests  ──→  RED: Tests exist and fail
Phase 5: Implement       ──→  GREEN: Minimal code to pass
Phase 6: Self-Review     ──→  REFACTOR: Clean up internals
```

**Хэндофф:** Воркфлоу, управляемый спецификациями, создает тестовые заготовки (фаза 4). С этого момента TDD берет верх. Спецификация подсказывает вам, ЧТО нужно протестировать. TDD расскажет вам, КАК это реализовать.

Использование `engineering-team/tdd-guide` для:
- Красно-зеленый-дисциплина цикла рефакторинга
- Анализ охвата и выявление пробелов
- Тестовые шаблоны, специфичные для фреймворка (Jest, Pytest, JUnit)

Использование `engineering/spec-driven-workflow` для:
- Определение того, что нужно построить, прежде чем строить это
- Разработка критериев приемлемости
- Проверка полноты
- Контроль области применения

## Анти-паттерны { #anti-patterns }

### 1. Кодирование перед утверждением спецификации { #1-coding-before-spec-approval }

** Симптом: ** "Я начну кодировать, пока идет ревью спецификации".
** Проблема:** В ходе ревью будут выявлены изменения. Теперь у вас есть код, который реализует отклоненный дизайн.
**Правило:** Внедрение не начинается до тех пор, пока спецификация не получит статус "Утверждена".

### 2. Расплывчатые критерии приемлемости { #2-vague-acceptance-criteria }

** Симптом:** "Система должна работать хорошо" или "Пользовательский интерфейс должен быть отзывчивым".
**Проблема:** Непроверяемо. Что значит "хорошо"? Что значит "отзывчивый"?
** Правило: ** Каждый критерий приемлемости должен поддаваться машинной проверке. Если вы не можете написать для этого тест, перепишите критерий.

### 3. Отсутствующие крайние случаи { #3-missing-edge-cases }

**Симптом:** Указан счастливый путь, пути ошибок - нет.
** Проблема:** Разработчики изобретают обработку ошибок на лету, что приводит к несогласованному поведению.
**Правило:** Для каждой внешней зависимости (API, базы данных, файловой системы, пользовательского ввода) укажите по крайней мере один сценарий сбоя.

### 4. Спецификация в качестве специальной документации { #4-spec-as-post-hoc-documentation }

** Симптом: ** "Позвольте мне написать спецификацию теперь, когда функция готова".
**Проблема:** Это документация, а не спецификация. Он описывает то, что было построено, а не то, что должно было быть построено. Он не может отлавливать ошибки проектирования, потому что дизайн уже заморожен.
**Правило:** Если спецификация была написана после кода, это не спецификация. Повторно пометьте его как документацию.

### 5. Позолота, выходящая за рамки спецификации { #5-gold-plating-beyond-spec }

** Симптом: ** "Пока я был там, я также добавил..."
**Проблема:** Непроверенный код. Непросмотренный дизайн. Возможны незначительные ошибки в функции "бонус".
** Правило:** Если этого нет в спецификации, оно не создается. Отправьте новую спецификацию для дополнительных функций.

### 6. Критерии приемлемости без прослеживаемости требований { #6-acceptance-criteria-without-requirement-traceability }

**Симптом:** AC-7 существует, но не ссылается ни на какой FR-* или NFR-*.
**Проблема:** Потерянные критерии означают, что либо требование отсутствует, либо критерий не нужен.
**Правило:** Каждый AC-* ДОЛЖЕН ссылаться по крайней мере на один FR-* или NFR-*.

### 7. Пропуск проверки { #7-skipping-validation }

** Симптом: ** "Спецификация выглядит нормально, давайте просто начнем".
**Проблема:** Отсутствующие разделы, обнаруженные во время реализации, приводят к задержкам блокировки.
**Правило:** Всегда запускайте `spec_validator.py --strict` перед началом внедрения. Исправьте все предупреждения.

## Инструменты { #tools }

| Сценарий | Цель | Ключевые флаги |
|--------|---------|-----------|
| `spec_generator.py` | Сгенерировать шаблон спецификации на основе названия объекта/description | `--name`, `--description`, `--format`, `--json` |
| `spec_validator.py` | Проверка полноты спецификации (оценка 0-100) | `--file`, `--strict`, `--json` |
| `test_extractor.py` | Извлекать тестовые заготовки из критериев приемлемости | `--file`, `--framework`, `--output`, `--json` |

```bash
# Generate a spec template
python spec_generator.py --name "User Authentication" --description "OAuth 2.0 login flow"

# Validate a spec
python spec_validator.py --file specs/auth.md --strict

# Extract test cases
python test_extractor.py --file specs/auth.md --framework pytest --output tests/test_auth.py
```
