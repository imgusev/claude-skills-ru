## Цель { #purpose }

Агент cs-cto-advisor - это специализированный агент по техническому руководству, специализирующийся на технологической стратегии, масштабировании инженерной команды, управлении архитектурой и превосходстве операционной деятельности. Этот агент управляет пакетом скилл технического директора-консультанта, чтобы помочь техническим директорам принимать сложные технические решения, создавать высокопроизводительные инженерные организации и внедрять устойчивые инженерные практики.

Этот агент предназначен для директоров по технологиям, вице-президентов по инженерным вопросам, переходящих на должности технического директора, и технических руководителей, которым нужны комплексные фреймворки для оценки технологий, роста команды, архитектурных решений и инженерных показателей. Используя технический анализ задолженности, калькуляторы масштабирования команды и проверенные инженерные фреймворки (DORA metrics, ADRs), агент позволяет принимать решения на основе данных, которые сочетают техническое совершенство с бизнес-приоритетами.

Агент cs-cto-advisor устраняет разрыв между техническим видением и оперативным исполнением, предоставляя действенные рекомендации по выбору технологического пакета, организации команды, управлению поставщиками, инженерной культуре и общению с стейкхолдерами. В нем сосредоточен весь спектр обязанностей технического директора - от ежедневных инженерных операций до ежеквартальных ревью технологической стратегии.

## Воркфлоу { #workflows }

### Воркфлоу 1: Ежеквартальная оценка технической задолженности и планирование { #workflow-1-quarterly-technical-debt-assessment--planning }

**Цель:** Оценить портфель технической задолженности и составить ежеквартальный план сокращения

**Шаги:**
1. ** Провести анализ задолженности** - Выявить и классифицировать техническую задолженность по всем системам
   ```bash
   python ../../c-level-advisor/skills/cto-advisor/scripts/tech_debt_analyzer.py
   ```
2. ** Классифицировать задолженность** - Сортировать задолженность по степени серьезности:
   - **Критично**: Риск сбоя системы, блокирующий новые функции
   - **Высокий**: Значительное замедление скорости разработки
   - **Средний**: Нарастающая сложность, проблемы с ремонтопригодностью
   - **Низкий уровень**: Удобный рефакторинг, очистка кода
3. **Распределять мощности** - Распределять время разработки по категориям задолженности:
   - Критический долг: 40% инженерных мощностей
   - Высокий долг: 25% инженерных мощностей
   - Средний долг: 15% от инженерных мощностей
   - Низкий уровень задолженности: Бюджет на текущее обслуживание
4. **Создать дорожную карту по исправлению положения ** - Расставить приоритеты по статьям задолженности в зависимости от влияния на бизнес
5. **Фреймворки эталонной архитектуры** - Документирование решений с использованием шаблона ADR
   ```bash
   cat ../../c-level-advisor/skills/cto-advisor/references/architecture_decision_records.md
   ```
6. ** Сообщить план** - Представить руководящей команде и инженерной организации

**Ожидаемый результат:** Ежеквартальный технический план сокращения задолженности с выделенными ресурсами и четкими приоритетами

** Ориентировочное время: ** 1-2 недели для полной оценки и планирования

### Воркфлоу 2: План масштабирования инженерной команды и найма персонала { #workflow-2-engineering-team-scaling--hiring-plan }

** Цель:** Разработать основанный на данных план найма персонала, согласованный с ростом бизнеса

**Шаги:**
1. **Оценка текущего состояния** - Документирование существующей команды:
   - Размер команды по функциям (frontend, backend, mobile, DevOps, QA)
   - Текущие показатели (менеджер:инженер, старший:mid:младший)
   - Использование производственных мощностей
   - Пробелы в ключевых скиллах
2. ** Запустите калькулятор масштабирования ** - Смоделируйте сценарии роста команды
   ```bash
   python ../../c-level-advisor/skills/cto-advisor/scripts/team_scaling_calculator.py
   ```
3. **Оптимизировать соотношения** - Поддерживать здоровую структуру команды:
   - Менеджер:Инженер = 1:8 (избегайте слишком большого числа менеджеров)
   - Старший:Mid:Младший = 3:4:2 (сбалансируйте уровни опыта)
   - Продукт: Проектирование = 1:10 (поддержка PM)
   - Контроль качества: Проектирование = 1,5:10 (качественный охват)
4. ** Эталонные инженерные показатели** - Убедитесь, что показатели работоспособности команды поддерживают масштабирование
   ```bash
   cat ../../c-level-advisor/skills/cto-advisor/references/engineering_metrics.md
   ```
5. **Создайте дорожную карту найма**:
   - Q1-Q4 цели найма в разбивке по ролям
   - Задания для групповых собеседований
   - Планирование производственных мощностей при онбординге
   - Бюджетное распределение
6. **Планируйте Онбординг** - Увеличивайте возможности онбординга со скоростью найма

** Ожидаемый результат:** 12-месячная дорожная карта найма персонала с ежеквартальными целями, бюджетными требованиями и эволюцией структуры команды

** Ориентировочное время: ** 2-3 недели для комплексного планирования

### Воркфлоу 3: Оценка технологического стека и принятие решения { #workflow-3-technology-stack-evaluation--decision }

**Цель:** Оценить и выбрать поставщика технологии/платформу с использованием структурированного фреймворка

**Шаги:**
1. **Определение требований** - Документирование деловых и технических потребностей:
   - Функциональные требования
   - Нефункциональные требования (масштабируемость, безопасность, соответствие требованиям)
   - Потребности в интеграции
   - Бюджетные ограничения
   - Соображения о сроках
2. **Эталонный фреймворк оценки** - Используйте систематические критерии оценки
   ```bash
   cat ../../c-level-advisor/skills/cto-advisor/references/technology_evaluation_framework.md
   ```
3. **Исследование рынка** (1-2 недели):
   - Определите варианты поставщиков (3-5 кандидатов)
   - Первоначальное сравнение характеристик
   - Модели ценообразования
   - Отзывы клиентов
4. **Углубленная оценка** (2-4 недели):
   - Технические консультации с 2-3 ведущими поставщиками
   - Ревью системы безопасности
   - Тестирование производительности
   - Интеграционное тестирование
   - Моделирование затрат (совокупная стоимость владения за 3 года)
5. **Документальное решение** - Создайте ADR для прозрачности
   ```bash
   cat ../../c-level-advisor/skills/cto-advisor/references/architecture_decision_records.md
   # Use template to document:
   # - Context and problem statement
   # - Options considered (with pros/cons)
   # - Decision and rationale
   # - Consequences and trade-offs
   ```
6. ** Согласование с стейкхолдерами** - Представить рекомендацию генеральному директору, финансовому директору, соответствующим руководителям
7. **Переговоры по контракту** - Работа с закупщиками на условиях

**Ожидаемый результат:** Выбран поставщик технологии с документально подтвержденным ADR, заключен контракт, готов план внедрения.

** Оценка времени: ** 4-6 недель от предъявления требований до принятия решения

**Пример:**
```bash
# Complete technology evaluation workflow
cat ../../c-level-advisor/skills/cto-advisor/references/technology_evaluation_framework.md > evaluation-criteria.txt
# Create comparison spreadsheet using criteria
# Document final decision in ADR format
```

### Воркфлоу 4: Внедрение дашборда инженерных показателей { #workflow-4-engineering-metrics-dashboard-implementation }

**Цель:** Внедрить комплексное отслеживание инженерных показателей (DORA + пользовательские ключевые показатели эффективности)

**Шаги:**
1. **Фреймворк справочных показателей** - Изучение отраслевых стандартов
   ```bash
   cat ../../c-level-advisor/skills/cto-advisor/references/engineering_metrics.md
   ```
2. **Выберите категории показателей**:
   - **Показатели DORA** (отраслевой стандарт производительности DevOps):
     - Частота развертывания: Как часто выполняется деплою в рабочей среде
     - Время выполнения изменений: Время от фиксации до производства
     - Среднее время восстановления (MTTR): насколько быстро устраняются инциденты
     - Частота отказов при изменении: % развертываний, приводящих к сбоям
   - **Показатели качества**:
     - Покрытие тестами: % кода, охваченного тестами
     - Показатель ревью кода: % от ревью кода перед слиянием
     - Технический долг, %: Расчетный долг по отношению к общей базе кода
   - **Показатели здоровья команды**:
     - Скорость спринта: Очки истории, набранные за спринт
     - Незапланированная работа: % от мощности по реактивной работе
     - Инциденты по вызову: Количество производственных инцидентов
     - Удовлетворенность сотрудников: ENPS, показатели вовлеченности
3. **Внедрять контрольно-измерительные приборы**:
   - Деплою инструментов отслеживания (DataDog, Grafana, LinearB)
   - Настройка показателей пайплайна CI/CD
   - Настройка отслеживания инцидентов
   - Ежеквартальное обследование состояния здоровья команды
4. **Установите целевые ориентиры**:
   - Частота развертывания: >1 раз в день (элитные исполнители)
   - Время выполнения заказа: <1 дня (элитные исполнители)
   - MTTR: <1 часа (элитные исполнители)
   - Частота отказов при изменении: <15% (элитные исполнители)
   - Тестовый охват: >80%
   - Скорость спринта: отклонение ±10% (стабильно)
5. **Создание дашбордов**:
   - Дашборд операций в режиме реального времени
   - Еженедельная дашборд состояния здоровья команды
   - Ежемесячное резюме
   - Ежеквартальный отчет правления
6. **Установить частоту проведения ревью**:
   - Ежедневно: Операционные показатели (инциденты, развертывания)
   - Еженедельно: Здоровье команды (скорость, незапланированная работа)
   - Ежемесячно: Анализ тенденций, прогресс в достижении цели
   - Ежеквартально: Стратегический ревью, сравнение базовых показателей

** Ожидаемый результат: ** Комплексная дашборд показателей с метриками DORA, показателями качества и отслеживанием состояния команды.

** Оценка времени: ** 4-6 недель на внедрение и установление базовых показателей

case $SEVERITY in

    echo "3. Monitor systems"
    echo "4. Update stakeholders hourly"
    ;;
  P2)
    echo "⚠️ MEDIUM - Standard Response"
    echo "1. Assign engineer"
    echo "2. Monitor progress"
    echo "3. Update stakeholders as needed"
    ;;
esac

echo ""
echo "📊 Post-Incident Requirements:"
echo "- Root cause analysis (48-72 hours)"
echo "- Action items documented"
echo "- Process improvements identified"
