# /сфокусированный-исправить { #focused-fix }

Систематически восстанавливайте всю функцию или модуль целиком, используя 5-фазный протокол. Цель: `$ARGUMENTS` (путь к объекту или имя модуля).

Если `$ARGUMENTS` пусто, спросите пользователя, какую функцию/ модуль нужно исправить.

## Протокол — Выполните ВСЕ 5 этапов ПО ПОРЯДКУ { #protocol--execute-all-5-phases-in-order }

### Этап 1: ОБЛАСТЬ применения — Нанесение на карту границы объекта { #phase-1-scope--map-the-feature-boundary }

1. Определите основную папку/файлы для целевой функции
2. Прочитайте КАЖДЫЙ файл в этой папке — поймите его назначение
3. Создайте манифест объекта:

```
FEATURE SCOPE:
  Primary path: <path>
  Entry points: [files imported by other parts of the app]
  Internal files: [files only used within this feature]
  Total files: N
```

### Фаза 2: ТРАССИРОВКА — сопоставление всех зависимостей { #phase-2-trace--map-all-dependencies }

**ВХОДЯЩИЙ** (что импортирует эта функция):
- Для каждого оператора импорта проследите до источника, убедитесь, что он существует и экспортирован
- Проверьте переменные env, конфигурационные файлы, модели баз данных, конечные точки API, сторонние пакеты

**ИСХОДЯЩИЙ** (что импортирует эту функцию):
- Выполните поиск по всей базе кода для импорта из этой функции
- Убедитесь, что потребители используют правильный API/интерфейс

Выведите карту зависимостей с входящими, исходящими, переменными env и конфигурационными файлами.

### Этап 3: ДИАГНОСТИКА — Поиск каждой проблемы { #phase-3-diagnose--find-every-issue }

Выполните ВСЕ диагностические проверки:

- **Код**: импорт разрешен, циклических удалений нет, типы согласованы, обработка ошибок, TODO/FIXME
- **Время выполнения**: заданы переменные env, текущие миграции, правильные формы API
- ** Тесты**: запустите ВСЕ связанные тесты, запишите сбои, проверьте покрытие
- **Журналы**: проверьте журнал git на наличие последних изменений, найдите журналы ошибок
- **Конфигурация**: проверка конфигурационных файлов, проверка несоответствий dev/prod

Для каждой найденной проблемы:
- Подтвердите первопричину доказательствами, прежде чем добавлять в список исправлений
- Назначьте риск: ВЫСОКИЙ (общедоступный API, авторизация, >3 вызывающих абонента) / СРЕДНИЙ (внутренний с тестами) / НИЗКИЙ (конечный модуль)

Выведите отчет о диагностике с проблемами, сгруппированными по степени серьезности.

### Фаза 4: ИСПРАВЛЕНИЕ — Систематический ремонт { #phase-4-fix--repair-systematically }

Исправьте именно в этом порядке:
1. **Зависимости** — нарушенный импорт, отсутствующие пакеты
2. **Типы** — несоответствия типов на границах
3. **Логика** — ошибки бизнес-логики
4. **Тесты** — исправьте или создайте тесты для каждого исправления
5. **Интеграция** — сквозная проверка с потребителями

Правила:
- Устраняйте по одной проблеме за раз, запускайте соответствующий тест после каждой
- Если исправление нарушает что-то еще → вернитесь к ДИАГНОСТИКЕ
- Зафиксируйте ВЫСОКИЙ уровень перед СРЕДНИМ, а затем НИЗКИЙ
- ** Правило 3-х исправлений **: Если более 3 исправлений создают НОВЫЕ проблемы, ОСТАНОВИТЕСЬ. Сообщите пользователю, что архитектура, возможно, нуждается в переосмыслении, а не в исправлении.

### Этап 5: ПРОВЕРКА — Подтвердите, что все работает { #phase-5-verify--confirm-everything-works }

1. Запустите ВСЕ тесты в папке компонентов
2. Запустите ВСЕ тесты в файлах, которые импортируются из этой функции
3. Запустите полный набор тестов, если он доступен
4. Обобщите все внесенные изменения

Выведите отчет о завершении с измененными файлами, примененными исправлениями, результатами тестирования и проверенными пользователями.

## Железный закон { #iron-law }

```
NO FIXES WITHOUT COMPLETING SCOPE → TRACE → DIAGNOSE FIRST
```

Если вы не завершили этап 3, вы не можете предлагать исправления.
