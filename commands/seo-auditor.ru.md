# /seo-аудитор { #seo-auditor }

Систематически сканируйте, проводите аудит и оптимизируйте файлы документации для SEO. Цели README.md файлы и документы/ страницы — исправляет проблемы на месте, сохраняет рейтинг на высокоэффективных страницах и формирует окончательный отчет.

## Использование { #usage }

```bash
/seo-auditor                    # Audit all docs/ and root README.md
/seo-auditor docs/skills/       # Audit a specific docs subdirectory
/seo-auditor --report-only      # Scan without making changes
```

## Что он делает { #what-it-does }

Выполните все 7 этапов последовательно. Автоматическое исправление неразрушающих проблем. Сохраняйте существующий контент высокого рейтинга. Доложите обо всем в конце.

## Фаза 1: Обнаружение и исходные данные { #phase-1-discovery--baseline }

### 1а. Идентификация целевых файлов { #1a-identify-target-files }

Сканируйте файлы документации, которые нуждаются в SEO-аудите:

```bash
# Find all markdown files in docs/ and root README files
find docs/ -name '*.md' -type f | sort
find . -maxdepth 2 -name 'README.md' -not -path './.codex/*' -not -path './.gemini/*' | sort
```

Классифицируйте каждый файл:
- **Новые/недавно измененные** — файлы, измененные за последние 2 фиксации (проверьте через `git log`)
- **Индексные страницы** — `index.md` файлы (высокий авторитет, обращаться с ними осторожно)
- **Страницы с скиллами** — `docs/skills/**/*.md` (сгенерированный `generate-docs.py`)
- **Статические страницы** — `docs/index.md`, `docs/getting-started.md`, `docs/integrations.md` и т.д.
- **Файлы README** — корневого уровня и уровня домена README.md

### 1b. Фиксация базовой линии { #1b-capture-baseline }

Для каждого целевого файла извлеките текущее состояние SEO:
- `title:` поле frontmatter → становится `<title>` тег
- `description:` поле frontmatter → становится `<meta name="description">`
- Первый `# H1` заголовок
- Все `## H2` и `### H3` подзаголовки
- Количество слов
- Количество внутренних ссылок
- Количество внешних ссылок

Сохраните базовую линию в памяти для отчета.

## Этап 2: Аудит мета-тегов { #phase-2-meta-tag-audit }

Для каждого файла с YAML frontmatter проверьте и исправьте:

### Тег заголовка (`title:`) { #title-tag-title }

**Правила:**
- Должно существовать и быть непустым
- Длина: в идеале 50-60 символов (Google сокращает до ~60)
- Должно содержать основное ключевое слово
- Заголовок другой страницы не должен дублировать
- Для страниц с скиллами: следует следовать шаблону `{Skill Name} — {Differentiator} - {site_name}`
- имя_сайта из `mkdocs.yml` добавляется автоматически — не дублируйте его в заголовке

**Автоматическое исправление:** Если заголовок является общим (например, просто название скилла), дополните его контекстом домена, используя шаблон DOMAIN_SEO_SUFFIX из `scripts/generate-docs.py`.

### Мета-описание (`description:`) { #meta-description-description }

**Правила:**
- Должно существовать и быть непустым
- Длина: 120-160 символов (Google сокращает до ~160)
- Естественно, должно содержать основное ключевое слово
- Должно быть уникальным для всех страниц — нет двух страниц с одинаковым описанием
- Должен содержать призыв к действию или ценностное предложение
- Не должно начинаться с "Эта страница..." или "Этот документ..."

** Автоматическое исправление:** Если описание отсутствует или является общим, сгенерируйте его из SKILL.md описание на переднем плане (если доступно) или из первого абзаца содержания. Используйте `extract_description_from_frontmatter()` функция от `generate-docs.py` в качестве ссылки.

### Сценарий проверки { #validation-script }

Запускается для каждого файла, который имеет HTML-вывод в `site/`:

```bash
python3 marketing-skill/skills/seo-audit/scripts/seo_checker.py --file site/{path}/index.html
```

Проанализируйте партитуру. Отмечайте любую страницу, набравшую менее 60 баллов.

## Этап 3: Качество контента и удобочитаемость { #phase-3-content-quality--readability }

Для каждого целевого файла проанализируйте и улучшите:

### Структура заголовка { #heading-structure }

**Правила:**
- Ровно один `# H1` на страницу
- H2s следуют за H1, H3s следуют за H2 — никаких пропусков уровней
- Заголовки должны содержать ключевые слова естественным образом (не напичканные).
- Никаких повторяющихся заголовков на одной странице

**Автоматическое исправление:** Если уровни заголовков пропущены (H1 → H3), настройте правильную иерархию.

### Удобочитаемость { #readability }

Запустите программу оценки содержимого для каждого файла:

```bash
python3 marketing-skill/skills/content-production/scripts/content_scorer.py {file_path}
```

Проверьте баллы за:
- ** Читабельность** — стремитесь к набору баллов ≥ 70
- ** Структура** — стремитесь набрать более 60 баллов
- ** Вовлеченность** — стремитесь набрать более 50 баллов

### Правила качества контента { #content-quality-rules }

- **Абзацы:** Ни один абзац не должен быть длиннее 5 предложений
- ** Предложения:** Средняя длина предложения 15-20 слов
- **Страдательный залог:** Менее 15% предложений
- **Переходные слова:** По крайней мере, в 30% предложений используются переходы
- ** Маркированные списки:** Используйте списки для более чем 3 элементов вместо встроенных списков, разделенных запятыми

### Обнаружение контента с помощью искусственного интеллекта { #ai-content-detection }

Запустите humanizer scorer для негенерированного контента (README.md файлы, статические страницы):

```bash
python3 marketing-skill/skills/content-humanizer/scripts/humanizer_scorer.py {file_path}
```

Отмечайте страницы, набравшие менее 50 баллов (слишком похоже на искусственный интеллект). Для этих страниц примените голосовые приемы из `marketing-skill/skills/content-humanizer/references/voice-techniques.md`:
- Замените клише искусственного интеллекта ("вникать", "использовать", "важно отметить").
- Варьируйте длину предложения
- Добавляйте конкретные примеры вместо общих утверждений
- Используйте активный голос

** Важно:** Изменяйте только тот контент, который был недавно создан или обновлен. Не переписывайте страницы с хорошим рейтингом — сохраняйте их содержимое.

## Этап 4: Оптимизация по ключевым словам { #phase-4-keyword-optimization }

### 4а. Определите целевые ключевые слова для каждой страницы { #4a-identify-target-keywords-per-page }

В зависимости от назначения страницы и домена:

| Тип страницы | Основные ключевые слова | Второстепенные ключевые слова |
|-----------|-----------------|-------------------|
| Домашняя страница (docs/index.md) | "Скиллы Claude Code", "плагины для агента" | "Скиллы Кодекса", "Gemini CLI", "OpenClaw" |
| Страницы с скиллами | Название скилла + "Код Клода" | "скилл агента", "плагин Codex", доменные термины |
| Страницы агента | Имя агента + "агент по кодированию искусственного интеллекта" | "Клод Код", "оркестратор" |
| Страницы команд | Название команды + "слэш-команда" | "Код Клода", "Кодирование с помощью искусственного интеллекта" |
| Приступаем к работе | "установите скиллы с кодом Клода" | названия платформ |
| Индекс домена | Домен + "Скиллы" + "плагины" | "Код Клода", названия платформ |

### 4b. Проверка размещения ключевых слов { #4b-keyword-placement-checks }

Для каждой страницы убедитесь, что основное ключевое слово отображается в:
- [ ] Тег заголовка (frontmatter `title:`)
- [ ] Мета-описание (frontmatter `description:`)
- [ ] Заголовок H1
- [ ] Первый абзац (в пределах первых 100 слов)
- [ ] По крайней мере, один подзаголовок H2
- [ ] Изображение с альтернативным текстом (при наличии изображений)
- [ ] URL slug (только для новых страниц — никогда не меняйте существующие URL-адреса)

### 4c. Плотность ключевых слов { #4c-keyword-density }

- Основное ключевое слово: 1-2% от общего количества слов
- Второстепенные ключевые слова: 0,5-1% каждое
- Отсутствие наполнения ключевыми словами — если плотность превышает 3%, уменьшите ее

**Важно:** Никогда не меняйте URL-адреса существующих страниц. Изменение URL-адреса приводит к разрыву входящих ссылок и снижению рейтинга. Оптимизируйте только контент и мета-теги.

## Этап 5: Аудит ссылок { #phase-5-link-audit }

### 5а. Внутренние ссылки { #5a-internal-links }

Для каждого целевого файла проверьте все ссылки на Markdown `[text](url)`:

- Убедитесь, что целевой объект существует (путь к файлу разрешен)
- Проверьте, нет ли неработающих относительных ссылок (`../`, `./`)
- Проверка якорных ссылок (`#section-name`) указать на существующие заголовки

**Автоматическое исправление:** Используйте `rewrite_skill_internal_links()` и `rewrite_relative_links()` функции из `generate-docs.py` в качестве ссылки. Перепишите сломанные скиллы - внутренние ссылки на исходные адреса GitHub.

### 5b. Обнаружение дублирующегося контента { #5b-duplicate-content-detection }

Сравните мета-описания на всех страницах:

```bash
grep -rh '^description:' docs/**/*.md | sort | uniq -d
```

Если обнаружены дубликаты, сделайте каждое описание уникальным, добавив контекст для конкретной страницы.

Сравните заголовки H1 на всех страницах — ни на одной из двух страниц не должно быть одинакового H1.

### 5c. Обнаружение потерянной страницы { #5c-orphan-page-detection }

Проверьте, все ли страницы в `docs/` на который ссылаются в `mkdocs.yml` навигатор. Страницы, отсутствующие в навигационной системе, являются сиротами — они не будут отображаться в навигации и могут не быть проиндексированы.

```bash
# Find doc pages not in mkdocs nav
find docs -name '*.md' -not -name 'index.md' | while read f; do
  slug=$(echo "$f" | sed 's|docs/||')
  grep -q "$slug" mkdocs.yml || echo "ORPHAN: $f"
done
```

** Автоматическое исправление:** Добавьте потерянные страницы в правильный раздел навигации в `mkdocs.yml`.

## Этап 6: Карта сайта и сборка { #phase-6-sitemap--build }

### 6a. Перестройте сайт заново { #6a-rebuild-the-site }

```bash
mkdocs build
```

Это восстанавливает `site/sitemap.xml` автоматически (материал MkDocs генерирует его во время сборки).

### 6b. Проверьте карту сайта { #6b-verify-sitemap }

Проверьте сгенерированную карту сайта:

```bash
python3 marketing-skill/skills/site-architecture/scripts/sitemap_analyzer.py site/sitemap.xml
```

Проверить:
- Все страницы документации отображаются на карте сайта
- Нет битых/404 URL-адресов
- Количество URL-адресов соответствует ожидаемому количеству страниц
- Распределение по глубине является разумным (страницы не должны быть глубже 4 уровней)

### 6c. Проверьте, нет ли проблем с картой сайта { #6c-check-for-sitemap-issues }

- **Отсутствующие страницы:** Страницы в `mkdocs.yml` навигационные системы, которые не отображаются на карте сайта
- ** Дополнительные страницы:** Страницы на карте сайта, которых нет в навигационной системе (сироты)
- ** Повторяющиеся URL-адреса:** Одна и та же страница доступна по нескольким URL-адресам

### Страницы для сохранения (не изменять) { #pages-to-preserve-do-not-modify }

Эти страницы хорошо ранжируются по своим целевым ключевым словам. Исправляйте только критические проблемы (неработающие ссылки, отсутствующие мета-данные). Не переписывайте содержимое:

- Любая страница, которую пользователь явно помечает как "сохранить"
