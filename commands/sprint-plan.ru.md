# /план спринта { #sprint-plan }

Создайте план спринта для `$ARGUMENTS` с явной математикой емкости, проверкой переноса и определением готового гейта. Первый токен(ы) из `$ARGUMENTS` являются целью спринта; конечное число рассматривается как вместимость команды (сюжетные очки или человеко-дни). Если мощность не указана, вычислите ее на этапе 1 — никогда не изобретайте ее.

## Использование { #usage }

```bash
/sprint-plan <goal> [capacity]
# e.g. /sprint-plan "Checkout v2 ready for beta" 34
```

## Фаза 1 — Расчет емкости (выполните арифметику, покажите ее) { #phase-1--capacity-math-do-the-arithmetic-show-it }

1. **Исходная мощность ** = размер команды × рабочие дни в спринте × коэффициент фокусировки (по умолчанию 0,7; уточняйте, если неизвестно)
2. ** Вычеты** — вычитайте явно и построчно: праздники / ВОМ, ротацию по вызову/поддержку, церемонии (~10%), известные прерывания
3. ** Перекрестная проверка скорости ** — сравнение со скользящим средним за последние 3 спринта '*завершенные* (не зафиксированные) баллы. Если вычисленная пропускная способность превышает конечную скорость более чем на 15%, запланируйте конечную скорость и скажите об этом.

Выведите небольшую таблицу: исходные данные → вычеты → чистая пропускная способность → конечная скорость → плановое число.

## Этап 2 — Проверка переноса (перед добавлением чего-либо нового) { #phase-2--carry-over-check-before-adding-anything-new }

1. Перечислите все элементы, перенесенные с последнего спринта (не выполнено при закрытии спринта).
2. Переоцените * оставшиеся* усилия — никогда не переносите первоначальную оценку
3. Перенос сначала потребляет емкость ***; новая область получает только то, что осталось
4. Если перенос превышает ~30% от емкости, отметьте это как системный сигнал о чрезмерных обязательствах и порекомендуйте в этом спринте взять на себя меньшие обязательства, а не усиливать толчок

## Фаза 3 — Определение готовности гейта (для каждого этажа) { #phase-3--definition-of-ready-gate-per-story }

История может попасть в выделенную область только в том случае, если ** все** из них выполняются — в противном случае она переходит в "нуждается в доработке", а не в спринт:

- [ ] Пользовательская история имеет четкого участника, действие и результат (соответствует требованиям INVEST)
- [ ] Критерии приемлемости написаны и поддаются проверке
- [ ] Оценивается командой (не только планировщиком)
- [ ] Зависимости идентифицированы и либо устранены, либо запланированы
- [ ] Достаточно мал, чтобы финишировать в рамках спринта (разделите, если нет)

Создавайте проверенные инвесторами истории из эпопеи с:

```bash
python3 product-team/agile-product-owner/skills/agile-product-owner/scripts/user_story_generator.py
```

## Фаза 4 — Структура выходных данных { #phase-4--output-structure }

- ** Цель спринта** — одно предложение; все, что сделано, должно служить ей
- **Таблица пропускной способности** — начиная с этапа 1
- **Перенос** — с этапа 2, указанный первым в области действия обязательств
- **Зафиксированный объем** — истории, которые прошли гейт DoR, суммируются до ≤ планируемого числа
- **Растягиваемая область** — четко разделена; вытягивается только в том случае, если фиксированная область завершается
- **Риски и зависимости** — с названными владельцами
- **Для исключений** — пусто, если гейт был соблюден; в противном случае обоснуйте каждый
