# Генерировать тесты драматурга { #generate-playwright-tests }

Создавайте готовые к производству тесты драматурга на основе пользовательской истории, URL-адреса, названия компонента или описания функции.

## Входной сигнал { #input }

`$ARGUMENTS` содержит то, что нужно протестировать. Примеры:
- `"user can log in with email and password"`
- `"the checkout flow"`
- `"src/components/UserProfile.tsx"`
- `"the search page with filters"`

## Шаги { #steps }

### 1. Поймите цель { #1-understand-the-target }

Разобрать `$ARGUMENTS` чтобы определить:
- ** История пользователя**: Извлеките поведение для проверки
- **Путь к компоненту**: Прочитайте исходный код компонента
- **Страница/URL**: Идентифицируйте маршрут и его элементы
- ** Название функции **: Привязка к соответствующим областям приложения

### 2. Изучите кодовую базу { #2-explore-the-codebase }

Используйте `Explore` субагент для сбора контекста:

- Читать `playwright.config.ts` для `testDir`, `baseURL`, `projects`
- Проверьте существующие тесты в `testDir` для шаблонов, приспособлений и условных обозначений
- Если указан путь к компоненту, прочтите этот компонент, чтобы понять его свойства, состояния и взаимодействия
- Проверьте наличие существующих объектов страницы в `pages/`
- Проверьте наличие существующих приспособлений в `fixtures/`
- Проверьте правильность настройки авторизации (`auth.setup.ts` или `storageState` конфигурация)

### 3. Выберите шаблоны { #3-select-templates }

Проверьте `templates/` в этом плагине для сопоставления шаблонов:

| Если тестируете... | Загрузите шаблон из |
|---|---|
| Поток входа в систему/авторизации | `../pw/templates/auth/login.md` |
| Грубые операции | `templates/crud/` |
| Оформление заказа/оплата | `templates/checkout/` |
| Пользовательский интерфейс поиска/фильтрации | `templates/search/` |
| Отправка формы | `templates/forms/` |
| Дашборд/данные | `templates/dashboard/` |
| Страница настроек | `templates/settings/` |
| Поток онбординга | `templates/onboarding/` |
| Конечные точки API | `templates/api/` |
| Доступность | `templates/accessibility/` |

Адаптируйте шаблон к конкретному приложению — замените `{{placeholders}}` с реальными селекторами, URL-адресами и данными.

### 4. Сгенерируйте тест { #4-generate-the-test }

Следуйте этим правилам:

**Структура:**
```typescript
import { test, expect } from '@playwright/test';
// Import custom fixtures if the project uses them

test.describe('Feature Name', () => {
  // Group related behaviors

  test('should <expected behavior>', async ({ page }) => {
    // Arrange: navigate, set up state
    // Act: perform user action
    // Assert: verify outcome
  });
});
```

**Приоритет локатора** (используйте первый, который работает):
1. `getByRole()` — кнопки, ссылки, заголовки, элементы формы
2. `getByLabel()` — поля формы с надписями
3. `getByText()` — неинтерактивный текстовый контент
4. `getByPlaceholder()` — вводимые данные с текстом-заполнителем
5. `getByTestId()` — когда семантические параметры недоступны

**Утверждения** — всегда сначала в Интернете:
```typescript
// GOOD — auto-retries
await expect(page.getByRole('heading')).toBeVisible();
await expect(page.getByRole('alert')).toHaveText('Success');

// BAD — no retry
const text = await page.textContent('.msg');
expect(text).toBe('Success');
```

**Никогда не используйте:**
- `page.waitForTimeout()`
- `page.$(selector)` или `page.$$(selector)`
- Пустые CSS-селекторы без крайней необходимости
- `page.evaluate()` для того, что могут делать локаторы

**Всегда включайте:**
- Описательные названия тестов, объясняющие поведение
- Тесты на ошибки / пограничные случаи наряду с happy path
- Правильный `await` на каждый звонок драматурга
- `baseURL`-относительная навигация (`page.goto('/')` не `page.goto('http://...')`)

### 5. Соблюдайте соглашения по проекту { #5-match-project-conventions }

- Если в проекте используется TypeScript → сгенерировать `.spec.ts`
- Если проект использует JavaScript → сгенерировать `.spec.js` с `require()` импорт
- Если в проекте есть объекты страницы → используйте их вместо встроенных локаторов
- Если в проекте есть пользовательские приспособления → импортируйте и используйте их
- Если в проекте есть каталог тестовых данных → создайте там файлы тестовых данных

### 6. Сгенерируйте вспомогательные файлы (при необходимости) { #6-generate-supporting-files-if-needed }

- **Объект страницы**: Если тест затрагивает более 5 уникальных локаторов на одной странице, создайте объект страницы
- **Приспособление**: Если тест нуждается в общей настройке (авторизация, данные), создайте или расширьте приспособление
- **Тестовые данные**: Если в тесте используются структурированные данные, создайте файл JSON в `test-data/`

### 7. Проверьте { #7-verify }

Запустите сгенерированный тест:

```bash
npx playwright test <generated-file> --reporter=list
```

Если это не удастся:
1. Прочитайте сообщение об ошибке
2. Исправьте тест (не приложение)
3. Беги снова
4. Если это проблема с приложением, сообщите об этом пользователю

## Выход { #output }

- Сгенерированный тестовый файл(ы) с путем
- Любые созданные вспомогательные файлы (объекты страницы, приспособления, данные)
- Результат тестового запуска
- Примечание по охвату: какие модели поведения сейчас тестируются
