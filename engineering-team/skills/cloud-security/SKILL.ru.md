# Облачная безопасность { #cloud-security }

Скилл оценки состояния облачной безопасности для обнаружения эскалации привилегий IAM, уязвимости общедоступного хранилища, рисков конфигурации сети и неправильных конфигураций инфраструктуры как кода. Это не реакция на инцидент при активном компрометировании облака (см. Ответ на инцидент) или сканирование уязвимостей приложений (см. ручное тестирование безопасности) - речь идет о систематическом анализе конфигурации облака для предотвращения эксплуатации.

## Обзор { #overview }

### Что делает этот Скилл { #what-this-skill-does }

Этот скилл предоставляет методологию и инструменты для **управления состоянием облачной безопасности (CSPM)** — систематической проверки облачных конфигураций на наличие неправильных конфигураций, которые создают уязвимую поверхность для атак. В нем рассматриваются пути эскалации привилегий IAM, публичный доступ к хранилищу, чрезмерное разрешение сети и безопасность кода инфраструктуры.

### Отличие от других Скилл по обеспечению безопасности { #distinction-from-other-security-skills }

| Скилл | Сосредоточься | Подход |
|-------|-------|----------|
| **облачная безопасность** (это) | Риск конфигурации облака | Профилактический — оценка перед эксплуатацией |
| реагирование на инцидент | Активные облачные инциденты | Подтвержденный с помощью реактивной сортировки облачный компромисс |
| обнаружение угроз | Поведенческие аномалии | Проактивный поиск активности злоумышленников в облачных журналах |
| безопасность-ручное тестирование | Уязвимости приложений | Наступление — активное использование обнаруженных слабостей |

### Предварительные условия { #prerequisites }

Доступ на чтение к документам политики IAM, конфигурациям сегмента S3 и правилам группы безопасности в формате JSON. Для непрерывного мониторинга интегрируйтесь с API облачных провайдеров (AWS Config, политика Azure, центр команд безопасности GCP).

## Инструмент для проверки положения облака { #cloud-posture-check-tool }

Тот `cloud_posture_check.py` инструмент выполняет три типа проверок: `iam` (эскалация привилегий), `s3` (публичный доступ), и `sg` (доступ к сети). Он автоматически определяет тип проверки из структуры конфигурационного файла или принимает явный `--check` флаги.

```bash
# Analyze an IAM policy for privilege escalation paths
python3 scripts/cloud_posture_check.py policy.json --check iam --json

# Assess S3 bucket configuration for public access
python3 scripts/cloud_posture_check.py bucket_config.json --check s3 --json

# Check security group rules for open admin ports
python3 scripts/cloud_posture_check.py sg.json --check sg --json

# Run all checks with internet-facing severity bump
python3 scripts/cloud_posture_check.py config.json --check all \
  --provider aws --severity-modifier internet-facing --json

# Regulated data context (bumps severity by one level for all findings)
python3 scripts/cloud_posture_check.py config.json --check all \
  --severity-modifier regulated-data --json

# Pipe IAM policy from AWS CLI
aws iam get-policy-version --policy-arn arn:aws:iam::123456789012:policy/MyPolicy \
  --version-id v1 | jq '.PolicyVersion.Document' | \
  python3 scripts/cloud_posture_check.py - --check iam --json
```

### Коды выхода { #exit-codes }

| Код | Значение | Требуемое действие |
|------|---------|-----------------|
| 0 | Никаких высоких/критических результатов | Никаких действий не требуется |
| 1 | Результаты с высокой степенью тяжести | Устраните неполадки в течение 24 часов |
| 2 | Важнейшие выводы | Немедленно устранить — эскалация до уровня инцидента - реагирование, если оно активно |

## Анализ политики IAM { #iam-policy-analysis }

Анализ IAM обнаруживает пути эскалации привилегий, чрезмерно привилегированные гранты, публичный доступ к основным ресурсам и риск утечки данных.

### Схемы эскалации привилегий { #privilege-escalation-patterns }

| Узор | Серьезность | Комбинация ключевых действий | МИТРА |
|---------|----------|------------------------|-------|
| Эскалация лямбда-пароля | Критический | iam:пароль + лямбда:CreateFunction | T1078.004 |
| Злоупотребление профилем экземпляра EC2 | Критический | iam:пароль + ec2:RunInstances | T1078.004 |
| Пароль для облачной информации | Критический | iam:PassRole + cloudformation:CreateStack | T1078.004 |
| Эскалация политики самостоятельного присоединения | Критический | iam:AttachUserPolicy + sts:GetCallerIdentity | T1484.001 |
| Самораскрытие встроенной политики - эскалация | Критический | iam:PutUserPolicy + sts:GetCallerIdentity | T1484.001 |
| Бэкдор версии политики | Критический | iam:CreatePolicyVersion + iam:список политик | T1484.001 |
| Сбор учетных данных | Высокий | iam:CreateAccessKey + iam:список пользователей | T1098.001 |
| Эскалация членства в группе | Высокий | iam:добавить пользовательскую группу + iam:список групп | T1098 |
| Атака со сбросом пароля | Высокий | iam:UpdateLoginProfile + iam:список пользователей | T1098 |
| Подстановочный знак уровня обслуживания | Высокий | iam:* или s3:* или ec2:* | T1078.004 |

### Я ищу руководство по строгости { #iam-finding-severity-guide }

| Поиск типа | Условие | Серьезность |
|-------------|-----------|----------|
| Полный подстановочный знак администратора | Действие=* Ресурс=* | Критический |
| Публичный принципал | Принципал: '*' | Критический |
| Опасное сочетание действий | Путь эскалации с двумя действиями | Критический |
| Индивидуальные действия priv-esc | На ресурсе с подстановочными знаками | Высокий |
| Действия по извлечению данных | s3:GetObject, secretsmanager:получает secretvalue на * | Высокий |
| Служебный подстановочный знак | услуга:* акция | Высокий |
| Действия с данными на именованном ресурсе | Соответствующий объем | Низкий/Чистый |

### Рекомендации с наименьшими привилегиями { #least-privilege-recommendations }

Для каждого критического или высокого результата инструмент выдает `least_privilege_suggestion` поле с конкретными рекомендациями по восстановлению:
- Заменить `Action: *` с именованным списком необходимых действий
- Заменить `Resource: *` с определенными шаблонами ARN
- Используйте AWS Access Analyzer для определения фактически используемых разрешений
- Распределите опасные комбинации действий по разным ролям с помощью различных политик доверия

## Оценка воздействия S3 { #s3-exposure-assessment }

Оценка S3 проверяет четыре параметра: конфигурацию блока общедоступного доступа, список управления доступом к корзине, доступ к основной политике корзины и шифрование по умолчанию.

### Матрица проверки конфигурации S3 { #s3-configuration-check-matrix }

| Проверьте | Условие нахождения | Серьезность |
|-------|------------------|----------|
| Блок общественного доступа | Любой из четырех флагов отсутствует/ложен | Высокий |
| ACL ковша | открытый доступ-чтение-запись | Критический |
| ACL ковша | общедоступное чтение или аутентифицированное чтение | Высокий |
| Принцип политики корзины | "Принципал": "*" с разрешением | Критический |
| Шифрование по умолчанию | Нет конфигурации шифрования на стороне сервера | Высокий |
| Шифрование по умолчанию | Нестандартный алгоритм SSEAlgorithm | Средний |
| Нет конфигурации PublicAccessBlockConfiguration | Статус неизвестен | Средний |

### Рекомендуемая базовая конфигурация S3 { #recommended-s3-baseline-configuration }

```json
{
  "PublicAccessBlockConfiguration": {
    "BlockPublicAcls": true,
    "BlockPublicPolicy": true,
    "IgnorePublicAcls": true,
    "RestrictPublicBuckets": true
  },
  "ServerSideEncryptionConfiguration": {
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "arn:aws:kms:region:account:key/key-id"
      },
      "BucketKeyEnabled": true
    }]
  },
  "ACL": "private"
}
```

Все четыре параметра блокировки общедоступного доступа должны быть включены как на уровне корзины, так и на уровне учетной записи AWS. Настройки на уровне учетной записи могут быть переопределены настройками на уровне корзины, если оба они не применяются.

## Анализ группы безопасности { #security-group-analysis }

Анализ группы безопасности помечает входящие правила, которые предоставляют доступ к портам администратора, портам базы данных или всему трафику для интернет-CIDR (0.0.0.0/0, ::/0).

### Правила доступа к критическим портам { #critical-port-exposure-rules }

| Порт | Обслуживание | Определение степени серьезности | Восстановление |
|------|---------|-----------------|-------------|
| 22 | SSH | Критический | Ограничьтесь VPN CIDR или используйте AWS Systems Manager Session Manager |
| 3389 | RDP | Критический | Ограничьтесь VPN CIDR или используйте AWS Fleet Manager |
| 0-65535 (все) | Весь трафик | Критический | Удалить правило; добавлять только определенные требуемые порты |

### Правила переноса базы данных с высоким уровнем риска { #high-risk-database-port-rules }

| Порт | Обслуживание | Определение степени серьезности | Восстановление |
|------|---------|-----------------|-------------|
| 1433 | MSSQL | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |
| 3306 | MySQL | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |
| 5432 | PostgreSQL | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |
| 27017 | MongoDB | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |
| 6379 | Переделать | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |
| 9200 | Эластичный поиск | Высокий | Разрешить только с уровня приложений SG — перейти в частную подсеть |

### Модификаторы серьезности { #severity-modifiers }

Использование `--severity-modifier internet-facing` когда оцениваемый ресурс напрямую доступен через Интернет (балансировщик нагрузки, API-шлюз, общедоступный EC2). Использование `--severity-modifier regulated-data` когда ресурс обрабатывает данные, регулируемые PCI, HIPAA или GDPR. Оба модификатора повышают серьезность каждого обнаружения на один уровень.

## Ревью по безопасности IaC { #iac-security-review }

Ревью инфраструктуры как кода выявляет проблемы с конфигурацией во время определения, перед развертыванием.

### Матрица проверки IaC { #iac-check-matrix }

| Инструмент | Типы проверок | Когда запускать |
|------|-------------|-------------|
| Терраформировать | Проверки на уровне ресурсов (aws_s3_bucket_acl, aws_security_group, aws_iam_policy_document) | Предварительное планирование, предварительная подача заявки, PR-гейт |
| Формирование облака | Проверка свойств шаблона (PublicAccessBlockConfiguration, SecurityGroupIngress) | Ворс шаблона, деплою гейта |
| Манифесты Kubernetes | Привилегии контейнера, сетевые политики, доступ к секретной информации | PR-гейт, контролер допуска |
| Рулевые карты | То же, что и Kubernetes | PR-гейт |

### Пример политики Terraform IAM — поиск по сравнению с Чистый { #terraform-iam-policy-example--finding-vs-clean }

```hcl
# BAD: Will generate critical findings
resource "aws_iam_policy" "bad_policy" {
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = "*"
      Resource = "*"
    }]
  })
}

# GOOD: Least privilege
resource "aws_iam_policy" "good_policy" {
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["s3:GetObject", "s3:PutObject"]
      Resource = "arn:aws:s3:::my-specific-bucket/*"
    }]
  })
}
```

## Матрица покрытия облачных провайдеров { #cloud-provider-coverage-matrix }

| Тип проверки | AWS | Лазурный | GCP |
|-----------|-----|-------|-----|
| Эскалация привилегий IAM | Полный (политики IAM, политики доверия, комбинации ЭСКАЛАЦИИ) | Частичные (назначения RBAC, основные риски обслуживания) | Частичный (привязки IAM, идентификация рабочей нагрузки) |
| Открытый доступ к хранилищу | Полный (политики сегмента S3, списки управления доступом, блокировка общего доступа) | Частичный (токены Blob SAS, уровни доступа к контейнерам) | Частичный (IAM корзины GCS, единый доступ на уровне корзины) |

| Сканирование IaC | Полный (Terraform, CloudFormation) | Частичный (шаблоны для рук, бицепс) | Частичный (менеджер развертывания) |

## Воркфлоу { #workflows }

### Воркфлоу 1: Быстрая проверка осанки (20 минут) { #workflow-1-quick-posture-check-20-minutes }

Для нового выделенного ресурса или ревью перед развертыванием:

```bash
# 1. Export IAM policy document
aws iam get-policy-version --policy-arn ARN --version-id v1 | \
  jq '.PolicyVersion.Document' > policy.json
python3 scripts/cloud_posture_check.py policy.json --check iam --json

# 2. Check S3 bucket configuration
aws s3api get-bucket-acl --bucket my-bucket > acl.json
aws s3api get-public-access-block --bucket my-bucket >> bucket.json
python3 scripts/cloud_posture_check.py bucket.json --check s3 --json

# 3. Review security groups for open admin ports
aws ec2 describe-security-groups --group-ids sg-123456 | \
  jq '.SecurityGroups[0]' > sg.json
python3 scripts/cloud_posture_check.py sg.json --check sg --json
```

**Решение**: Код выхода 2 = заблокировать развертывание и устранить неполадки. Код выхода 1 = запланируйте исправление в течение 24 часов.

### Воркфлоу 2: Полная оценка безопасности облака (многодневный) { #workflow-2-full-cloud-security-assessment-multi-day }

**День 1 — IAM и идентичность:**
1. Экспортируйте все политики IAM, привязанные к производственным ролям
2. Бежать cloud_posture_check.py --проверьте iam для каждой политики
3. Сопоставьте все найденные пути эскалации привилегий
4. Определение учетных записей служб с избыточными привилегиями и ролей
5. Ревью политики доверия между учетными записями

**День 2 — Хранение и сеть:**
1. Перечислите все сегменты S3 и экспортируйте конфигурации
2. Бежать cloud_posture_check.py --проверка s3 --серьезность-модификатор регулируется-данные для блоков данных
3. Экспорт конфигураций групп безопасности для всех VPC
4. Бежать cloud_posture_check.py --проверьте sg на наличие интернет-ресурсов
5. Ревью правила NACL для устранения пробелов в сегментации сети

**День 3 — IaC и непрерывная интеграция:**
1. Ревью шаблонов Terraform/CloudFormation в системе управления версиями
2. Проверьте пайплайн CI/CD на наличие гейтов безопасности IaC
3. Подтверждать полученные результаты с помощью `references/cspm-checks.md`
4. Составить план восстановительных работ с указанием приоритета (Критический → Высокий → средний)

### Воркфлоу 3: Гейт безопасности CI/CD { #workflow-3-cicd-security-gate }

Интегрируйте проверки состояния в пайплайны развертывания, чтобы предотвратить попадание неправильно сконфигурированных ресурсов в производственный процесс:

```bash
# Validate IaC before terraform apply
terraform show -json plan.json | \
  jq '[.resource_changes[].change.after | select(. != null)]' > resources.json
python3 scripts/cloud_posture_check.py resources.json --check all --json
if [ $? -eq 2 ]; then
  echo "Critical cloud security findings — blocking deployment"
  exit 1
fi

# Validate existing S3 bucket before modifying
aws s3api get-bucket-policy --bucket "${BUCKET}" | jq '.Policy | fromjson' | \
  python3 scripts/cloud_posture_check.py - --check s3 \
  --severity-modifier regulated-data --json
```

## Анти-паттерны { #anti-patterns }

1. **Выполнение анализа IAM без проверки комбинаций эскалации** — Отдельные действия с высоким риском по отдельности могут показаться малорискованными. Опасность заключается в комбинациях: `iam:PassRole` само по себе это не критично, но `iam:PassRole + lambda:CreateFunction` это подтвержденный путь эскалации привилегий. Всегда анализируйте заявление в целом, а не отдельные действия.
2. **Включение блокировки общего доступа только на уровне сегмента** - AWS S3 имеет настройки блокировки общего доступа как на уровне учетной записи, так и на уровне сегмента. Параметр на уровне корзины может переопределять параметр на уровне учетной записи. Оба должны быть настроены. Одного блока на уровне учетной записи недостаточно, если какой-либо сегмент имеет явные переопределения.
3. **Лечение `--severity-modifier internet-facing` необязательно для общедоступных ресурсов** — Доступ к ресурсам, ориентированным на Интернет, значительно выше, чем к внутренним ресурсам. Высокие результаты по инфраструктуре, ориентированной на Интернет, следует рассматривать как критические. Всегда применяйте `--severity-modifier internet-facing` для конфигураций DMZ, балансировщика нагрузки и API-шлюза.
4. ** Проверка только политик администратора** — Пути эскалации привилегий часто исходят из политик, не относящихся к администраторам, которые сочетают безобидные на вид разрешения. Должны быть проверены все политики, привязанные к производственным идентификаторам, а не только политики с очевидным расширенным доступом.
5. ** Исправление результатов без анализа первопричин** — Удаление опасного разрешения без понимания того, почему оно было предоставлено, приведет к повторному добавлению. Задокументируйте бизнес-обоснование каждого разрешения с высокой степенью риска, прежде чем удалять его, чтобы предотвратить повторное введение без предупреждения.
6. **Игнорирование чрезмерных разрешений учетной записи службы** - Учетные записи служб часто перегружаются во время разработки и никогда не обрезаются для производства. Каждая учетная запись службы в рабочей среде должна пройти аудит с помощью AWS Access Analyzer или аналогичного средства для выявления и удаления неиспользуемых разрешений.
7. **Не применяются модификаторы серьезности для рабочих нагрузок с регулируемыми данными** — Высокий результат в корзине общего назначения S3 отличается от такого же результата в корзине, содержащей данные PHI или держателя карты. Всегда используйте `--severity-modifier regulated-data` при оценке ресурсов в регулируемых средах обработки данных.
