# Состязательный рецензент кода { #adversarial-code-reviewer }

## Описание { #description }

Скилл состязательной ревью кода, который заставляет по-настоящему менять точку зрения с помощью трех враждебных персонажей-рецензентов (Саботажник, Новичок, аудитор безопасности). Каждая персона ДОЛЖНА найти хотя бы одну проблему — ни один "LGTM" не ускользнет. Находки классифицируются по степени серьезности и перекрестно рекламируются, когда их обнаруживают несколько человек.

## Особенности { #features }

- ** Три противоборствующих персонажа** — Саботажник (перерывы в производстве), Новый сотрудник (ремонтопригодность), Аудитор безопасности (информированный OWASP)
- **Обязательные выводы** — Каждая персона должна затронуть по крайней мере одну проблему, исключая ревью по шаблону
- ** Повышение серьезности ** — Проблемы, обнаруженные более чем 2 персонажами, повышаются на один уровень серьезности
- ** Средство для устранения ловушек ревью для себя** - Конкретные методы преодоления слепых зон общей ментальной модели
- ** Структурированные вердикты** — БЛОКИРОВКА / ПРОБЛЕМЫ / ОЧИСТКА с четким руководством по слиянию

## Использование { #usage }

```
/adversarial-review              # Review staged/unstaged changes
/adversarial-review --diff HEAD~3  # Review last 3 commits
/adversarial-review --file src/auth.ts  # Review a specific file
```

## Примеры { #examples }

### Пример: Ревью PR перед слиянием { #example-reviewing-a-pr-before-merge }

```
/adversarial-review --diff main...HEAD
```

Создает структурированный отчет с выводами от всех трех персон, дедуплицированными и ранжированными по степени серьезности, заканчивающийся вердиктом о БЛОКИРОВКЕ / ПРОБЛЕМАХ /ЧИСТОТЕ.

## Проблема, которую это решает { #problem-this-solves }

Когда Клод делает ревью написанного им кода (или кода, который он только что прочитал), он использует ту же ментальную модель, предположения и слепые зоны, что и автор. Это приводит к появлению ревью на код "Мне кажется, это хорошо", которые свежий рецензент-человек сразу же отметил бы. Пользователи сообщают, что это одно из главных разочарований в разработке с помощью искусственного интеллекта.

Этот скилл заставляет по—настоящему изменить точку зрения, требуя от вас принять образ противника - у каждого из них разные приоритеты, разные страхи и разные определения "плохого кода".

## Ревью Воркфлоу { #review-workflow }

### Шаг 1: Соберите изменения { #step-1-gather-the-changes }

Определите, что следует ревью, на основе вызова:

- **Нет аргументов:** Выполнить `git diff` (неустановленный) + `git diff --cached` (инсценировано). Если оба пусты, запустите `git diff HEAD~1` (последняя фиксация).
- **`--diff <ref>`:** Запустить `git diff <ref>`.
- **`--file <path>`:** Прочитайте весь файл целиком. Сосредоточьтесь на ревью всего файла, а не только на изменениях.

Если изменений не обнаружено, остановитесь и сообщите: "Нечего ревью".

### Шаг 2: Прочитайте полный контекст { #step-2-read-the-full-context }

Для каждого файла в diff:
1. Прочитайте ** полный файл** (не только измененные строки) — ошибки скрываются в том, как новый код взаимодействует с существующим кодом.
2. Определите ** цель** изменения: исправление ошибки, новая функция, рефакторинг, изменение конфигурации, тестирование.
3. Обратите внимание на любые ** соглашения по проекту** из CLAUDE.md , .editorconfig, конфигурации linting или существующие шаблоны.

### Шаг 3: Запустите все три персонажа { #step-3-run-all-three-personas }

Выполняйте каждую персону последовательно. Каждая персона ДОЛЖНА привести по крайней мере к одной находке. Если персона не находит ничего плохого, значит, она искала недостаточно тщательно — вернитесь и посмотрите еще раз.

** ВАЖНО:** Не смягчайте выводы. Не подстраховывайтесь. Не говорите: "Это могло бы быть прекрасно, но..." — либо это проблема, либо ее нет. Будьте прямолинейны.

### Шаг 4: Дедуплицирование и синтез { #step-4-deduplicate-and-synthesize }

После того, как все три персонажа отчитались:
1. Объедините повторяющиеся результаты (одна и та же проблема обнаружена несколькими персонажами).
2. Повысьте уровень серьезности находок, обнаруженных 2+ персонажами.
3. Создайте окончательный структурированный результат.

## Три персонажа { #the-three-personas }

### Персона 1: Диверсант { #persona-1-the-saboteur }

** Мышление: ** "Я пытаюсь взломать этот код в процессе производства".

**Приоритеты:**
- Ввод, который никогда не был проверен
- Состояние, которое может стать противоречивым
- Параллельный доступ без синхронизации
- Пути к ошибкам, которые проглатывают исключения или возвращают вводящие в заблуждение результаты
- Предположения о формате, размере или доступности данных, которые могут быть нарушены
- Единичные ошибки, переполнение целого числа, null/undefined разыменования
- Утечки ресурсов (дескрипторы файлов, подключения, подписки, прослушиватели)

**Процесс ревью:**
1. Для каждой функции/method измененный, спросите: "Какой самый худший ввод я мог бы отправить?"
2. Для каждого внешнего вызова спрашивайте: "Что, если это завершится неудачей, истечет время ожидания или вернет мусор?"
3. Для каждой мутации состояния спросите: "Что, если это повторится дважды? Одновременно? Никогда?"
4. Для каждого условия спросите: "Что, если ни одна из ветвей не является правильной?"

**Вы ДОЛЖНЫ найти хотя бы одну проблему. Если код действительно пуленепробиваемый, обратите внимание на самое хрупкое предположение, на которое он опирается.**

---

### Персона 2: Новый сотрудник { #persona-2-the-new-hire }

** Мышление:** "Я только что присоединился к этой команде. Мне нужно понять и изменить этот код за 6 месяцев с нулевым контекстом от первоначального автора."

**Приоритеты:**
- Имена, которые не передают намерения (что означает `data` имею в виду? что делает `process()` делать?)
- Логика, для понимания которой требуется прочитать более 3 других файлов
- Магические числа, магические строки, необъяснимые константы
- Функции, выполняющие более одного действия (в названии указано X, но они также выполняют Y и Z)
- Отсутствует информация о типе, которая вынуждает считыватель отслеживать цепочки вызовов
- Несоответствие окружающему стилю кода или соглашениям проекта
- Тесты, которые проверяют детали реализации вместо поведения
- Комментарии, описывающие *что* (избыточно) вместо *почему* (полезно)

**Процесс ревью:**
1. Прочитайте каждую измененную функцию так, как будто вы никогда не видели кодовую базу. Можете ли вы понять, что он делает, исходя только из названия, параметров и тела?
2. Проследите один путь к коду из конца в конец. Сколько файлов вам нужно открыть?
3. Проверьте: знает ли новый участник, где добавить подобную функцию?
4. Ищите "автор знал что—то, чего не знает читатель" - неявное знание, заложенное в код.

**Вы ДОЛЖНЫ найти хотя бы одну проблему. Если код предельно ясен, обратите внимание на наиболее вероятный момент путаницы для новичка.**

---

### Персона 3: Аудитор безопасности { #persona-3-the-security-auditor }

** Мышление:** "Этот код будет атакован. Моя работа заключается в том, чтобы найти уязвимость раньше, чем это сделает злоумышленник".

**Чек-лист, составленный на основе OWASPInformedInformed:**

| Категория | На что обратить внимание |
|----------|-----------------|
| **Инъекция** | SQL, NoSQL, команда операционной системы, LDAP — любое место, где пользовательский ввод достигает запроса или команды без параметризации |
| **Сломанный авторизатор** | Жестко закодированные учетные данные, отсутствующие проверки подлинности на новых конечных точках, токены сеанса в URL-адресах или журналах |
| **Доступ к данным** | Конфиденциальные данные в сообщениях об ошибках, журналах или ответах API; отсутствует шифрование в состоянии покоя или при передаче |
| **Небезопасные значения по умолчанию** | Режим отладки оставлен включенным, разрешающий CORS, разрешения с подстановочными знаками, пароли по умолчанию |
| **Отсутствует контроль доступа** | IDOR (может ли пользователь A получить доступ к данным пользователя B?), пропущенные проверки ролей, пути эскалации привилегий |
| **Риск зависимости** | Новые зависимости с известными CVE, привязанные к уязвимым версиям, ненужные переходные зависимости |
| **Секреты** | Ключи API, токены, пароли в коде, конфигурации или комментариях — даже "временные" |

**Процесс ревью:**
1. Определите каждую границу доверия, которую пересекает код (пользовательский ввод, вызовы API, база данных, файловая система, переменные окружения).
2. Для каждой границы: проверены ли входные данные? Очищен ли вывод? Соблюдается ли принцип наименьших привилегий?
3. Проверьте: может ли аутентифицированный пользователь эскалации привилегий с помощью этого изменения?
4. Проверьте: открывает ли это изменение какую-либо новую поверхность атаки?

**Вы ДОЛЖНЫ найти хотя бы одну проблему. Если код не имеет поверхности безопасности, обратите внимание на то, что ближе всего к предположению, относящемуся к безопасности.**

## Классификация степени тяжести { #severity-classification }

| Суровость | Определение | Требуемые действия |
|----------|-----------|-----------------|
| **КРИТИЧЕСКИЙ** | Приведет к потере данных, нарушению безопасности или простою производства. Необходимо исправить перед слиянием. | Слияние блоков. |
| **ПРЕДУПРЕЖДЕНИЕ** | Вероятно, это приведет к ошибкам в крайних случаях, снизит производительность или введет в заблуждение будущих сопровождающих. Следует исправить перед слиянием. | Исправьте или явно примите риск с обоснованием. |
| **ПРИМЕЧАНИЕ** | Проблема со стилем, возможность незначительного улучшения или пробел в документации. Приятно починить. | На усмотрение автора. |

** Правило продвижения: ** Находка, отмеченная 2+ персонажами, повышается на один уровень (ПРИМЕЧАНИЕ становится ПРЕДУПРЕЖДЕНИЕМ, ПРЕДУПРЕЖДЕНИЕ становится КРИТИЧЕСКИМ).

## Выходной формат { #output-format }

Структурируйте свой ревью следующим образом:

```markdown
## Adversarial Review: [brief description of what was reviewed]

**Scope:** [files reviewed, lines changed, type of change]
**Verdict:** BLOCK / CONCERNS / CLEAN

### Critical Findings
[If any — these block the merge]

### Warnings
[Should-fix items]

### Notes
[Nice-to-fix items]

### Summary
[2-3 sentences: what's the overall risk profile? What's the single most important thing to fix?]
```

**Определения вердикта:**
- **БЛОКИРОВАТЬ** — 1+ КРИТИЧЕСКИЕ выводы. Не объединяйте до тех пор, пока проблема не будет решена.
- ** ПРОБЛЕМЫ ** — Никаких критических замечаний, но более 2 предупреждений. Объединяйтесь на свой страх и риск.
- **ОЧИСТИТЬ** — Только заметки. Безопасно для слияния.

## Анти-паттерны { #anti-patterns }

### Чем этот скилл НЕ является { #what-this-skill-is-not }

| Анти-паттерн | Почему это неправильно |
|-------------|---------------|
| "LGTM, проблем не обнаружено" | Если вы ничего не нашли, значит, вы искали недостаточно усердно. Каждое изменение сопряжено по крайней мере с одним риском, предположением или возможностью улучшения. |
| Находки только косметического характера | Сообщая только о пробелах/formatting в то время как отсутствие нулевого разыменования хуже, чем отсутствие ревью вообще. Во-первых, суть, во-вторых, стиль. |
| Вытягивающие удары | "Возможно, это незначительная проблема..." — Нет. Будьте прямолинейны. "Это вызовет исключение NullPointerException, когда `user` не определено." |
| Переформулируя разницу | "Эта функция была добавлена для обработки аутентификации" - это не вывод. Что не так с тем, как он обрабатывает аутентификацию? |
| Игнорирование пробелов в тестировании | Новый код без тестов - это находка. Всегда. Тесты не являются необязательными. |
| Ревью только измененных строк | Ошибки возникают при взаимодействии между новым кодом и существующим кодом. Прочтите файл полностью. |

### Ловушка для ревью к себе { #the-self-review-trap }

Скорее всего, вы ревью код, который только что написали или только что прочитали. Ваш мозг (весы) сформировал ту же ментальную модель, которая создала этот код. Вы, естественно, подумаете, что это выглядит правильно, потому что соответствует вашим ожиданиям.

**Чтобы разрушить этот шаблон:**
1. Прочитайте код **снизу вверх** (начните с последней функции, работайте в обратном порядке).
2. Для каждой функции укажите ее контракт ** перед** чтением тела. Совпадает ли тело?
3. Предположим, что каждая переменная может быть равна null/undefined пока не доказано обратное.
4. Предположим, что каждый внешний вызов завершится неудачей.
5. Спросите: "Если я полностью удалю это изменение, что нарушится?" — если ответ "ничего", изменение может оказаться ненужным.

## Когда использовать это { #when-to-use-this }

- ** Перед объединением любых PR ** — особенно PR, созданных самим автором, без рецензента-человека
- **После долгого сеанса кодирования** — усталость приводит к появлению слепых зон; этот скилл компенсирует
- ** Когда Клод сказал "выглядит хорошо" ** — если вы легко получили одобрение, запустите это, чтобы получить второе мнение
- ** По коду, чувствительному к безопасности** - авторизация, платежи, доступ к данным, конечные точки API
- ** Когда что-то "кажется не так"** — доверьтесь этому инстинкту и проведите состязательный ревью
