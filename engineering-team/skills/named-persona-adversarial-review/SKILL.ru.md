# Названный-Состязательный ревью персоны { #named-persona-adversarial-review }

> **TL;DR:** Абстрактные роли находят абстрактные проблемы. Именитые инженеры с *документированной, исходной* философией находят проблемы, которые вы действительно могли бы решить — при условии, что вы приводите реальный принцип и никогда не выдумываете цитату.

**Триггеры:** "Ревью этого PR с настоящими инженерами" | "ревью по имени персона" | "ревью, основанный на философии"

## Пример вывода { #example-output }

```
CRITICAL [Torvalds]: Special-case error handling at auth.ts:47 duplicates the
  happy path. Torvalds' documented "good taste" principle: restructure so the
  special case disappears rather than adding a branch. (confidence: high — TED 2016)
WARNING  [Thompson]: parseConfig() does three unrelated things; the Unix
  "do one thing well" principle argues to split it. (confidence: high)
NOTE     [Jobs]: Error "EACCES:13" leaks an errno at the user surface; "start
  from the customer experience" argues for a human message. (confidence: high — WWDC 1997)
Verdict: CONCERNS — fix CRITICAL before merge.
```

## Проблема { #problem }

Абстрактный состязательный ревью ("действуй как саботажник") приводит к общим выводам — модель представляет, что *мог бы* сказать рецензент. Этот скилл основывает каждый объектив на ** реальной инженерной философии, основанной на источниках **, задокументированной в [`references/persona_principles.md`](references/persona_principles.md): что Кен Томпсон на самом деле утверждал о доверии, что Лайнус на самом деле продемонстрировал о хорошем вкусе — не то, что воображает искусственный интеллект.

**Чем это отличается от `adversarial-reviewer`:** абстрактные роли → выводы поверхностного уровня; именованные персонажи из источников → выводы, привязанные к документированному принципу, который вы можете цитировать и защищать.

**Стоимость:** 1 раунд - 8-12 мин. Сравнимо с ожиданием CI.

## Дисциплина присвоения (сначала прочтите это — это основное правило) { #attribution-discipline-read-this-first--it-is-the-load-bearing-rule }

Этот скилл применяет названные, реальные человеческие * принципы* к работе. Эта сила также является его режимом сбоя: ** языковые модели галлюцинируют кавычками.** Оставаться честным:

1. ** Цитируйте принцип, а не сфабрикованную дословную цитату.** Предпочитайте перефразировать документированную позицию ("Размышления Томпсона о доверии доверию* утверждают, что вы не можете доверять коду, который вы не полностью создали"), а не придумывать кавычки вокруг слов, которые человек, возможно, никогда не произносил.
2. **Присваивайте уровень достоверности каждой атрибуции** — `high` (задокументировано, в `references/persona_principles.md` с источником), `moderate` (широко распространено, источник не указан), `low`/`unknown` (ты делаешь вывод). Зеркала `productivity/andreessen`это дисциплина цитирования.
3. ** Если вы не можете использовать объектив персоны в реальном источнике, отбросьте эту персону. ** Заведомо неверная цитата, приписываемая живому инженеру, хуже, чем одним рецензентом меньше. Никогда не выдумывайте цитату, чтобы попасть в строку "найдено ≥1".
4. ** Вывод должен основываться на его собственных технических достоинствах.** Персона - это *объектив, который направляет внимание*, а не авторитет, который делает вывод верным. Реальная ошибка, обнаруженная "через призму Кармака", реальна потому, что это ошибка, а не потому, что Кармак так сказал.

## Правила { #rules }

- ** Подготовка перед ролевой игрой.** Закрепите каждую персону в `references/persona_principles.md` (или поддающийся проверке поиск) во-первых. Необоснованный = недопустимый.
- ** Выводы основаны на технических достоинствах**, с учетом принципа персоны в качестве объектива — смотрите дисциплину выше.
- ** Персона продукта обязательна в каждом раунде.** Инженерам не хватает UX. Всегда включайте его.
- ** Честность важнее количества.** Не выдумывайте выводы * или* цитаты. Чистые измерения отображаются в отчетах в чистом виде (с приведенной ниже нагрузкой на поиск нуля).
- ** Нулевая нагрузка на поиск.** "Выглядит нормально" допустимо только в том случае, если вы назовете более 3 принципов, которым код явно удовлетворяет, и каким образом. Не-находки стоят так же дорого, как и находки.

## Бассейны персон { #persona-pools }

Задокументированные принципы каждой персоны + источники + уверенность живут в [`references/persona_principles.md`](references/persona_principles.md).

**Продукт** (выберите 1 за раунд — обязательно):

| Персона | Документированный принцип | Лучше всего подходит для |
|---------|----------------------|----------|
| Стив Джобс | Начните с клиентского опыта, затем вернитесь к технологиям | UX, онбординг |
| Марти Кейган | Влюбляйтесь в проблему, а не в решение | PRDs, спецификации функций, ползучесть области |
| Де Трейнор (интерком) | Первые 30 секунд решают вопрос об усыновлении | Документы, программы для чтения, быстрые старты |

**Инженеры** (выберите 2 за раунд):

| Персона | Документированный принцип | Лучше всего подходит для | Слепое пятно |
|---------|----------------------|----------|------------|
| Кен Томпсон | Доверяйте границам; делайте что-то одно хорошо | Архитектура, цепочка поставок, API | UX, документы |
| Линус Торвальдс | Исключите особый случай ("хороший вкус"); никогда не нарушайте пользовательское пространство | Логика, структуры данных, совместимость | Сочувствие пользователя, DX |
| Джон Кармак | Измеряйте, прежде чем оптимизировать; производительность как ремесло | Алгоритмы, горячие пути | Минимализм |
| Кент Бек | Простой дизайн; заставьте его работать → правильно → быстро | Процесс, проверяемость | Производительность, безопасность |
| Фред Брукс | Существенная и случайная сложность | Проектирование системы, оценка | Низкоуровневый перфоратор |

**Маршрутизация (какие персонажи и когда):**
- Корректность кода → Торвальдс + Кармак + Джобс
- Архитектура / дизайн → Томпсон + Брукс + Кейган
- Документация / API → Томпсон + Бек + Трейнор
- Производительность → Кармак + Торвальдс + Джобс
- Безопасность / цепочка поставок → Томпсон + Торвальдс + Каган
- 1-й раунд по любому PR → Торвальдс + Томпсон + Джобс (самый широкий охват)

## Уровни серьезности { #severity-levels }

| Уровень | Определение | Действие |
|-------|-----------|--------|
| БЛОКИРАТОР | Более 2 человек сходятся во мнении о КРИТИЧЕСКОМ риске или риске потери безопасности / данных | Исправьте перед любой дальнейшей работой |
| КРИТИЧЕСКИЙ | Неверный результат, потеря данных, дыра в системе безопасности или нарушенный базовый инвариант | Исправить перед слиянием |
| ПРЕДУПРЕЖДЕНИЕ | Хрупкий, вводящий в заблуждение или способный вызвать ошибки в будущем | Исправить или объяснить, если отложено |
| ПРИМЕЧАНИЕ | Улучшение, которое не влияет на корректность | Необязательно; запись для последующего наблюдения |

** Акция:** ПРИМЕЧАНИЕ → ПРЕДУПРЕЖДЕНИЕ → КРИТИЧНО → БЛОКИРОВЩИК. Два персонажа, независимо друг от друга решающие одну и ту же проблему, продвигают ее на один уровень (совпадение - это сигнал). БЛОКИРАТОР - это потолок.

## Процесс { #the-process }

### Шаг 0: Прочитайте дважды { #step-0-read-twice }
1. **Сверху вниз** (понимание): что изменилось и почему.
2. **Снизу вверх ** (состязательный): считывание функции за функцией, от последней к первой. Спросите, что каждая функция * на самом деле* гарантирует по сравнению с тем, что подразумевает ее название, где она может потерпеть неудачу и что она предполагает о вызывающих. Чтение "снизу вверх" разрушает ментальную модель автора. Мультифайл → трассировка одного сквозного пути.

### Шаг 1: Сначала закрепите принципы { #step-1-ground-the-principles-first }
Для каждой персоны извлеките их задокументированные принципы из `references/persona_principles.md` (или поиск `"[Name] engineering philosophy principles"` и извлекать только исходные позиции) ** прежде чем ** ознакомиться с кодом, вы применяете принцип, а не адаптируете его к мнению, которое у вас уже сложилось.

### Шаг 2: Ревью (3 независимых — 2 инженера + 1 продукт) { #step-2-review-3-independent--2-engineers--1-product }
Каждая персона получает: ** Образ мышления** (одно предложение из их принципов), ** Приоритеты** (3-5 критериев), ** Выводы** (каждый сопоставлен с документированным принципом + уровень достоверности) или ** нулевое бремя поиска** (3+ принципы кодекса удовлетворяет, каким образом).

### Шаг 3: Синтезируйте и опубликуйте { #step-3-synthesize--post }
Объединяйте дубликаты; подсчитывайте совпадения; продвигайте в соответствии с правилом; отмечайте находки с одним объективом (часто самые интересные). Опубликуйте отчет в качестве PR-комментария (по умолчанию) или сохраните в `.claude/review-[timestamp].md`.

## Проверка целостности (Фейнман) { #integrity-check-feynman }

> "Первый принцип заключается в том, что вы не должны обманывать себя — а вас легче всего одурачить". — Ричард Фейнман, "Наука о культе Карго" (начало в Калифорнийском технологическом институте, 1974)

После каждого раунда спрашивайте:
1. Действительно ли *документированная* философия этого человека привлекает здесь внимание — или я проецирую?
2. Привел ли я реальный принцип, основанный на источниках (с пометкой "уверенность"), или облек общий совет в известное название?
3. Верны ли мои выводы с технической точки зрения независимо от прилагаемого названия?
4. Все на уровне НОТ? Затем я рассказываю об одной точке зрения разными голосами. Поменяйте более 2 персонажей и повторите ревью.

## Условие выхода { #exit-condition }

- **минимум 1 раунд** для любого PR.
- ** Обнаружен БЛОКИРОВЩИК/КРИТИЧЕСКОЕ состояние ** → исправить, затем 1 раунд повторного ревью.
- **ПРОБЛЕМЫ (ПРЕДУПРЕЖДЕНИЕ)** → исправьте или примите риск, затем еще 1 раунд.
- **ОЧИСТИТЬ 2 раунда подряд** → готово.
- **ОЧИСТИТЕ в первом раунде для получения PR с низким уровнем воздействия ** → готово (достаточно 1 раунда).

## Когда использовать { #when-to-use }

- Вам нужен более глубокий охват, чем только стандартные автоматические проверки.
- PR, созданный самостоятельно, нуждается в предварительной обработке перед отправкой.
- `adversarial-reviewer` выводы кажутся общими, а вам нужна конкретика источника.
- Ревью методологий или документов (здесь представлены персонажи продукта).
- Изменения в аутентификации, данных, архитектуре или общедоступном API.

## Когда не следует использовать { #when-not-to-use }

- PR с низким уровнем воздействия (только косметический, без логических изменений) → использовать `adversarial-reviewer`.
- Нет доступа к Интернету, И персона не описана в `references/persona_principles.md` → вы не можете обосновать это; не выдумывайте.
- Одноразовый код / прототип.

## Анти-паттерны { #anti-patterns }

Наследует все от `adversarial-reviewer`. Плюс:

| Анти-паттерн | Почему неправильно |
|-------------|----------|
| Придумываю дословную цитату, чтобы она звучала авторитетно | Сфабрикованное приписывание реальному человеку. Приведите исходный принцип + уверенность или откажитесь от него. |
| "В качестве старшего инженера" без заземления | Объектив не с именем, а из другого источника. Сначала земля. |
| Каждый раз одни и те же 3 персонажа | Поворот в зависимости от типа проблемы — см. раздел Маршрутизация. |
| Сотрудник по продукту пропущен | Продукт улавливает то, что упускают инженеры. |
| Фальсификация результатов для выявления "проблемы ≥1" | Планка - это честность, а не квота. Вместо этого используйте нагрузку по поиску нуля. |
| Пропуск проверки целостности | Проверка без проверки = резиновый штамп. |
| 3 раунда для тривиального изменения | PR с низкой отдачей: достаточно 1 выстрела. |
