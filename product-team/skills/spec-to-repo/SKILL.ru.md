# Спецификация для репо { #spec-to-repo }

Превратите спецификацию проекта на естественном языке в полноценный, доступный для запуска стартовый репозиторий. Не заполнитель шаблонов — интерпретатор спецификаций, который генерирует реальный, рабочий код для любого стека.

## Когда использовать { #when-to-use }

- Пользователь предоставляет текстовое описание приложения и хочет получить код
- У пользователя есть PRD, документ с требованиями или список функций, и ему нужна кодовая база
- Пользователь говорит: "создайте мне приложение, которое...", "создайте это", "загрузите проект".
- Пользователю нужно работающее начальное репозиторий, а не просто файловое дерево

** Не этот скилл ** если пользователь хочет использовать SaaS—приложение конкретно с Stripe + Auth - используйте `product-team/saas-scaffolder` вместо этого.

## Основной воркфлоу { #core-workflow }

### Фаза 1 — Анализ и интерпретация { #phase-1--parse--interpret }

Прочтите спецификацию. Извлеките эти поля автоматически:

| Поле | Источник | Требуемый |
|-------|--------|----------|
| Название приложения | Явный или выводимый из описания | да |
| Описание | Первое предложение спецификации | да |
| Особенности | Выделенные пункты или предложения, описывающие поведение | да |
| Технический стек | Явный ("использовать FastAPI") или вывод из контекста | да |
| Автор | "логин", "пользователи", "учетные записи", "роли" | если упомянуто |
| База данных | "хранить", "сохранять", "сохраняться", "записи", "схема" | если упомянуто |
| Поверхность API | "конечная точка", "API", "REST", "GraphQL" | если упомянуто |
| Цель для деплою | "Vercel", "Docker", "AWS", "Железная дорога" | если упомянуто |

**Правила вывода стека** (когда пользователь не указывает):

| Сигнал | Предполагаемый стек |
|--------|---------------|
| "веб-приложение", "дашборд", "SaaS" | Next.js + Машинописный текст |
| "API", "серверная часть", "микросервис" | FastAPI (Python) или Express (Node) |
| "мобильное приложение" | Трепещите или реагируйте нативно |
| "Инструмент CLI" | Go или Python |
| "пайплайн передачи данных" | Питон |
| "высокая производительность", "системы" | Ржаветь или уходить |

После синтаксического анализа верните пользователю структурированную интерпретацию:

```
## Spec Interpretation

**App:** [name]
**Stack:** [framework + language]
**Features:**
1. [feature]
2. [feature]

**Database:** [yes/no — engine]
**Auth:** [yes/no — method]
**Deploy:** [target]

Does this match your intent? Any corrections before I generate?
```

Отмечайте двусмысленности. Задайте ** не более 3** уточняющих вопросов. Если пользователь говорит "просто создайте это", действуйте с наилучшими предположениями по умолчанию.

### Фаза 2 — Архитектура { #phase-2--architecture }

Разработайте проект перед записью каких-либо файлов:

1. **Выбрать шаблон** — Сопоставить с шаблоном стека из `references/stack-templates.md`
2. **Определить дерево файлов** — Перечислить все файлы, которые будут созданы
3. ** Сопоставление объектов с файлами** — Каждый объект получает как минимум один файл/component
4. **Разработайте схему базы данных** — Если применимо, определите таблицы/collections с полями и типами
5. **Определить зависимости** — Перечислить каждый пакет с ограничениями версии
6. **Планируйте маршруты API** — Если применимо, перечислите каждую конечную точку с указанием метода, пути, запроса/response форма

Представьте дерево файлов пользователю перед созданием:

```
project-name/
├── README.md
├── .env.example
├── .gitignore
├── .github/workflows/ci.yml
├── package.json / requirements.txt / go.mod
├── src/
│   ├── ...
├── tests/
│   ├── ...
└── ...
```

### Фаза 3 — Генерация { #phase-3--generate }

Запишите каждый файл. Правила:

- ** Реальный код, а не заглушки.** Каждая функция имеет реальную реализацию. Нет `// TODO: implement` или `pass` заполнители.
- ** Синтаксически корректен.** Каждый файл должен быть проанализирован без ошибок на своем языке.
- **Импортирует соответствующие зависимости.** Каждый импорт должен соответствовать пакету в манифесте (package.json, requirements.txt , go.mod и т.д.).
- ** Включенные типы.** В проектах TypeScript используются типы. Проекты на Python используют подсказки по типу. Проекты Go используют типизированные структуры.
- **Переменные окружения.** Генерировать `.env.example` с каждой требуемой переменной, прокомментированной целенаправленно.
- **README.md .** Включает: описание проекта, предварительные требования, шаги настройки (клонирование, установка, настройка env, запуск) и доступные скрипты/commands.
- **Конфигурация CI.** Сгенерировать `.github/workflows/ci.yml` с помощью: install, lint (если linter в deps), test, build.
- **.gitignore.** Соответствующие стеку игнорирует (node_modules, __pycache__, .env, артефакты сборки).

**Порядок формирования файла:**
1. Манифест (package.json / requirements.txt / go.mod)
2. Конфигурационные файлы (.env.example, .gitignore, CI)
3. Схема базы данных / миграции
4. Основная бизнес-логика
5. Маршруты / конечные точки API
6. Компоненты пользовательского интерфейса (если применимо)
7. Тесты
8. README.md

### Этап 4 — Проверка { #phase-4--validate }

После генерации пройдитесь по этому чек-листу:

- [ ] Каждый импортированный пакет существует в манифесте
- [ ] Каждый файл, на который ссылается импорт, существует в дереве
- [ ] `.env.example` перечисляет все переменные env, используемые в коде
- [ ] `.gitignore` охватывает строительные артефакты и секреты
- [ ] В README есть инструкции по настройке, которые действительно работают
- [ ] Никаких жестко закодированных секретов, API-ключей или паролей
- [ ] Существует по крайней мере один тестовый файл
- [ ] Строить/start команда задокументирована и будет работать

Бежать `scripts/validate_project.py` по сгенерированному каталогу, чтобы выявить распространенные проблемы.

## Примеры { #examples }

### Пример 1: API управления задачами { #example-1-task-management-api }

**Входная спецификация:**
> "Создайте мне API для управления задачами. Пользователи могут создавать, перечислять, обновлять и удалять задачи. Задачи имеют название, описание, статус (todo/in-progress/done), и срок оплаты. Используйте FastAPI с SQLite. Добавьте базовую аутентификацию с помощью API-ключей."

**Дерево выходных файлов:**
```
task-api/
├── README.md
├── .env.example              # API_KEY, DATABASE_URL
├── .gitignore
├── .github/workflows/ci.yml
├── requirements.txt          # fastapi, uvicorn, sqlalchemy, pytest
├── main.py                   # FastAPI app, CORS, lifespan
├── models.py                 # SQLAlchemy Task model
├── schemas.py                # Pydantic request/response schemas
├── database.py               # SQLite engine + session
├── auth.py                   # API key middleware
├── routers/
│   └── tasks.py              # CRUD endpoints
└── tests/
    └── test_tasks.py         # Smoke tests for each endpoint
```

## Анти-паттерны { #anti-patterns }

| Анти-паттерн | Исправить |
|---|---|
| **Код-заполнитель** — `// TODO: implement`, `pass`, пустые функциональные тела | Каждая функция имеет реальную реализацию. Если это сложно, внедрите рабочую упрощенную версию. |
| **Переопределение стека** — выбор Next.js когда пользователь сказал Flask | Всегда соблюдайте явные технические предпочтения. Делайте вывод только в том случае, если пользователь не указывает. |
| **Отсутствует .gitignore** — фиксация node_modules или .env | Сгенерируйте соответствующий стеку .gitignore в качестве одного из первых файлов. |
| **Фантомный импорт** — импорт пакетов, отсутствующих в манифесте | Перепроверяйте каждый импорт по package.json / requirements.txt прежде чем закончить. |
| ** Чрезмерная разработка MVP ** - добавление кэширования Redis, ограничения скорости, веб—сокетов в версию 1 | Создайте тот минимум, который работает. Пользователь может выполнять итерацию. |
| **Игнорирование заявленных предпочтений** — пользователь говорит "PostgreSQL", и вы генерируете MongoDB | Внимательно проанализируйте спецификацию. Явные предпочтения не подлежат обсуждению. |
| **Отсутствуют переменные env** — код считывается `process.env.X` но `.env.example` в нем это не указано | Каждый env var, используемый в коде, должен отображаться в `.env.example` с комментарием. |
| **Без тестов** — отправка репозитория с нулевыми тестовыми файлами | Как минимум: один тест на дым на конечную точку API или один тест на основную функцию. |
| **Галлюцинированные API** — генерирующий код, вызывающий несуществующие библиотечные методы | Придерживайтесь хорошо документированных, стабильных API. Если вы не уверены, используйте самый простой подход. |

## Сценарий проверки { #validation-script }

### `scripts/validate_project.py` { #scriptsvalidate_projectpy }

Проверяет сгенерированный каталог проекта на наличие распространенных проблем:

```bash
# Validate a generated project
python3 scripts/validate_project.py /path/to/generated-project

# JSON output
python3 scripts/validate_project.py /path/to/generated-project --format json
```

Выполненные проверки:
- README.md существует и не является пустым
- .gitignore существует
- .env.example существует (если код ссылается на переменные env)
- Существует манифест пакета (package.json, requirements.txt , go.mod, Cargo.toml, pubspec.yaml)
- Нет зафиксированного файла env (утечка секретов)
- Существует по крайней мере один тестовый файл
- Никаких заполнителей TODO/FIXME в сгенерированном коде

## Прогрессивное улучшение { #progressive-enhancement }

Для сложных спецификаций создавайте поэтапно:

1. **MVP** — только основная функция, работающая от начала до конца
2. **Auth** — Добавить аутентификацию по запросу
3. **Польский** — Обработка ошибок, проверка, состояния загрузки
4. **Деплей** — Конфигурация Docker, CI, деплей

Спросите пользователя после MVP: "Ядро работает. Хотите, чтобы я добавил auth/polish/deploy следующий, или повторить то, что здесь?"
