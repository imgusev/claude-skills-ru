## Чем отличается этот Скилл от других { #what-makes-this-skill-different }

- ** Математика пропускной способности, соответствующая реальности: ** Пропускная способность спринта основана на коэффициенте скорости × доступности, а не на надежде.
- ** Критерии приемлемости, масштабируемые по размеру истории: ** минимальное количество AC соответствует точкам истории, чтобы избежать недооценки крупных элементов.
- ** Взвешенная расстановка приоритетов, которая остается неизменной: ** ценность - 40%, воздействие - 30%, риск - 15%, усилия - 15% позволяет четко определить компромиссы.
- ** Систематические методы разделения эпоса: ** пять конкретных схем разделения предотвращают чрезмерное количество историй.
- ** ВНЕДРИТЕ проверку, встроенную в воркфлоу: ** каждая история включает в себя этап проверки, а не просто руководство.

## Воркфлоу для создания пользовательских историй { #user-story-generation-workflow }

Создавайте пользовательские истории, соответствующие требованиям к инвестициям, на основе требований:

1. Определите персону (кому выгодна эта функция)
2. Определите необходимое действие или способность
3. Сформулируйте полученную выгоду или ценность
4. Напишите критерии приемлемости, используя Given-When-Then
5. Оцените сюжетные точки, используя шкалу Фибоначчи
6. Проверка на соответствие критериям инвестирования
7. Добавить в список невыполненных работ с приоритетом
8. ** Проверка:** История соответствует всем инвестиционным критериям; критерии приемлемости поддаются проверке

### Шаблон пользовательской истории { #user-story-template }

```
As a [persona],
I want to [action/capability],
So that [benefit/value].
```

**Пример:**
```
As a marketing manager,
I want to export campaign reports to PDF,
So that I can share results with stakeholders who don't have system access.
```

### Типы историй { #story-types }

| Тип | Шаблон | Пример |
|------|----------|---------|
| Особенность | Как [персона], я хочу [действие] так, чтобы [выгода] | Как пользователь, я хочу фильтровать результаты поиска, чтобы быстрее находить нужные элементы |
| Улучшение | Как [персона], мне нужно [способность] к [цель] | Как пользователю, мне нужна более быстрая загрузка страниц, чтобы выполнять задачи без разочарований |
| Исправлена ошибка | Как [персона], я полагаю [поведение], когда [условие] | Как пользователь, я ожидаю, что моя корзина сохранится при обновлении страницы |
| Средство, способствующее | Как разработчику, мне нужно [техническое задание], позволяющее [способность] | Как разработчику, мне нужно реализовать кэширование, чтобы включить мгновенный поиск |

### Ссылка на персону { #persona-reference }

| Персона | Типичные потребности | Контекст |
|---------|--------------|---------|
| Конечный пользователь | Эффективность, простота, надежность | Ежедневное использование функций |
| Администратор | Контроль, видимость, безопасность | Управление системой |
| Опытный пользователь | Автоматизация, настройка, ярлыки | Экспертный воркфлоу |
| Новый пользователь | Руководство, обучение, безопасность | Онбординг |

## Шаблоны критериев приемлемости { #acceptance-criteria-patterns }

Напишите проверяемые критерии приемлемости, используя формат Given-When-Then.

### Данный-Когда-То-шаблон { #given-when-then-template }

```
Given [precondition/context],
When [action/trigger],
Then [expected outcome].
```

**Примеры:**
```
Given the user is logged in with valid credentials,
When they click the "Export" button,
Then a PDF download starts within 2 seconds.

Given the user has entered an invalid email format,
When they submit the registration form,
Then an inline error message displays "Please enter a valid email address."

Given the shopping cart contains items,
When the user refreshes the browser,
Then the cart contents remain unchanged.
```

### Чек-лист критериев приемлемости { #acceptance-criteria-checklist }

Каждая история должна включать критерии для:

| Категория | Пример |
|----------|---------|
| Счастливый путь | При вводе корректных данных при отправке отображается сообщение об успешном завершении |
| Проверка подлинности | Следует отклонять ввод, если обязательное поле пусто |
| Обработка ошибок | Должно отображаться удобное для пользователя сообщение при сбое API |
| Производительность | Операция должна завершиться в течение 2 секунд |
| Доступность | Навигация должна осуществляться только с помощью клавиатуры |

### Минимальные критерии по размеру истории { #minimum-criteria-by-story-size }

| Сюжетные моменты | Минимальное количество переменного тока |
|--------------|------------------|
| 1-2 | 3-4 критерия |
| 3-5 | 4-6 критериев |
| 8 | 5-8 критериев |
| 13+ | Разделите историю |

Видишь `references/user-story-templates.md` для получения полной библиотеки шаблонов.

## Эпический воркфлоу с разбивкой { #epic-breakdown-workflow }

Разбивайте эпопеи на истории размером с спринт, которые можно воплотить в жизнь:

1. Определите масштаб эпопеи и критерии успеха
2. Определите всех персонажей, затронутых эпопеей
3. Перечислите все возможности, необходимые для каждой персоны
4. Группируйте возможности в логические истории
5. Оценка каждой истории составляет ≤8 баллов
6. Выявлять зависимости между историями
7. Последовательные истории для поэтапной доставки
8. ** Проверка:** Каждая история представляет самостоятельную ценность; общее количество историй охватывает эпический масштаб

### Методы расщепления { #splitting-techniques }

| Техника | Когда использовать | Пример |
|-----------|-------------|---------|
| По шагам воркфлоу | Линейный процесс | "Оформить заказ" → "Добавить в корзину" + "Ввести платеж" + "Подтвердить заказ" |
| По персоне | Несколько типов пользователей | "Дашборд" → "Дашборд администратора" + "Дашборд пользователя". |
| По типу данных | Несколько входов | "Импорт" → "Импорт CSV" + "Импорт Excel" |
| По эксплуатации | Функциональность CRUD | "Управление пользователями" → "Создать" + "Редактировать" + "Удалить" |
| Сначала счастливого пути | Снижение риска | "Функция" → "Базовый поток" + "Обработка ошибок" + "Крайние случаи" |

### Эпический пример { #epic-example }

** Epic:** Дашборд пользователя

**Поломка:**
```
Epic: User Dashboard (34 points total)
├── US-001: View key metrics (5 pts) - End User
├── US-002: Customize layout (5 pts) - Power User
├── US-003: Export data to CSV (3 pts) - End User
├── US-004: Share with team (5 pts) - End User
├── US-005: Set up alerts (5 pts) - Power User
├── US-006: Filter by date range (3 pts) - End User
├── US-007: Admin overview (5 pts) - Admin
└── US-008: Enable caching (3 pts) - Enabler
```

## Планирование спринта по воркфлоу { #sprint-planning-workflow }

Планируйте пропускную способность спринта и выбирайте истории:

1. Рассчитать вместимость команды (скорость × доступность)
2. Ревью цели спринта с стейкхолдерами
3. Выберите истории из списка невыполненных работ с приоритетом
4. Заполните до 80-85% емкости (обязательно)
5. Добавьте цели растяжки (дополнительно на 10-15%)
6. Выявлять зависимости и риски
7. Разбейте сложные истории на задачи
8. ** Проверка:** Количество зафиксированных баллов составляет ≤85%; все истории имеют критерии приемлемости

### Расчет пропускной способности { #capacity-calculation }

```
Sprint Capacity = Average Velocity × Availability Factor

Example:
Average Velocity: 30 points
Team availability: 90% (one member partially out)
Adjusted Capacity: 27 points

Committed: 23 points (85% of 27)
Stretch: 4 points (15% of 27)
```

### Факторы доступности { #availability-factors }

| Сценарий | Фактор |
|----------|--------|
| Полный спринт, без отбора мощности | 1.0 |
| Один член команды из 50% | 0.9 |
| Отпуск во время спринта | 0.8 |
| Несколько участников вышли | 0.7 |

### Загрузка шаблона для спринта { #sprint-loading-template }

```
Sprint Capacity: 27 points
Sprint Goal: [Clear, measurable objective]

COMMITTED (23 points):
[H] US-001: User dashboard (5 pts)
[H] US-002: Export feature (3 pts)
[H] US-003: Search filter (5 pts)
[M] US-004: Settings page (5 pts)
[M] US-005: Help tooltips (3 pts)
[L] US-006: Theme options (2 pts)

STRETCH (4 points):
[L] US-007: Sort options (2 pts)
[L] US-008: Print view (2 pts)
```

Видишь `references/sprint-planning-guide.md` для завершения процедур планирования.

## Определение приоритетов невыполненной работы { #backlog-prioritization }

Расставьте приоритеты в невыполненной работе, используя оценку ценности и усилий.

### Уровни приоритета { #priority-levels }

| Приоритет | Определение | Цель спринта |
|----------|------------|---------------|
| Критический | Блокировка пользователей, безопасность, потеря данных | Немедленный |
| Высокий | Основная функциональность, ключевые потребности пользователя | Этот спринт |
| Средний | Улучшения, усовершенствования | Следующие 2-3 спринта |
| Низкий | Приятные в использовании, незначительные улучшения | Накопившееся |

### Факторы расстановки приоритетов { #prioritization-factors }

| Фактор | Вес | Вопросы |
|--------|--------|-----------|
| Ценность для бизнеса | 40% | Влияние на доходы? Спрос пользователей? Стратегическое согласование? |
| Влияние на пользователя | 30% | Сколько пользователей? Как часто используется? |
| Риски/зависимости | 15% | Технический риск? Внешние зависимости? |
| Усилие | 15% | Размер? Сложность? Неуверенность? |

### Проверка инвестиционных критериев { #invest-criteria-validation }

Перед добавлением в спринт проверьте каждую историю:

| Критерий | Вопрос | Пройди, если... |
|-----------|----------|------------|
| **Я**не зависим | Можно ли это развить без других незафиксированных историй? | Никаких блокирующих зависимостей |
| **Не**эгоистичный | Является ли реализация гибкой? | Возможно несколько подходов |
| **V**изменяемый | Приносит ли это пользу пользователям или бизнесу? | Очевидная выгода в том, "чтобы" |
| **E** стимулируемый | Может ли команда оценить это? | Понят достаточно хорошо, чтобы определить размер |
| **Торговый центр S** | Можно ли это завершить за один спринт? | ≤8 сюжетных точек |
| **Т** устойчивый | Можем ли мы убедиться, что это сделано? | Четкие критерии приемлемости |

## Инструменты { #tools }

### Генератор пользовательских историй { #user-story-generator }

```bash
# Generate stories from sample epic
python scripts/user_story_generator.py

# Plan sprint with capacity
python scripts/user_story_generator.py sprint 30
```

Генерирует:
- Истории пользователей, совместимые с инвестированием
- Заданные критерии приемлемости "Когда-то"
- Оценки сюжетных точек (шкала Фибоначчи)
- Приоритетные назначения
- Загрузка спринта с фиксированными и растянутыми элементами

### Примерный вывод { #sample-output }

```
USER STORY: USR-001
========================================
Title: View Key Metrics
Type: story
Priority: HIGH
Points: 5

Story:
As a End User, I want to view key metrics and KPIs
so that I can save time and work more efficiently

Acceptance Criteria:
  1. Given user has access, When they view key metrics, Then the result is displayed
  2. Should validate input before processing
  3. Must show clear error message when action fails
  4. Should complete within 2 seconds
  5. Must be accessible via keyboard navigation

INVEST Checklist:
  ✓ Independent
  ✓ Negotiable
  ✓ Valuable
  ✓ Estimable
  ✓ Small
  ✓ Testable
```

## Показатели спринта { #sprint-metrics }

Следите за состоянием здоровья в спринте и результативностью команды.

### Ключевые показатели { #key-metrics }

| Метрика | Формула | Цель |
|--------|---------|--------|
| Скорость | Набранные очки / спринт | Стабильный ±10% |
| Приверженность и надежность | Завершено / зафиксировано | >85% |
| Изменение области применения | Очки, добавленные или снятые в середине спринта | <10% |
| Переходящий | Баллы не заполнены | <15% |

### Отслеживание скорости { #velocity-tracking }

```
Sprint 1: 25 points
Sprint 2: 28 points
Sprint 3: 30 points
Sprint 4: 32 points
Sprint 5: 29 points
------------------------
Average Velocity: 28.8 points
Trend: Stable

Planning: Commit to 24-26 points
```

### Определение сделанного { #definition-of-done }

История будет завершена, когда:

- [ ] Код завершен и прошел экспертную ревью
- [ ] Написанные и проходящие модульные тесты
- [ ] Проверены критерии приемлемости
- [ ] Обновлена документация
- [ ] Депло в промежуточную среду
- [ ] Владелец продукта принят
- [ ] Критических ошибок не осталось
