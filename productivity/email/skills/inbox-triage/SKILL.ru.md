# Сортировка входящих сообщений — Повторяющаяся сортировка электронной почты { #inbox-triage--recurring-email-triage }

> **В паре с `inbox-setup`.** Этот скилл использует базу знаний из 7 файлов, которая `inbox-setup` пишет в `${WORKSPACE}/Email/`. Файловые контракты ДОЛЖНЫ точно совпадать. Видишь [`references/kb_file_contract.md`](references/kb_file_contract.md) — это зеркальное отображение контракта на стороне установки, просматриваемое со стороны чтения.

Запускается по повторяющемуся расписанию (1-3 раза в день) или по требованию. Классифицируйте последние электронные письма, исследуйте новых отправителей, формируйте рекомендации по принятию решений, составляйте черновики ответов (** НИКОГДА НЕ ОТПРАВЛЯЙТЕ **), составляйте чистый отчет и обновляйте базу знаний тем, что было изучено в ходе выполнения.

- "сортировка электронной почты"

## Предварительные условия { #prerequisites }

Требуемое чтение при запуске (сбойное, если отсутствует):

**Ядро (обязательно):**
- `${WORKSPACE}/Email/email-taxonomy.md` — классификация + настройки отчета
- `${WORKSPACE}/Email/email-patterns.md` — голос, персона, шаблоны, жесткие правила

**Необязательное ядро (прочитано, если существует):**
- `${WORKSPACE}/Email/evaluation-framework.md`
- `${WORKSPACE}/Email/rate-card.md`

** Эволюционирует (читается И обновляется при каждом запуске):**
- `${WORKSPACE}/Email/blocklist.md`
- `${WORKSPACE}/Email/tracker.md`

**Выход:**
- `${WORKSPACE}/Email/triage-log/<YYYY-MM-DD>-<run-label>.md` — журнал для каждого запуска

Если какой-либо необходимый файл ядра отсутствует → ** остановка**, направьте пользователя на запуск `inbox-setup` первый. Использование `scripts/kb_reader.py` чтобы выполнить чтение + проверку.

## ТОЛЬКО ЧЕРНОВИКИ — Никогда не отправляйте { #drafts-only--never-send }

> **Этот скилл создает черновики. Он НИКОГДА не отправляется.**

Это свойство безопасности, которое делает автоматический запуск скилла безопасным. Указано несколько раз в этом теле скилла. Это не подлежит обсуждению.

Тот `scripts/draft_safety_validator.py` применяет его после запуска. Любой вызов инструмента в форме отправки в журнале действий не проходит проверку. Видишь [`references/drafts_only_safety.md`](references/drafts_only_safety.md) для полного канона дисциплины.

## Шаг 0: Приготовление на гриле (Свет — 0-2 необязательных дополнительных вопроса) { #step-0-grill-me-intake-light--02-optional-override-questions }

Сортировка входящих сообщений ** по замыслу является малозатратной ** - она выполняется в повторяющемся режиме с предпочтениями, предварительно записанными в базу знаний из `inbox-setup`. Дисциплина grill-me здесь заключается в том, чтобы задавать ТОЛЬКО основные вопросы, которые имеют значение в ЭТОМ прогоне.

### Q1 (необязательно, запрашивается только тогда, когда запуск по требованию выходит за рамки обычной частоты) { #q1-optional-asked-only-when-on-demand-run-is-outside-normal-cadence }

> **Переопределить 9-часовое окно поиска по умолчанию? Выберите: да (укажите часы) / нет (используйте по умолчанию).**
>
> *Почему я спрашиваю:* Если вы работаете по требованию не с обычной частотой 2 раза в день, вам может потребоваться более широкое окно (24 часа после длительного перерыва) или более узкое (2 часа для быстрой проверки).

Пропустите, если частота в норме.

### Q2 (необязательно, запрашивается только при вызове пользователем с намерением пропустить категорию) { #q2-optional-asked-only-when-user-invokes-with-category-skip-intent }

> ** Пропустить какие-либо категории в этом цикле? например, "пропустить информационные бюллетени", "пропустить финансовые".**
>
> * Почему я спрашиваю: * Иногда вы просто хотите просмотреть возможности или просто очистить активные потоки. Пропуск категории сужает область выполнения.

Пропустить, если пользователь не дал сигнала о пропуске категории.

** Условие остановки:** Максимум 2 вопроса. Вызовы по умолчанию пропускают оба вопроса и выполняются с настройками KB-default. Скилл оптимизирован для быстрого повторяющегося выполнения; потребление является исключением, а не нормой.

## Шаг 1: Определите окно поиска { #step-1-determine-search-window }

Вычислите с помощью математики текущей даты. Обратный просмотр по умолчанию: ** 9 часов ** (работает с частотой 2 раза в день с небольшим перекрытием, чтобы электронные письма между запусками не пропускались).

Использование `scripts/search_window_calculator.py --cadence <CADENCE> --now <ISO>`:

```
now = current_datetime
window_start = now - 9_hours   (default for 2x-daily)
run_label = "Morning" if now.hour < 12 else "Afternoon" if now.hour < 17 else "Evening"
```

Сопоставление каденции с окном по умолчанию (переопределение через Q1):

| Ритм (от email-taxonomy.md S1.Q5) | Окно по умолчанию |
|---|---|
| один раз в день | 26 часов |
| 2 раза в день | 9 часов |
| 3 раза в день | 6 часов |
| только по запросу | 24 часа (спрашивает Q1) |

## Шаг 2: Поиск по электронной почте { #step-2-email-search }

Два запроса (шаблон адаптера, не зависящий от поставщика):

- **Основной:** Почтовый ящик "Входящие" + отправлено после `window_start`
- ** Вторичный:** Помеченный непрочитанным (перехватывать помеченные элементы, пропущенные в первичном)

Соберите для каждого электронного письма: отправителя, тему, дату, фрагмент, идентификатор темы, ярлыки.

Сопоставление адаптера поставщика:

| Поставщик | Инструмент |
|---|---|
| Gmail | Gmail MCP |
| Outlook / Microsoft 365 | Прогноз MCP |
| IMAP (Fastmail, ProtonMail и т.д.) | IMAP MCP, если доступен; в противном случае остановите |
| (инструмент электронной почты недоступен) | Остановка с четким сообщением: "Для этого сеанса не зарегистрирован ни один инструмент электронной почты". |

## Шаг 3: Классификация { #step-3-classification }

Примените таксономию из `email-taxonomy.md`. Для категории ** с самым низким приоритетом** (информационные бюллетени / автоматизация / спам): полностью пропустить чтение потока — затраты на контекст того не стоят. Для всего остального: прочитайте полный поток.

## Шаг 4: Исследование отправителя { #step-4-sender-research }

Для отправителей, которых нет в трекере / списке блокировок / предыдущих журналах:

1. Проверьте `blocklist.md` → при совпадении автоматический пропуск
2. Проверьте `tracker.md` → если известен поток, обратите внимание на существующий контекст
3. Для отправителей возможностей (согласно фреймворку оценки): веб-поиск по легитимности компании, социальному присутствию, статусу посредника

** Полностью пропустите исследование ** для: известных отправителей (в трекере), внутренней электронной почты, автоматических уведомлений, очевидного низкого приоритета.

## Шаг 5: Рекомендации { #step-5-recommendations }

Для электронных писем, требующих принятия решения, примените фреймворк из `evaluation-framework.md`. Классифицировать:

| Категория | Когда | Выход |
|---|---|---|
| ** ВОЗЬМИ ЭТО** | Соответствует критериям | Рекомендую принять участие; черновик ответа (шаг 6) |
| **СТОИТ РАССМОТРЕТЬ** | Обладает потенциалом, нуждается в оценке пользователя | Контекст ключа поверхности; черновик для редактирования пользователем |
| **ПРОПУСК** | Не соответствует критериям | Краткое "почему" (1-3 предложения); черновик вежливого отказа |
| **ОТМЕТЬТЕ ДЛЯ РЕВЬЮ** | Необычно; требуется прямое решение пользователя | Поверхность полностью обработана; осадка отсутствует (пользователь определяет форму отклика) |

Каждое: краткое "почему", соответствующий контекст, сравнение цен / сроков, если применимо.

**Полностью пропустите шаг 5, если нет `evaluation-framework.md` существует.**

Видишь [`references/triage_decision_framework.md`](references/triage_decision_framework.md) для канона фреймворка.

## Шаг 6: Черновики { #step-6-drafts }

Для каждого кандидата с разумным ответом создайте черновик, используя `email-patterns.md` голосовые правила.

** Черновик для:** ответов на возможные вопросы (ПРИНЯТЬ ЭТО / СТОИТ / ПРОПУСТИТЬ), активных разговоров, требующих ответа, пунктов о действиях, важных личных электронных писем.

**Не делайте черновик для:**
- Очевидно, что электронные письма без ответа (информационные бюллетени, автоматизация, к вашему сведению)
- Темы, на которые пользователь уже ответил
- Заблокированные отправители (если только новая информация не изменит расчет)

**Механика:**

- Черновик только в существующем потоке, когда это возможно (сохраняет контекст)
- Набор `to`, `subject` (`Re: [original]`)
- **НИКОГДА не вызывайте какую-либо операцию отправки. Создавайте только черновики.**

Призывной орган ДОЛЖЕН соблюдать:
- Голосовой регистр с `email-patterns.md`
- Запрещенные жетоны (S3.Q2 мозоли домашних животных)
- Шаблоны выхода из системы
- Контекст персоны
- Жесткие правила (S3.Q6 — не подлежат обсуждению)
- Длина ответа на каждый `email-patterns.md`

Если `evaluation-framework.md` существует, тон проекта соответствует рекомендации:
- СДЕЛАЙ ЭТО → вовлечен + конкретный следующий шаг
- СТОИТ → любопытно + 1-2 уточняющих вопроса
- ПРОПУСК → вежливый отказ + краткая причина (никаких обещаний хеджирования)
- ФЛАГ → НЕТ черновика

## Шаг 7: Отправка отчета { #step-7-report-delivery }

Соблюдайте предпочтения пользователя из `email-taxonomy.md` Раздел "Настройки отчета". По умолчанию: отправляйте черновик по электронной почте себе с помощью HTML.

**Тема:** `Inbox Triage — [Day], [Month Date] ([Run Label])`

**Разделы (по порядку):**

1. ** Обзор** — 2-3 предложения. Что случилось? Что-нибудь срочное?
2. ** Статистика** — Количество обработанных, созданных черновиков, необходимых действий, пропущенных.
3. ** Необходимые действия** — Просроченные пункты, решения, проекты для ревью, крайние сроки.
4. ** Краткая справка ** — По одной строке на каждое электронное письмо, в алфавитном порядке по отправителю. `**Sender** — one-sentence summary + recommendation`.
5. **Подробные карточки** — Возможности, активные темы, флаги. Каждое: отправитель / тема / категория, рекомендация + обоснование, ключевой контекст. ** НЕТ предварительного просмотра черновиков текста ** (черновики уже есть в почтовом клиенте, чтобы пользователь мог их прочитать там).
6. **Нижний колонтитул** — Временная метка генерации + краткое описание обновления в КБ.

**Форматирование (если HTML):**

- ** Только встроенный CSS ** (полосы Gmail `<style>`)
- Цветовая маркировка по рекомендации:
  - зеленый → ВОЗЬМИ ЭТО
  - янтарь → СТОИТ РАССМОТРЕТЬ
  - красный → ПРОПУСК
  - фиолетовый → ФЛАГ ДЛЯ РЕВЬЮ
  - синий → активный разговор

## Шаг 8: Обновление базы знаний { #step-8-knowledge-base-update }

**`blocklist.md`** (добавить новый):

- Новые отклоненные отправители + причина + дата
- Новые шаблоны отклонений на основе наблюдаемого поведения (например, "все электронные письма, содержащие "ищу бэкенд-инженеров" с адресов gmail → шаблон холодного рекрутера")
- Удалить записи, если пользователь переопределил их (пользователь ответил "заблокированному" отправителю → разблокировать)

**`tracker.md`** (добавить + обновить):

- Новые дополнения к электронным письмам, требующим дальнейших действий
- Обновить существующие последующие действия (изменен крайний срок, изменен статус)
- Отметьте разрешенные элементы завершенными
- Отмечать просроченные товары
- Удалить разрешенные элементы старше 30 дней
- Добавить запись в журнал обновлений

**Изучение закономерностей для наблюдения во время прогонов:**

- Черновики, отправленные как есть, или отредактированные, или удаленные → сигнал калибровки тона
- ПЕРЕДАВАТЬ рекомендации пользователь переопределяет → сигнал настройки фреймворка
- Вовлеченные или проигнорированные электронные письма → сигнал об уточнении таксономии
- Новые шаблоны отклонений → добавления в список блокировок

После более чем 5 запусков предложите пользователю улучшить KB (например, "Вы всегда отклоняете электронные письма от X — add как автоматически пропускаемые?").

## Шаг 9: Внутренний журнал { #step-9-internal-log }

Сохранить в `${WORKSPACE}/Email/triage-log/[YYYY-MM-DD]-[run-label].md`:

- Электронные письма обрабатываются с использованием классификаций
- Вынесенные рекомендации
- Созданные черновики (с идентификаторами / ссылками на потоки)
- Внесены обновления в КБ
- Добавлены / устранены последующие действия
- Примечательные наблюдения (обнаружены закономерности, обработаны крайние случаи)

Журнал - это журнал аудита для `scripts/draft_safety_validator.py` для проверки на наличие операций отправки после запуска.

## Шаг 10: Обработка пустых входящих сообщений { #step-10-empty-inbox-handling }

Даже при нулевом количестве новых электронных писем:

1. Проверьте `tracker.md` для товаров, подлежащих оплате сегодня или просроченных
2. Сгенерировать минимальный отчет: "С момента последнего запуска не было новых писем, требующих действий"
3. Отмечайте все просроченные товары
4. Эскалация в соответствии с правилами отслеживания

Полностью пропустите шаги 3-6 в пустом почтовом ящике.

## Критические правила (Указаны несколько раз) { #critical-rules-stated-multiple-times }

1. ** ТОЛЬКО ЧЕРНОВИКИ — НИКОГДА НЕ ОТПРАВЛЯЙТЕ.** Не подлежит обсуждению. Изложено еще раз здесь.
2. ** Конфиденциальность.** Нет паролей / учетных данных в KB. Ссылайтесь на потоки по идентификатору для конфиденциального контента.
3. ** Точность важнее скорости.** Если вы не уверены, отметьте для ревью. Неправильный автоматический черновик хуже, чем отсутствие черновика.
4. **Уважайте KB.** Задокументированные предпочтения являются источником истины. Не переоценивайте себя с помощью суждений.
5. ** Прозрачность.** Отмечайте каждое изменение в КБАЙТ в журнале сортировки.
6. ** Первые запуски требуют контроля.** Задокументируйте это ожидание для пользователя.

## Обработка ошибок { #error-handling }

| Ситуация | Поведение |
|---|---|
| Отсутствуют файлы размером в КБ | Остановка; указание пользователю выполнить `inbox-setup` |
| Инструмент электронной почты недоступен | Остановка с четким сообщением о требуемом инструменте |
| Веб-поиск недоступен для поиска отправителей | Пропустите этап исследования; обратите внимание на отправителей, которые не были исследованы |
| Не удается создать черновик | Пропустите этот черновик; отметьте в журнале; отчет продолжается |
| Сбой доставки отчета | Сохранить отчет в файл в качестве запасного варианта; уведомить пользователя |
| Пользователь получил более 100 новых электронных писем | Оставайтесь в разумных пределах; отмечайте объем; предлагайте сосредоточиться только на приоритетных категориях |
| Отправитель отображается как в блок-листе, так и в трекере | Трекер выигрывает (активный разговор); обратите внимание на несоответствие в журнале |

## Портативность { #portability }

- ** Claude Code CLI:** Native — использует Gmail / Outlook MCP, файловые инструменты для KB, веб-поиск для исследований.
- ** Клод.ai web:** Работает, когда подключен email MCP connector (доступен Gmail MCP). Прежде чем приступать к работе, Скилл должен проверить наличие инструмента. Если нет инструмента электронной почты: остановитесь с четким сообщением.

## Анти-Паттерны для отклонения { #anti-patterns-to-reject }

- **Отправка электронных писем** (только черновики — обсуждению не подлежат)
- Работа без файлов базы знаний
- Хранение паролей / учетных данных в КБАЙТ
- Пропуск цикла обучения (обновления KB) в конце выполнения
- Переопределение задокументированных предпочтений пользователя собственным суждением
- Чтение потоков с самым низким приоритетом (пустая трата контекста)
- Включение предварительного просмотра чернового текста в отчет (черновики уже есть в почтовом клиенте)
- Блокировка провайдера без шаблона адаптера
- Молчаливый сбой из-за отсутствующих инструментов
