# Исследовательские операции — оркестратор предметной области { #research-operations--domain-orchestrator }

Поверхность исследовательских операций - это ** то, как предприятие планирует, финансирует, определяет масштабы и обобщает исследования** по четырем направлениям работы: клинические исследования и разработки, финансирование НИОКР, исследование рынка и исследование продукта. Этот оркестратор разветвляет свой контекст, направляет ваш запрос к одному из четырех суб-скиллам, а затем возвращает дайджест. Интенсивный прием (черновики протоколов, бухгалтерские книги программ, экспорт опросов, стенограммы интервью) остается в раздвоенном контексте.

Это корпоративный аналог академического `research/` домен. Если ваш вопрос касается ** поиска** литературы, грантов или патентов, используйте `research/`. Если речь идет о планировании, финансировании, определении объема или обобщении исследований как операционной дисциплины, вы находитесь в правильном месте.

## Когда вызывать { #when-to-invoke }

| Симптом | Вспомогательный скилл |
|---|---|
| "Мы разрабатываем исследование фазы 2 — какова конечная точка и размер выборки?" | `clinical-research` |
| "Какова стоимость нашей программы исследований и разработок, и это капитальные затраты или эксплуатационные расходы?" | `research-finance` |
| "Каков спрос на этот продукт и как мы проводим исследование этого сегмента?" | `market-research` |
| "Со сколькими пользователями мы проводим собеседования и как обобщаем полученные результаты?" | `product-research` |

## Логика маршрутизации (детерминированная) { #routing-logic-deterministic }

Та же пороговая схема с двумя сигналами, что и `commercial-skills`. Одиночный сигнал → уточняющий вопрос. Смешанные сигналы → сначала самый достоверный, второй по цепочке в последующем повороте. Никогда не цепляйтесь молча.

### Таблица сигналов { #signal-table }

| Класс сигнала | Ключевые слова | Вспомогательный скилл |
|---|---|---|
| **КЛИНИЧЕСКИЙ** | клиническое испытание, дизайн исследования, протокол, конечная точка, размер выборки, мощность, фаза 1/2/3, биостатистика, приемлемость, осуществимость, оценка | `clinical-research` |

## Воркфлоу (дисциплина "Гриль Мэтта Покока") { #workflow-matt-pocock-grill-discipline }

Взято из книги Мэтта Покока `grill-with-docs` схема: ** исследуйте, затем задавайте, по одному вопросу за ход с рекомендуемым ответом, сначала пройдитесь по дереву решений в глубину, отслеживайте зависимости, закрепляйте каждую проблему в каноне исследования ** (`references/` каждого под-скилла).

### Шаг 1 — Исследуйте, прежде чем спрашивать { #step-1--explore-before-asking }

Сначала проверьте рабочий каталог пользователя:
- Есть ли уже в рабочей области черновик протокола, реестр программ, модель TAM или руководство по проведению собеседований?
- Устраняет ли запрос уже неоднозначность полосы (например, "каков размер выборки для испытания с двумя руками" - это `clinical-research`, вопрос не нужен)?
- Существует ли имя файла артефакта, которое разрешает полосу движения (`protocol.json` → клинический; `program-budget.json` → финансы; `tam-model.json` → рынок; `interview-guide.md` → продукт)?

Если рабочее пространство разрешает полосу движения, **проложите маршрут автоматически**.

### Шаг 2 — Если все еще неясно, задайте ОДИН форсирующий вопрос с рекомендуемым ответом { #step-2--if-still-ambiguous-one-forcing-question-with-a-recommended-answer }

Правило Мэтта: никогда не связывайся. Всегда рекомендую.

Узор:
```
Q1/1: [precise question naming the two candidate lanes]
Recommended: [Lane X, because <signal-table rationale>]

(Confirm, or override?)
```

### Шаг 3 — Прохождение по дереву принятия решений для многополосных запросов { #step-3--decision-tree-walk-for-multi-lane-inquiries }

Если запрос законно пересекает две полосы (например, "спроектируйте это исследование И выделите на него бюджет" = КЛИНИЧЕСКОЕ ИССЛЕДОВАНИЕ + RD_FINANCE), сначала пройдите вглубь:

1. Сначала пройдите полосу наивысшей уверенности → запустите вспомогательный скилл в раздвоенном контексте → дайджест
2. Спросите: "Теперь беги [вторая полоса]? Рекомендуется: да, потому что [зависимость]."
3. Подтвердите перед соединением в цепочку.

Никогда не цепляйтесь молча.

### Шаг 4 — Вызов вспомогательного скилла в раздвоенном контексте { #step-4--invoke-sub-skill-in-forked-context }

Пересылайте исходный промпт + структурированные входные данные (протокол JSON, программный регистр CSV, модель рынка, экспорт наблюдений).

### Шаг 5 — Верните дайджест с цитируемым вызовом по канону { #step-5--return-digest-with-cited-canon-challenge }

≤ 200 слов: проанализировано, 3 лучших результата (привязанных к цитате из канона), 3 лучших следующих действия (с именем владельца, где применимо), путь к артефакту и ** одна сложная задача ** для пользователя. Примеры:

- "Ваш расчет мощности предполагает размер эффекта 0,5 без опубликованной привязки. ICH E9 требует обоснованного, клинически значимого различия. Откуда взялось 0,5?"
- "Ваш TAM - это единственное нисходящее число (1% от рынка в 40 миллиардов долларов). Дисциплина Бессемера по определению размера рынка требует перекрестной проверки снизу вверх. Что такое единицы измерения × цена × принятие?"

## Библиотека принудительных вопросов (шаблон grill-with-docs) { #forcing-question-library-grill-with-docs-pattern }

Проконсультируйте пользователя по поводу решений, определяющих полосу движения, прежде чем использовать вспомогательный скилл. По одному за ход, рекомендуемый ответ, цитата из канона:

- ** КЛИНИЧЕСКАЯ дорожка**: "Является ли ваша основная конечная точка клиническим исходом или суррогатной — и если суррогатной, подтверждена ли она по данному показанию? Рекомендуется: клинический исход, если суррогатная мать не указана в таблице, утвержденной FDA. Канон: Таблица суррогатных конечных точек FDA; ЛУЧШИЙ глоссарий."
- **RD_FINANCE lane**: "Находятся ли эти расходы на стадии исследования или разработки, и можете ли вы подтвердить техническую осуществимость? Рекомендуется: исследование = расходы; разработка = капитализация - кандидат только с подтверждением технико-экономического обоснования, направляемым указанному финансовому владельцу. Канон: МСФО (IAS) 38; ASC 730."
- ** МАРКЕТ-лейн **: "Ваш TAM направлен сверху вниз или снизу вверх - и вы вычислили его обоими способами для триангуляции? Рекомендуется: и то, и другое; выверить дельту. Канон: Оценка рынка Bessemer / a16z; оценка Ферми."
- ** PRODUCT lane**: "Является ли это исследование генеративным (выявление проблем) или оценочным (тестирование решения)? Рекомендуется: сначала назовите его; далее следует метод. Канон: "Ландшафт методов исследования UX" Рорера (NN/g)."

Никогда не запускайте вспомогательный скилл до тех пор, пока не будет зафиксировано решение об определении полосы движения.

## Онбординг-первый (для каждого суб-скилла) { #onboarding-first-per-sub-skill }

Перед первым вызовом вспомогательного скилла в рабочей области укажите пользователю на анкету для онбординга этого скилла, чтобы инструменты запускались, предварительно настроенные в соответствии с их контекстом:

```bash
python3 skills/<sub-skill>/scripts/onboard.py          # interactive Q&A
python3 skills/<sub-skill>/scripts/onboard.py --show    # questions + current config
```

У каждого под-скилла есть свой ** собственный** набор вопросов (клинический: область / альфа / власть / отсев /владельцы · финансовый: область / F & A/ взлетно-посадочная полоса /стандарт / владелец · рынок: профиль / уверенность /Министерство здравоохранения / метод · продукт: профиль / понимание-порог /метод/колья). Ответы сохраняются до `~/.config/research-ops/<sub-skill>.json` (или `./.research-ops/<sub-skill>.json` с `--scope project`) и автоматически используются каждым инструментом в этом скилле. Кастомизация здесь является обязательной дисциплиной, а не украшением — это этап онбординга, когда пользователь приступает к новому исследовательскому процессу.

## Хэндофф автоматического поиска (изолированный, по желанию) { #autoresearch-handoff-isolated-opt-in }

Каждый вспомогательный скилл обладает своим собственным `skills/<sub-skill>/scripts/ar_evaluator.py` — ** изолированный** мост к `engineering/autoresearch-agent`. Вызывайте автоматический поиск ** только тогда, когда пользователь явно запрашивает** "оптимизировать", "улучшить" или "запустить цикл". Хэндофф выполняется для каждого скилла (без общей связи): цикл редактирует входной файл скилла, и оценщик оценивает его (клинический → `feasibility_composite` высшее; финансы → `runway_months` выше; рынок → `tam_divergence` ниже; продукт → `validated_insights` выше). Никогда не запускайте цикл автоматически; никогда не позволяйте циклу редактировать средство оценки.

## Допущения { #assumptions }

1. Пользователь обладает полномочиями на проведение исследований ИЛИ готовит анализ для кого-то, кто это делает.
2. Пользователю нужна ** детерминированная поддержка принятия решений **, а не окончательный ответ — врач утверждает протокол, контролер регистрирует запись, человек выбирает рыночный номер.
3. Вводимые данные могут быть частичными — каждый вспомогательный скилл предоставляет шаблонный образец, чтобы пользователь мог увидеть форму, прежде чем заполнять свою собственную.

## Нецели { #non-goals }

- Не является EDC, системой управления клиническими испытаниями, системой учета, платформой для проведения опросов или хранилищем исследований.
- Не предоставляет клинические, бухгалтерские или юридические консультации как факт. Каждый вывод - это ** рекомендация + имя пользователя-владельца **.
- Не сохраняет историю исследований между сеансами.

## Отличный от { #distinct-from }

- **`research/` (академический)** — этот домен ** находит** литературу, гранты и патенты. Эта область ** планирует, финансирует, определяет масштабы и обобщает** исследования.
- **`ra-qm-team`** — это ** нормативное представление/QM ** (ISO 13485/14971, MDR, FDA 510(k)/PMA/QSR). клиническое исследование разрабатывает ** исследование**; оно направляет материалы в ra-qm-team.
- **`finance/financial-analysis`** — это ** корпоративное закрытие + оценка**. research-finance управляет ** расходами на программу НИОКР/портфолио **.
- **`research/grants`** — это ** открытие финансирования**. research-finance управляет **уже выигранными деньгами**.
- **`product-team`** — это ** артефакты персоны /путешествия, спринты открытий и живые A/ B эксперименты **. исследование продукта - это **метод + дисциплина хранилища**.
- **`marketing-skill`** — это ** аналитика кампаний и анализ спроса **. исследование рынка - это ** восходящая методология**.

## Анти-паттерны (не делать) { #anti-patterns-do-not }

- ❌ Представьте клиническую мощность/выходные данные конечной точки как факт — это **оценка** с указанием имени владельца клиники
- ❌ Автоматическое определение направления капитализации по сравнению с расходами к ** названному финансовому владельцу**
- ❌ Укажите размер рынка в виде единственного числа без источника — показать ** метод + двусторонняя триангуляция + допущения**
- ❌ Подтвердите информацию о продукте от одного участника — отметьте это как ** анекдот**
- ❌ Выполните все 4 вспомогательных скилла "досконально" - выберите один, переварите, соедините в цепочку, если необходимо
