# /cs:freeze — Блокировка времени восстановления при принятии решения { #csfreeze--cooldown-lock-on-a-decision }

**Команда:** `/cs:freeze <decision-path> <days>`

Блокирует решение на определенный период восстановления. Во время замораживания маршрутизатор начальника штаба отказывается повторно оспаривать решение, если явно не срабатывает критерий уничтожения. Триггер.

Вдохновленный gstack's `/freeze` и `/guard` примитивы безопасности — адаптированы от анализа кода к стратегическому анализу.

## Когда использовать { #when-to-use }

Основатели - это те, кто подбирает шаблоны; подбор шаблонов после принятия трудного решения часто приводит к обратному результату, который на самом деле является просто усталостью от принятия решений. Замораживание обеспечивает соблюдение дисциплины:

- После любого **необратимого** или **требующего больших затрат на отмену** решения (сбор средств, увольнение, выход на рынок)
- После ** раздельного голосования в зале заседаний** (сохраните вызов на случай повторных предположений)
- После того, как ** чутье основателя ** отменило единодушный консенсус консультантов (пусть все работает)
- Во время ** кадровой перестановки** (заблокируйте стратегию, чтобы новый руководитель мог выполнять, а не пересматривать)

## Периоды замораживания по умолчанию { #default-freeze-periods }

| Тип решения | Замораживание по умолчанию |
|---|---|
| Размер раунда сбора средств / выбор ведущего | 30 дней |
| Изменение ценообразования | 60 дней |
| Вход / выход с рынка | 90 дней |
| Увольнение / RIF | 30 дней |
| Стратегический стержень | 90 дней |
| Персонал (наем/ увольнение руководителя) | 60 дней |
| Объем сделок по слияниям и поглощениям | 30 дней |
| Обычай | укажите в команде |

## Воркфлоу { #workflow }

1. Ознакомьтесь с протоколом принятия решения
2. Подтвердите, что он имеет статус УТВЕРЖДЕН
3. Применить замораживание: запись `freeze_until: YYYY-MM-DD` к протоколу принятия решения
4. Добавить в индекс активных зависаний по адресу `~/.claude/freezes/active.md`
5. маршрутизатор cs-chief-of-staff теперь отказывается перенаправлять эту тему в зал заседаний до тех пор, пока:
   - Период замораживания истекает, ИЛИ
   - Критерий уничтожения явно запускает триггер

## Выход { #output }

Запись о принятии решения обновляется на месте:

```markdown
# Decision: <title>
...
**Status:** FROZEN
**Frozen until:** YYYY-MM-DD
**Reason for freeze:** <text>
**Override condition:** Kill criterion <name> triggers OR founder issues `/cs:unfreeze` with stated reason
```

Обновлен индекс активных зависаний:

```markdown
# Active Freezes
**Updated:** YYYY-MM-DD

| Decision | Frozen until | Override condition |
|---|---|---|
| <decision title> | YYYY-MM-DD | <kill criterion or /cs:unfreeze> |
```

## Переопределять { #override }

Чтобы разморозить до истечения срока, основатель запускает:

```
/cs:unfreeze <decision> <reason>
```

Размораживание регистрируется в истории принятия решений (сохраняется постоянно). Принудительные переопределения создают бумажный след, который всплывает при вскрытии.

## Автоматическое переопределение { #auto-override }

Если в решении срабатывает критерий отмены, триггер автоматически отключается, и начальник штаба немедленно направляется к `/cs:post-mortem` Замораживание не защищает от реальности; оно защищает от импульса.

## Почему это лучше, чем "Просто не принимай повторного решения"? { #why-this-beats-just-dont-re-decide }

Основатели обладают властью. Без явного lock + log каждое колебание приводит к "давайте обсудим это еще раз", что утомляет консультантов и снижает ценность зала заседаний. Замораживание - это ** процесс**, а не правило; оно регистрирует каждое переопределение, чтобы вскрытие могло провести аудит дисциплины основателя.

## Маршрутизация { #routing }

- `/cs:unfreeze` — явное досрочное освобождение
- `/cs:post-mortem` — автоматически триггер, если срабатывает критерий уничтожения
- `/cs:boardroom` — заблокирован до размораживания или истечения срока годности
