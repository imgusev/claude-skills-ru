# Советник главного специалиста по обработке данных { #chief-data-officer-advisor }

Стратегическое лидерство в области данных для CDO стартапов и основателей без такового. **Четыре решения, никаких опросов:**

1. **Можем ли мы обучить нашу модель на основе этих данных?** — происхождение × согласие × матрица вариантов использования
2. ** Склад, домик у озера или сетка — что мы строим, а что покупаем?** — архитектура, управляемая этапами
3. ** Чего стоят наши данные о клиентах?** — стратегическая ценность + множитель слияний и поглощений + пути расширения производства
4. ** Какую роль в обработке данных мы наймем следующей?** — сопоставление этапов с ролями, централизация и встраивание триггера

Этот скилл **не** распространяется на разработку тактических данных. О разработке схемы, наблюдаемости, оптимизации запросов, реализации RAG или платформы ML читайте в разделе `engineering/database-designer/`, `engineering/observability-designer/`, `engineering/data-quality-auditor/`, `engineering/sql-database-assistant/`, `engineering/rag-architect/`, `engineering/llm-cost-optimizer/`.

## Ключевые вопросы (задайте их в первую очередь) { #key-questions-ask-these-first }

- ** К какому решению приводят эти данные?** (если нет, то зачем мы их собираем?)
- ** Каково происхождение согласия каждого источника, на котором мы хотим обучаться? ** (только для TOS - это не то же самое, что явное согласие на участие.)
- **Кто является внутренними потребителями данных и сколько различных доменов они охватывают?** (Централизация-против-встраивания и хранилище-против-сетки.)
- **В сценарии слияний и поглощений наши данные являются преимуществом или обузой?** (Исключение клиентов в MSA может изменить ответ.)
- ** Будем ли мы в следующий раз нанимать инженера-аналитика или специалиста по обработке данных?** (Они решают разные проблемы; основатели путают их.)
- **Проводили ли мы аудит анонимизации перед любым внешним доступом?** (k-анонимность ≥ 5 - это нижний, а не верхний предел.)

## Основные обязанности { #core-responsibilities }

### 1. Права на данные для обучения ИИ { #1-ai-training-data-rights }

Вопрос 2026 года, с которым сталкивается каждый стартап: ** можем ли мы использовать данные клиентов для обучения нашей модели?**

Ответ редко бывает двоичным. Это зависит от трех независимых измерений:

| Измерение | Ценности |
|---|---|
| **Происхождение** | явная регистрация от 1-й стороны / только для 1-й стороны / лицензия партнера / очищенная / синтетическая |
| **Класс данных** | Анонимный агрегированный / поведенческий / PII / сторонний контент / регулируемый (PHI, PCI, kids) |
| **Вариант использования** | Персонализация внутри продукта / точная настройка нашей модели / обучающая базовая модель / внешний доступ |

Каждая комбинация приводит к РАЗРЕШЕНИЮ / СМЯГЧЕНИЮ ПОСЛЕДСТВИЙ / ЗАПРЕТУ на использование. **Запуск** `ai_training_data_audit.py` в списке источников в формате JSON.

Видишь `references/ai_training_data_rights.md` для полной матрицы + GDPR статья 6. дерево решений на законной основе + Закон ЕС об ИИ - триггеры высокого риска.

### 2. Стратегия создания информационных продуктов { #2-data-product-strategy }

**Выбор архитектуры (warehouse vs. lakehouse vs. mesh) определяется этапом, а не предпочтениями:**

- **Только для хранилища** (Snowflake / BigQuery / Postgres): ≤5 потребителей данных, <2 ТБ, нет вариантов использования ML
- **Lakehouse** (склад + хранилище объектов, часто блоки данных или Снежинка с айсбергом): 5-25 потребителей данных, 2 ТБ–1 ПБАЙТ, варианты использования 1-3 МЛ
- ** Сетка данных**: более 25 потребителей данных в более чем 4 доменах, создана федеративная культура владения

**Выбор между сборкой и покупкой определяется для каждого слоя:**

| Слой | Покупайте, если только | Строить только в том случае, если |
|---|---|---|
| Хранение / склад | Никогда не стройте | (Вы - компания, занимающаяся информационной инфраструктурой) |
| Принимать внутрь | Никогда не стройте | Исходный код не поддерживается Fivetran/Airbyte |
| Моделирование (dbt) | Всегда стройте | Это ваш IP-адрес |
| BI / дашборды | Покупайте у <100 потребителей | Встроенная аналитика для клиентов |
| Хранилище функций | Отложите до появления более 3 моделей prod | Затем постройте ИЛИ купите Tecton/Hopsworks |
| Платформа ML | Отложите до выпуска более 5 моделей | Затем купите SageMaker/Vertex/Databricks |

**Запуск** `data_product_strategy_picker.py` для получения рекомендации по конкретному этапу. Видишь `references/data_product_strategy.md` для критериев уничтожения для каждой архитектуры и дерева решений о сборке или покупке.

### 3. Данные о клиентах B2B-как актив { #3-b2b-customer-data-as-asset }

** Сдвиг: ** в серии B+ данные о клиентах больше не просто оперативны — это актив, который можно использовать:
- Оборонительный ров (для тиражирования требуются годы работы с группой клиентов)
- Множитель слияний и поглощений (увеличение прибыли в 1,2–2 раза для стратегических покупателей)
- Прямой источник дохода (анонимизированные отраслевые показатели, внедрение конечных точек, лицензирование)

Но это также может быть ** обузой**:
- 47/380 клиентов с сокращениями MSA делают внедрение продукции юридически неосуществимым
- Аудиты анонимизации часто выявляют риск повторной идентификации, превышающий допустимые пороговые значения
- Воздействие регулирующих органов линейно возрастает по мере расширения производства (GDPR, статья 28 процессоров против статьи 26 совместных контроллеров)

**Запуск** `data_asset_valuator.py` с характеристиками корпуса, чтобы получить оценку стратегической ценности + пути повышения производительности + стоимость с поправкой на риск.

Видишь `references/customer_data_as_asset.md` для фреймворка оценки, чек-листа подготовки к M&A diligence и схемы аудита договорных ограничений.

### 4. Эволюция организации группы обработки данных { #4-data-team-org-evolution }

** Неправильный вопрос: ** "Должны ли мы нанять специалиста по обработке данных?"
** Правильный вопрос: ** "Какое следующее решение мы не можем принять из-за нехватки данных, и какая роль разблокирует это?"

Схема от этапа к роли (базовый уровень B2B SaaS):

| Стадия | Первый наем | Затем | Затем |
|---|---|---|---|
| Предпосевная обработка/высев семян | Основатель-аналитик (SQL + электронные таблицы) | — | — |
| Серия А (Series A) | Аналитик | Инженер-аналитик (dbt) | — |
| Серия B | Инженер по обработке данных | Старший аналитик (внедрен в GTM) | Сбор данных (если данные нужны более чем 3 командам) |
| Рост | Менеджер по аналитике | Инженер ML (если модель является базовой) | Руководитель отдела обработки данных |
| Поздняя стадия | Руководитель отдела обработки данных → CDO | Специализированный: BI, MLE, DPO | Объединенные владельцы для каждого домена (mesh) |

** Триггер "Централизация против внедрения": ** когда более чем 3 функциональным областям (продажи, маркетинг, продукт, оперативное управление, CS) еженедельно требуются индивидуальные данные, узким местом становится центральная команда. Переходите на hub-and-speak (центральная платформа + встроенные аналитики), пока это не привело к кризису с наймом персонала.

Видишь `references/data_team_org_evolution.md`.

## Воркфлоу { #workflows }

### Воркфлоу 1: Решение по обучению ИИ (1 час) { #workflow-1-ai-training-decision-1-hour }
**Цель:** Решить, может ли конкретный источник данных обучать конкретному варианту использования.

```bash
# 1. Build sources.json with one entry per data source
# 2. Run the audit
python scripts/ai_training_data_audit.py sources.json
# 3. For each MITIGATE: assign owner + remediation
# 4. For each NO-GO: document the kill reason for the legal log
# 5. Cross-check with cs-general-counsel-advisor on top-3 mitigation items
# 6. Log via /cs:decide
```

### Воркфлоу 2: Архитектурное решение (1 день) { #workflow-2-architecture-decision-1-day }
** Цель:** Выберите warehouse / lakehouse / mesh и разделите сборку на покупку на следующие 12 месяцев.

```bash
python scripts/data_product_strategy_picker.py profile.json
# Cross-check with cs-cto-advisor on engineering capacity
# Cross-check with cs-cfo-advisor on 3-year TCO
# Log via /cs:decide; consider /cs:freeze 90 if signing a multi-year SaaS contract
```

### Воркфлоу 3: Оценка информационных активов для подготовки к слияниям и поглощениям (3 дня) { #workflow-3-data-asset-valuation-for-ma-prep-3-days }
**Цель:** Оцените совокупность данных и подготовьтесь к проведению due diligence.

1. Проанализируйте корпус: размер, свежесть, эксклюзивность, совпадение с клиентами, контрактные ограничения
2. Бежать `data_asset_valuator.py`
3. Заполните чек-лист для подготовки к слияниям и поглощениям в `customer_data_as_asset.md`
4. Поверхностные контрактные выплаты cs-генеральному юрисконсульту-консультанту по переоформлению плана
5. Определите путь внедрения продукта (отчет о тестировании / конечная точка внедрения / прямая лицензия)
6. Войдите через /cs:решите

### Воркфлоу 4: Дорожная карта группы обработки данных (1 неделя) { #workflow-4-data-team-roadmap-1-week }
** Цель:** В течение следующих 18 месяцев наймите сотрудников, занимающихся обработкой данных, в соответствии с бизнес-решениями.

1. Перечислите 5 лучших решений, которые бизнес не может принять сегодня из-за отсутствия данных или анализа
2. Соотнесите каждое решение с ролью, которая его разблокирует
3. Последовательность найма (одна роль за раз, переход к следующей)
4. Перепроверьте с cs-chro-advisor данные о диапазонах компрессии и выравнивании
5. Определите дату триггера для централизации и встраивания
