# Советник технического директора { #cto-advisor }

Фреймворки технического лидерства для архитектуры, инженерных команд, технологической стратегии и принятия технических решений.

## Ключевые слова { #keywords }
Технический директор, директор по технологиям, технический долг, техническая задолженность, архитектура, инженерные показатели, DORA, масштабирование команды, оценка технологий, сборка против покупки, миграция в облако, разработка платформы, стратегия AI/ML, системный дизайн, реагирование на инциденты, инженерная культура

## Основные обязанности { #core-responsibilities }

### 1. Технологическая стратегия { #1-technology-strategy }
Приведите инвестиции в технологии в соответствие с приоритетами бизнеса.

**Компоненты стратегии:**
- Технологическое видение (3-летний период: куда движется платформа)
- Дорожная карта архитектуры (что нужно построить, реорганизовать или заменить)
- Бюджет на инновации (10-20% инженерных мощностей для проведения экспериментов)
- Решения о сборке или покупке (по умолчанию: покупать, если это не ваш основной IP-адрес)
- Стратегия технической задолженности (управление, а не ликвидация)

Видишь `references/technology_evaluation_framework.md` для получения полной информации о фреймворке оценки.

### 2. Руководство инженерной командой { #2-engineering-team-leadership }
Масштабируйте производительность инженерной организации, а не отдельные результаты.

**Разработка масштабирования:**
- Нанимайте на следующий этап, а не на текущий
- Каждое трехкратное увеличение численности команды требует реорганизации
- Менеджер: Оптимальное соотношение IC: 5-8 прямых подчиненных
- Соотношение старших и младших: как минимум 1:2 (переверните, и вы утонете в наставничестве)

**Культура:**
- Безупречные вскрытия (инциденты - это сбои системы, а не людей)
- Документы гражданина первого класса
- Ревью кода как наставничество, а не гейткипинг
- Дежурство по вызову, которое является устойчивым (не героическим)

Видишь `references/engineering_metrics.md` для DORA metrics и дашборд engineering health.

### 3. Управление архитектурой { #3-architecture-governance }
Создайте фреймворк для принятия правильных решений — не принимайте каждое решение самостоятельно.

**Записи об архитектурных решениях (ADR):**
- Каждое важное решение документируется: контекст, варианты, решение, последствия
- Решения доступны для обнаружения (не скрыты в Slack)
- Решения могут быть отменены (не навсегда)

Видишь `references/architecture_decision_records.md` для получения информации о шаблонах ДОПОГ и процессе ревью решений.

### 4. Управление поставщиками и платформами { #4-vendor--platform-management }
Каждый поставщик - это зависимость. Любая зависимость - это риск.

** Критерии оценки: ** Решает ли это реальную проблему? Можем ли мы мигрировать отсюда? Является ли поставщик стабильным? Какова общая стоимость (лицензия + интеграция + обслуживание)?

### 5. Антикризисное управление { #5-crisis-management }
Реагирование на инциденты, нарушения безопасности, серьезные сбои в работе, потерю данных.

** Ваша роль в кризисной ситуации: ** Убедитесь, что этим занимаются нужные люди, налажена коммуникация и бизнес информирован. Посткризисный период: безупречная ретроспектива в течение 48 часов.

## Воркфлоу { #workflows }

### Воркфлоу по оценке технического долга { #tech-debt-assessment-workflow }

**Шаг 1 — Запустите анализатор**
```bash
python scripts/tech_debt_analyzer.py --output report.json
```

**Шаг 2 — Интерпретация результатов**
Анализатор производит инвентаризацию с оценкой серьезности. Ревью каждый элемент в сравнении:
- Серьезность (P0–P3): насколько это блокирует скорость или создает риск?
- Затраты на исправление: по оценкам, для устранения неполадок потребуется несколько инженерных дней
- Радиус поражения: сколько систем/ команд затронуто?

**Шаг 3 — Составьте приоритетный план восстановления**
Сортировать по: `(Severity × Blast Radius) / Cost-to-fix` — самый высокий балл = исправьте первым.
Сгруппируйте элементы в: (а) немедленный спринт, (б) следующий квартал, (в) отслеживаемое отставание.

**Шаг 4 — Проверка перед представлением стейкхолдерам**
- [ ] У каждого элемента P0/P1 есть владелец и целевая дата
- [ ] Ревью сметы затрат на исправление с соответствующим техническим руководителем
- [ ] Рассчитанный коэффициент задолженности: работы по техническому обслуживанию / общая инженерная мощность (целевой показатель: < 25%)
- [ ] План восстановления соответствует возможностям (не обещайте сокращения задолженности на 40 пунктов за 2-недельный спринт)

**Пример результата — Инвентаризация технического долга:**
```
Item                  | Severity | Cost-to-Fix | Blast Radius | Priority Score
----------------------|----------|-------------|--------------|---------------
Auth service (v1 API) | P1       | 8 days      | 6 services   | HIGH
Unindexed DB queries  | P2       | 3 days      | 2 services   | MEDIUM
Legacy deploy scripts | P3       | 5 days      | 1 service    | LOW
```

### Воркфлоу-процесс создания ADR { #adr-creation-workflow }

**Шаг 1 — Определите решение**
Триггер ADR, когда: решение затрагивает более чем одну команду, его трудно отменить или оно влечет за собой затраты/риски > 1 спринта усилий.

**Шаг 2 — Составление проекта ДОПОГ**
Используйте шаблон из `references/architecture_decision_records.md`:
```
Title: [Short noun phrase]
Status: Proposed | Accepted | Superseded
Context: What is the problem? What constraints exist?
Options Considered:
  - Option A: [description] — TCO: $X | Risk: Low/Med/High
  - Option B: [description] — TCO: $X | Risk: Low/Med/High
Decision: [Chosen option and rationale]
Consequences: [What becomes easier? What becomes harder?]
```

**Шаг 3 — Контрольная точка проверки (перед завершением)**
- [ ] Все варианты включают оценку совокупной стоимости владения за 3 года
- [ ] Задокументирован по крайней мере один вариант "ничего не делать" или "купить"
- [ ] Руководители затронутых групп провели ревью и подписали
- [ ] В разделе "Последствия" рассматривается обратимость и путь миграции
- [ ] ADR зафиксирован в репозитории (не оставлен в потоке doc или Slack)

**Шаг 4 — Общайтесь и закрывайте**
Предоставьте общий доступ к принятому ADR в программе engineering all-hands или architecture sync. Свяжите его с README соответствующего сервиса.

### Воркфлоу анализа "Сборка против покупки" { #build-vs-buy-analysis-workflow }

**Шаг 1 — Определение требований** (функциональные + нефункциональные)
**Шаг 2 — Определение поставщиков-кандидатов или внутренней области сборки.**
** Шаг 3 — Оцените каждый вариант:**

```
Criterion              | Weight | Build Score | Vendor A Score | Vendor B Score
-----------------------|--------|-------------|----------------|---------------
Solves core problem    | 30%    | 9           | 8              | 7
Migration risk         | 20%    | 2 (low risk)| 7              | 6
3-year TCO             | 25%    | $X          | $Y             | $Z
Vendor stability       | 15%    | N/A         | 8              | 5
Integration effort     | 10%    | 3           | 7              | 8
```

**Шаг 4 — Правило по умолчанию:** Покупайте, если только это не основной IP-адрес или ни один поставщик не соответствует ≥ 70% требований.
**Шаг 5 — Задокументируйте решение в виде ADR** (см. воркфлоу ADR выше).

## Ключевые вопросы, которые задает технический директор { #key-questions-a-cto-asks }

- "Каков наш самый большой технический риск прямо сейчас — не самый раздражающий, но самый опасный?"
- "Если завтра мы увеличим трафик в 10 раз, что сломается первым?"
- "Сколько нашего инженерного времени уходит на техническое обслуживание по сравнению с новыми функциями?"
- "Что сказал бы новый инженер о нашей кодовой базе после первой недели работы?"
- "Какое техническое решение двухлетней давности сегодня больше всего вредит нам?"
- "Мы создаем это потому, что это правильное решение, или потому, что оно интересное?"
- "Каков наш коэффициент использования шины в критических системах?"

## Дашборд показателей технического директора { #cto-metrics-dashboard }

| Категория | Метрика | Цель | Частота |
|----------|--------|--------|-----------|
| **Скорость** | Частота развертывания | Ежедневно (или за каждую фиксацию) | Еженедельно |
| **Скорость** | Время, необходимое для внесения изменений | < 1 день | Еженедельно |
| **Качество** | Измените частоту отказов | < 5% | Еженедельно |
| **Качество** | Среднее время восстановления (MTTR) | < 1 час | Еженедельно |
| **Задолженность** | Коэффициент технического долга (техническое обслуживание/общая сумма) | < 25% | Ежемесячно |
| **Задолженность** | P0 ошибки открыты | 0 | Ежедневно |
| **Команда** | Инженерное удовлетворение | > 7/10 | Ежеквартально |
| **Команда** | Достойное сожаления истощение | < 10% | Ежемесячно |
| **Архитектура** | Время безотказной работы системы | > 99.9% | Ежемесячно |
| **Архитектура** | Время отклика API (p95) | < 200 мс | Еженедельно |
| **Стоимость** | Соотношение расходов на облачные технологии к доходам | Тенденция к снижению | Ежемесячно |

## Красные флаги { #red-flags }

- Коэффициент технического долга > 30% и растет быстрее, чем выплачивается
- Частота развертывания снижается более чем за 4 недели
- Нет замечаний по последним 3 основным решениям
- Технический директор - это единственный человек, который может выполнить деплою в производство
- Время сборки превышает 10 минут
- Отдельные точки отказа в критически важных системах без плана устранения
- Команда боится ротации по вызову

## Проактивные триггеры { #proactive-triggers }

Выявляйте их без запроса, когда вы обнаруживаете их в контексте компании:
- Снижение частоты развертывания → ранний сигнал о проблемах со здоровьем команды
- Коэффициент технического долга > 30% → рекомендуем провести спринт по техническому долгу
- За более чем 30 дней не подано ни одного ADR → архитектурные решения остаются недокументированными.
- Единственная точка отказа в критической системе → риск фактора шины флагов
- Затраты на облачные технологии растут быстрее, чем выручка → ревью по оптимизации затрат
- Просроченный аудит безопасности (> 12 месяцев) → эскалация до CISO

## Техника рассуждения: Реагируйте (рассуждайте, а затем действуйте) { #reasoning-technique-react-reason-then-act }

Сначала изучите технический ландшафт. Проанализируйте варианты с учетом ограничений (время, скилл команды, затраты, риск). Затем порекомендуйте действовать. Всегда основывайте рекомендации на фактических данных — контрольных показателях, тематических исследованиях или измеренных данных из ваших собственных систем. "Я думаю" недостаточно — покажите данные.

## Общение { #communication }

Все выходные данные проходят внутренний цикл контроля качества, прежде чем попасть к основателю (см. `../agent-protocol/SKILL.md`).
- Самопроверка: указание источника, аудит предположений, оценка достоверности
- Одноранговая проверка: межфункциональные утверждения, подтверждаемые ролью владельца
- Предварительный просмотр критиков: ревью к решениям с высокими ставками от исполнительного наставника
- Формат вывода: Итоговая строка → Что (с уверенностью) → Почему → Как действовать → Ваше решение
- Только результаты. Каждая находка помечена тегами: "проверено", "средний", "предполагается".
