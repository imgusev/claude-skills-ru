# /em:challenge — Анализ плана вскрытия { #emchallenge--pre-mortem-plan-analysis }

**Команда:** `/em:challenge <plan>`

Систематически находит слабые места в любом плане до того, как это сделает реальность. Не для того, чтобы разрушить план — для того, чтобы он пережил контакт с реальностью.

---

## Основная идея { #the-core-idea }

Большинство планов проваливаются по предсказуемым причинам. Не невезение — плохие предположения. Завышенный спрос. Недооцениваемая сложность. Зависимости, которые никто не ставил под сомнение. Время, которое имело смысл в электронной таблице, но не в реальном мире.

Техника вскрытия: ** представьте, что прошло 12 месяцев, и этот план с треском провалился. Теперь работайте в обратном направлении. Почему?**

Это не пессимизм. Это то, как вы строите что-то, что не разрушается.

---

## Когда следует выполнять задание { #when-to-run-a-challenge }

- Прежде чем выделять значительные ресурсы на реализацию плана
- Перед представлением совету директоров или инвесторам
- Когда вы замечаете, что слышите только положительные отзывы о плане
- Когда для согласования плана требуется несколько внешних зависимостей
- Когда возникает необходимость действовать быстро и "разобраться с этим позже"
- Когда вы чувствуете волнение по поводу плана (волнение - это сигнал к более тщательному изучению)

## Фреймворк для решения задач { #the-challenge-framework }

### Шаг 1: Извлеките основные допущения { #step-1-extract-core-assumptions }
Прежде чем вы сможете протестировать план, вам нужно выявить все, что он предполагает как истинное.

По каждому разделу плана задавайте вопросы:
- Что должно быть правдой, чтобы это сработало?
- Что мы предполагаем о поведении клиентов?
- Что мы предполагаем относительно реакции конкурентов?
- Что мы предполагаем о наших собственных возможностях выполнения?
- От каких внешних факторов это зависит?

**Общие категории допущений:**
- **Рыночные предположения** — размер, темпы роста, готовность клиентов платить, цикл покупки
- ** Допущения к выполнению ** — потенциал команды, скорость, отсутствие необходимости в крупном найме
- ** Предположения клиентов ** — у них есть проблема, они знают, что она у них есть, они заплатят, чтобы решить ее
- ** Конкурентные предположения ** — действующие лица не откликаются, новых участников нет, ров удерживается
- **Финансовые допущения** — скорость выгорания, сроки получения выручки, CAC, коэффициенты LTV
- ** Предположения о зависимостях ** — партнер выполнит работу, API не изменится, правила не изменятся

### Шаг 2: Оцените каждое предположение { #step-2-rate-each-assumption }

Для каждого извлеченного предположения оцените его по двум параметрам:

**Уровень уверенности (насколько вы уверены, что это правда):**
- **Высокий** — проверено данными, беседами с клиентами, исследованиями рынка
- **Средний** — направление правильное, но не подтверждено
- **Низкий** — правдоподобный, но непроверенный
- **Неизвестно** — мы просто не знаем

**Влияние в случае ошибки (что произойдет, если это предположение не сработает):**
- **Критический** — план полностью проваливается
- **Высокий** — значительная задержка или перерасход средств
- **Средний** — требуется значительная доработка
- **Низкий уровень** — управляемая регулировка

### Шаг 3: Составьте карту уязвимостей { #step-3-map-vulnerabilities }

Матрица низкой/неизвестной достоверности × Критического/высокого воздействия = ваши предположения с наибольшим риском.

**Уязвимость = Низкая уверенность + высокая отдача**

Это не те проблемы, которые можно игнорировать. Это ставки, которые вы делаете. Вопрос в том, делаете ли вы их сознательно?

### Шаг 4: Найдите цепочку зависимостей { #step-4-find-the-dependency-chain }

Многие планы терпят неудачу не потому, что какое-то одно предположение неверно, а потому, что несколько предположений должны быть правильными одновременно.

Составьте карту цепочки:
- Зависит ли предположение B от того, что предположение A является истинным в первую очередь?
- Если первое что-то пойдет не так, сколько последующих вещей сломается?
- Каков критический путь? Что имеет нулевую слабину?

### Шаг 5: Проверьте обратимость { #step-5-test-the-reversibility }

Для каждой критической уязвимости: если это предположение окажется неверным на 3-м месяце, что вы будете делать?

- Ты можешь повернуться?
- Вы можете сократить масштаб?
- Деньги уже потрачены?
- Взяты ли уже обязательства?

Чем менее обратимо, тем более тщательную проверку вам нужно провести перед фиксацией.

## Выходной формат { #output-format }

**Отчет о вызове: [Название плана]**

```
CORE ASSUMPTIONS (extracted)
1. [Assumption] — Confidence: [H/M/L/?] — Impact if wrong: [Critical/High/Medium/Low]
2. ...

VULNERABILITY MAP
Critical risks (act before proceeding):
• [#N] [Assumption] — WHY it might be wrong — WHAT breaks if it is

High risks (validate before scaling):
• ...

DEPENDENCY CHAIN
[Assumption A] → depends on → [Assumption B] → which enables → [Assumption C]
Weakest link: [X] — if this breaks, [Y] and [Z] also fail

REVERSIBILITY ASSESSMENT
• Reversible bets: [list]
• Irreversible commitments: [list — treat with extreme care]

KILL SWITCHES
What would have to be true at [30/60/90 days] to continue vs. kill/pivot?
• Continue if: ...
• Kill/pivot if: ...

HARDENING ACTIONS
1. [Specific validation to do before proceeding]
2. [Alternative approach to consider]
3. [Contingency to build into the plan]
```

## Шаблоны вызовов по типу плана { #challenge-patterns-by-plan-type }

### Дорожная карта продукта { #product-roadmap }
- Создаем ли мы то, за что клиенты будут платить, или то, что, по их словам, они хотели?
- Учитывает ли оценка скорости реальную вместимость команды (не теоретическую)?
- Что произойдет, если привязка объекта займет в 3 раза больше времени, чем предполагалось?
- Кому принадлежат решения, когда требования вступают в противоречие?

### План выхода на рынок { #go-to-market-plan }
- Каков фактический коэффициент конверсии ICP, а не ожидаемый?
- Сколько касаний нужно закрыть, и есть ли у вас для этого возможности по продажам?
- Что произойдет, если первые 10 сделок займут 3 месяца вместо 1?
- Является ли "приземляться и расширяться" реальным движением или надеждой?

### План найма { #hiring-plan }
- Что произойдет, если поиск ключевого сотрудника займет 4 месяца, а не 6 недель?
- Зависит ли план от удержания конкретных людей, которые могут уйти?
- Учитывается ли в плане время нарастания (обычно за 3-6 месяцев до полной производительности)?
- Каков эффект от сокращения расходов, если численность персонала превысит выручку на 6 месяцев?

### План сбора средств { #fundraising-plan }
- Каков ваш запасной вариант, если ведущий инвестор откажется?
- Смоделировали ли вы временную шкалу, если это займет 6 месяцев, а не 3?
- Какова ваша взлетно-посадочная полоса на текущем этапе, если раунд закроется на низком уровне?
- Какие предположения нарушатся, если вы соберете 50% от целевой суммы?

## Самые трудные вопросы { #the-hardest-questions }

Это те, которые люди пропускают:
- - А что такое "медвежий случай", а не базовый?
- "Если бы этим точным планом руководила команда, которой мы не доверяем, сработал бы он?"
- "Что мы не говорим вслух, потому что это неудобно?"
- "У кого есть стимулы для того, чтобы этот план звучал лучше, чем он есть на самом деле?"
- "На что враг этого плана напал бы в первую очередь?"

## Конечный результат { #deliverable }

Результат работы `/em:challenge` это не разрешение останавливаться. Это карта уязвимостей. Теперь вы можете принимать осознанные решения: подтверждать рискованные предположения, хеджировать критические или принимать ставки, которые вы делаете сознательно.

Неизвестные риски опасны. Известные риски поддаются управлению.
