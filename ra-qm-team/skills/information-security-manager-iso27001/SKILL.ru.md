## Инструменты { #tools }

### risk_assessment.py { #risk_assessmentpy }

Автоматизированная оценка рисков безопасности в соответствии с методологией пункта 6.1.2 стандарта ISO 27001.

**Использование:**

```bash
# Full risk assessment
python scripts/risk_assessment.py --scope "cloud-infrastructure" --output risks.json

# Healthcare-specific assessment
python scripts/risk_assessment.py --scope "ehr-system" --template healthcare --output risks.json

# Quick asset-based assessment
python scripts/risk_assessment.py --assets assets.csv --output risks.json
```

**Параметры:**

| Параметр | Требуемый | Описание |
|-----------|----------|-------------|
| `--scope` | Да | Система или область для оценки |
| `--template` | Нет | Шаблон оценки: `general`, `healthcare`, `cloud` |
| `--assets` | Нет | CSV-файл с описью активов |
| `--output` | Нет | Выходной файл (по умолчанию: стандартный вывод) |
| `--format` | Нет | Выходной формат: `json`, `csv`, `markdown` |

**Выход:**
- Инвентаризация активов с классификацией
- Отображение угроз и уязвимостей
- Оценки риска (вероятность × воздействие)
- Рекомендации по лечению
- Расчеты остаточного риска

### compliance_checker.py { #compliance_checkerpy }

Проверьте статус внедрения системы контроля ISO 27001/27002.

**Использование:**

```bash
# Check all ISO 27001 controls
python scripts/compliance_checker.py --standard iso27001

# Gap analysis with recommendations
python scripts/compliance_checker.py --standard iso27001 --gap-analysis

# Check specific control domains
python scripts/compliance_checker.py --standard iso27001 --domains "access-control,cryptography"

# Export compliance report
python scripts/compliance_checker.py --standard iso27001 --output compliance_report.md
```

**Параметры:**

| Параметр | Требуемый | Описание |
|-----------|----------|-------------|
| `--standard` | Да | Стандарт для проверки: `iso27001`, `iso27002`, `hipaa` |
| `--controls-file` | Нет | CSV с текущим состоянием управления |
| `--gap-analysis` | Нет | Включать рекомендации по исправлению положения |
| `--domains` | Нет | Конкретные управляющие домены для проверки |
| `--output` | Нет | Путь к выходному файлу |

**Выход:**
- Статус реализации контроля
- Процент соответствия требованиям по доменам
- Анализ пробелов с указанием приоритетов
- Рекомендации по исправлению положения

## Воркфлоу { #workflows }

### Воркфлоу 1: Внедрение ISMS { #workflow-1-isms-implementation }

**Шаг 1: Определите область применения и контекст**

Документируйте организационный контекст и границы ISMS:
- Определить заинтересованные стороны и требования
- Определите сферу применения и границы ISMS
- Внутренний документ/external проблемы

**Валидация: ** Заявление о сфере применения было ревью и одобрено руководством.

**Шаг 2: Проведите оценку рисков**

```bash
python scripts/risk_assessment.py --scope "full-organization" --template general --output initial_risks.json
```

- Идентификация информационных активов
- Оценка угроз и уязвимостей
- Рассчитать уровни риска
- Определите варианты лечения рисков

**Проверка:** Реестр рисков содержит все критически важные активы с назначенными владельцами.

**Шаг 3: Выберите и внедрите элементы управления**

Сопоставьте риски с элементами управления по стандарту ISO 27002:

```bash
python scripts/compliance_checker.py --standard iso27002 --gap-analysis --output control_gaps.md
```

Контрольные категории:
- Организационный (политика, роли, ответственность)
- Люди (скрининг, информирование, обучение)
- Физические (периметры, оборудование, носители)
- Технологический (доступ, криптография, сеть, приложение)

**Валидация: ** Заявление о применимости (SoA) документирует все элементы управления с обоснованием.

**Шаг 4: Установите мониторинг**

Определение показателей безопасности:
- Количество инцидентов и тенденции их серьезности
- Показатели эффективности контроля
- Показатели завершения обучения
- Процент закрытия результатов аудита

** Проверка: ** Дашборд показывает статус соответствия требованиям в режиме реального времени.

### Воркфлоу 2: Оценка рисков для безопасности { #workflow-2-security-risk-assessment }

**Шаг 1: Идентификация актива**

Создание инвентаризации активов:

| Тип актива | Примеры | Классификация |
|------------|----------|----------------|
| Информация | Записи пациентов, исходный код | Конфиденциальный |
| Программное обеспечение | Система EHR, API | Критический |
| Аппаратное обеспечение | Серверы, медицинское оборудование | Высокий |
| Услуги | Облачный хостинг, резервное копирование | Высокий |
| Люди | Учетные записи администраторов, разработчиков | Меняется |

** Проверка:** Всем активам назначены владельцы и классификации.

**Шаг 2: Анализ угроз**

Определение угроз для каждой категории активов:

| Актив | Угрозы | Вероятность |
|-------|---------|------------|
| Данные пациента | Несанкционированный доступ, нарушение | Высокий |
| Медицинские приборы | Вредоносное ПО, подделка | Средний |
| Облачные сервисы | Неправильная конфигурация, сбой в работе | Средний |
| Полномочия | Фишинг, грубая сила | Высокий |

** Проверка:** Модель угроз охватывает топ-10 отраслевых угроз.

**Шаг 3: Оценка уязвимости**

```bash
python scripts/risk_assessment.py --scope "network-infrastructure" --output vuln_risks.json
```

Уязвимости документа:
- Технические (непатченные системы, слабые конфигурации)
- Процесс (отсутствующие процедуры, пробелы)
- Люди (отсутствие подготовки, инсайдерский риск)

**Проверка:** Результаты сканирования уязвимостей сопоставляются с реестром рисков.

**Шаг 4: Оценка риска и лечение**

Рассчитать риск: `Risk = Likelihood × Impact`

| Уровень риска | Оценка | Лечение |
|------------|-------|-----------|
| Критический | 20-25 | Требуются немедленные действия |
| Высокий | 15-19 | План лечения в течение 30 дней |
| Средний | 10-14 | План лечения в течение 90 дней |
| Низкий | 5-9 | Принимать или контролировать |
| Минимальный | 1-4 | Принять |

** Проверка:** Все высокие/critical риски имеют утвержденные планы лечения.

### Воркфлоу 3: Реагирование на инциденты { #workflow-3-incident-response }

**Шаг 1: Обнаружение и отчетность**

Категории инцидентов:
- Нарушение безопасности (несанкционированный доступ)
- Заражение вредоносным ПО
- Утечка данных
- Системный компромисс
- Нарушение правил

** Проверка:** инцидент регистрируется в течение 15 минут с момента обнаружения.

**Шаг 2: Сортировка и классификация**

| Суровость | Критерии | Время отклика |
|----------|----------|---------------|
| Критический | Утечка данных, сбой системы | Немедленный |
| Высокий | Активная угроза, значительный риск | 1 час |
| Средний | Сдерживаемая угроза, ограниченное воздействие | 4 часа |
| Низкий | Незначительное нарушение, без последствий | 24 часа |

** Проверка: ** Назначена степень серьезности и, при необходимости, триггер эскалации.

**Шаг 3: Сдерживание и искоренение**

Немедленные действия:
1. Изолировать затронутые системы
2. Сохранять улики
3. Блокировать векторы угроз
4. Удаление вредоносных артефактов

** Проверка: ** Сдерживание подтверждено, никаких текущих компромиссов.

**Шаг 4: Восстановление и извлеченные уроки**

Мероприятия после инцидента:
1. Восстановление систем из чистых резервных копий
2. Проверьте целостность перед повторным подключением
3. Документируйте временную шкалу и действия
4. Провести ревью после инцидента
5. Обновлять элементы управления и процедуры

** Проверка:** Отчет о инциденте, составленный после него, заполняется в течение 5 рабочих дней.

## Контрольные точки проверки { #validation-checkpoints }

### Проверка внедрения ISMS { #isms-implementation-validation }

| Фаза | Контрольный пункт | Требуемые доказательства |
|-------|------------|-------------------|
| Сфера применения | Утвержденная область применения | Подписанный документ о сфере применения |
| Риск | Регистрация завершена | Регистрация рисков у владельцев |
| Элементы управления | Одобрено SoA | Заявление о применимости |
| Операция | Активные показатели | Скриншоты дашборда |
| Аудит | Проведен внутренний аудит | Отчет о аудите |

### Готовность к сертификации { #certification-readiness }

Перед этапом 1 аудита:
- [ ] Область применения ISMS задокументирована и утверждена
- [ ] Опубликована политика информационной безопасности
- [ ] Оценка рисков завершена
- [ ] Заявление о применимости завершено
- [ ] Проведен внутренний аудит
- [ ] Ревью руководства завершен
- [ ] Устраненные несоответствия

Перед этапом 2 аудита:
- [ ] Внедренные и действующие средства контроля
- [ ] Имеющиеся доказательства эффективности
- [ ] Персонал обучен и осведомлен
- [ ] Инциденты регистрируются и управляются
- [ ] Показатели, собранные за более чем 3 месяца

## Отработанный пример: Оценка рисков для здравоохранения { #worked-example-healthcare-risk-assessment }

**Сценарий:** Оценка рисков безопасности для системы управления данными пациентов.

### Шаг 1: Определите активы { #step-1-define-assets }

```bash
python scripts/risk_assessment.py --scope "patient-data-system" --template healthcare
```

**Результаты инвентаризации активов:**

| Идентификатор актива | Актив | Тип | Владелец | Классификация |
|----------|-------|------|-------|----------------|
| A001 | База данных пациентов | Информация | Команда администратора баз данных | Конфиденциальный |
| A002 | Применение EHR | Программное обеспечение | Команда разработчиков приложений | Критический |
| A003 | Сервер базы данных | Аппаратное обеспечение | Команда Infra | Высокий |
| A004 | Учетные данные администратора | Доступ | Безопасность | Критический |

### Шаг 2: Определите риски { #step-2-identify-risks }

**Вывод реестра рисков:**

| Идентификатор риска | Актив | Угроза | Уязвимость | L | Я | Оценка |
|---------|-------|--------|---------------|---|---|-------|
| R001 | A001 | Утечка данных | Слабое шифрование | 3 | 5 | 15 |
| R002 | A002 | SQL-инъекция | Проверка входных данных | 4 | 4 | 16 |
| R003 | A004 | Кража учетных данных | Нет Министерства иностранных дел | 4 | 5 | 20 |

### Шаг 3: Определите лечение { #step-3-determine-treatment }

| Риск | Лечение | Контроль | Временная шкала |
|------|-----------|---------|----------|
| R001 | Смягчать | Внедрить шифрование AES-256 | 30 дней |
| R002 | Смягчать | Добавить проверку ввода, WAF | 14 дней |
| R003 | Смягчать | Примените MFA для всех администраторов | 7 дней |
