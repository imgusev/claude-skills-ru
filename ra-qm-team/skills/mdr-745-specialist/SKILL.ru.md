## Классификация устройств по воркфлоу { #device-classification-workflow }

Классифицировать устройство в соответствии с приложением VIII к MDR:

1. Определить продолжительность работы устройства (переходная, кратковременная, долгосрочная)
2. Определить уровень инвазивности (неинвазивный, через отверстие в теле, хирургический)
3. Оценить контакт с системами организма (ЦНС, сердце, другие)
4. Проверьте, активно ли устройство (зависит от энергопотребления)
5. Применяйте правила классификации 1-22
6. Для программного обеспечения примените алгоритм MDCG 2019-11
7. Обоснование классификации документов
8. **Валидация:** Классификация подтверждена Нотифицированным органом

### Классификационная матрица { #classification-matrix }

| Фактор | Класс I | Класс IIa | Класс IIb | Класс III |
|--------|---------|-----------|-----------|-----------|
| Продолжительность | Любой | Краткосрочный | Долгосрочный | Долгосрочный |
| Агрессивность | Неинвазивный | Отверстие в корпусе | Хирургический | Имплантируемый |
| Система | Любой | Некритичный | Важнейшие органы | ЦНС/сердце |
| Риск | Самый низкий | Низкий-средний | Средне-высокий | Самый высокий |

### Классификация программного обеспечения (MDCG 2019-11) { #software-classification-mdcg-2019-11 }

| Использование информации | Тяжесть состояния | Класс |
|-----------------|-------------------|-------|
| Информирует о решении | Несерьезный | IIa |
| Информирует о решении | Серьезный | IIb |
| Приводы/угощения | Критический | III |

### Примеры классификации { #classification-examples }

**Пример 1: Рассасывающийся хирургический шов**
- Правило 8 (имплантируемый, долгосрочный)
- Продолжительность: > 30 дней (впитывается)
- Контакт: Общая ткань
- Классификация: **Класс IIb**

**Пример 2: Программное обеспечение для диагностики искусственного интеллекта**
- Правило 11 + MDCG 2019-11
- Функция: Диагностирует серьезное состояние
- Классификация: **Класс IIb**

**Пример 3: Кардиостимулятор**
- Правило 8 (имплантируемое)
- Контакт: Центральная кровеносная система
- Классификация: **Класс III**

## Техническая документация { #technical-documentation }

Подготовьте технический файл в соответствии с приложениями II и III:

1. Создать описание устройства (варианты, аксессуары, назначение)
2. Разработать маркировку (требования статьи 13, IFU)
3. Разработка документа и производственный процесс
4. Полная матрица соответствия требованиям GSPR
5. Подготовить анализ соотношения выгод и рисков
6. Собирать доказательства проверки и валидации
7. Интегрировать файл управления рисками (ISO 14971)
8. ** Проверка:** Ревью технического файла на предмет полноты

### Техническая структура файла { #technical-file-structure }

```
ANNEX II TECHNICAL DOCUMENTATION
├── Device description and UDI-DI
├── Label and instructions for use
├── Design and manufacturing info
├── GSPR compliance matrix
├── Benefit-risk analysis
├── Verification and validation
└── Clinical evaluation report
```

### Чек-лист соответствия требованиям GSPR Compliance Compliance { #gspr-compliance-checklist }

| Требование | Доказательства | Статус |
|-------------|----------|--------|
| Безопасная конструкция (GSPR 1-3) | Файл управления рисками | ☐ |
| Химические свойства (GSPR 10.1) | Отчет о биосовместимости | ☐ |
| Риск заражения (GSPR 10.2) | Валидация стерилизации | ☐ |
| Требования к программному обеспечению (GSPR 17) | Документация по IEC 62304 | ☐ |
| Маркировка (GSPR 23) | Оформление этикетки, IFU | ☐ |

### Маршруты оценки соответствия { #conformity-assessment-routes }

| Класс | Маршрут | Участие НБ |
|-------|-------|----------------|
| Я | Приложение II самопровозглашение | Нет |
| Есть/Им | Приложение II + IX/XI | Аспекты стерильности/измерения |
| IIa | Приложение II + IX или XI | Продукт или СМК |
| IIb | Приложение IX или приложение X + XI | СМК + оценка технического документа или типовой экзамен + производство |
| III | Приложение IX или приложение X + XI | Полная система менеджмента качества + досье на продукцию или типовой экзамен + производство |

## Клинические данные { #clinical-evidence }

Разработать стратегию получения клинических данных в соответствии с приложением XIV:

1. Определите клинические требования и конечные точки
2. Проводить систематический поиск литературы
3. Оценить качество клинических данных
4. Оценка эквивалентности (технической, биологической, клинической)
5. Выявлять пробелы в доказательствах
6. Определите, требуется ли клиническое исследование
7. Подготовить отчет о клинической оценке (CER)
8. **Валидация:** CER ревью проводится квалифицированным специалистом по оценке

### Требования к доказательствам в разбивке по классам { #evidence-requirements-by-class }

| Класс | Минимум доказательств | Расследование |
|-------|------------------|---------------|
| Я | Анализ соотношения рисков и выгод | Обычно не требуется |
| IIa | Литература + постмаркетинговая | Может потребоваться |
| IIb | Систематический ревью литературы | Часто требуется |
| III | Исчерпывающие клинические данные | Требуется (статья 61) |

### Структура отчета о клинической оценке { #clinical-evaluation-report-structure }

```
CER CONTENTS
├── Executive summary
├── Device scope and intended purpose
├── Clinical background (state of the art)
├── Literature search methodology
├── Data appraisal and analysis
├── Safety and performance conclusions
├── Benefit-risk determination
└── PMCF plan summary
```

### Требования к квалифицированному оценщику { #qualified-evaluator-requirements }

- Медицинская степень или эквивалентная медицинская квалификация
- более 4 лет клинического опыта в соответствующей области
- Обучение методологии клинической оценки
- Понимание требований к MDR

## Пострыночный надзор { #post-market-surveillance }

Создать систему PMS в соответствии с главой VII:

1. Разработать план PMS (статья 84)
2. Определите методы сбора данных
3. Установить процедуры рассмотрения жалоб
4. Создать процесс отчетности о бдительности
5. Планируйте периодические отчеты об обновлениях безопасности (PSUR)
6. Интеграция с деятельностью PMCF
7. Определите анализ тренда и обнаружение сигналов
8. **Валидация:** Система PMS ежегодно проходит аудит

### Компоненты системы PMS { #pms-system-components }

| Компонент | Требование | Частота |
|-----------|-------------|-----------|
| План PMS | Статья 84 | Поддерживать текущий |
| ПСУР | Статья 86 — Класс IIa и выше | В соответствии со статьей 86(1), приведенной ниже. |
| План PMCF | Приложение XIV, часть B | Обновление с помощью CER |
| Отчет PMCF | Приложение XIV, часть B | Ежегодный (III класс) |
| Бдительность | Статьи 87-92 | По мере того, как происходят события |

### Расписание PSUR { #psur-schedule }

| Класс | Частота (статья 86(1) MDR) |
|-------|-----------------------------|
| Класс III | Обновляется не реже одного раза в год |
| Класс IIb (все, включая поддающийся имплантации) | Обновляется не реже одного раза в год |
| Класс IIa | При необходимости, по крайней мере, каждые 2 года |
| Класс I | Вместо этого нет отчета PSUR — PMS (статья 85) |

### Сообщение о серьезном инциденте { #serious-incident-reporting }

| Временная шкала | Требование |
|----------|-------------|
| 2 дня | Серьезная угроза общественному здоровью |
| 10 дней | Смерть или серьезное ухудшение состояния |
| 15 дней | Другие серьезные инциденты |

## ЭВДАМЕД и УДИ { #eudamed-and-udi }

Внедрить систему UDI в соответствии со статьей 27:

1. Получить код организации-эмитента (GS1, HIBCC, ICCBBA)
2. Назначьте UDI-DI каждому варианту устройства
3. Присвоить UDI-PI (производственный идентификатор)
4. Нанесение UDI-носителя на этикетки (AIDC + HRI)
5. Зарегистрировать актера в EUDAMED
6. Регистрируйте устройства в EUDAMED
7. Загружайте сертификаты, когда они доступны
8. **Валидация:** UDI проверен на этикетках образцов

### Модули EUDAMED { #eudamed-modules }

| Модуль | Содержание | Актер |
|--------|---------|-------|
| Актер | Регистрация компании | Производитель, AR |
| UDI/Устройство | Данные об устройстве и вариантах | Производитель |
| Сертификаты | Сертификаты NB | Уведомленный орган |
| Клиническое исследование | Регистрация на учебу | Спонсор |
| Бдительность | Отчеты о инцидентах | Производитель |
| Надзор за рынком | Действия властей | Компетентный орган |

### Требования к этикетке UDI { #udi-label-requirements }

Обязательные элементы в соответствии со статьей 13:

- [ ] UDI-DI (идентификатор устройства)
- [ ] UDI-PI (производственный идентификатор) для класса II+
- [ ] Формат AIDC (штрих-код/RFID)
- [ ] Формат HRI (удобочитаемый)
- [ ] Название и адрес производителя
- [ ] Партия/серийный номер
- [ ] Срок годности (если применимо)

## Инструменты { #tools }

### Анализатор зазоров MDR { #mdr-gap-analyzer }

```bash
# Quick gap analysis
python scripts/mdr_gap_analyzer.py --device "Device Name" --class IIa

# JSON output for integration
python scripts/mdr_gap_analyzer.py --device "Device Name" --class III --output json

# Interactive assessment
python scripts/mdr_gap_analyzer.py --interactive
```

Анализирует устройство на соответствие требованиям MDR, выявляет пробелы в соответствии, формирует рекомендации по приоритетам.

**Выходные данные включают в себя:**
- Чек-лист требований по категориям
- Выявление пробелов в приоритетах
- Выделение критического пробела
- Рекомендации по соблюдению требований дорожной карты
